## 第 14 章：セキュリティ対策：安全な Salesforce 環境を構築

Salesforce は、ビジネスの中核を担う顧客データや取引情報を一元管理する強力なプラットフォームです。しかし、その利便性と引き換えに、セキュリティ対策は非常に重要となります。本章では、Salesforce 環境を安全に保つための実践的なセキュリティ対策について、初心者から上級者まで理解できるように解説します。オブジェクト権限から API セキュリティ、データ暗号化まで、段階的に解説し、実際のユースケースを交えながら、堅牢な Salesforce 環境構築を目指しましょう。

### 14.1 Salesforce のセキュリティモデル：オブジェクト権限、項目レベルセキュリティ、レコードレベルセキュリティ

#### 14.1.1 概要と重要性

Salesforce のセキュリティモデルは、組織全体のデータを保護するための基盤です。オブジェクト権限、項目レベルセキュリティ、レコードレベルセキュリティの 3 層構造で構成されており、それぞれ異なるレベルでデータへのアクセスを制御します。これらの設定を適切に行うことで、許可されたユーザーのみが特定のデータにアクセスできるようにし、機密情報の漏洩や不正アクセスを防ぐことができます。

- **オブジェクト権限:** どのオブジェクト（取引先、商談、リードなど）にアクセスできるかを制御します。
- **項目レベルセキュリティ:** オブジェクト内の特定の項目（電話番号、メールアドレス、金額など）へのアクセスを制御します。
- **レコードレベルセキュリティ:** どのレコード（特定の取引先の情報、特定の商談の情報など）にアクセスできるかを制御します。

これらの設定を怠ると、機密情報が意図しないユーザーに公開されたり、誤った操作によってデータが破損したりする可能性があります。

#### 14.1.2 特徴と利点

- **オブジェクト権限:**
  - 特徴：プロファイルまたは権限セットに割り当てられ、オブジェクト全体の作成、参照、編集、削除権限を制御します。
  - 利点：ユーザーが必要なオブジェクトのみにアクセスできるように制限することで、不要な情報へのアクセスを防ぎます。
- **項目レベルセキュリティ:**
  - 特徴：プロファイルまたは権限セットに割り当てられ、オブジェクト内の特定の項目への参照、編集権限を制御します。
  - 利点：機密性の高い項目（給与情報、顧客のクレジットカード情報など）へのアクセスを制限し、情報漏洩のリスクを軽減します。
- **レコードレベルセキュリティ:**
  - 特徴：組織の共有設定、ロール階層、共有ルール、Apex 管理共有などを組み合わせて、ユーザーがどのレコードにアクセスできるかを制御します。
  - 利点：組織の構造やビジネスニーズに合わせて、柔軟なアクセス制御を実現します。例えば、営業担当者は自分の担当する顧客情報のみにアクセスできるように設定できます。

#### 14.1.3 事前準備と前提条件

- Salesforce の管理者権限が必要です。
- 組織のビジネス要件とデータアクセスに関する明確な方針が必要です。
- プロファイルと権限セットの基本的な理解が必要です。
- 組織の共有設定とロール階層の基本的な理解が必要です。

#### 14.1.4 基本的な使い方

**オブジェクト権限の設定:**

1.  **プロファイルの設定:**
    - `設定` > `ユーザー` > `プロファイル` にアクセスし、編集するプロファイルを選択します。
    - `オブジェクト設定` セクションで、オブジェクトごとに必要な権限を付与します（参照、作成、編集、削除など）。
2.  **権限セットの設定:**
    - `設定` > `権限セット` にアクセスし、新しい権限セットを作成するか、既存のものを編集します。
    - `オブジェクト設定` セクションで、オブジェクトごとに必要な権限を付与します。
    - 権限セットをユーザーに割り当てます。

**項目レベルセキュリティの設定:**

1.  **プロファイルの設定:**
    - `設定` > `ユーザー` > `プロファイル` にアクセスし、編集するプロファイルを選択します。
    - `オブジェクト設定` セクションで、オブジェクトを選択し、`項目レベルセキュリティ` をクリックします。
    - 項目ごとに、参照可能と編集可能のチェックボックスをオン/オフします。
2.  **権限セットの設定:**
    - `設定` > `権限セット` にアクセスし、新しい権限セットを作成するか、既存のものを編集します。
    - `オブジェクト設定` セクションで、オブジェクトを選択し、`項目レベルセキュリティ` をクリックします。
    - 項目ごとに、参照可能と編集可能のチェックボックスをオン/オフします。

**レコードレベルセキュリティの設定:**

1.  **組織の共有設定:**
    - `設定` > `セキュリティ` > `共有設定` にアクセスします。
    - オブジェクトごとに、組織全体のデフォルトのアクセス権を設定します（公開/参照・更新可能、公開/参照のみ、非公開など）。
2.  **ロール階層:**
    - `設定` > `ユーザー` > `ロール` にアクセスし、組織のロール階層を定義します。
    - ロール階層に基づいて、上位のロールのユーザーは下位のロールのユーザーが所有するレコードにアクセスできるようになります。
3.  **共有ルール:**
    - `設定` > `セキュリティ` > `共有ルール` にアクセスします。
    - 特定の条件に基づいて、特定のユーザーまたはグループにレコードへのアクセス権を付与するルールを作成します。
    - 共有ルールは、組織の共有設定よりも優先されます。

#### 14.1.5 実践的なテクニック

- **最小権限の原則:** ユーザーには、業務に必要な最小限の権限のみを付与します。
- **権限セットの活用:** プロファイルは組織全体に適用されるため、特定のユーザーグループにのみ適用される権限は権限セットで管理します。
- **監査証跡の活用:** Salesforce の監査証跡機能を使用して、ユーザーのデータアクセス状況を監視し、不正アクセスを早期に発見します。
- **定期的な見直し:** セキュリティ設定は、組織の成長やビジネスの変化に合わせて定期的に見直す必要があります。
- **レポートとダッシュボードの活用:** 特定の権限を持つユーザーの数を把握するためのレポートや、セキュリティ関連の設定状況を可視化するダッシュボードを作成し、継続的に監視します。

#### 14.1.6 応用例とユースケース

- **ユースケース 1:** 営業マネージャーは、自分のチームのメンバーが担当する商談の金額とステージを確認できるが、他のチームの商談にはアクセスできないようにする。
  - 解決策：組織の共有設定を「非公開」に設定し、ロール階層で営業マネージャーが自分のチームのメンバーよりも上位のロールになるように設定します。必要に応じて、共有ルールを使用して、特定の条件に合致する商談へのアクセス権を付与します。
- **ユースケース 2:** 人事担当者は、従業員の給与情報を参照できるが、他のユーザーは参照できないようにする。
  - 解決策：従業員の給与情報を格納するオブジェクトのオブジェクト権限を人事担当者のプロファイルまたは権限セットにのみ付与し、他のユーザーには付与しません。給与情報が格納されている項目の項目レベルセキュリティで、人事担当者のプロファイルまたは権限セットに対してのみ参照可能を設定します。
- **ユースケース 3:** 特定の顧客との契約情報へのアクセスを、特定の担当者のみに制限する。
  - 解決策：組織の共有設定を「非公開」に設定し、契約オブジェクトの共有ルールを作成して、特定の担当者またはグループにのみアクセス権を付与します。

#### 14.1.7 トラブルシューティング

- **ユーザーが特定のレコードにアクセスできない:**
  - 組織の共有設定、ロール階層、共有ルール、Apex 管理共有の設定を確認します。
  - ユーザーが適切なプロファイルまたは権限セットに割り当てられていることを確認します。
- **ユーザーが特定の項目を編集できない:**
  - 項目の項目レベルセキュリティの設定を確認します。
  - ユーザーが適切なプロファイルまたは権限セットに割り当てられていることを確認します。

#### 14.1.8 まとめと次のステップ

Salesforce のセキュリティモデルは、組織のデータを保護するための重要な基盤です。オブジェクト権限、項目レベルセキュリティ、レコードレベルセキュリティを適切に設定することで、不正アクセスや情報漏洩のリスクを軽減することができます。次のステップとして、組織のビジネス要件とデータアクセスに関する明確な方針を作成し、定期的にセキュリティ設定を見直すことをお勧めします。

### 14.2 API セキュリティ：OAuth 2.0、IP 制限、証明書認証

#### 14.2.1 概要と重要性

Salesforce の API は、外部システムとの連携を可能にする強力なツールですが、同時にセキュリティ上のリスクも伴います。API セキュリティ対策を怠ると、悪意のある攻撃者によってデータが不正にアクセスされたり、システムが乗っ取られたりする可能性があります。OAuth 2.0、IP 制限、証明書認証は、Salesforce API を安全に利用するための主要なセキュリティ対策です。

- **OAuth 2.0:** アプリケーションがユーザーの代わりに Salesforce にアクセスするための安全な認証プロトコルです。
- **IP 制限:** 特定の IP アドレスからの API アクセスのみを許可することで、不正アクセスを防止します。
- **証明書認証:** クライアントアプリケーションが Salesforce にアクセスする際に、証明書を使用して認証を行う方法です。

#### 14.2.2 特徴と利点

- **OAuth 2.0:**
  - 特徴：リソース所有者（ユーザー）の資格情報をアプリケーションに公開することなく、リソース（Salesforce データ）へのアクセスを委譲します。
  - 利点：ユーザー名とパスワードを共有する必要がないため、セキュリティリスクを軽減できます。また、様々な認可グラントタイプ（Authorization Code Grant、Resource Owner Password Credentials Grant など）に対応しており、様々なユースケースに対応できます。
- **IP 制限:**
  - 特徴：特定の IP アドレスまたは IP アドレス範囲からの API アクセスのみを許可します。
  - 利点：不正な IP アドレスからのアクセスをブロックすることで、セキュリティリスクを軽減できます。
- **証明書認証:**
  - 特徴：クライアントアプリケーションが Salesforce にアクセスする際に、証明書を使用して認証を行います。
  - 利点：ユーザー名とパスワードを使用しないため、セキュリティリスクを軽減できます。また、IP 制限と組み合わせることで、より強固なセキュリティを実現できます。

#### 14.2.3 事前準備と前提条件

- Salesforce の管理者権限が必要です。
- OAuth 2.0、IP 制限、証明書認証に関する基本的な知識が必要です。
- 連携する外部システムの技術的な知識が必要です。

#### 14.2.4 基本的な使い方

**OAuth 2.0 の設定:**

1.  **接続アプリケーションの作成:**
    - `設定` > `プラットフォームツール` > `アプリケーション` > `アプリケーションマネージャ` にアクセスし、`新しい接続アプリケーション` をクリックします。
    - `基本情報` セクションで、アプリケーション名、API 名、連絡先メールアドレスを入力します。
    - `API (OAuth 設定の有効化)` セクションで、`OAuth 設定の有効化` チェックボックスをオンにします。
    - `コールバック URL` に、認証後にリダイレクトされる URL を入力します。
    - `選択された OAuth 範囲` で、アプリケーションに必要な範囲を選択します（API アクセス、データアクセスなど）。
    - `保存` をクリックします。
2.  **コンシューマ鍵とコンシューマの秘密の取得:**
    - 作成した接続アプリケーションの詳細ページで、`コンシューマ鍵` と `コンシューマの秘密` を確認します。
3.  **OAuth 2.0 フローの実行:**
    - `コンシューマ鍵`、`コールバック URL`、`選択された OAuth 範囲` を使用して、OAuth 2.0 フローを実行します。
    - Authorization Code Grant の場合：
      - ユーザーを Salesforce の認証エンドポイントにリダイレクトします。
      - ユーザーがログインし、アプリケーションにアクセスを許可すると、指定された`コールバック URL` に認証コードが渡されます。
      - 認証コードを使用して、アクセストークンを取得します。
    - 取得したアクセストークンを使用して、Salesforce API にアクセスします。

**IP 制限の設定:**

1.  **プロファイルの設定:**
    - `設定` > `ユーザー` > `プロファイル` にアクセスし、編集するプロファイルを選択します。
    - `ログイン IP アドレスの制限` セクションで、許可する IP アドレスまたは IP アドレス範囲を入力します。
2.  **組織全体の設定:**
    - `設定` > `セキュリティ` > `ネットワークアクセス` にアクセスし、信頼できる IP アドレス範囲を設定します。

**証明書認証の設定:**

1.  **自己署名証明書の生成:**
    - OpenSSL などのツールを使用して、自己署名証明書を生成します。
    - `openssl req -newkey rsa:2048 -nodes -keyout key.pem -x509 -days 365 -out certificate.pem`
2.  **証明書の Salesforce へのアップロード:**
    - `設定` > `セキュリティ` > `証明書と鍵の管理` にアクセスし、`自己署名証明書` をクリックします。
    - `表示ラベル` と `名前` を入力し、生成した証明書ファイル（certificate.pem）をアップロードします。
3.  **接続アプリケーションの設定:**
    - OAuth 2.0 の設定と同様に、接続アプリケーションを作成します。
    - `API (OAuth 設定の有効化)` セクションで、`OAuth 設定の有効化` チェックボックスをオンにします。
    - `コールバック URL` を入力します。
    - `デジタル署名` セクションで、アップロードした証明書を選択します。
    - `選択された OAuth 範囲` で、アプリケーションに必要な範囲を選択します。
4.  **証明書を使用したアクセストークンの取得:**
    - JWT（JSON Web Token）を使用して、アクセストークンをリクエストします。
    - JWT には、コンシューマ鍵、ユーザー ID、証明書などの情報を含めます。
    - Salesforce のトークンエンドポイントに JWT を送信し、アクセストークンを取得します。

#### 14.2.5 実践的なテクニック

- **OAuth 2.0 の適切なグラントタイプの選択:**
  - Web アプリケーションの場合は、Authorization Code Grant を使用します。
  - 機密性の低いアプリケーションの場合は、Resource Owner Password Credentials Grant を使用します。
  - サーバ間連携の場合は、JWT Bearer Token Flow を使用します。
- **IP 制限と証明書認証の組み合わせ:** IP 制限と証明書認証を組み合わせることで、より強固なセキュリティを実現できます。
- **定期的な証明書の更新:** 証明書の有効期限が切れる前に、定期的に更新する必要があります。
- **API 利用状況の監視:** Salesforce の API 利用状況を監視し、異常なアクセスを早期に発見します。
- **レート制限の利用:** API のレート制限を設定し、DoS 攻撃などを防止します。

#### 14.2.6 応用例とユースケース

- **ユースケース 1:** モバイルアプリケーションから Salesforce データに安全にアクセスする。
  - 解決策：OAuth 2.0 を使用して、モバイルアプリケーションがユーザーの代わりに Salesforce にアクセスできるようにします。
- **ユースケース 2:** 社内システムから Salesforce データに安全にアクセスする。
  - 解決策：IP 制限と証明書認証を使用して、社内システムからの API アクセスのみを許可します。
- **ユースケース 3:** 他のクラウドサービスとの連携を安全に行う。
  - 解決策：OAuth 2.0 を使用して、クラウドサービスが Salesforce データに安全にアクセスできるようにします。

#### 14.2.7 トラブルシューティング

- **OAuth 2.0 認証に失敗する:**
  - コンシューマ鍵、コンシューマの秘密、コールバック URL、選択された OAuth 範囲が正しいことを確認します。
  - Salesforce 側の設定が正しいことを確認します（接続アプリケーションの設定など）。
- **IP 制限によって API アクセスが拒否される:**
  - API アクセス元の IP アドレスが、許可された IP アドレスまたは IP アドレス範囲に含まれていることを確認します。
- **証明書認証に失敗する:**
  - 証明書が有効期限内であることを確認します。
  - JWT の署名が正しいことを確認します。
  - Salesforce 側の設定が正しいことを確認します（証明書のアップロード、接続アプリケーションの設定など）。

#### 14.2.8 まとめと次のステップ

Salesforce API を安全に利用するためには、OAuth 2.0、IP 制限、証明書認証などのセキュリティ対策が不可欠です。これらの対策を適切に設定することで、不正アクセスや情報漏洩のリスクを軽減することができます。次のステップとして、組織の API 利用状況を把握し、セキュリティポリシーを策定することをお勧めします。

### 14.3 データ保護と暗号化：Salesforce Shield

#### 14.3.1 概要と重要性

Salesforce Shield は、機密性の高いデータを保護するための包括的なセキュリティプラットフォームです。プラットフォームの暗号化、イベント監視、項目監査証跡の 3 つの主要な機能を提供し、データの保護、セキュリティ脅威の検出、コンプライアンス要件への対応を支援します。

- **プラットフォームの暗号化（Shield Platform Encryption）:** 機密データを保管時に暗号化し、不正アクセスから保護します。
- **イベント監視（Event Monitoring）:** ユーザーの活動やシステムイベントを監視し、セキュリティ脅威を早期に検出します。
- **項目監査証跡（Field Audit Trail）:** データの変更履歴を追跡し、監査やコンプライアンス要件への対応を支援します。

これらの機能を活用することで、組織は高度なセキュリティ体制を構築し、顧客からの信頼を獲得することができます。

#### 14.3.2 特徴と利点

- **プラットフォームの暗号化:**
  - 特徴：標準オブジェクト、カスタムオブジェクト、ファイル、添付ファイルなど、様々な種類のデータを暗号化します。
  - 利点：不正アクセスが発生した場合でも、暗号化されたデータは解読が困難なため、情報漏洩のリスクを大幅に軽減できます。コンプライアンス要件（HIPAA、PCI DSS など）への対応を支援します。
- **イベント監視:**
  - 特徴：ログインイベント、レポートのエクスポート、API の使用状況など、様々なイベントを監視します。
  - 利点：異常なアクティビティや潜在的なセキュリティ脅威をリアルタイムで検出できます。セキュリティインシデントの発生を未然に防ぎ、迅速な対応を可能にします。
- **項目監査証跡:**
  - 特徴：データの変更履歴（変更日時、変更者、変更内容）を最大 10 年間保持します。
  - 利点：データガバナンスとコンプライアンスを強化します。監査や調査の際に、データの変更履歴を容易に追跡できます。

#### 14.3.3 事前準備と前提条件

- Salesforce Shield ライセンスが必要です。
- 暗号化、イベント監視、監査に関する基本的な知識が必要です。
- 組織のデータ保護要件とコンプライアンス要件を明確にする必要があります。

#### 14.3.4 基本的な使い方

**プラットフォームの暗号化の設定:**

1.  **鍵管理の選択:**
    - Salesforce 鍵管理：Salesforce が鍵を管理します。
    - Bring Your Own Key (BYOK)：組織が独自の鍵を管理します。
2.  **暗号化ポリシーの設定:**
    - `設定` > `プラットフォームツール` > `暗号化と鍵の管理` にアクセスします。
    - 暗号化するオブジェクトと項目を選択します。
    - 暗号化の種類（確定的暗号化、確率的暗号化）を選択します。
    - `保存` をクリックします。
3.  **データの暗号化:**
    - 暗号化ポリシーを有効にすると、新しいデータは自動的に暗号化されます。
    - 既存のデータを暗号化するには、Salesforce のサポートに依頼する必要があります。

**イベント監視の設定:**

1.  **イベント監視の有効化:**
    - `設定` > `プラットフォームツール` > `イベント監視` にアクセスします。
    - `イベント監視の有効化` チェックボックスをオンにします。
2.  **イベントログファイルのダウンロード:**
    - イベントが発生すると、イベントログファイルが生成されます。
    - イベントログファイルをダウンロードして、分析ツール（Splunk、Sumo Logic など）で分析します。
3.  **リアルタイムイベント監視:**
    - リアルタイムイベント監視を使用して、特定のイベントが発生した場合にアラートを送信します。
    - Apex を使用して、カスタムのイベント監視ロジックを実装することもできます。

**項目監査証跡の設定:**

1.  **項目監査証跡の有効化:**
    - `設定` > `プラットフォームツール` > `項目監査証跡` にアクセスします。
    - 監査するオブジェクトと項目を選択します。
    - データ保持期間（最大 10 年間）を設定します。
    - `保存` をクリックします。
2.  **監査データの確認:**
    - 項目監査証跡レポートを使用して、データの変更履歴を確認します。

#### 14.3.5 実践的なテクニック

- **適切な暗号化の種類の選択:**
  - 確定的暗号化：完全に一致する値に対してのみ検索やフィルターが可能です。
  - 確率的暗号化：より安全ですが、検索やフィルターが困難です。
- **イベント監視のアラート設定:**
  - 重要なイベント（ログイン失敗、大量のデータのエクスポートなど）が発生した場合に、アラートを送信するように設定します。
- **監査データの定期的な確認:** 監査データを定期的に確認し、不正なデータ変更がないかを確認します。
- **鍵管理のベストプラクティス:**
  - BYOK を選択した場合は、鍵を安全に保管し、定期的にローテーションする必要があります。
- **イベントログファイルの分析:** イベントログファイルを分析して、セキュリティ脅威を早期に発見します。

#### 14.3.6 応用例とユースケース

- **ユースケース 1:** 金融機関が顧客の口座情報を安全に保護する。
  - 解決策：プラットフォームの暗号化を使用して、顧客の口座情報を暗号化します。イベント監視を使用して、不正なログインや口座情報の変更を監視します。
- **ユースケース 2:** ヘルスケアプロバイダーが患者の医療情報を HIPAA に準拠して保護する。
  - 解決策：プラットフォームの暗号化を使用して、患者の医療情報を暗号化します。項目監査証跡を使用して、データの変更履歴を追跡します。
- **ユースケース 3:** 小売業者が顧客のクレジットカード情報を PCI DSS に準拠して保護する。
  - 解決策：プラットフォームの暗号化を使用して、顧客のクレジットカード情報を暗号化します。IP 制限と OAuth 2.0 を使用して、API アクセスを制限します。

#### 14.3.7 トラブルシューティング

- **暗号化されたデータが検索できない:**
  - 確定的暗号化を使用していることを確認します。
  - 検索時に完全に一致する値を入力していることを確認します。
- **イベントログファイルが見つからない:**
  - イベント監視が有効になっていることを確認します。
  - イベントログファイルの生成間隔を確認します。
- **項目監査証跡レポートにデータが表示されない:**
  - 項目監査証跡が有効になっていることを確認します。
  - 監査対象のオブジェクトと項目が選択されていることを確認します。

#### 14.3.8 まとめと次のステップ

Salesforce Shield は、組織のデータを保護するための強力なツールです。プラットフォームの暗号化、イベント監視、項目監査証跡を適切に設定することで、セキュリティ脅威からデータを保護し、コンプライアンス要件に対応することができます。次のステップとして、Salesforce Shield の機能をより深く理解し、組織のデータ保護要件に合わせて最適な設定を行うことをお勧めします。また、セキュリティ専門家と協力して、組織全体のセキュリティ戦略を策定することも重要です。
