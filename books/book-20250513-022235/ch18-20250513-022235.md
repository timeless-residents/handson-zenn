## 第 18 章：Salesforce アーキテクチャ設計：大規模組織への適用

### 18.1 マルチオーグ戦略：グローバル展開、ビジネスユニット分離

#### 18.1.1 概要と重要性

大規模組織が Salesforce を導入する際、単一の巨大なオーグ（組織）で全てを管理するアプローチは、多くの場合、拡張性、メンテナンス性、セキュリティの面で限界に達します。マルチオーグ戦略は、複数の Salesforce オーグを運用し、それぞれ特定のビジネスユニット、地域、または機能をサポートするアプローチです。

この戦略は、組織の成長に伴う複雑さを軽減し、各ビジネスユニットが独自の要件に合わせて Salesforce をカスタマイズできるようにします。また、データ分離、コンプライアンス対応、システム障害時の影響範囲の局所化など、多くのメリットを提供します。

#### 18.1.2 特徴と利点

マルチオーグ戦略の主な特徴と利点は以下の通りです。

- **独立性:** 各オーグは独立して運用されるため、ビジネスユニットの変更やシステム障害が他のオーグに影響を与えるリスクを軽減できます。
- **カスタマイズ性:** 各ビジネスユニットは、独自の要件に合わせて Salesforce をカスタマイズできます。
- **拡張性:** 組織の成長に合わせて、新しいオーグを容易に追加できます。
- **データ分離:** 各オーグは独自のデータを保持するため、データセキュリティとコンプライアンスを強化できます。特に GDPR や CCPA などの規制遵守に有効です。
- **ガバナンスの柔軟性:** 各オーグは、それぞれのビジネスユニットのニーズに合わせて独自のガバナンスポリシーを適用できます。
- **開発効率の向上:** 各オーグは独立して開発およびテストできるため、開発サイクルを短縮できます。
- **コスト効率:** リソースの効率的な配分を可能にし、不要な機能やデータストレージのコストを削減できます。

#### 18.1.3 事前準備と前提条件

マルチオーグ戦略を導入する前に、以下の点を検討する必要があります。

- **ビジネス要件の明確化:** 各ビジネスユニットのニーズ、データ要件、セキュリティ要件を明確に定義します。
- **組織構造の理解:** ビジネスユニット間の関係、データ共有の要件、ガバナンス構造を理解します。
- **技術的な検討:** データ連携、ID 管理、セキュリティポリシー、開発標準など、技術的な側面を検討します。
- **予算とリソースの確保:** 複数のオーグを管理するための予算とリソースを確保します。
- **ガバナンスモデルの策定:** 複数のオーグをどのように管理し、整合性を維持するかを定義します。
- **チェンジマネジメント:** 組織全体への影響を考慮し、変更管理計画を策定します。

#### 18.1.4 基本的な使い方

マルチオーグ戦略の基本的な使い方は以下の通りです。

1.  **オーグの設計:** ビジネス要件に基づいて、各オーグの目的、機能、データを定義します。
2.  **オーグの構築:** 定義された要件に基づいて、Salesforce オーグを構築します。
3.  **データ連携の構築:** 異なるオーグ間でデータを連携するためのメカニズムを構築します。
    - **例:** MuleSoft などの ETL ツールを利用して、顧客データ、製品データ、注文データを連携します。
4.  **ID 管理の統合:** ユーザーが複数のオーグにシームレスにアクセスできるように、シングルサインオン（SSO）を実装します。
    - **例:** Okta や Azure AD などの ID プロバイダーを利用して、SSO を実装します。
5.  **ガバナンスの適用:** 各オーグにガバナンスポリシーを適用し、整合性を維持します。
    - **例:** 各オーグに共通の開発標準、セキュリティポリシー、データ管理ポリシーを適用します。
6.  **監視とメンテナンス:** 各オーグのパフォーマンスを監視し、必要に応じてメンテナンスを行います。

#### 18.1.5 実践的なテクニック

マルチオーグ戦略を成功させるための実践的なテクニックをいくつか紹介します。

- **共通データモデルの定義:** 異なるオーグ間で共有するデータの共通データモデルを定義します。
  - **例:** 顧客オブジェクトの標準項目（名前、メールアドレス、電話番号）を共通化します。
- **API 主導の連携:** データ連携に API を使用することで、柔軟性と拡張性を高めます。
  - **例:** Salesforce の REST API を利用して、顧客データを他のオーグに連携します。
- **メタデータ駆動の開発:** メタデータ駆動の開発アプローチを採用することで、開発効率を向上させます。
  - **例:** Salesforce DX を利用して、メタデータを管理し、異なるオーグにデプロイします。
- **DevOps の導入:** DevOps プラクティスを導入することで、リリースサイクルを短縮し、品質を向上させます。
  - **例:** Jenkins や GitLab CI/CD を利用して、自動化されたビルド、テスト、デプロイパイプラインを構築します。
- **監視とアラート:** 各オーグのパフォーマンスを監視し、異常が発生した場合にアラートを送信するように設定します。
  - **例:** Salesforce Event Monitoring を利用して、ログイン履歴、API 利用状況、データ変更履歴を監視します。
- **サンドボックス戦略:** 各オーグに適切なサンドボックス環境を用意し、開発とテストを効率的に行えるようにします。
  - **例:** 開発、テスト、ステージングの各環境を用意し、変更を段階的にリリースします。

#### 18.1.6 応用例とユースケース

- **グローバル企業:** 異なる地域で事業を展開するグローバル企業では、地域ごとにオーグを分けて、現地の言語、通貨、法律に対応します。
- **多角化企業:** 複数のビジネスユニットを持つ企業では、ビジネスユニットごとにオーグを分けて、それぞれのニーズに合わせて Salesforce をカスタマイズします。
- **フランチャイズ企業:** フランチャイズ企業では、フランチャイズごとにオーグを分けて、それぞれのビジネスを支援します。
- **合弁会社:** 合弁会社では、親会社とは別にオーグを設けて、独立した運用を行います。

#### 18.1.7 トラブルシューティング

- **データ整合性の問題:** 異なるオーグ間でデータが矛盾する場合、データ連携のロジックを見直し、データ品質を改善します。
- **ID 管理の問題:** ユーザーが複数のオーグにログインできない場合、SSO の設定を見直し、ID プロバイダーとの連携を確認します。
- **パフォーマンスの問題:** 各オーグのパフォーマンスが低下した場合、クエリの最適化、インデックスの追加、データのアーカイブなどを検討します。

#### 18.1.8 まとめと次のステップ

マルチオーグ戦略は、大規模組織が Salesforce を効果的に活用するための強力なアプローチです。ビジネス要件を明確にし、適切なガバナンスモデルを策定し、技術的な課題を解決することで、組織全体の効率性と柔軟性を向上させることができます。

次のステップとしては、組織のビジネス要件に基づいて、最適なマルチオーグ戦略を策定し、パイロットプロジェクトを実施して、効果を検証することをお勧めします。

### 18.2 パフォーマンスチューニング：大規模データ、高トラフィック

#### 18.2.1 概要と重要性

Salesforce は強力なプラットフォームですが、大規模データや高トラフィックを扱う際には、パフォーマンスが低下する可能性があります。パフォーマンスチューニングは、Salesforce の応答速度を向上させ、ユーザーエクスペリエンスを最適化するために不可欠です。

パフォーマンスの最適化は、単なる技術的な課題ではありません。ビジネスプロセス効率、顧客満足度、そして最終的には収益に直接影響を与えます。特に、大規模な組織では、わずかなパフォーマンスの改善が全体的な生産性に大きな差を生むことがあります。

#### 18.2.2 特徴と利点

パフォーマンスチューニングの主な特徴と利点は以下の通りです。

- **応答速度の向上:** ユーザーがより迅速に情報を取得し、タスクを完了できるようになります。
- **ユーザーエクスペリエンスの向上:** 応答速度の向上により、ユーザーエクスペリエンスが向上し、顧客満足度が高まります。
- **システムリソースの効率的な利用:** パフォーマンスチューニングにより、CPU、メモリ、ディスクなどのシステムリソースを効率的に利用できます。
- **スケーラビリティの向上:** パフォーマンスチューニングにより、Salesforce の拡張性が向上し、将来的な成長に対応できます。
- **コスト削減:** システムリソースの効率的な利用により、インフラストラクチャコストを削減できます。

#### 18.2.3 事前準備と前提条件

パフォーマンスチューニングを行う前に、以下の点を準備する必要があります。

- **パフォーマンスの問題の特定:** どの処理に時間がかかっているか、具体的な問題を特定します。Salesforce Setup の「デバッグログ」や「イベントモニタリング」が役立ちます。
- **パフォーマンス指標の定義:** 応答時間、スループット、エラー率など、パフォーマンスを評価するための指標を定義します。
- **ベースラインの確立:** パフォーマンスチューニング前のパフォーマンスを測定し、ベースラインを確立します。
- **テスト環境の準備:** パフォーマンスチューニングの影響を評価するために、テスト環境を用意します。
- **変更管理:** 変更内容、テスト結果、およびロールバック計画を文書化します。
- **関係者との連携:** 開発者、管理者、ビジネスユーザーなど、関係者と連携して、パフォーマンスチューニングの目標と計画を共有します。

#### 18.2.4 基本的な使い方

パフォーマンスチューニングの基本的な手順は以下の通りです。

1.  **問題の特定:** Salesforce Setup の「Health Check」を利用して、セキュリティとパフォーマンスの問題を特定します。デバッグログを活用し、処理に時間がかかっている部分を特定します。
2.  **クエリの最適化:** SOQL クエリが効率的に実行されるように最適化します。

    - **例:** 不要な項目を除外、適切なインデックスを使用、絞り込み条件を追加します。

    ```sql
    // 非効率なクエリ
    SELECT Id, Name FROM Account WHERE Name LIKE '%test%';

    // 効率的なクエリ (LIKE句の先頭に%を使用しない)
    SELECT Id, Name FROM Account WHERE Name LIKE 'test%';

    // 効率的なクエリ (インデックスを利用できる)
    SELECT Id, Name FROM Account WHERE Industry = 'Technology';
    ```

3.  **インデックスの最適化:** Salesforce にインデックスを追加して、クエリのパフォーマンスを向上させます。
    - **注意:** カスタムインデックスは、過剰に使用するとパフォーマンスに悪影響を与える可能性があります。
4.  **Apex コードの最適化:** Apex コードが効率的に実行されるように最適化します。

    - **例:** バルク処理、非同期処理、ガバナ制限の考慮。

    ```java
    // 非効率なコード (ループ内でDML操作)
    List<Account> accounts = [SELECT Id, Name FROM Account LIMIT 100];
    for (Account acc : accounts) {
        acc.Description = 'Updated Description';
        update acc; // ガバナ制限に注意
    }

    // 効率的なコード (バルク処理)
    List<Account> accounts = [SELECT Id, Name FROM Account LIMIT 100];
    for (Account acc : accounts) {
        acc.Description = 'Updated Description';
    }
    update accounts; // 一括で更新
    ```

5.  **Visualforce/Lightning コンポーネントの最適化:** Visualforce ページや Lightning コンポーネントが効率的に表示されるように最適化します。
    - **例:** 不要なコンポーネントの削除、キャッシュの活用、JavaScript の最適化。
6.  **設定の最適化:** Salesforce の設定がパフォーマンスに影響を与えないように最適化します。
    - **例:** 不要なワークフロールールの削除、有効化されたトリガーの確認、データ量の削減。
7.  **ハードウェアの最適化:** Salesforce のハードウェア（CPU、メモリ、ディスク）が適切に構成されているかを確認します。これは Salesforce 側に依存しますが、状況によってはサポートに相談することを検討します。

#### 18.2.5 実践的なテクニック

- **SOQL クエリのヒント:** `WITH SECURITY_ENFORCED`句を使用すると、ユーザー権限に基づいてクエリ結果をフィルタリングできます。
- **Apex バッチ処理:** 大量のデータを処理する場合、Apex バッチ処理を使用して、ガバナ制限を回避します。
- **非同期処理:** 長時間かかる処理は、非同期処理（Queueable Apex、Future Methods、Schedulable Apex）を使用して、ユーザーエクスペリエンスを向上させます。
- **キャッシュの活用:** 頻繁にアクセスされるデータは、プラットフォームキャッシュや組織キャッシュに保存して、応答速度を向上させます。
- **CDN の利用:** 静的コンテンツ（画像、JavaScript、CSS）は、CDN（Content Delivery Network）を利用して、ユーザーに近いサーバーから配信することで、応答速度を向上させます。
- **レポートの最適化:** 大量のデータを扱うレポートは、集計フィールドやバケット項目を使用して、パフォーマンスを向上させます。
- **アーカイブ戦略:** 古いデータをアーカイブすることで、データ量を削減し、クエリのパフォーマンスを向上させます。
- **Salesforce Optimizer:** Salesforce が提供する Optimizer ツールを利用して、パフォーマンスの問題を特定し、改善策を提案してもらいます。

#### 18.2.6 応用例とユースケース

- **大規模な商談管理:** 多数の商談を扱う場合、商談オブジェクトのインデックスを最適化し、SOQL クエリを効率的に実行できるようにします。
- **コールセンター:** コールセンターでは、顧客情報を迅速に表示するために、顧客オブジェクトのキャッシュを活用し、Visualforce ページのパフォーマンスを最適化します。
- **E コマースサイト:** E コマースサイトでは、商品情報を大量に扱うため、商品オブジェクトのインデックスを最適化し、検索クエリを効率的に実行できるようにします。
- **マーケティングオートメーション:** 大量のメールを送信する場合、Apex バッチ処理を使用して、メール送信処理を非同期化し、ガバナ制限を回避します。

#### 18.2.7 トラブルシューティング

- **SOQL クエリがタイムアウトする場合:** クエリを分割するか、インデックスを追加するか、またはデータをアーカイブします。
- **Apex コードがガバナ制限に達する場合:** バルク処理を実装するか、非同期処理を使用します。
- **Visualforce ページが遅い場合:** 不要なコンポーネントを削除するか、キャッシュを活用します。
- **Lightning コンポーネントが遅い場合:** JavaScript を最適化するか、CDN を利用します。

#### 18.2.8 まとめと次のステップ

パフォーマンスチューニングは、Salesforce のパフォーマンスを最適化し、ユーザーエクスペリエンスを向上させるために不可欠です。パフォーマンスの問題を特定し、クエリ、コード、設定、ハードウェアを最適化することで、Salesforce の応答速度を向上させ、システムリソースを効率的に利用できます。

次のステップとしては、パフォーマンスチューニング計画を策定し、定期的にパフォーマンスを監視し、必要に応じてチューニングを行うことをお勧めします。Salesforce が提供するツール（Health Check、Optimizer、Event Monitoring）を活用して、パフォーマンスの問題を特定し、改善策を検討します。

### 18.3 ドメイン駆動設計：ビジネスロジックの分離

#### 18.3.1 概要と重要性

ドメイン駆動設計（DDD）は、複雑なソフトウェアを開発するための設計パラダイムです。Salesforce における DDD は、ビジネスロジックをデータ層と UI 層から分離し、モデル化することで、アプリケーションの保守性、テスト容易性、拡張性を向上させます。

従来の Salesforce 開発では、トリガー、ワークフロールール、Visualforce コントローラーなどにビジネスロジックが散在し、複雑化しやすい傾向があります。DDD を適用することで、ビジネスロジックを集中管理し、変更の影響範囲を局所化し、より柔軟なアプリケーションを構築できます。

#### 18.3.2 特徴と利点

ドメイン駆動設計の主な特徴と利点は以下の通りです。

- **ビジネスロジックの集中管理:** ビジネスロジックをドメイン層に集中させることで、コードの可読性と保守性が向上します。
- **テスト容易性の向上:** ビジネスロジックが UI やデータ層から分離されるため、単体テストが容易になります。
- **拡張性の向上:** ビジネスロジックの変更が他の層に影響を与えにくいため、アプリケーションの拡張性が向上します。
- **ビジネス用語の活用:** ドメイン層でビジネス用語を使用することで、開発者とビジネス担当者のコミュニケーションが円滑になります。
- **モデルの再利用:** ドメインモデルを複数のアプリケーションで再利用することで、開発効率を向上させます。

#### 18.3.3 事前準備と前提条件

DDD を Salesforce に適用する前に、以下の点を準備する必要があります。

- **ビジネスドメインの理解:** 対象となるビジネスドメインを深く理解し、主要な概念、ルール、プロセスを明確にします。
- **ドメインモデルの設計:** ビジネスドメインを表現するドメインモデルを設計します。エンティティ、値オブジェクト、集約、ドメインサービスなどを定義します。
- **設計原則の理解:** SOLID 原則、DRY 原則、KISS 原則など、オブジェクト指向設計の原則を理解します。
- **リファクタリングスキル:** 既存のコードをリファクタリングして、DDD アーキテクチャに適合させるためのスキルが必要です。
- **チームのトレーニング:** DDD の概念と実践方法をチームにトレーニングし、共通理解を深めます。

#### 18.3.4 基本的な使い方

DDD を Salesforce に適用する基本的な手順は以下の通りです。

1.  **ドメイン層の作成:** Apex クラスを使用して、ドメインモデル（エンティティ、値オブジェクト、集約、ドメインサービス）を実装します。
2.  **データ層の作成:** Apex クラスを使用して、データアクセスオブジェクト（DAO）を実装し、データベースとのやり取りを抽象化します。
3.  **UI 層の作成:** Visualforce ページや Lightning コンポーネントを使用して、ユーザーインターフェースを実装します。UI 層はドメイン層を直接呼び出さず、アプリケーションサービスを介して間接的に呼び出します。
4.  **アプリケーションサービスの作成:** Apex クラスを使用して、アプリケーションサービスを実装します。アプリケーションサービスは、UI 層からのリクエストを受け付け、ドメイン層の操作をオーケストレーションし、結果を UI 層に返します。
5.  **トリガーからのビジネスロジックの分離:** トリガーに直接ビジネスロジックを記述せず、ドメインサービスを呼び出すようにします。

    - **例:**

    ```java
    // トリガーハンドラー
    public class AccountTriggerHandler {
        public static void beforeInsert(List<Account> newAccounts) {
            // ドメインサービスを呼び出す
            AccountDomainService.validateAccount(newAccounts);
        }
    }

    // ドメインサービス
    public class AccountDomainService {
        public static void validateAccount(List<Account> accounts) {
            for (Account acc : accounts) {
                if (String.isBlank(acc.Name)) {
                    acc.addError('Account Name cannot be blank.');
                }
            }
        }
    }
    ```

#### 18.3.5 実践的なテクニック

- **値オブジェクトの活用:** 複数の属性をまとめて表現する値オブジェクトを活用することで、コードの可読性と保守性を向上させます。
  - **例:** 住所、金額、期間など。
- **集約の活用:** 関連するエンティティをまとめて集約として扱うことで、データの一貫性を保ちます。
- **ドメインイベントの活用:** ドメイン内で発生したイベントを通知することで、疎結合なアーキテクチャを実現します。
  - **例:** 注文確定イベント、顧客登録イベントなど。
- **サービスの活用:** 複数のエンティティを操作する複雑なビジネスロジックは、ドメインサービスとして実装します。
- **リポジトリパターン:** データアクセスロジックをリポジトリパターンで抽象化することで、データソースの変更に柔軟に対応できます。

#### 18.3.6 応用例とユースケース

- **複雑な見積もりロジック:** 複雑な見積もりロジックをドメイン層に実装することで、見積もりルールの変更に柔軟に対応できます。
- **契約管理:** 契約の作成、更新、終了などの処理をドメイン層に実装することで、契約ライフサイクル全体を管理できます。
- **在庫管理:** 在庫の増減、補充、調整などの処理をドメイン層に実装することで、在庫状況を正確に管理できます。
- **顧客ロイヤリティプログラム:** ロイヤリティポイントの計算、特典の付与、ステータスの管理などの処理をドメイン層に実装することで、顧客ロイヤリティプログラムを効率的に管理できます。

#### 18.3.7 トラブルシューティング

- **ドメインモデルが肥大化する場合:** ドメインモデルを分割するか、集約を再設計します。
- **アプリケーションサービスが複雑化する場合:** 複数のアプリケーションサービスに分割するか、ドメインサービスを活用します。
- **パフォーマンスが低下する場合:** クエリの最適化、インデックスの追加、キャッシュの活用などを検討します。
- **ガバナ制限に達する場合:** バルク処理を実装するか、非同期処理を使用します。

#### 18.3.8 まとめと次のステップ

ドメイン駆動設計は、Salesforce アプリケーションの複雑さを軽減し、保守性、テスト容易性、拡張性を向上させるための有効なアプローチです。ビジネスドメインを理解し、適切なドメインモデルを設計し、ビジネスロジックをドメイン層に集中させることで、より柔軟で持続可能なアプリケーションを構築できます。

次のステップとしては、小規模なプロジェクトから DDD を適用し始め、徐々に複雑なプロジェクトに拡大していくことをお勧めします。オープンソースの DDD フレームワークやライブラリを活用して、開発効率を向上させることも検討してください。継続的な学習と実践を通じて、DDD のスキルを向上させ、Salesforce アプリケーションの品質を高めていきましょう。
