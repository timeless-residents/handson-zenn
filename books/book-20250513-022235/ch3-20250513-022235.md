## 第 3 章：Apex 言語集中講座：Java エンジニアが陥りやすい落とし穴

### 3.1 Apex の基本構文とデータ型：Java との違いを徹底解説

**概要と重要性**

Java エンジニアの皆さん、Salesforce の Apex 言語へようこそ！Apex は Salesforce プラットフォーム上で動作するプロプライエタリなプログラミング言語であり、Java と似た構文を持つため比較的学習しやすいですが、Salesforce 特有の環境下で動作するため、いくつかの重要な違いを理解しておく必要があります。このセクションでは、Apex の基本的な構文とデータ型について、Java との比較を通して詳しく解説します。この違いを理解することで、スムーズに Apex 開発に移行し、効率的なコードを書くことができるようになります。

**特徴と利点**

Apex は、Salesforce のデータモデル（SObject）を操作するために最適化されており、データベース操作、ビジネスロジックの実行、UI イベントの処理などを簡単に行うことができます。また、Salesforce プラットフォームに統合されているため、セキュリティ、ガバナ制限、トランザクション管理などの機能が自動的に提供されます。

**事前準備と前提条件**

- Salesforce 組織（Developer Edition を推奨）へのアクセス
- Salesforce Developer Console または VS Code + Salesforce Extension Pack のインストール
- Java の基本的な知識（変数、データ型、制御構造など）

**基本的な使い方**

まずは、基本的な構文とデータ型を見ていきましょう。

```apex
// ApexのHelloWorld
public class HelloWorld {
    public static void printMessage() {
        System.debug('Hello, Apex World!');
    }
}

// Developer Consoleで実行
HelloWorld.printMessage();
```

**データ型:**

| データ型       | Apex                             | Java                             | 備考                                                                                              |
| -------------- | -------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------- |
| 文字列         | String                           | String                           | ほぼ同じ。ただし、Apex の String は immutable。                                                   |
| 整数           | Integer, Long                    | int, long                        | Integer は 32 ビット、Long は 64 ビット。                                                         |
| 浮動小数点数   | Decimal, Double                  | float, double                    | Decimal は任意精度。財務計算に適している。                                                        |
| 真偽値         | Boolean                          | boolean                          | 同じ。                                                                                            |
| 日付と時刻     | Date, Datetime, Time             | java.util.Date, java.time.\*     | Date は日付のみ、Datetime は日付と時刻、Time は時刻のみを表す。Java の Date/Time API とは異なる。 |
| SObject        | Account, Contact, etc.           | （対応するクラスなし）           | Salesforce のデータモデルを表すオブジェクト。カスタムオブジェクトも同様に扱える。                 |
| ID             | ID                               | String（UUID）など               | Salesforce レコードの一意な識別子。15 桁または 18 桁の文字列で表現される。                        |
| リスト         | List\<DataType>                  | List\<DataType>                  | ArrayList のようなもの。                                                                          |
| セット         | Set\<DataType>                   | Set\<DataType>                   | HashSet のようなもの。                                                                            |
| マップ         | Map\<KeyDataType, ValueDataType> | Map\<KeyDataType, ValueDataType> | HashMap のようなもの。                                                                            |
| 列挙型（Enum） | enum                             | enum                             | 同じ。                                                                                            |
| Blob           | Blob                             | byte[]                           | バイナリデータを扱う。ファイルのアップロード/ダウンロードなどに使用する。                         |
| オブジェクト   | Object                           | Object                           | 全ての Apex クラスの基底クラス。                                                                  |

**Java エンジニアが陥りやすい落とし穴:**

1.  **SObject の扱い:** Java のクラスのように自由にインスタンス化できません。データベースから取得するか、DML 操作で作成する必要があります。
2.  **ID 型の理解:** 単なる文字列ではなく、Salesforce のレコードを一意に識別するための型です。ID 型に対する演算はできません。
3.  **Decimal 型の重要性:** 金額や税率など、精度が重要な数値計算には、Double 型ではなく Decimal 型を使用しましょう。

**実践的なテクニック**

- **SOQL の利用:** Salesforce のデータベース（SObject）からデータを取得するには、SOQL（Salesforce Object Query Language）を使用します。

  ```apex
  List<Account> accounts = [SELECT Id, Name, Industry FROM Account WHERE Industry = 'Technology' LIMIT 10];

  for (Account acc : accounts) {
      System.debug(acc.Name + ' (' + acc.Industry + ')');
  }
  ```

- **DML 操作:** データベースへの変更（挿入、更新、削除）は、DML（Data Manipulation Language）操作で行います。

  ```apex
  Account newAccount = new Account(Name = 'Acme Corp', Industry = 'Technology');
  insert newAccount;

  newAccount.Description = 'Leading tech company';
  update newAccount;
  ```

**応用例とユースケース**

- **取引先責任者の重複チェック:** 同じメールアドレスを持つ取引先責任者を検索し、重複を防ぐ。

  ```apex
  public class ContactDuplicateCheck {
      public static void checkDuplicateContacts(List<Contact> contacts) {
          Set<String> emailAddresses = new Set<String>();
          for (Contact con : contacts) {
              if (con.Email != null && !emailAddresses.contains(con.Email)) {
                  emailAddresses.add(con.Email);
              }
          }

          List<Contact> duplicateContacts = [SELECT Id, Name, Email FROM Contact WHERE Email IN :emailAddresses];

          if (!duplicateContacts.isEmpty()) {
              System.debug('Duplicate contacts found: ' + duplicateContacts);
              // 例：カスタムエラーメッセージをセットする
              for (Contact con : contacts) {
                  for (Contact dup : duplicateContacts) {
                      if (con.Email == dup.Email && con.Id != dup.Id) {
                          con.addError('このメールアドレスは既に存在します。');
                      }
                  }
              }
          }
      }
  }
  ```

**トラブルシューティング**

- **NullPointerException:** SObject のフィールドにアクセスする前に、null チェックを行いましょう。
- **DML 操作のエラー:** DML 操作は例外をスローする可能性があります。try-catch ブロックで囲んでエラー処理を行いましょう。

### 3.2 制御構文とコレクション：効率的なロジックの実装

**概要と重要性**

Apex における制御構文とコレクションは、複雑なビジネスロジックを効率的に実装するための重要な要素です。Java と同様の`if-else`、`for`、`while`文に加え、Salesforce 特有の`SOQL FOR`ループなどを使いこなすことで、柔軟なデータ処理や条件分岐を実現できます。また、`List`、`Set`、`Map`といったコレクションを効果的に活用することで、大量のデータを効率的に処理し、パフォーマンスを向上させることが可能です。

**特徴と利点**

- **制御構文:** 条件分岐や繰り返し処理を記述することで、複雑なロジックを表現できる。
- **コレクション:** 複数のデータをまとめて扱うことができ、データ操作の効率化に貢献する。
- **SOQL FOR ループ:** 大量のレコードを効率的に処理できる。

**事前準備と前提条件**

- 3.1 の知識
- Java における制御構文とコレクションの基本的な知識

**基本的な使い方**

**制御構文:**

- **if-else 文:**

  ```apex
  Integer score = 85;
  String grade;

  if (score >= 90) {
      grade = 'A';
  } else if (score >= 80) {
      grade = 'B';
  } else {
      grade = 'C';
  }

  System.debug('Grade: ' + grade);
  ```

- **for ループ:**

  ```apex
  List<String> fruits = new List<String>{'Apple', 'Banana', 'Orange'};

  for (String fruit : fruits) {
      System.debug('Fruit: ' + fruit);
  }
  ```

- **while ループ:**

  ```apex
  Integer count = 0;
  while (count < 5) {
      System.debug('Count: ' + count);
      count++;
  }
  ```

- **do-while ループ:**

  ```apex
  Integer count = 0;
  do {
      System.debug('Count: ' + count);
      count++;
  } while (count < 5);
  ```

- **SOQL FOR ループ:**
  ```apex
  for (Account acc : [SELECT Id, Name FROM Account LIMIT 200]) {
      System.debug('Account Name: ' + acc.Name);
  }
  ```

**コレクション:**

- **List:**

  ```apex
  List<String> names = new List<String>{'Alice', 'Bob', 'Charlie'};
  names.add('David');
  System.debug('List size: ' + names.size());
  System.debug('First element: ' + names[0]);
  ```

- **Set:**

  ```apex
  Set<String> uniqueNames = new Set<String>{'Alice', 'Bob', 'Alice'}; // Aliceは重複しない
  uniqueNames.add('Charlie');
  System.debug('Set size: ' + uniqueNames.size()); // 3
  ```

- **Map:**

  ```apex
  Map<String, Integer> ages = new Map<String, Integer>{
      'Alice' => 30,
      'Bob' => 25
  };
  ages.put('Charlie', 35);
  System.debug('Alice\'s age: ' + ages.get('Alice'));
  System.debug('Map size: ' + ages.size());
  ```

**Java エンジニアが陥りやすい落とし穴:**

1.  **SOQL FOR ループのガバナ制限:** SOQL FOR ループは、内部で暗黙的に SOQL クエリを実行するため、ガバナ制限に注意が必要です。特に、1 つのトランザクション内で実行できる SOQL クエリの数（100 個）を超えないように注意しましょう。
2.  **コレクションの null チェック:** コレクションを使用する前に、null チェックを必ず行いましょう。NullPointerException を避けるために重要です。
3.  **コレクションのサイズ制限:** Apex のコレクションにはサイズ制限があります。大規模なデータを扱う場合は、バッチ処理などを検討する必要があります。

**実践的なテクニック**

- **SOQL FOR ループの最適化:** SOQL FOR ループで大量のレコードを処理する場合は、`LIMIT`句を使用してレコード数を制限したり、`OFFSET`句を使用して処理範囲を分割したりすることで、ガバナ制限を回避できます。
- **コレクションの効率的な操作:** `addAll()`メソッドや`removeAll()`メソッドを使用することで、コレクションの要素を一括で追加/削除できます。
- **Map のキーのユニーク性:** Map のキーはユニークである必要があります。重複したキーを put すると、既存の値が上書きされます。

**応用例とユースケース**

- **取引先に関連する取引先責任者を検索し、特定の条件を満たす取引先責任者のみを処理する:**

  ```apex
  List<Account> accounts = [SELECT Id, Name FROM Account WHERE Industry = 'Technology' LIMIT 10];

  for (Account acc : accounts) {
      for (Contact con : [SELECT Id, Name, Email FROM Contact WHERE AccountId = :acc.Id AND Email != null]) {
          System.debug('Contact: ' + con.Name + ' (' + con.Email + ')');
          // ここで特定の条件を満たす取引先責任者に対する処理を行う
      }
  }
  ```

**トラブルシューティング**

- **System.LimitException: Too many SOQL queries:** SOQL クエリの数が制限を超えた場合に発生します。SOQL FOR ループのネストを避ける、SOQL クエリの数を減らすなどの対策が必要です。
- **NullPointerException:** コレクションが null の場合に発生します。null チェックを徹底しましょう。

### 3.3 Apex ガバナ制限との戦い：リソースを賢く使うテクニック

**概要と重要性**

Apex は、Salesforce のマルチテナント環境で動作するため、リソースの利用を制限するガバナ制限が設けられています。この制限を理解せずに開発を進めると、コードが実行時エラーになるだけでなく、Salesforce 組織全体のパフォーマンスに悪影響を及ぼす可能性があります。このセクションでは、Apex の主要なガバナ制限について解説し、リソースを賢く使うためのテクニックを紹介します。

**特徴と利点**

- **安全なマルチテナント環境の維持:** ガバナ制限は、すべての Salesforce ユーザが平等にリソースを利用できるようにするために設けられています。
- **パフォーマンスの維持:** ガバナ制限を超えるコードは実行されないため、組織全体のパフォーマンス低下を防ぎます。
- **質の高いコードの奨励:** ガバナ制限を意識することで、効率的で最適化されたコードを書く習慣が身につきます。

**事前準備と前提条件**

- 3.1、3.2 の知識
- Salesforce のマルチテナントアーキテクチャに関する基本的な理解

**主要なガバナ制限:**

| 制限項目                                     | 制限値                         | 備考                                                                                                         |
| -------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| SOQL クエリの発行数                          | 100                            | 1 つのトランザクション内で実行できる SOQL クエリの数。                                                       |
| DML ステートメントの発行数                   | 150                            | 1 つのトランザクション内で実行できる DML ステートメントの数（insert, update, delete など）。                 |
| CPU タイム（ミリ秒）                         | 10,000                         | Apex コードが消費できる CPU 時間。                                                                           |
| 合計ヒープサイズ                             | 12 MB                          | Apex コードが使用できるヒープメモリの合計サイズ。                                                            |
| Future メソッドの実行数                      | 50                             | `@future`アノテーションを付けたメソッドの実行数。                                                            |
| governor limits によって監視される SOQL 行数 | 50,000                         | SOQL クエリによって返されるレコードの合計数。                                                                |
| sendEmail メソッドの呼び出し                 | 10 (シングル) / 5,000 (バルク) | メール送信の制限。シングルメール（1 通ずつ送信）とバルクメール（複数のメールをまとめて送信）で制限が異なる。 |

**Java エンジニアが陥りやすい落とし穴:**

1.  **ガバナ制限の存在を意識しない:** Java 開発ではリソース制限をあまり意識しないことが多いため、Apex 開発でも同様に考えてしまうと、ガバナ制限に引っかかる可能性があります。
2.  **SOQL クエリの非効率な使用:** SOQL クエリをループ内で実行したり、必要以上に多くのフィールドを取得したりすると、SOQL クエリ数の制限や CPU タイムの制限に引っかかる可能性があります。
3.  **ヒープサイズの過剰な消費:** 大規模なコレクションを作成したり、複雑なオブジェクトグラフを構築したりすると、ヒープサイズの制限に引っかかる可能性があります。

**実践的なテクニック**

1.  **Bulkify:** 大量のレコードを処理する場合は、DML 操作をまとめて実行することで、DML ステートメント数の制限を回避できます。

    ```apex
    List<Account> accountsToInsert = new List<Account>();
    for (Integer i = 0; i < 200; i++) {
        Account acc = new Account(Name = 'Account ' + i);
        accountsToInsert.add(acc);
    }

    // 一括でinsert
    insert accountsToInsert; // DMLステートメント数は1
    ```

2.  **SOQL クエリの最適化:** 必要なフィールドのみを選択し、WHERE 句で条件を絞り込むことで、SOQL クエリの効率を向上させることができます。

    ```apex
    // 効率的なSOQLクエリ
    List<Account> accounts = [SELECT Id, Name FROM Account WHERE Industry = 'Technology' LIMIT 100];

    // 非効率なSOQLクエリ (避けるべき)
    List<Account> allAccounts = [SELECT Id, Name, Industry, Description, BillingAddress FROM Account];
    List<Account> technologyAccounts = new List<Account>();
    for (Account acc : allAccounts) {
        if (acc.Industry == 'Technology') {
            technologyAccounts.add(acc);
        }
    }
    ```

3.  **Iterable インターフェースと iterator メソッドの利用:** 大量のレコードを処理する場合、イテレータを利用することでヒープサイズを節約できます。

4.  **Cache の利用:** 頻繁にアクセスするデータをプラットフォームキャッシュに保存することで、データベースへのアクセスを減らし、SOQL クエリ数の制限を回避できます。

5.  **Future メソッドの活用:** 時間のかかる処理を非同期的に実行することで、CPU タイムの制限を回避できます。ただし、Future メソッドの実行数には制限があるため、注意が必要です。

    ```apex
    public class AccountProcessor {
        @future
        public static void updateAccountDescription(Set<Id> accountIds) {
            List<Account> accountsToUpdate = [SELECT Id, Description FROM Account WHERE Id IN :accountIds];
            for (Account acc : accountsToUpdate) {
                acc.Description = 'Updated by future method';
            }
            update accountsToUpdate;
        }
    }

    // 呼び出し元
    Set<Id> accountIds = new Set<Id>{'001xx0000000001AAA', '001xx0000000002AAA'};
    AccountProcessor.updateAccountDescription(accountIds);
    ```

6.  **ガバナ制限を監視する:** `Limits`クラスを利用することで、現在のトランザクションで使用されているリソース量を確認できます。開発中に定期的に監視することで、ガバナ制限を超えないように対策を講じることができます。

    ```apex
    System.debug('SOQL queries: ' + Limits.getQueries() + ' / ' + Limits.getLimitQueries());
    System.debug('CPU time: ' + Limits.getCpuTime() + ' / ' + Limits.getLimitCpuTime());
    ```

**応用例とユースケース**

- **取引先の一括更新処理:** 大量の取引先の情報を CSV ファイルから読み込み、更新する処理。Bulkify や Iterable インターフェースを活用して、ガバナ制限を回避する必要があります。
- **複雑なビジネスロジックを含むトリガー:** トリガー内で実行されるロジックが複雑な場合、Future メソッドを活用して処理を非同期化することで、CPU タイムの制限を回避できます。

**トラブルシューティング**

- **System.LimitException: Too many SOQL queries:** SOQL クエリ数を減らすために、SOQL クエリの最適化やキャッシュの利用を検討しましょう。
- **System.LimitException: CPU time limit exceeded:** CPU タイムを消費する処理を最適化する、Future メソッドを活用するなどの対策が必要です。
- **System.LimitException: Apex heap size too large:** 大規模なコレクションの使用を避け、Iterable インターフェースを活用してヒープサイズを節約しましょう。
