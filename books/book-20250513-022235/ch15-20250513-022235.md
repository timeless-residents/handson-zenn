## 第 15 章：パフォーマンスチューニング：高速化とスケーラビリティ

### 15.1 SOQL パフォーマンス：インデックス、クエリプラン、ガバナ制限

**1. 概要と重要性**

Salesforce におけるパフォーマンスチューニングの最重要課題の一つが SOQL の最適化です。遅い SOQL クエリは、ユーザエクスペリエンスの低下だけでなく、ガバナ制限超過によるシステム全体の不安定化を招きます。本セクションでは、SOQL のパフォーマンスを向上させるためのインデックス、クエリプラン、ガバナ制限について深く掘り下げて解説します。

**2. 特徴と利点**

SOQL の最適化は、応答時間の短縮、スケーラビリティの向上、ガバナ制限内の安定動作を実現します。 具体的には、

- **応答時間短縮:** ユーザインターフェースの応答速度が向上し、操作性が改善されます。
- **スケーラビリティ向上:** 大量のデータを扱うアプリケーションでも、安定したパフォーマンスを維持できます。
- **ガバナ制限対策:** SOQL クエリが効率的に実行されることで、制限に達する可能性を減らすことができます。

**3. 事前準備と前提条件**

- Salesforce 組織への管理者権限、または適切な開発権限が必要です。
- Salesforce Data Loader などのデータ操作ツールがあると便利です。
- 開発者コンソールや Workbench などのクエリ実行ツールが必要です。

**4. 基本的な使い方**

**4.1 インデックスの理解**

Salesforce には、標準インデックスとカスタムインデックスの 2 種類があります。標準インデックスは、AccountId や Name などの標準項目に自動的に作成されます。カスタムインデックスは、カスタム項目や複合項目に手動で作成します。

**インデックス作成のヒント:**

- 頻繁に WHERE 句で使用される項目にインデックスを作成します。
- 複合インデックスは、複数の項目を組み合わせてクエリを実行する場合に有効です。
- 数式項目や選択リスト項目へのインデックス作成は慎重に行う必要があります（パフォーマンスに悪影響を及ぼす可能性があります）。

**4.2 クエリプランの確認**

クエリプランは、SOQL クエリがどのように実行されるかを詳細に示したものです。クエリプランを確認することで、ボトルネックとなっている箇所を特定し、改善策を検討できます。

**クエリプランの確認方法:**

1.  開発者コンソールを開きます。
2.  "Query Plan"タブを選択します。
3.  SOQL クエリを入力し、"Explain"ボタンをクリックします。

クエリプランの出力結果を分析し、"Full Table Scan"が発生している箇所や、"Index Not Selected"となっている箇所を特定します。

**4.3 ガバナ制限の考慮**

Salesforce には、SOQL クエリの実行回数、CPU 時間、メモリ使用量などのガバナ制限が設けられています。これらの制限を超えると、SOQL クエリは実行されず、エラーが発生します。

**ガバナ制限対策:**

- SOQL クエリの数を最小限に抑えます。
- 不要な項目は SELECT 句で指定しないようにします。
- WHERE 句でフィルタリングを徹底し、返されるレコード数を減らします。
- SOQL For ループの使用を避け、バルク API を利用します。

**5. 実践的なテクニック**

**5.1 WHERE 句の最適化**

- "="演算子よりも、"<"や">"演算子の方がパフォーマンスが向上する場合があります。
- LIKE 演算子の使用は最小限に抑えます。LIKE 演算子の先頭にワイルドカード（%）を使用すると、インデックスが使用されません。
- 日付項目を比較する場合は、Date 関数を利用するとパフォーマンスが向上します。例：`WHERE CreatedDate >= TODAY - 30`
- IN 句を使用する場合は、リストの要素数を減らすようにします。

**5.2 SOQL For ループの回避**

SOQL For ループは、ガバナ制限に達しやすい処理です。代わりに、バルク API や Batch Apex を利用します。

```java
// 悪い例：SOQL Forループ
List<Account> accounts = [SELECT Id, Name FROM Account WHERE Industry = 'Technology'];
for (Account acc : accounts) {
    List<Contact> contacts = [SELECT Id, Name FROM Contact WHERE AccountId = :acc.Id];
    // 何らかの処理
}
```

```java
// 良い例：1回のSOQLでデータを取得
List<Account> accounts = [SELECT Id, Name, (SELECT Id, Name FROM Contacts) FROM Account WHERE Industry = 'Technology'];
for (Account acc : accounts) {
    for (Contact con : acc.Contacts) {
        // 何らかの処理
    }
}
```

**5.3 Bulk API の利用**

大量のデータを処理する場合は、Bulk API を利用します。Bulk API は、SOQL クエリを非同期で実行し、大量のデータを効率的に処理できます。

**Bulk API の利用例:**

```java
// Bulk APIを使用してAccountをクエリする例（Apex）
AsyncApexJob job = new AsyncApexJob();
job.ApexClassId = [SELECT Id FROM ApexClass WHERE Name = 'BulkQueryAccount'].Id; // BulkQueryAccountはApexクラス
job.MethodName = 'queryAccounts';
job.JobType = 'BatchApex';
job.Status = 'Holding';
insert job;

// BulkQueryAccount Apexクラスの例
global class BulkQueryAccount implements Database.Batchable<sObject> {
    global Database.QueryLocator start(Database.BatchableContext BC) {
        return Database.getQueryLocator([SELECT Id, Name FROM Account]);
    }

    global void execute(Database.BatchableContext BC, List<Account> scope) {
        // 処理
    }

    global void finish(Database.BatchableContext BC) {
        // 完了処理
    }
}

```

**6. 応用例とユースケース**

- **リードの一括更新:** 大量のリード情報を一括で更新する場合、Bulk API を利用して効率的に処理できます。
- **取引先のレポート作成:** 大量の取引先データを集計してレポートを作成する場合、SOQL クエリを最適化し、ガバナ制限を超えないように工夫する必要があります。
- **カスタム検索機能の実装:** 高度な検索機能を実現するために、SOQL クエリを動的に生成し、最適なインデックスを使用するように設計します。

**7. トラブルシューティング**

- **SOQL クエリが遅い:** クエリプランを確認し、インデックスが適切に使用されているか確認します。
- **ガバナ制限を超えた:** SOQL クエリの数を減らすか、バルク API を利用します。
- **カスタムインデックスが効かない:** カスタムインデックスの作成条件を満たしているか確認します。（例：WHERE 句での使用頻度、データの偏り）
- **複合インデックスを作成したが、クエリプランで使用されていない:** WHERE 句の条件の順番をインデックスの順番と合わせることで改善される可能性があります。

**8. まとめと次のステップ**

SOQL のパフォーマンスチューニングは、Salesforce アプリケーションのパフォーマンスを向上させるための重要な要素です。インデックスの適切な使用、クエリプランの確認、ガバナ制限の考慮など、さまざまなテクニックを駆使して、SOQL クエリを最適化しましょう。

次のステップとして、Batch Apex や Queueable Apex を利用した非同期処理の最適化について学習することをお勧めします。

### 15.2 大規模データセットの処理：バルク API、Batch Apex

**1. 概要と重要性**

Salesforce で扱うデータ量が大きくなると、標準的な SOQL クエリや DML 操作では、パフォーマンスやガバナ制限の問題が発生しやすくなります。このセクションでは、大規模データセットを効率的に処理するための Bulk API と Batch Apex について解説します。

**2. 特徴と利点**

- **Bulk API:** 大量のデータを非同期で処理するための API です。データの挿入、更新、削除、クエリを効率的に実行できます。
- **Batch Apex:** 大量のレコードをバッチ処理するための Apex クラスです。非同期処理により、ユーザエクスペリエンスを損なわずに、複雑なロジックを実行できます。

**3. 事前準備と前提条件**

- Salesforce 組織への管理者権限、または適切な開発権限が必要です。
- Apex 開発の基本的な知識が必要です。
- Bulk API を使用する場合は、REST クライアント（Postman など）があると便利です。

**4. 基本的な使い方**

**4.1 Bulk API**

Bulk API は、SOAP API または REST API を使用して利用できます。ここでは REST API の使用例を示します。

**手順:**

1.  **ジョブの作成:** Bulk API にジョブを作成し、処理の種類（挿入、更新、削除、クエリ）を指定します。
2.  **バッチの追加:** ジョブにバッチを追加し、処理するデータを CSV 形式でアップロードします。
3.  **ジョブのクローズ:** ジョブをクローズすると、処理が開始されます。
4.  **結果の確認:** ジョブのステータスを確認し、処理結果（成功、失敗）を取得します。

**REST API の例 (ジョブの作成):**

```bash
curl -X POST \
  https://your-instance.salesforce.com/services/async/48.0/job \
  -H 'Authorization: Bearer YOUR_ACCESS_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{
    "operation" : "insert",
    "object" : "Account",
    "contentType" : "CSV"
  }'
```

**4.2 Batch Apex**

Batch Apex は、`Database.Batchable`インターフェースを実装した Apex クラスです。

**手順:**

1.  `Database.Batchable`インターフェースを実装した Apex クラスを作成します。
2.  `start()`メソッドで処理対象のデータを取得します。
3.  `execute()`メソッドで、取得したデータを処理します。
4.  `finish()`メソッドで、処理完了後の処理を行います。
5.  `Database.executeBatch()`メソッドで、Batch Apex を実行します。

**Batch Apex の例:**

```java
global class AccountBatch implements Database.Batchable<sObject> {
    global Database.QueryLocator start(Database.BatchableContext BC) {
        return Database.getQueryLocator('SELECT Id, Name FROM Account');
    }

    global void execute(Database.BatchableContext BC, List<Account> scope) {
        // 各Accountに対して何らかの処理を行う
        for (Account acc : scope) {
            acc.Description = 'Batch Processed';
        }
        update scope;
    }

    global void finish(Database.BatchableContext BC) {
        // バッチ処理完了後の処理
        System.debug('Batch Process Completed');
    }
}

// 実行
AccountBatch ab = new AccountBatch();
Database.executeBatch(ab, 200); // 200はバッチサイズ
```

**5. 実践的なテクニック**

- **バッチサイズの調整:** Batch Apex のバッチサイズは、処理内容に応じて調整します。複雑な処理の場合は、バッチサイズを小さくすると、ガバナ制限を超えにくくなります。
- **Bulk API の並列処理:** Bulk API は、複数のバッチを並列で処理できます。並列処理を行うことで、処理時間を短縮できます。
- **Bulk API と Batch Apex の組み合わせ:** Bulk API でデータを一括で挿入し、Batch Apex で挿入されたデータを処理するなど、Bulk API と Batch Apex を組み合わせることで、複雑な処理を実現できます。
- **ID の外部キー参照:** 大量のレコードを Bulk API で挿入する際、外部キーとなる ID を参照する必要がある場合、外部 ID 項目を利用するとパフォーマンスが向上します。

**6. 応用例とユースケース**

- **データの移行:** 別のシステムから Salesforce に大量のデータを移行する場合、Bulk API を利用して効率的にデータを挿入できます。
- **データのクレンジング:** 大量のデータに対して、重複排除や不整合データの修正を行う場合、Batch Apex を利用して効率的に処理できます。
- **定期的なデータ更新:** 定期的に大量のデータを更新する必要がある場合、Batch Apex をスケジュール実行することで、自動的にデータを更新できます。

**7. トラブルシューティング**

- **Bulk API のジョブが失敗する:** エラーメッセージを確認し、データの問題（必須項目の欠落、データ型の不一致など）や設定の問題（API バージョンの不一致など）を修正します。
- **Batch Apex がガバナ制限を超える:** バッチサイズを小さくするか、処理ロジックを最適化します。
- **Bulk API の処理が遅い:** バッチサイズを調整するか、並列処理を有効にします。

**8. まとめと次のステップ**

Bulk API と Batch Apex は、Salesforce で大規模データセットを効率的に処理するための強力なツールです。これらのツールを適切に活用することで、パフォーマンスの問題を解決し、スケーラビリティの高いアプリケーションを構築できます。

次のステップとして、プラットフォームイベントや変更データキャプチャ(CDC)を利用したリアルタイムデータ処理について学習することをお勧めします。

### 15.3 アーキテクチャパターン：CQRS、Event Sourcing

**1. 概要と重要性**

従来の CRUD (Create, Read, Update, Delete) モデルでは、複雑なビジネスロジックや大量のデータを扱うアプリケーションにおいて、パフォーマンスやスケーラビリティの問題が発生しやすくなります。CQRS (Command Query Responsibility Segregation) と Event Sourcing は、そのような課題を解決するためのアーキテクチャパターンです。

**2. 特徴と利点**

- **CQRS:** コマンド（更新処理）とクエリ（参照処理）を分離することで、それぞれの処理に最適化されたモデルを構築できます。
  - **利点:** パフォーマンスの向上、スケーラビリティの向上、複雑なロジックの簡素化
- **Event Sourcing:** アプリケーションの状態をイベントのシーケンスとして記録することで、データの監査、デバッグ、およびシステムの再構築を容易にします。
  - **利点:** データの完全性、監査可能性、デバッグの容易性、システムの柔軟性

**3. 事前準備と前提条件**

- Apex 開発の高度な知識が必要です。
- アーキテクチャパターンに関する一般的な知識が必要です。
- 非同期処理に関する理解が必要です。

**4. 基本的な使い方**

**4.1 CQRS**

CQRS では、コマンドモデルとクエリモデルを分離します。

- **コマンドモデル:** データの更新処理を担当します。通常、ドメインオブジェクトを中心とした複雑なロジックを持ちます。
- **クエリモデル:** データの参照処理を担当します。通常、特定の画面やレポートに最適化されたシンプルなデータ構造を持ちます。

**例:** 顧客情報を更新する処理 (コマンド) と、顧客情報を表示する処理 (クエリ) を分離します。

```java
// コマンド (顧客情報の更新)
public class UpdateCustomerCommand {
    public String customerId;
    public String newName;
    // ...

    public void execute() {
        // ドメインロジックに基づいて顧客情報を更新
        Customer customer = CustomerRepository.findById(customerId);
        customer.changeName(newName);
        CustomerRepository.save(customer);
    }
}

// クエリ (顧客情報の取得)
public class CustomerQuery {
    public String customerId;

    public CustomerViewModel execute() {
        // データベースから必要な情報のみを取得
        return [SELECT Name, Email FROM Account WHERE Id = :customerId LIMIT 1]; // ViewModelとして返す
    }
}
```

**4.2 Event Sourcing**

Event Sourcing では、アプリケーションの状態変化をイベントとして記録します。

**例:** 顧客の名前が変更された場合、"CustomerNameChangedEvent"というイベントを記録します。

```java
// イベント
public class CustomerNameChangedEvent {
    public String customerId;
    public String newName;
    public Datetime occurredAt;

    public CustomerNameChangedEvent(String customerId, String newName) {
        this.customerId = customerId;
        this.newName = newName;
        this.occurredAt = Datetime.now();
    }
}

// イベントの保存
public class EventStore {
    public static void save(Object event) {
        // カスタムオブジェクトにイベントを保存
        Event__c eventRecord = new Event__c();
        eventRecord.EventType__c = event.getTypeName(); // イベントの型を文字列で保存
        eventRecord.EventData__c = JSON.serialize(event); // イベントデータをJSONでシリアライズして保存
        insert eventRecord;
    }
}

// アプリケーションの状態を再構築
public class Customer {
    public String id;
    public String name;

    public Customer(String id) {
        this.id = id;
        // イベントストアからすべてのイベントを取得し、状態を再構築
        List<Event__c> events = [SELECT EventData__c, EventType__c FROM Event__c WHERE CustomerId__c = :id ORDER BY CreatedDate ASC];
        for (Event__c event : events) {
            if (event.EventType__c == 'CustomerNameChangedEvent') {
                CustomerNameChangedEvent nameChangedEvent = (CustomerNameChangedEvent) JSON.deserialize(event.EventData__c, CustomerNameChangedEvent.class);
                this.name = nameChangedEvent.newName;
            }
            // 他のイベントの処理
        }
    }

    public void changeName(String newName) {
        this.name = newName;
        EventStore.save(new CustomerNameChangedEvent(this.id, newName));
    }
}
```

**5. 実践的なテクニック**

- **コマンドバスの実装:** コマンドを処理するハンドラーを登録し、コマンドバスを通じてコマンドをディスパッチします。
- **イベントストアの実装:** イベントを永続化するためのストレージを実装します。
- **Read Model の構築:** イベントから Read Model を構築し、クエリのパフォーマンスを向上させます。
- **プラットフォームイベントの利用:** Salesforce のプラットフォームイベントを利用して、イベント駆動型のアーキテクチャを構築します。

**6. 応用例とユースケース**

- **大規模な E コマースサイト:** 注文処理、在庫管理、顧客管理などの複雑なロジックを CQRS と Event Sourcing で分離し、パフォーマンスとスケーラビリティを向上させます。
- **金融取引システム:** 取引履歴を Event Sourcing で記録し、監査可能性とデータの完全性を確保します。
- **IoT プラットフォーム:** デバイスからのイベントを Event Sourcing で記録し、リアルタイム分析や異常検知を行います。

**7. トラブルシューティング**

- **CQRS の実装が複雑になる:** ドメインモデルの設計を十分に検討し、コマンドモデルとクエリモデルの境界を明確にします。
- **Event Sourcing のイベントストアのサイズが大きくなる:** イベントのアーカイブやスナップショットの作成を検討します。
- **Read Model の整合性が保てない:** イベントの処理順序を保証する仕組みを導入します。

**8. まとめと次のステップ**

CQRS と Event Sourcing は、複雑なビジネスロジックや大量のデータを扱うアプリケーションにおいて、パフォーマンス、スケーラビリティ、および保守性を向上させるための強力なアーキテクチャパターンです。これらのパターンを適切に理解し、活用することで、より高度な Salesforce アプリケーションを構築できます。

次のステップとして、マイクロサービスアーキテクチャや Serverless アーキテクチャなど、より分散化されたシステム構成について学習することをお勧めします。
