## 第 16 章：テスト駆動開発：品質を保証するテスト戦略

この章では、Salesforce 開発におけるテスト駆動開発（TDD）の概念と実践的なテクニックについて解説します。品質の高いアプリケーションを開発し、長期的な保守性を確保するために、テスト戦略がいかに重要であるかを理解していきましょう。Apex テストから Selenium による UI テスト、そしてテストデータ戦略まで、Salesforce 開発者が知っておくべきテストの知識を網羅的に解説します。

### 16.1 Apex テスト：単体テスト、結合テスト、システムテスト

#### 16.1.1 概要と重要性

Apex テストは、Salesforce プラットフォーム上で実行される Apex コードの品質を保証するための基盤です。Apex はガバナ制限という制約があるため、コードの品質だけでなく、パフォーマンスも考慮したテスト戦略が求められます。単体テスト、結合テスト、システムテストを適切に組み合わせることで、早期にバグを発見し、開発サイクルを効率化できます。

#### 16.1.2 特徴と利点

Apex テストの主な特徴は以下の通りです。

- **コードカバレッジ**: Salesforce は、本番環境へのデプロイ時に 75%以上のコードカバレッジを義務付けています。これは、コードの実行パスを十分にテストする必要があることを意味します。
- **ガバナ制限への対応**: テストコードもガバナ制限の影響を受けるため、大量のデータを扱うテストでは、Bulk API などを活用する必要があります。
- **自動テスト**: CI/CD パイプラインに組み込むことで、コード変更ごとに自動的にテストを実行し、リグレッションを早期に検出できます。
- **アサーション**: `System.assertEquals()`, `System.assertNotEquals()`, `System.assert()`などのアサーションメソッドを使用して、期待される結果と実際の結果を比較し、テストの成否を判定します。

Apex テストの利点は以下の通りです。

- **早期バグ発見**: 開発初期段階でバグを発見することで、修正コストを大幅に削減できます。
- **リファクタリングの安全性**: テストが十分に整備されていれば、リファクタリング時に既存の機能を破壊することなく安全にコードを変更できます。
- **コード品質の向上**: テストを書くことを前提にコード設計を行うことで、よりモジュール化され、保守性の高いコードを作成できます。
- **Salesforce のデプロイ要件のクリア**: コードカバレッジの要件を満たすことで、本番環境へのデプロイが可能になります。

#### 16.1.3 事前準備と前提条件

- **Salesforce Developer Edition 組織**: 無料で利用できる Developer Edition 組織を用意します。
- **Apex 知識**: Apex の基本的な構文、クラス、トリガーの知識が必要です。
- **テスト駆動開発の原則**: テストを先に書き、テストが成功するようにコードを実装するという TDD の原則を理解しておくと、より効果的に Apex テストを実践できます。

#### 16.1.4 基本的な使い方

基本的な Apex テストの例を以下に示します。

```java
@isTest
private class AccountServiceTest {

    @testSetup
    static void setup() {
        // テストデータを作成
        Account acc = new Account(Name = 'Test Account');
        insert acc;
    }

    @isTest
    static void testCreateContact() {
        // テストデータ取得
        Account acc = [SELECT Id, Name FROM Account WHERE Name = 'Test Account' LIMIT 1];

        // テスト対象メソッド実行
        Contact con = AccountService.createContact(acc.Id, 'Test Contact');

        // 結果検証
        System.assertEquals('Test Contact', con.LastName, 'LastNameが一致しません');
        System.assert(con.AccountId == acc.Id, 'AccountIdが一致しません');
    }

    @isTest
    static void testCreateContactWithNullAccountId() {
        // NullのAccount Idを渡した場合の例外処理をテスト
        Test.startTest(); // ガバナ制限のリセット
        try {
            AccountService.createContact(null, 'Test Contact');
            System.assert(false, '例外が発生しませんでした');
        } catch (IllegalArgumentException e) {
            System.assertEquals('AccountIdは必須です', e.getMessage(), 'エラーメッセージが一致しません');
        }
        Test.stopTest(); // ガバナ制限のリセット
    }
}
```

**コード解説**

- `@isTest`アノテーション: このクラスがテストクラスであることを示します。
- `@testSetup`アノテーション: テストメソッド実行前に実行されるメソッドで、テストに必要なデータを事前に作成します。これにより、各テストメソッドが独立した環境で実行できます。
- `Test.startTest()`と`Test.stopTest()`: これらはガバナ制限をリセットし、非同期処理の実行を保証するために使用されます。特に、DML 操作を行うテストでは重要です。
- `System.assertEquals()`と`System.assert()`: アサーションメソッドで、期待される結果と実際の結果を比較します。アサーションが失敗すると、テストは失敗します。
- `try-catchブロック`: 例外処理をテストするために使用されます。

#### 16.1.5 実践的なテクニック

- **モック**: 外部サービスやデータベースへの依存性を解消するために、モックオブジェクトを使用します。これにより、テストの独立性と信頼性を高めることができます。
- **Bulk API**: 大量のデータを扱うテストでは、Bulk API を使用することでガバナ制限を回避できます。
- **テストデータビルダー**: 複雑なテストデータを生成するために、テストデータビルダーパターンを使用します。これにより、テストコードの可読性と保守性を向上させることができます。
- **SOQL の最適化**: テストコードで SOQL クエリを使用する場合は、パフォーマンスを考慮して最適化します。

#### 16.1.6 応用例とユースケース

- **トリガーのテスト**: トリガーが正しく動作することを確認するために、トリガーのテストを記述します。トリガーは複数のレコードを処理する可能性があるため、Bulk DML 操作を伴うテストケースを作成することが重要です。
- **Future メソッドのテスト**: `@future`アノテーションが付与された非同期メソッドをテストします。`Test.startTest()`と`Test.stopTest()`を使用して、非同期処理が完了するのを待ちます。
- **Queueable ジョブのテスト**: `Queueable`インターフェースを実装したジョブをテストします。`System.enqueueJob()`を使用してジョブをキューに入れ、`Test.startTest()`と`Test.stopTest()`を使用してジョブが完了するのを待ちます。
- **Batch Apex のテスト**: `Batch Apex`をテストします。start, execute, finish メソッドをそれぞれテストし、特に execute メソッドではチャンクサイズを考慮したテストケースを作成することが重要です。

#### 16.1.7 トラブルシューティング

- **コードカバレッジが 75%に満たない**: テストコードが十分に書かれていない可能性があります。コードの実行パスを網羅的にテストするように、テストケースを追加してください。
- **ガバナ制限に違反する**: テストコードがガバナ制限を超えている可能性があります。Bulk API を使用したり、テストデータを削減したり、`Test.startTest()`と`Test.stopTest()`を使用してガバナ制限をリセットしたりしてください。
- **テストが不安定**: テストが実行するたびに結果が変わる場合、テストデータが不適切であるか、外部サービスへの依存性がある可能性があります。モックオブジェクトを使用したり、テストデータを固定したりすることで、テストの安定性を高めることができます。
- **AsyncApexJob が完了しない**: `Test.startTest()`と`Test.stopTest()`の間に非同期処理が実行されない場合、AsyncApexJob は完了しません。適切な処理を`Test.startTest()`と`Test.stopTest()`の間に記述する必要があります。

#### 16.1.8 まとめと次のステップ

Apex テストは、Salesforce 開発における品質保証の要です。単体テスト、結合テスト、システムテストを適切に組み合わせ、モックや Bulk API などのテクニックを活用することで、信頼性の高いアプリケーションを開発できます。次のステップとして、CI/CD パイプラインに Apex テストを組み込み、自動テストの導入を検討しましょう。

### 16.2 Selenium による UI テスト：自動テストの構築

#### 16.2.1 概要と重要性

Selenium は、Web アプリケーションの UI を自動的にテストするためのオープンソースのフレームワークです。Salesforce の Visualforce ページや Lightning Web Components (LWC) の UI テストに利用できます。UI テストは、エンドユーザーが実際にアプリケーションを操作する際の動作を検証するため、システムの品質を保証する上で非常に重要です。

#### 16.2.2 特徴と利点

Selenium の主な特徴は以下の通りです。

- **クロスブラウザ対応**: Chrome、Firefox、Safari など、主要な Web ブラウザをサポートしています。
- **多言語対応**: Java、Python、C#など、様々なプログラミング言語でテストコードを記述できます。
- **柔軟なロケーター**: CSS セレクター、XPath など、様々な方法で UI 要素を特定できます。
- **豊富な API**: UI 要素のクリック、テキスト入力、スクロールなど、様々な操作を自動化できます。

Selenium の利点は以下の通りです。

- **手動テストの削減**: 反復的な UI テストを自動化することで、テストにかかる時間とコストを削減できます。
- **リグレッションテストの自動化**: コード変更ごとに UI テストを自動的に実行することで、既存の機能が破壊されていないことを確認できます。
- **エンドユーザー視点のテスト**: 実際のユーザーがアプリケーションを操作する際の動作を検証することで、ユーザーエクスペリエンスを向上させることができます。
- **品質向上**: UI の不具合を早期に発見することで、アプリケーションの品質を向上させることができます。

#### 16.2.3 事前準備と前提条件

- **Java Development Kit (JDK)**: Selenium は Java で記述されているため、JDK が必要です。
- **Selenium WebDriver**: 各ブラウザに対応した WebDriver をダウンロードし、環境変数にパスを設定します。
- **Selenium IDE (オプション)**: ブラウザのアドオンとして利用できる Selenium IDE は、テストスクリプトの記録と再生に便利です。
- **テストフレームワーク**: JUnit や TestNG などのテストフレームワークを使用すると、テストコードの構造化と実行が容易になります。
- **Salesforce 組織**: テスト対象の Salesforce 組織へのアクセス権が必要です。

#### 16.2.4 基本的な使い方

基本的な Selenium UI テストの例を以下に示します。（Java + JUnit の場合）

```java
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.WebElement;
import org.openqa.selenium.chrome.ChromeDriver;

import static org.junit.jupiter.api.Assertions.assertEquals;

public class SalesforceLoginTest {

    private WebDriver driver;
    private final String SALESFORCE_LOGIN_URL = "https://login.salesforce.com"; // 本番環境以外を利用

    @BeforeEach
    public void setUp() {
        // Chrome Driverのパスを設定 (各自の環境に合わせてください)
        System.setProperty("webdriver.chrome.driver", "/path/to/chromedriver");
        driver = new ChromeDriver();
    }

    @AfterEach
    public void tearDown() {
        if (driver != null) {
            driver.quit();
        }
    }

    @Test
    public void testSuccessfulLogin() {
        driver.get(SALESFORCE_LOGIN_URL);

        WebElement usernameField = driver.findElement(By.id("username"));
        WebElement passwordField = driver.findElement(By.id("password"));
        WebElement loginButton = driver.findElement(By.id("Login"));

        // 実際のSalesforceのユーザ名とパスワードを設定 (テスト用アカウントを使用)
        usernameField.sendKeys("testuser@example.com");
        passwordField.sendKeys("password123");
        loginButton.click();

        // ログイン成功後のページのタイトルを検証 (適宜変更)
        String expectedTitle = "Salesforce - Developer Edition"; // または実際のタイトル
        String actualTitle = driver.getTitle();

        assertEquals(expectedTitle, actualTitle, "ログイン後のタイトルが一致しません。");
    }
}
```

**コード解説**

- `@BeforeEach`: 各テストメソッドの実行前に実行されるメソッドで、WebDriver の初期化を行います。
- `@AfterEach`: 各テストメソッドの実行後に実行されるメソッドで、WebDriver を終了します。
- `driver.get()`: 指定された URL に Web ブラウザでアクセスします。
- `driver.findElement()`: 指定されたロケーターを使用して UI 要素を特定します。
- `sendKeys()`: UI 要素にテキストを入力します。
- `click()`: UI 要素をクリックします。
- `driver.getTitle()`: ページのタイトルを取得します。
- `assertEquals()`: 期待される結果と実際の結果を比較します。

#### 16.2.5 実践的なテクニック

- **Page Object Model (POM)**: UI 要素の特定と操作を抽象化するために、Page Object Model パターンを使用します。これにより、テストコードの可読性と保守性を向上させることができます。
- **Explicit Wait**: UI 要素が表示されるまで待機するために、Explicit Wait を使用します。これにより、非同期処理が完了するのを待つことができます。
- **Headless Browser**: UI を表示せずにテストを実行するために、Headless Browser を使用します。これにより、テストの実行速度を向上させることができます。
- **テストデータ**: テストデータを外部ファイルから読み込むことで、テストデータの管理と再利用を容易にすることができます。

#### 16.2.6 応用例とユースケース

- **Lightning Web Components (LWC) のテスト**: Shadow DOM 内の要素を特定するために、JavaScript Executor を使用します。
- **Visualforce ページのテスト**: Visualforce ページが正しく表示されること、およびフォームの入力と送信が正しく行われることを検証します。
- **カスタムコンポーネントのテスト**: カスタムコンポーネントが正しく動作することを確認するために、コンポーネントの属性とイベントを検証します。
- **動的な UI のテスト**: JavaScript によって動的に変更される UI 要素をテストするために、Explicit Wait と JavaScript Executor を使用します。

#### 16.2.7 トラブルシューティング

- **UI 要素が見つからない**: ロケーターが誤っているか、UI 要素がまだ表示されていない可能性があります。ロケーターを確認し、Explicit Wait を使用してください。
- **テストが不安定**: テストが実行するたびに結果が変わる場合、非同期処理が完了する前にテストを実行している可能性があります。Explicit Wait を使用して、非同期処理が完了するのを待ってください。
- **WebDriver が起動しない**: WebDriver のパスが正しく設定されていないか、WebDriver のバージョンが古い可能性があります。WebDriver のパスを確認し、最新の WebDriver をダウンロードしてください。
- **Salesforce のアップデートによるテストの破損**: Salesforce の UI が変更された場合、テストコードを修正する必要があります。定期的にテストコードを見直し、最新の UI に対応するように更新してください。

#### 16.2.8 まとめと次のステップ

Selenium による UI テストは、Salesforce アプリケーションの品質を保証する上で非常に重要です。Page Object Model や Explicit Wait などのテクニックを活用することで、信頼性の高い自動テストを構築できます。次のステップとして、CI/CD パイプラインに Selenium テストを組み込み、自動テストの頻度を高めることを検討しましょう。また、Salesforce DX を利用したスクラッチ組織でのテスト自動化も視野に入れると良いでしょう。

### 16.3 テストデータ戦略：本番環境を模倣したデータセット

#### 16.3.1 概要と重要性

テストデータは、Apex テストや Selenium UI テストを実行する際に必要なデータです。テストデータの品質は、テストの有効性に直接影響します。本番環境を模倣したデータセットを使用することで、より現実的なシナリオでテストを実行し、潜在的な問題を早期に発見できます。

#### 16.3.2 特徴と利点

適切なテストデータ戦略の特徴は以下の通りです。

- **現実的なデータ**: 本番環境のデータ分布、値の範囲、およびデータ間の関係を模倣したデータを使用します。
- **多様なデータ**: 正常系と異常系の両方のテストケースをカバーするために、様々な種類のデータを用意します。
- **管理されたデータ**: テストデータを一元的に管理し、再利用可能な形式で保存します。
- **自動生成**: テストデータを自動的に生成するためのツールやスクリプトを使用します。

適切なテストデータ戦略の利点は以下の通りです。

- **テストの信頼性向上**: 現実的なデータを使用することで、テストの信頼性を向上させることができます。
- **カバレッジの向上**: 多様なデータを使用することで、テストカバレッジを向上させることができます。
- **テストの効率化**: テストデータを一元的に管理し、自動生成することで、テストの効率を向上させることができます。
- **早期バグ発見**: 本番環境で発生する可能性のある問題を早期に発見できます。

#### 16.3.3 事前準備と前提条件

- **データモデルの理解**: テスト対象の Salesforce 組織のデータモデルを理解します。オブジェクト、フィールド、およびリレーションシップを把握します。
- **データプロファイリング**: 本番環境のデータを分析し、データ分布、値の範囲、およびデータ間の関係を把握します。
- **テストデータ設計**: テストケースを定義し、各テストケースに必要なテストデータを設計します。
- **データ生成ツール**: テストデータを生成するためのツール（例：Dataloader, データローダー CLI, データ生成スクリプト）を用意します。
- **スクラッチ組織**: テストデータを安全に管理するために、スクラッチ組織または開発環境を使用します。

#### 16.3.4 基本的な使い方

基本的なテストデータ作成の手順を以下に示します。

1.  **データモデルの分析**: テスト対象のオブジェクトとフィールドを特定します。
2.  **データプロファイリング**: 本番環境のデータを分析し、データ分布、値の範囲、およびデータ間の関係を把握します。例えば、取引先責任者の役職の分布、取引先の業種などを分析します。
3.  **テストケースの設計**: テストケースを定義し、各テストケースに必要なテストデータを設計します。例えば、取引先作成、取引先責任者作成、商談作成などのテストケースを定義します。
4.  **データ生成**: テストデータを生成します。手動でデータを作成することもできますが、自動化されたツールを使用することをお勧めします。
5.  **データロード**: 生成されたテストデータを Salesforce 組織にロードします。
6.  **データ検証**: ロードされたテストデータが正しいことを確認します。

#### 16.3.5 実践的なテクニック

- **データマスキング**: 本番環境の機密データを保護するために、テストデータにマスキング処理を施します。
- **データサンプリング**: 本番環境からランダムにデータを抽出し、テストデータとして使用します。
- **データジェネレーター**: ランダムなデータを生成するためのツール（例：Faker ライブラリ）を使用します。
- **テストデータ管理ツール**: テストデータを一元的に管理するためのツールを使用します。

#### 16.3.6 応用例とユースケース

- **ガバナ制限のテスト**: 大量のデータを扱うシナリオをテストするために、Bulk API を使用して大量のテストデータを生成します。
- **共有ルールのテスト**: 異なるユーザープロファイルでテストを実行し、共有ルールが正しく動作することを確認します。
- **ワークフロールールのテスト**: ワークフロールールが正しく動作することを確認するために、ワークフロールールの条件を満たすテストデータを作成します。
- **カスタム設定のテスト**: カスタム設定が正しく動作することを確認するために、カスタム設定の値を変更し、テストを実行します。

#### 16.3.7 トラブルシューティング

- **テストデータが不足している**: テストケースを再検討し、必要なテストデータを洗い出します。
- **テストデータが現実的でない**: 本番環境のデータを分析し、より現実的なテストデータを作成します。
- **テストデータの管理が煩雑**: テストデータ管理ツールを導入し、テストデータを一元的に管理します。
- **テストデータが競合する**: テストデータを隔離するために、スクラッチ組織または開発環境を使用します。
- **Sandbox 環境のデータ容量を超過**: Sandbox 環境のデータ容量を超過しないように、データサンプリングやデータアーカイブなどの対策を実施します。

#### 16.3.8 まとめと次のステップ

適切なテストデータ戦略は、高品質な Salesforce アプリケーションを開発するために不可欠です。本番環境を模倣したデータセットを使用し、多様なテストケースをカバーすることで、テストの信頼性を向上させることができます。次のステップとして、テストデータ管理ツールの導入を検討し、テストデータの自動生成と管理を効率化しましょう。また、定期的に本番環境のデータを分析し、テストデータを最新の状態に保つように心がけましょう。

この章では、Apex テスト、Selenium UI テスト、およびテストデータ戦略について解説しました。これらのテスト戦略を実践することで、より高品質な Salesforce アプリケーションを開発し、長期的な保守性を確保できます。
