## 第14章：ドメイン駆動設計 (DDD) の導入 - ビジネスロジックの明確化

**はじめに**

この章では、ソフトウェア開発における重要な設計思想であるドメイン駆動設計（DDD）について深く掘り下げていきます。DDDは、複雑なビジネスロジックを扱うアプリケーションを開発する際に特に有効です。単なる理論ではなく、実践的なテクニックや具体的なユースケースを通じて、DDDの概念を理解し、あなたのプロジェクトに適用できるようになることを目指します。初心者の方にもわかりやすいように、基本的な概念から丁寧に解説し、経験豊富な開発者の方には新たな視点を提供できるよう、実践的なテクニックや応用例も紹介します。

### ドメイン駆動設計とは

**概要と重要性**

ドメイン駆動設計（Domain-Driven Design, DDD）は、ソフトウェア開発のアプローチの一つで、ソフトウェアの中心をビジネスドメインに据え、そのドメインの専門家の知識（ドメイン知識）に基づいて設計を行うことを重視します。従来の開発手法では、データベースやUIといった技術的な側面から設計が始まることが多かったのですが、DDDではビジネスの本質を理解し、それをモデルとして表現することで、より保守性が高く、ビジネスの変化に対応しやすいソフトウェアを構築することを目指します。

DDDが重要な理由は、複雑なビジネスロジックを抱えるシステムにおいて、ソフトウェアの複雑さを管理し、ビジネス要件の変化に柔軟に対応できるようにするためです。ビジネスと技術の溝を埋め、共通の言語で議論できるようにすることで、開発チーム全体の理解を深め、コミュニケーションを円滑にします。

**特徴と利点**

*   **ビジネスに焦点を当てる:** 最も重要な点は、ビジネスドメインを深く理解し、ソフトウェア設計の中心に据えることです。
*   **ユビキタス言語:** ドメイン専門家と開発者の間で共通の言語（ユビキタス言語）を確立し、誤解を減らし、コミュニケーションを改善します。
*   **ドメインモデル:** ビジネスドメインを表現するモデルを構築し、ソフトウェアの構造を明確にします。
*   **戦略的設計と戦術的設計:** 全体的なアーキテクチャ（戦略的設計）と、具体的な実装（戦術的設計）を区別して考えることで、より効果的な設計が可能になります。
*   **変更容易性:** ビジネスロジックが明確に定義されているため、ビジネス要件の変更に柔軟に対応できます。
*   **保守性:** コードの可読性が高く、理解しやすいため、保守が容易になります。

**事前準備と前提条件**

DDDを導入するにあたり、特別なツールやフレームワークは必須ではありません。ただし、以下の点を考慮しておくことが望ましいです。

*   **オブジェクト指向プログラミングの基礎知識:** DDDはオブジェクト指向の原則に基づいているため、基本的な概念を理解していることが前提となります。
*   **設計原則の理解:** SOLID原則など、ソフトウェア設計の原則を理解していると、より効果的にDDDを適用できます。
*   **モデリングの基礎知識:** UMLなどのモデリングツールに精通している必要はありませんが、概念的なモデルを作成する能力があると役立ちます。
*   **ドメインエキスパートとの連携体制:** DDDの成功には、ドメインエキスパートとの密な連携が不可欠です。協力を得られる体制を整えておく必要があります。

**基本的な使い方**

DDDの基本的な流れは以下のようになります。

1.  **ドメイン知識の学習:** ドメインエキスパートからビジネスドメインについて学び、理解を深めます。
2.  **ユビキタス言語の確立:** ドメインエキスパートと開発者の間で共通の言語（ユビキタス言語）を定義します。
3.  **ドメインモデルの構築:** ユビキタス言語に基づいて、ドメインモデルを構築します。エンティティ、値オブジェクト、集約などを定義します。
4.  **リポジトリの設計:** ドメインオブジェクトの永続化を担当するリポジトリを設計します。
5.  **ドメインサービスの設計:** ドメインロジックのうち、特定のエンティティに属さないものをドメインサービスとして設計します。
6.  **実装:** ドメインモデル、リポジトリ、ドメインサービスを実装します。

**実践的なテクニック**

*   **イベントストーミング:** ドメインの全体像を把握し、ユビキタス言語を確立するための効果的なワークショップ形式です。
*   **境界づけられたコンテキスト (Bounded Context):** 大きなドメインをより小さな、独立したサブドメインに分割します。それぞれのサブドメインは独自のユビキタス言語を持ちます。これにより、複雑さを軽減し、より管理しやすいモデルを構築できます。
*   **コンテキストマップ:** 複数の境界づけられたコンテキスト間の関係性を記述します。これにより、異なるサブドメイン間の連携方法を明確にし、誤解を減らすことができます。
*   **貧血ドメインモデルの回避:** データホルダーとして機能するだけで、ビジネスロジックを持たない貧血ドメインモデルは避けるべきです。ドメインオブジェクト自体にビジネスロジックを実装し、より豊かなドメインモデルを構築します。

**応用例とユースケース**

*   **Eコマース:** 注文、商品、顧客などのエンティティをモデル化し、注文処理、在庫管理、決済などのドメインサービスを実装できます。
*   **金融システム:** 口座、取引、顧客などのエンティティをモデル化し、入出金処理、残高照会、不正検知などのドメインサービスを実装できます。
*   **医療システム:** 患者、診断、処方箋などのエンティティをモデル化し、予約管理、診療記録管理、薬歴管理などのドメインサービスを実装できます。

**トラブルシューティング**

*   **過剰な複雑さ:** すべてのアプリケーションにDDDが適しているわけではありません。単純なCRUDアプリケーションにはオーバースペックになる可能性があります。
*   **ドメイン知識の不足:** ドメイン知識が不足していると、不正確なドメインモデルを構築してしまう可能性があります。ドメインエキスパートとの連携を密に行い、理解を深めることが重要です。
*   **貧血ドメインモデル:** データホルダーとして機能するだけのドメインモデルは、ビジネスロジックが分散し、保守性を損なう可能性があります。ドメインオブジェクト自体にビジネスロジックを実装するように心がけましょう。
*   **境界づけられたコンテキストの誤り:** 境界づけられたコンテキストの分割を誤ると、サブドメイン間の連携が複雑になり、システム全体の複雑さを増してしまう可能性があります。慎重に分割し、コンテキストマップを用いて関係性を明確にすることが重要です。

**まとめと次のステップ**

DDDは、複雑なビジネスロジックを扱うアプリケーションを開発するための強力な設計思想です。ユビキタス言語、ドメインモデル、境界づけられたコンテキストなどの概念を理解し、実践的なテクニックを習得することで、より保守性が高く、ビジネスの変化に柔軟に対応できるソフトウェアを構築できます。

次のステップとしては、実際に小さなプロジェクトでDDDを試してみることをお勧めします。シンプルなドメインモデルを設計・実装し、DDDの利点を実感してみてください。また、関連書籍や記事を読み、さらに知識を深めることも重要です。

### ユビキタス言語とドメインモデル

**概要と重要性**

ユビキタス言語（Ubiquitous Language）は、ドメイン駆動設計（DDD）の中核となる概念の一つです。これは、開発チーム、ドメイン専門家（ビジネス担当者）、そしてその他関係者全員が共有し、一貫して使用する共通の言語のことです。ユビキタス言語は、コード、ドキュメント、会話、そして頭の中にあるモデルなど、プロジェクトのあらゆる場所で使われるべきです。

ユビキタス言語の重要性は、コミュニケーションの齟齬を減らし、誤解を防ぎ、開発チームとドメイン専門家の間の連携を円滑にすることにあります。異なる人々が同じ言葉で同じ意味を理解することで、ソフトウェアがビジネス要件を正確に反映し、価値を提供できるようになります。

ドメインモデルは、ユビキタス言語を用いて表現された、ビジネスドメインの概念的な表現です。これは、ソフトウェアの中心的な構造を定義し、ビジネスロジックを具体的に実装するための基盤となります。良いドメインモデルは、ビジネスの本質を捉え、複雑さを管理し、変更に強く、理解しやすいものであるべきです。

**特徴と利点**

*   **明確なコミュニケーション:** 関係者全員が同じ言語を使用するため、誤解や誤訳が減少します。
*   **正確なビジネス要件の実装:** ビジネス要件が正確に理解され、ソフトウェアに反映されるため、ビジネス価値の高いソフトウェアを開発できます。
*   **ドメイン知識の共有:** ユビキタス言語は、ドメイン知識を共有するための共通の基盤となります。
*   **保守性の向上:** ドメインモデルが明確であるため、コードの可読性が向上し、保守が容易になります。
*   **ビジネスの変化への対応:** ビジネス要件の変化に合わせて、ドメインモデルを柔軟に変更できます。

**事前準備と前提条件**

*   **ドメイン専門家との協力:** ドメイン専門家は、ユビキタス言語を確立し、ドメインモデルを構築するために不可欠な存在です。協力を得るための体制を整えておく必要があります。
*   **積極的に質問する姿勢:** 不明な点や疑問点があれば、積極的にドメイン専門家に質問し、理解を深めることが重要です。
*   **リスニングスキル:** ドメイン専門家の話を注意深く聞き、ビジネスの背景や意図を理解することが重要です。

**基本的な使い方**

1.  **ドメイン知識の学習:** ドメイン専門家からビジネスドメインについて学び、理解を深めます。
2.  **ユビキタス言語の定義:** ドメイン専門家との会話を通して、ユビキタス言語を定義します。用語集を作成したり、図を作成したりすることも有効です。
3.  **ドメインモデルの構築:** ユビキタス言語に基づいて、ドメインモデルを構築します。エンティティ、値オブジェクト、集約などを定義します。
4.  **レビューと改善:** ドメイン専門家と一緒にドメインモデルをレビューし、改善します。モデルがビジネスを正確に反映しているかを確認します。
5.  **コードへの適用:** ドメインモデルに基づいて、コードを記述します。コードの命名規則やコメントにもユビキタス言語を使用します。

**実践的なテクニック**

*   **イベントストーミング:** ドメインの全体像を把握し、ユビキタス言語を確立するための効果的なワークショップ形式です。
*   **用語集の作成:** ユビキタス言語を文書化するために、用語集を作成します。用語の意味、関連する概念、使用例などを記述します。
*   **図の活用:** ドメインモデルを視覚的に表現するために、UMLなどの図を活用します。エンティティ間の関係性や、属性などを明確に表現します。
*   **プロトタイピング:** ドメインモデルの理解を深めるために、簡単なプロトタイプを作成します。プロトタイプを通じて、ドメイン専門家とのコミュニケーションを円滑にし、要件の理解を深めます。
*   **コードレビュー:** コードレビューの際に、ユビキタス言語が適切に使用されているかを確認します。命名規則やコメントが適切であるか、ドメインモデルと一致しているかなどを確認します。

**応用例とユースケース**

*   **Eコマース:**
    *   **ユビキタス言語:** 注文、商品、顧客、カート、支払い、配送など
    *   **ドメインモデル:** `Order` (注文), `Product` (商品), `Customer` (顧客), `Cart` (カート), `Payment` (支払い), `Shipping` (配送) などのエンティティと、それらの間の関係性をモデル化します。
*   **金融システム:**
    *   **ユビキタス言語:** 口座、取引、顧客、残高、入金、出金など
    *   **ドメインモデル:** `Account` (口座), `Transaction` (取引), `Customer` (顧客), `Balance` (残高), `Deposit` (入金), `Withdrawal` (出金) などのエンティティと、それらの間の関係性をモデル化します。

**トラブルシューティング**

*   **ユビキタス言語の曖昧さ:** ユビキタス言語が曖昧であると、誤解が生じやすくなります。用語の意味を明確に定義し、関係者全員が同じ理解を持つように努める必要があります。
*   **ドメインモデルの複雑さ:** ドメインモデルが複雑すぎると、理解しにくくなり、保守が困難になります。モデルをシンプルに保ち、必要に応じて分割することを検討しましょう。
*   **ドメイン専門家の不在:** ドメイン専門家が不在であると、正確なドメインモデルを構築することができません。ドメイン専門家の協力を得るために、積極的にコミュニケーションを取りましょう。

**まとめと次のステップ**

ユビキタス言語とドメインモデルは、DDDの成功に不可欠な要素です。ユビキタス言語を確立し、ドメインモデルを構築することで、ビジネス要件を正確に理解し、価値の高いソフトウェアを開発できます。

次のステップとしては、実際にプロジェクトでユビキタス言語とドメインモデルを適用してみることをお勧めします。小さなプロジェクトから始め、徐々に複雑さを増していくと良いでしょう。また、ドメイン駆動設計に関する書籍や記事を読み、知識を深めることも重要です。

### エンティティ、値オブジェクト、集約

**概要と重要性**

DDDにおいて、ドメインモデルを構築する上で重要な概念がエンティティ、値オブジェクト、集約です。これらは、ドメインオブジェクトを分類し、それぞれの役割を明確にすることで、モデルの複雑さを軽減し、保守性を高めるのに役立ちます。

*   **エンティティ:** 一意な識別子を持ち、時間経過とともに状態が変化するオブジェクトです。例えば、顧客、商品、注文などが該当します。
*   **値オブジェクト:** 識別子を持たず、その属性の集合によって一意性が決まる不変なオブジェクトです。例えば、住所、金額、色などが該当します。
*   **集約:** 一つ以上のエンティティと値オブジェクトをまとめたもので、一貫性を保つための境界を定義します。集約のルートとなるエンティティ（集約ルート）を通じてのみ、集約内のオブジェクトにアクセスできます。例えば、注文集約は、注文エンティティ、注文明細エンティティ、配送先住所値オブジェクトなどを含む場合があります。

これらの概念を理解し、適切に適用することで、より堅牢で保守性の高いドメインモデルを構築できます。

**特徴と利点**

*   **エンティティ:**
    *   **状態の変化を追跡:** ライフサイクルを持つオブジェクトを表現するのに適しています。
    *   **一意性の保証:** 識別子によってオブジェクトを一意に識別できます。
*   **値オブジェクト:**
    *   **不変性:** 状態が変化しないため、安全に共有できます。
    *   **意味の明確化:** プリミティブ型をラップすることで、より意味のある表現を可能にします。
*   **集約:**
    *   **一貫性の保証:** 集約ルートを通じてのみアクセスを制限することで、集約内の一貫性を保つことができます。
    *   **モデルの複雑さの軽減:** 関連するオブジェクトをまとめることで、モデル全体の複雑さを軽減できます。

**事前準備と前提条件**

*   **オブジェクト指向プログラミングの基礎知識:** エンティティ、値オブジェクト、集約は、オブジェクト指向の原則に基づいています。
*   **ドメイン知識の理解:** どのオブジェクトをエンティティとして、どのオブジェクトを値オブジェクトとしてモデル化するかは、ドメイン知識に依存します。

**基本的な使い方**

*   **エンティティの定義:**
    *   一意な識別子を定義します（例：ID、UUID）。
    *   状態を表現する属性を定義します。
    *   状態を変更するメソッドを定義します。
*   **値オブジェクトの定義:**
    *   すべての属性をfinalとして定義し、不変性を保証します。
    *   equals()メソッドとhashCode()メソッドをオーバーライドし、属性の集合に基づいてオブジェクトの同一性を判定します。
*   **集約の定義:**
    *   集約ルートとなるエンティティを決定します。
    *   集約ルートを通じてのみ、集約内のオブジェクトにアクセスできるように制限します。
    *   集約内の一貫性を保つためのルールを定義します。

**実践的なテクニック**

*   **集約のサイズ:** 集約は小さく保つことが推奨されます。大きすぎる集約は、一貫性を保つのが難しく、パフォーマンスにも影響を与える可能性があります。
*   **参照の制限:** 集約間では、識別子による参照のみを許可し、オブジェクト参照は避けるべきです。これにより、結合度を下げ、変更の影響範囲を局所化できます。
*   **イベント駆動アーキテクチャ:** 集約間の連携には、ドメインイベントを活用することを検討しましょう。これにより、疎結合なアーキテクチャを実現できます。

**応用例とユースケース**

*   **Eコマース:**
    *   **エンティティ:** 顧客、商品、注文
    *   **値オブジェクト:** 住所、金額、色、サイズ
    *   **集約:** 注文集約（注文、注文明細、配送先住所）
*   **金融システム:**
    *   **エンティティ:** 口座、取引
    *   **値オブジェクト:** 金額、通貨
    *   **集約:** 口座集約（口座、取引履歴）

**コード例 (Java):**

```java
// 値オブジェクト
public final class Address {
    private final String street;
    private final String city;
    private final String zipCode;

    public Address(String street, String city, String zipCode) {
        this.street = street;
        this.city = city;
        this.zipCode = zipCode;
    }

    // getterのみ (setterはなし、不変)

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Address address = (Address) o;
        return Objects.equals(street, address.street) &&
               Objects.equals(city, address.city) &&
               Objects.equals(zipCode, address.zipCode);
    }

    @Override
    public int hashCode() {
        return Objects.hash(street, city, zipCode);
    }
}

// エンティティ
public class Customer {
    private UUID id;
    private String name;
    private Address address;

    public Customer(UUID id, String name, Address address) {
        this.id = id;
        this.name = name;
        this.address = address;
    }

    // getterとsetter (状態を変更できる)

    public void changeAddress(Address newAddress) {
        this.address = newAddress;
    }
}

// 集約ルート
public class Order {
    private UUID id;
    private Customer customer;
    private List<OrderItem> orderItems;
    private Address shippingAddress; // 値オブジェクト
```

### リポジトリとドメインサービス

**概要と重要性**

DDDにおけるリポジトリとドメインサービスは、ビジネスロジックと技術的な詳細を分離し、ドメインモデルを永続化し、複雑なビジネスルールを実装するための重要な要素です。

*   **リポジトリ:** ドメインオブジェクトの永続化を担当するインターフェースです。データベースやファイルシステムなどの永続化技術を隠蔽し、ドメイン層が技術的な詳細に依存しないようにします。リポジトリは、ドメインオブジェクトの取得、保存、削除などの操作を提供します。
*   **ドメインサービス:** 特定のエンティティや値オブジェクトに属さない、複雑なビジネスロジックを実装するためのコンポーネントです。複数のエンティティにまたがる処理や、外部システムとの連携が必要な処理などを担当します。

これらの要素を適切に設計・実装することで、ドメインモデルの独立性を保ち、テスト容易性を高め、変更に強いアーキテクチャを実現できます。

**特徴と利点**

*   **リポジトリ:**
    *   **永続化技術の隠蔽:** ドメイン層が永続化技術に依存しないようにします。
    *   **テスト容易性の向上:** モックオブジェクトを使用して、リポジトリを簡単にテストできます。
    *   **インフラストラクチャ層との分離:** ドメイン層とインフラストラクチャ層を分離します。
*   **ドメインサービス:**
    *   **ドメインロジックの集約:** 複雑なビジネスロジックを一箇所に集約します。
    *   **テスト容易性の向上:** 単体テストが容易になります。
    *   **コードの再利用性:** 複数の場所で利用されるロジックを共通化できます。

**事前準備と前提条件**

*   **インターフェースの理解:** リポジトリはインターフェースとして定義され、具体的な実装はインフラストラクチャ層に委ねられます。
*   **設計原則の理解:** 単一責任の原則、インターフェース分離の原則など、設計原則を理解していると、より効果的にリポジトリとドメインサービスを設計できます。

**基本的な使い方**

*   **リポジトリの定義:**
    *   ドメインオブジェクトの種類ごとにリポジトリインターフェースを定義します。
    *   findById(), save(), delete()などのメソッドを定義します。
*   **リポジトリの実装:**
    *   リポジトリインターフェースを実装し、具体的な永続化技術を使用してドメインオブジェクトを永続化します。
*   **ドメインサービスの定義:**
    *   インターフェースまたはクラスとしてドメインサービスを定義します。
    *   ビジネスロジックを実装するメソッドを定義します。

**実践的なテクニック**

*   **リポジトリの抽象化:** リポジトリを抽象化することで、永続化技術の変更に柔軟に対応できます。
*   **ドメインイベント:** ドメインサービス内で発生したイベントをドメインイベントとして公開し、他のコンポーネントに通知できます。これにより、疎結合なアーキテクチャを実現できます。
*   **トランザクション管理:** ドメインサービス内で複数のリポジトリを操作する場合、トランザクション管理を適切に行う必要があります。

**応用例とユースケース**

*   **Eコマース:**
    *   **リポジトリ:** `ProductRepository`（商品）、`OrderRepository`（注文）、`CustomerRepository`（顧客）
    *   **ドメインサービス:** `OrderService`（注文処理）、`PaymentService`（決済処理）、`ShippingService`（配送処理）
*   **金融システム:**
    *   **リポジトリ:** `AccountRepository`（口座）、`TransactionRepository`（取引）
    *   **ドメインサービス:** `TransferService`（送金処理）、`InterestCalculationService`（利息計算処理）、`FraudDetectionService`（不正検知処理）

**コード例 (Java):**

```java
// ドメインオブジェクト (Customer)
public class Customer {
    private UUID id;
    private String name;

    // ...
}

// リポジトリインターフェース
public interface CustomerRepository {
    Customer findById(UUID id);
    void save(Customer customer);
    void delete(Customer customer);
}

// リポジトリ実装 (JPA)
@Repository
public class JpaCustomerRepository implements CustomerRepository {

    @PersistenceContext
    private EntityManager entityManager;

    @Override
    public Customer findById(UUID id) {
        return entityManager.find(Customer.class, id);
    }

    @Override
    public void save(Customer customer) {
        entityManager.persist(customer);
    }

    @Override
    public void delete(Customer customer) {
        entityManager.remove(customer);
    }
}

// ドメインサービス
public interface OrderService {
    void placeOrder(UUID customerId, List<UUID> productIds);
}

// ドメインサービス実装
@Service
public class OrderServiceImpl implements OrderService {

    private final CustomerRepository customerRepository;
    private final ProductRepository productRepository;
    private final OrderRepository orderRepository;

    public OrderServiceImpl(CustomerRepository customerRepository, ProductRepository productRepository, OrderRepository orderRepository) {
        this.customerRepository = customerRepository;
        this.productRepository = productRepository;
        this.orderRepository = orderRepository;
    }

    @Override
    @Transactional
    public void placeOrder(UUID customerId, List<UUID> productIds) {
        Customer customer = customerRepository.findById(customerId);
        if (customer == null) {
            throw new IllegalArgumentException("Customer not found");
        }

        List<Product> products = productIds.stream()
                .map(productRepository::findById)
                .collect(Collectors.toList());

        // 複雑なビジネスロジック (在庫確認、価格計算など)

        Order order = new Order(UUID.randomUUID(), customer);
        orderRepository.save(order);
    }
}
```

**トラブルシューティング**

*   **リポジトリの肥大化:** リポジトリにすべてのデータアクセスロジックを詰め込むと、肥大化し、テストが難しくなります。クエリオブジェクトパターンなどを活用して、リポジトリをシンプルに保つことを検討しましょう。
*   **ドメインサービスのアンチパターン:** ドメインサービスを単なる手続き型の処理を行う場所として使用すると、ドメインモデルが貧血状態になります。ドメインモデルを中心に設計し、ドメインサービスは必要最小限に留めるべきです。

**まとめと次のステップ**

リポジトリとドメインサービスは、DDDにおいてドメインモデルの独立性を保ち、複雑なビジネスロジックを実装するための重要な要素です。これらの要素を適切に設計・実装することで、テスト容易性が高く、変更に強いアーキテクチャを実現できます。

### 実践課題：簡単なドメインモデルを設計・実装

**概要と重要性**

これまでの学習内容を基に、簡単な課題を通じてDDDの実践的な経験を積むことは、理解を深める上で非常に重要です。このセクションでは、具体的な課題に取り組みながら、ユビキタス言語の確立、ドメインモデルの設計、エンティティ、値オブジェクト、集約の識別、リポジトリとドメインサービスの設計・実装といった一連のプロセスを体験します。

**課題:**

シンプルな図書館システムを題材に、以下の要件を満たすドメインモデルを設計・実装してください。

*   **要件:**
    *   図書館は複数の本を所蔵している。
    *   利用者は本を借りることができる。
    *   利用者は本を返却することができる。
    *   本の貸出状況（貸出中、在庫あり）を管理する。
    *   本の種類（小説、技術書、雑誌など）を管理する。

**事前準備と前提条件**

*   これまでの章で解説したDDDの基本的な概念を理解していること。
*   Javaなどのオブジェクト指向プログラミング言語の基本的な知識。
*   IDE (IntelliJ IDEA, Eclipseなど) の利用経験。
*   バージョン管理システム (Git) の利用経験 (推奨)。

**設計・実装手順**

1.  **ユビキタス言語の確立:**
    *   図書館の業務に携わる人（司書など）と会話を想定し、関連する用語を洗い出します。（例: 本、利用者、貸出、返却、在庫、著者、タイトル、ISBNなど）
    *   洗い出した用語について、意味を明確に定義し、関係者間で共通認識を持つようにします。

2.  **ドメインモデルの設計:**
    *   ユビキタス言語を基に、ドメインモデルを設計します。
    *   エンティティ、値オブジェクト、集約を識別し、それぞれの属性とメソッドを定義します。

    *   **例:**
        *   **エンティティ:**
            *   `Book`（本）: `bookId`（ISBN）, `title`, `author`, `bookType`, `loanStatus`
            *   `User`（利用者）: `userId`, `name`, `address`
        *   **値オブジェクト:**
            *   `BookType`（本の種類）: `name` (小説, 技術書, 雑誌)
        *   **集約:**
            *   `Library`（図書館）: `libraryId`, `books` (List<Book>)

3.  **リポジトリの設計:**
    *   エンティティごとにリポジトリインターフェースを定義します。
        *   `BookRepository`, `UserRepository`
    *   findById(), save(), delete()などの基本的なメソッドを定義します。

4.  **ドメインサービスの設計:**
    *   エンティティに属さないビジネスロジックをドメインサービスとして定義します。
        *   `LoanService`（貸出処理、返却処理）

5.  **実装:**
    *   設計したドメインモデル、リポジトリ、ドメインサービスを実装します。
    *   リポジトリの実装には、インメモリデータベース (H2 Database) などを使用すると、手軽に試すことができます。

**コード例 (Java):**

```java
// 値オブジェクト

    MAGAZINE
}

// エンティティ

    private LoanStatus loanStatus;

        this.title = title;
        this.author = author;
        this.bookType = bookType;
        this.loanStatus = LoanStatus.AVAILABLE;
    }

  // ... getter, setter
    public void setLoanStatus(LoanStatus loanStatus) {
      this.loanStatus = loanStatus;
    }
}

public class User {
    private UUID userId;
    private String name;
    private String address;

  // ... getter, setter
}

    private UUID libraryId;
    private List<Book> books;

    public Library(UUID libraryId) {
        this.libraryId = libraryId;
        this.books = new ArrayList<>();
    }

        this.books.add(book);
    }

        return Collections.unmodifiableList(books);

        return books.stream().filter(book -> book.getBookId().equals(bookId)).findFirst();

}

    Optional<Book> findById(String bookId);

    void save(User user);
}

// ドメインサービス
public class LoanService {
    private final BookRepository bookRepository;
    private final UserRepository userRepository;

    public LoanService(BookRepository bookRepository, UserRepository userRepository) {
        this.bookRepository = bookRepository;
        this.userRepository = userRepository;
    }

    public void lendBook(UUID userId, String bookId) {
        User user = userRepository.findById(userId).orElseThrow(() -> new IllegalArgumentException("User not found"));
        Book book = bookRepository.findById(bookId).orElseThrow(() -> new IllegalArgumentException("Book not found"));

        if (book.getLoanStatus() == LoanStatus.BORROWED) {
            throw new IllegalStateException("Book is already borrowed");
        }

        book.setLoanStatus(LoanStatus.BORROWED);
        bookRepository.save(book);
    }

    public void returnBook(String bookId) {
        Book book = bookRepository.findById(bookId).orElseThrow(() -> new IllegalArgumentException("Book not found"));

        if (book.getLoanStatus() == LoanStatus.AVAILABLE) {
            throw new IllegalStateException("Book is already available");
        }

        book.setLoanStatus(LoanStatus.AVAILABLE);
        bookRepository.save(book);
    }
}
```
