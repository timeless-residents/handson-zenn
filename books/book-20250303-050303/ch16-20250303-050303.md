# 16. バックアップとリカバリ戦略

Hyperledger Fabric ネットワークは、その堅牢性と分散性によりエンタープライズ利用に適していますが、一方で、運用中に発生する各種障害に対しては、迅速かつ確実なバックアップと復旧戦略が不可欠です。本章では、台帳データ、設定ファイル、証明書などの重要データのバックアップ方法から、障害発生時の迅速な復旧手順の設計、及び自動化と継続的最適化のための最新技術に至るまで、詳細に解説します。

---

## 16.1 バックアップとリカバリ戦略の重要性

企業におけるブロックチェーンネットワークは、膨大なビジネスプロセスの根幹を担っています。台帳データ、設定ファイル、証明書、及びその他の運用情報は、万一の障害発生時に迅速に復旧し、システムの継続運用を可能にするための最重要資産です。以下の点がバックアップとリカバリ戦略の重要性を示しています。

- **データの不可逆性:**  
  ブロックチェーンはデータが不変であることが特長ですが、誤操作や障害でデータの一部が失われると、修復が困難になるため、定期的なバックアップが必要です。

- **障害発生時の迅速な対応:**  
  台帳データや設定ファイルのバックアップがあれば、システム障害発生時に迅速な復旧が可能になり、業務への影響を最小限に抑えることができます。

- **コンプライアンスと監査:**  
  多くの業界でデータ保持や監査が義務付けられているため、バックアップは法令遵守と内部監査の両面で重要な役割を果たします。

---

## 16.2 バックアップ対象と範囲の定義

### 16.2.1 バックアップ対象の特定

バックアップ対象は、ネットワークの運用において不可欠な以下の要素に分けられます。

- **台帳データ:**  
  すべてのトランザクション履歴、ブロックデータ、チェーンコードの実行結果を含む台帳ファイル。  
- **設定ファイル:**  
  `core.yaml`、`orderer.yaml`、`configtx.yaml` などのネットワーク設定ファイル。  
- **証明書と秘密鍵:**  
  各組織の MSP ディレクトリ内の証明書、秘密鍵、及び関連する証明書失効リスト（CRL）。
- **コンテナボリューム:**  
  Docker や Kubernetes によって管理される各種永続ボリューム。  

### 16.2.2 バックアップの頻度と保持期間

- **定期バックアップ:**  
  運用環境では、台帳データや設定ファイルは日次または週次でバックアップを取得する。  
- **リアルタイムバックアップ:**  
  重要なトランザクションデータに対しては、リアルタイムのレプリケーションやスナップショット機能を利用する。  
- **長期保存:**  
  コンプライアンス要件に基づき、一定期間（例：3年間、7年間など）のデータを安全に保存するポリシーを定める。

## 16.3 台帳データのバックアップ方法

### 16.3.1 台帳データの構成

Fabric の台帳は、各ピアが保持するローカルのデータベース（LevelDB や CouchDB）と、ブロックチェーンとして記録されたブロックファイルから構成されます。これらのデータを確実にバックアップするためのポイントを以下に示します。

### 16.3.2 バックアップ手法

#### 16.3.2.1 ファイルシステムバックアップ

- **バックアップスクリプト:**  
  台帳データを格納するディレクトリを tar や rsync を用いて定期的にバックアップするシェルスクリプトの例。

```bash
#!/bin/bash
# ledger_backup.sh

# バックアップ対象ディレクトリの定義
LEDGER_DIR="$HOME/fabric-samples/test-network/ledgersData"
BACKUP_DIR="$HOME/backups/ledgersData_$(date +%Y%m%d_%H%M%S)"

# バックアップディレクトリ作成
mkdir -p $BACKUP_DIR

# ディレクトリ全体を圧縮してバックアップ
tar -czvf $BACKUP_DIR/ledger_backup.tar.gz -C $LEDGER_DIR .

echo "台帳データのバックアップが完了しました: $BACKUP_DIR/ledger_backup.tar.gz"
```

#### 16.3.2.2 Docker ボリュームのバックアップ

- **Docker コマンドを用いたバックアップ:**  
  Docker ボリュームのバックアップには、`docker run` コマンドを利用し、永続ボリュームの内容をアーカイブする方法があります。

```bash
# Docker ボリュームの一覧確認
docker volume ls

# 例: peer0.org1.example.com ボリュームのバックアップ
docker run --rm -v peer0.org1.example.com:/source -v $HOME/backups:/backup alpine \
  tar -czvf /backup/peer0_org1_$(date +%Y%m%d_%H%M%S).tar.gz -C /source .
```

### 16.3.3 バックアップのスケジュールと自動化

- **cron ジョブの利用:**  
  Linux の cron を用いて、定期的なバックアップジョブをスケジュールする例。

```cron
# 毎日午前2時に台帳データのバックアップを実行
0 2 * * * /bin/bash /home/username/backup_scripts/ledger_backup.sh >> /home/username/backups/backup.log 2>&1
```

- **クラウドバックアップサービス:**  
  AWS S3 や Azure Blob Storage などのクラウドストレージサービスに、バックアップデータを自動でアップロードする仕組みを構築する。

## 16.4 設定ファイルと証明書のバックアップ

### 16.4.1 重要な設定ファイルの特定

- **configtx.yaml, core.yaml, orderer.yaml:**  
  ネットワークの運用に直接影響する設定ファイルは、必ずバックアップ対象に含める。

- **MSP ディレクトリ:**  
  各組織の MSP ディレクトリには、証明書、秘密鍵、及び関連する構成ファイルが含まれるため、慎重にバックアップする必要があります。

### 16.4.2 バックアップ手法

#### 16.4.2.1 ファイルコピーによるバックアップ

```bash
#!/bin/bash
# config_backup.sh

CONFIG_DIR="$HOME/fabric-samples/config"
MSP_DIR="$HOME/fabric-samples/test-network/organizations"
BACKUP_DIR="$HOME/backups/config_$(date +%Y%m%d_%H%M%S)"

mkdir -p $BACKUP_DIR
cp -r $CONFIG_DIR $BACKUP_DIR
cp -r $MSP_DIR $BACKUP_DIR

echo "設定ファイルと MSP ディレクトリのバックアップが完了しました: $BACKUP_DIR"
```

#### 16.4.2.2 バージョン管理システムの利用

- **Git リポジトリ:**  
  重要な設定ファイルは、Git リポジトリでバージョン管理し、変更履歴を常に記録する方法も有効です。これにより、必要な時点に簡単にロールバックできる。

### 16.4.3 定期バックアップと保持ポリシー

- **保持期間の設定:**  
  法令や内部規定に基づき、バックアップデータの保持期間を定める。例えば、少なくとも 1 年分のデータを保持する。

- **自動削除:**  
  古いバックアップファイルを自動で削除するスクリプトを導入し、ストレージ容量の管理を行う。

## 16.5 障害発生時の復旧手順

### 16.5.1 復旧プロセスの全体像

障害が発生した場合、以下のステップで迅速にシステムを復旧させます。

1. **障害の検知:**  
   監視システムや自動アラートにより、障害を即時検知する。
2. **障害の切り分け:**  
   ログ解析、分散トレーシングにより、どのコンポーネントが障害の原因かを特定する。
3. **バックアップデータの確認:**  
   最新のバックアップが正しく取得されているか確認し、復旧対象を決定する。
4. **データの復元:**  
   台帳データ、設定ファイル、証明書などのバックアップからデータを復元する。
5. **システム再起動:**  
   復元後、ネットワークコンポーネントを再起動し、同期状態を確認する。
6. **復旧後の検証:**  
   すべての機能が正常に動作しているか、テストと検証を実施する。

### 16.5.2 復旧手順の具体例

#### 16.5.2.1 台帳データの復元

```bash
#!/bin/bash
# ledger_restore.sh

# 復元対象バックアップファイルと復元先ディレクトリの指定
BACKUP_FILE="$HOME/backups/ledgersData_20250315_020000/ledger_backup.tar.gz"
LEDGER_DIR="$HOME/fabric-samples/test-network/ledgersData"

# 復元前に既存データのバックアップを取得（オプション）
tar -czvf "$LEDGER_DIR/old_ledger_backup_$(date +%Y%m%d_%H%M%S).tar.gz" -C "$LEDGER_DIR" .

# バックアップファイルからの復元
tar -xzvf $BACKUP_FILE -C $LEDGER_DIR

echo "台帳データの復元が完了しました。"
```

#### 16.5.2.2 設定ファイルと MSP ディレクトリの復元

```bash
#!/bin/bash
# config_restore.sh

BACKUP_DIR="$HOME/backups/config_20250315_020000"
CONFIG_DIR="$HOME/fabric-samples/config"
MSP_DIR="$HOME/fabric-samples/test-network/organizations"

# 復元前に現行の設定ファイルをバックアップ
cp -r $CONFIG_DIR "${CONFIG_DIR}_backup_$(date +%Y%m%d_%H%M%S)"
cp -r $MSP_DIR "${MSP_DIR}_backup_$(date +%Y%m%d_%H%M%S)"

# バックアップから復元
cp -r $BACKUP_DIR/config/* $CONFIG_DIR
cp -r $BACKUP_DIR/organizations/* $MSP_DIR

echo "設定ファイルと MSP ディレクトリの復元が完了しました。"
```

### 16.5.3 自動復旧システムの導入

- **Kubernetes の自動再起動:**  
  Pod のヘルスチェックを設定し、異常を検知した際に自動で再起動させる仕組みを構築する。  
- **監視ツールとの連携:**  
  Prometheus のアラートをトリガーとして、復旧スクリプトを自動実行するワークフローを構築する。

## 16.6 ケーススタディ：実運用における復旧事例

### 16.6.1 ケーススタディ 1: 金融機関の台帳復元

**背景:**  
大手金融機関で、システム障害が発生し、一部台帳データが不整合を起こした事例。

**対策:**  
- 定期的な台帳バックアップを活用し、障害発生直前の状態に復元。  
- 復旧後、各ピア間でデータの整合性検証を実施し、問題を解決。

**効果:**  
- 復旧時間が大幅に短縮され、業務停止期間が最小限に抑えられた。  
- ログ解析と分散トレーシングにより、障害原因の特定が迅速に行われた。

### 16.6.2 ケーススタディ 2: 製造業における設定ファイル復元

**背景:**  
製造業企業で、誤った設定変更によりネットワーク全体に影響が及んだ事例。

**対策:**  
- Git リポジトリによる設定ファイル管理により、迅速なロールバックが可能に。  
- 定期バックアップのスクリプトを利用し、問題発生時に即時復元を実施。

**効果:**  
- システム全体の稼働が迅速に回復し、業務への影響を最小限に抑えた。

### 16.6.3 ケーススタディ 3: 複数組織間での証明書復旧

**背景:**  
複数組織間ネットワークで、証明書の失効や更新が不整合となり、アクセス障害が発生した事例。

**対策:**  
- 定期的な MSP 設定ファイルの監査と、証明書の再エンロールによる復旧を実施。  
- CRL の自動更新と各ノードへの配布を強化し、迅速な認証エラーの解消を図った。

**効果:**  
- ネットワーク全体の認証が正常化し、運用信頼性が向上。
