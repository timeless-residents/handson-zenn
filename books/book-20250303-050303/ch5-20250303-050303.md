# 5. 運用管理：Hyperledger Fabric ネットワークの運用とモニタリング

本章では、Hyperledger Fabric ネットワークを実際の運用環境で管理・運用するためのノウハウについて、詳細かつ実践的に解説します。ネットワーク構築が完了した後は、運用管理がシステムの安定稼働と長期的な信頼性を左右します。本章は、ネットワークの状態確認、ログ解析、チャネル管理、ブロックデータの取得、証明書や鍵の管理、さらにバックアップ、復旧、パフォーマンスチューニング、そしてセキュリティ対策に至るまで、あらゆる運用フェーズを包括的にカバーします。各セクションでは具体的なコマンド例、設定ファイルのサンプル、トラブルシューティング事例を交えながら、実務で直面する課題への対処法を解説します。

本章を通して、読者は以下のスキルを習得できます。

- ネットワーク内の各コンポーネント（ピア、オーダラー、CA など）の状態確認と管理方法
- Docker コマンドを用いた各コンテナの監視、ログ解析、内部調査の手法
- チャネル管理およびブロックチェーンデータの取得・解析方法
- 証明書と秘密鍵の管理、更新手順、及びセキュリティ強化策
- Prometheus、Grafana、ELK スタック等を利用した外部モニタリングの設定と連携方法
- 定期的なバックアップと迅速な復旧手順、障害発生時の対処法
- ネットワークのアップグレードやパフォーマンス最適化のベストプラクティス

以下、各セクションごとに詳しく説明していきます。

---

## 5.1 ネットワーク管理の基本

### 5.1.1 コンポーネントの状態確認

ネットワークの健全性を維持するためには、各コンポーネントの状態を定期的に確認することが必要です。以下のコマンドを使用して、Docker コンテナの一覧や詳細情報を取得します。

- **Docker コンテナ一覧の確認**

  ```bash
  docker ps
  ```

  このコマンドにより、現在稼働中のすべてのコンテナが一覧表示され、各コンポーネント（例: `peer0.org1.example.com`、`orderer.example.com`、CA コンテナなど）の状態を把握できます。

- **特定コンテナの詳細情報取得**

  ```bash
  docker inspect peer0.org1.example.com
  ```

  このコマンドで、指定されたコンテナの詳細な設定情報やネットワーク設定、ボリュームマウント状況などを確認できます。定期的にこれらの情報をチェックすることで、コンテナのリソース利用状況や異常検出に役立ちます。

### 5.1.2 ログの確認と分析

各コンポーネントのログは、システムの状態を把握するための重要な情報源です。以下の手法でログの確認と分析を行います。

- **リアルタイムログの確認**

  ```bash
  docker logs -f peer0.org1.example.com
  docker logs -f orderer.example.com
  docker logs -f ca_org1
  ```

  これらのコマンドで、各コンテナのログをリアルタイムに表示し、エラーや警告メッセージ、その他の異常動作を即時に検知します。

- **ログのフィルタリング**

  特定のキーワードを用いてログを絞り込み、エラー発生箇所を迅速に特定することも重要です。

  ```bash
  docker logs peer0.org1.example.com | grep ERROR
  ```

  このように、エラーメッセージや特定のパターンを検索することで、障害発生時の原因調査が容易になります。

### 5.1.3 設定ファイルの管理

各コンポーネントの設定ファイル（例: `core.yaml`、`orderer.yaml`、`configtx.yaml`）は、ネットワーク運用の基盤となります。変更前には必ずバックアップを行い、変更履歴を管理することで、誤った設定変更による障害を防ぐことができます。

```bash
cd ~/fabric-samples/config
cp core.yaml core.yaml.bak
nano core.yaml
```

このように、設定ファイルを編集する際は必ずバックアップを取得し、変更内容を記録しておくことが推奨されます。

## 5.2 チャネル管理

チャネルは、参加組織間でデータの分離とプライバシーを確保するための重要な機能です。チャネル管理の基本操作として、チャネル一覧の取得、チャネル情報の取得、及びチャネル設定の更新が挙げられます。

### 5.2.1 チャネル情報の取得

チャネルに関する情報は、以下のコマンドで確認できます。

- **チャネル一覧の確認**

  ```bash
  peer channel list
  ```

  このコマンドにより、参加しているチャネルの一覧が表示され、各ピアがどのチャネルに所属しているかを確認できます。

- **チャネル詳細情報の取得**

  ```bash
  peer channel getinfo -c mychannel
  ```

  このコマンドは、チャネルの最新ブロック情報やチャネル構成の概要を取得するために使用され、ネットワークの整合性確認に役立ちます。

### 5.2.2 チャネル設定の更新

業務要件の変更や、新たな組織の追加に伴い、チャネル設定の変更が必要になる場合があります。設定更新のプロセスは以下の手順で行われます。

1. **現在のチャネル設定を取得し、JSON に変換する**

   ```bash
   peer channel fetch config channel-artifacts/config_block.pb -o localhost:7050 --ordererTLSHostnameOverride orderer.example.com -c mychannel --tls --cafile ${PWD}/organizations/ordererOrganizations/example.com/orderers/orderer.example.com/msp/tlscacerts/tlsca.example.com-cert.pem
   configtxlator proto_decode --input channel-artifacts/config_block.pb --type common.Block | jq .data.data[0].payload.data.config > channel-artifacts/config.json
   ```

2. **変更を加えた JSON ファイルを作成する**

   例として、バッチタイムアウトの値を変更する場合は、jq を使用して新しい JSON を生成します。

   ```bash
   jq '.channel_group.groups.Orderer.values.BatchTimeout.value.timeout = "2s"' channel-artifacts/config.json > channel-artifacts/modified_config.json
   ```

3. **設定の差分を計算し、更新ブロックを生成する**

   ```bash
   configtxlator proto_encode --input channel-artifacts/config.json --type common.Config > channel-artifacts/original_config.pb
   configtxlator proto_encode --input channel-artifacts/modified_config.json --type common.Config > channel-artifacts/modified_config.pb
   configtxlator compute_update --channel_id mychannel --original channel-artifacts/original_config.pb --updated channel-artifacts/modified_config.pb > channel-artifacts/config_update.pb
   ```

4. **更新ブロックをコミットする**

   ```bash
   configtxlator proto_decode --input channel-artifacts/config_update.pb --type common.ConfigUpdate | jq . > channel-artifacts/config_update.json
   echo '{"payload":{"header":{"channel_header":{"channel_id":"mychannel", "type":2}},"data":{"config_update":'$(cat channel-artifacts/config_update.json)'}}}' | jq . > channel-artifacts/config_update_in_envelope.json
   configtxlator proto_encode --input channel-artifacts/config_update_in_envelope.json --type common.Envelope > channel-artifacts/config_update_in_envelope.pb
   peer channel update -f channel-artifacts/config_update_in_envelope.pb -c mychannel -o localhost:7050 --ordererTLSHostnameOverride orderer.example.com --tls --cafile ${PWD}/organizations/ordererOrganizations/example.com/orderers/orderer.example.com/msp/tlscacerts/tlsca.example.com-cert.pem
   ```

このような手順を通じて、チャネル設定の変更が可能となり、運用環境に柔軟に対応することができます。

## 5.3 ブロックチェーンデータの管理

ネットワーク運用において、ブロックチェーン上のデータやトランザクション履歴の管理は、システムの透明性と信頼性を維持する上で不可欠です。以下は、ブロック情報やトランザクション履歴の取得方法についての解説です。

### 5.3.1 ブロック情報の取得

- **最新ブロックの取得**

  ```bash
  peer channel fetch newest channel-artifacts/newest_block.pb -o localhost:7050 --ordererTLSHostnameOverride orderer.example.com -c mychannel --tls --cafile ${PWD}/organizations/ordererOrganizations/example.com/orderers/orderer.example.com/msp/tlscacerts/tlsca.example.com-cert.pem
  ```

- **特定ブロック番号の取得**

  ```bash
  peer channel fetch 1 channel-artifacts/block_1.pb -o localhost:7050 --ordererTLSHostnameOverride orderer.example.com -c mychannel --tls --cafile ${PWD}/organizations/ordererOrganizations/example.com/orderers/orderer.example.com/msp/tlscacerts/tlsca.example.com-cert.pem
  ```

これらのコマンドにより、ネットワーク上のブロック情報を取得し、ブロックチェーンの状態を検証できます。

### 5.3.2 ブロック内容の解析

取得したブロックは、`configtxlator` を用いてデコードし、JSON 形式で確認できます。

```bash
configtxlator proto_decode --input channel-artifacts/newest_block.pb --type common.Block | jq . > channel-artifacts/newest_block.json
```

この手法を用いることで、ブロック内のトランザクションデータやチャネル設定の変更履歴を詳細に解析することができます。

### 5.3.3 トランザクション履歴の確認

トランザクション履歴は、チェーンコードのクエリ機能を利用して取得できます。

```bash
peer chaincode query -C mychannel -n basic -c '{"Args":["GetAllAssets"]}'
```

また、特定のトランザクション ID を基に詳細な履歴を取得する方法もあります。これにより、取引の監査や不正検出、システム障害時の原因追及が可能となります。

## 5.4 証明書と鍵の管理

Hyperledger Fabric におけるセキュリティの根幹をなすのが、証明書と秘密鍵の管理です。これらは、ネットワーク内の各参加者の身元を証明し、トランザクションの正当性を担保するために用いられます。

### 5.4.1 証明書の確認

各組織の証明書は、以下のコマンドで確認できます。

```bash
ls -la organizations/peerOrganizations/org1.example.com/msp/cacerts/
ls -la organizations/peerOrganizations/org1.example.com/peers/peer0.org1.example.com/msp/signcerts/
```

これにより、証明書が正しく配置され、必要な権限が付与されているかを確認します。

### 5.4.2 証明書の更新

証明書の有効期限が切れる前に、Fabric CA を利用して新しい証明書を発行する必要があります。

```bash
fabric-ca-client enroll -u https://admin:adminpw@localhost:7054 --caname ca-org1 -M ${PWD}/organizations/peerOrganizations/org1.example.com/users/Admin@org1.example.com/msp --tls.certfiles ${PWD}/organizations/fabric-ca/org1/tls-cert.pem
```

この手順により、組織の管理者証明書を更新し、ネットワークのセキュリティを維持します。

### 5.4.3 秘密鍵の保護

秘密鍵は、非常に重要な情報であるため、以下のような対策を講じます。

- **ファイル権限の設定**

  ```bash
  chmod 600 organizations/peerOrganizations/org1.example.com/users/Admin@org1.example.com/msp/keystore/*
  ```

- **ハードウェアセキュリティモジュール（HSM）の利用**

  本番環境では、秘密鍵を安全に保管するため、HSM の導入を検討することが推奨されます。

## 5.5 モニタリングとログ管理

ネットワーク運用の安定性とパフォーマンスを維持するためには、リアルタイムのモニタリングと詳細なログ管理が不可欠です。本節では、内蔵の Docker ログ管理に加え、Prometheus や Grafana、ELK スタックを用いた外部モニタリングの設定方法について解説します。

### 5.5.1 Docker ログの活用

Docker ログは、各コンテナの動作状況を把握するための基本ツールです。以下のコマンドを利用して、ログを継続的に監視します。

```bash
docker logs -f peer0.org1.example.com
docker logs -f orderer.example.com
```

### 5.5.2 Prometheus と Grafana の設定

Hyperledger Fabric のメトリクスをモニタリングするため、Prometheus と Grafana を導入します。以下は、簡単な設定例です。

#### 5.5.2.1 Docker Compose でのセットアップ例

```yaml
version: '2.1'

networks:
  fabric_test:
    external: true

services:
  prometheus:
    image: prom/prometheus:latest
    container_name: prometheus
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
    command:
      - --config.file=/etc/prometheus/prometheus.yml
    ports:
      - "9090:9090"
    networks:
      - fabric_test

  grafana:
    image: grafana/grafana:latest
    container_name: grafana
    ports:
      - "3000:3000"
    volumes:
      - ./grafana/provisioning:/etc/grafana/provisioning
      - ./grafana/dashboards:/var/lib/grafana/dashboards
    networks:
      - fabric_test
    depends_on:
      - prometheus
```

#### 5.5.2.2 Prometheus 設定例（prometheus.yml）

```yaml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: 'fabric'
    static_configs:
      - targets: ['peer0.org1.example.com:9443', 'peer0.org2.example.com:9443', 'orderer.example.com:9443']
```

これにより、各コンテナからメトリクスを収集し、Grafana 上で可視化することが可能になります。

### 5.5.3 ELK スタックによるログ管理

Elasticsearch、Logstash、Kibana を用いて、ネットワーク全体のログを集中管理・解析する方法もあります。

#### 5.5.3.1 Docker Compose での ELK スタック例

```yaml
version: '2.1'

networks:
  fabric_test:
    external: true

services:
  elasticsearch:
    image: docker.elastic.co/elasticsearch/elasticsearch:7.12.0
    container_name: elasticsearch
    environment:
      - discovery.type=single-node
    ports:
      - "9200:9200"
    networks:
      - fabric_test

  logstash:
    image: docker.elastic.co/logstash/logstash:7.12.0
    container_name: logstash
    volumes:
      - ./logstash/pipeline:/usr/share/logstash/pipeline
    ports:
      - "5000:5000"
    networks:
      - fabric_test
    depends_on:
      - elasticsearch

  kibana:
    image: docker.elastic.co/kibana/kibana:7.12.0
    container_name: kibana
    ports:
      - "5601:5601"
    networks:
      - fabric_test
    depends_on:
      - elasticsearch
```

#### 5.5.3.2 Logstash パイプラインの設定例

```conf
input {
  tcp {
    port => 5000
    codec => json
  }
}

filter {
  json {
    source => "message"
  }
}

output {
  elasticsearch {
    hosts => ["elasticsearch:9200"]
    index => "fabric-logs-%{+YYYY.MM.dd}"
  }
}
```

各コンテナのログドライバーを GELF に設定することで、Logstash 経由で ELK スタックにログを転送できます。

## 5.6 バックアップと復旧

システム運用において、障害発生時の迅速な復旧とデータ保護は極めて重要です。本節では、台帳データ、設定ファイル、証明書のバックアップ方法と、障害発生時の復旧手順について解説します。

### 5.6.1 台帳データのバックアップ

ネットワーク停止前に、台帳データをバックアップすることで、データの損失を防ぎます。

1. ネットワーク停止：

   ```bash
   cd ~/fabric-samples/test-network
   ./network.sh down
   ```

2. Docker ボリュームのバックアップ：

   ```bash
   docker volume ls | grep fabric
   docker volume create --name fabric_data_backup
   docker run --rm -v fabric_peer0.org1.example.com:/source -v fabric_data_backup:/dest alpine cp -a /source/. /dest
   ```

### 5.6.2 設定ファイルと証明書のバックアップ

重要な設定ファイルと証明書は、以下のようにバックアップしておきます。

```bash
mkdir -p backups/config
cp -r ~/fabric-samples/config backups/config/
cp -r ~/fabric-samples/test-network/organizations backups/organizations/

mkdir -p backups/crypto
cp -r ~/fabric-samples/test-network/organizations backups/crypto/
```

### 5.6.3 復旧手順

障害発生時は、バックアップからデータや設定を復元し、ネットワークを再起動します。

1. Docker ボリュームからデータを復元：

   ```bash
   docker run --rm -v fabric_data_backup:/source -v fabric_peer0.org1.example.com:/dest alpine cp -a /source/. /dest
   ```

2. ネットワークの再起動：

   ```bash
   cd ~/fabric-samples/test-network
   ./network.sh up
   ```

これにより、迅速な障害復旧とシステムの安定運用が可能となります。

## 5.7 障害対応と復旧計画

ネットワーク運用中に予期せぬ障害が発生することは避けられません。ここでは、よくある問題とその対処法、及び障害復旧計画について解説します。

### 5.7.1 よくある障害事例と対策

#### ピアの同期不良
- **原因**: ネットワーク通信エラーやリソース不足、設定ミスが考えられます。
- **対策**:
  - ピアのログを確認してエラー原因を特定。
  - 必要に応じてピアの再起動を実施。
  - チャネル参加状態を確認し、再参加を検討。

#### トランザクション失敗
- **原因**: エンドースメントポリシーの不一致、チェーンコードのバグ、入力値の不正など。
- **対策**:
  - オーダラーおよび各ピアのログを調査し、エラー箇所を特定。
  - チェーンコードの実装および承認状況を確認し、必要なら再デプロイ。
  - トランザクションシミュレーションの結果を詳細に検証する。

#### ポート競合
- **原因**: 既に使用中のポートがある場合、コンテナの起動が失敗することがあります。
- **対策**:
  - 以下のコマンドで、ポート使用状況を確認：
  
    ```bash
    lsof -i :7050
    lsof -i :7051
    lsof -i :9051
    ```
    
  - 競合プロセスの停止や、必要に応じてポート番号の変更を行う。

#### Docker リソース不足
- **原因**: Docker Desktop に割り当てるリソースが不足している場合、コンテナのパフォーマンス低下や起動失敗が発生する。
- **対策**:
  - Docker Desktop の設定画面でリソース割り当て（CPU、メモリ、ディスク容量）を再確認。
  - 不要なコンテナやボリュームを削除してリソースを解放する。

### 5.7.2 障害復旧計画の策定

障害発生時の迅速な対応のため、以下の手順を含む復旧計画を策定しておくことが重要です。

1. **定期的なバックアップの実施**  
   台帳データ、設定ファイル、証明書など、重要な情報のバックアップを定期的に実施する。

2. **障害発生時の連絡体制の確立**  
   システム管理者、運用チーム、開発チーム間で迅速に情報共有できる連絡体制を整備する。

3. **復旧手順のドキュメント化と訓練**  
   復旧手順を詳細にドキュメント化し、定期的な訓練を実施することで、実際の障害時に迅速に対応できるようにする。

4. **フェイルオーバー手順の確立**  
   主要コンポーネントの冗長化や自動フェイルオーバー機能を構築し、障害時のシステム停止時間を最小限に抑える。

## 5.8 ネットワークのアップグレード

ネットワークの運用管理には、定期的なアップグレードも欠かせません。新バージョンの Fabric やチェーンコードのアップグレードを適切に行うことで、最新のセキュリティパッチや機能拡張を取り入れることができます。

### 5.8.1 Fabric バージョンのアップグレード

1. **最新バージョンの確認**

   ```bash
   curl -sSL https://hyperledger.github.io/fabric/latest_release | grep -o "v[0-9]\.[0-9]\.[0-9]"
   ```

2. **環境のバックアップの取得**

   事前に台帳データや設定ファイルのバックアップを必ず取得します。

3. **新バージョンのバイナリのダウンロードとネットワーク停止**

   ```bash
   cd ~/fabric-samples
   curl -sSL https://bit.ly/2ysbOFE | bash -s -- <新バージョン> <CAバージョン>
   cd ~/fabric-samples/test-network
   ./network.sh down
   ```

4. **新バージョンでのネットワーク再起動**

   ```bash
   ./network.sh up createChannel -c mychannel -ca -i <新バージョン>
   ```

### 5.8.2 チェーンコードのアップグレード

チェーンコードのアップグレードは、既存のシステムに変更を加える際の重要なプロセスです。アップグレード手順は以下の通りです。

1. **新バージョンパッケージの作成とインストール**
2. **各組織で新バージョンの承認を行い、シーケンス番号を更新**
3. **新バージョンのコミットを実施**

アップグレードにより、既存のチェーンコードの機能拡張やバグ修正を実施し、システムの品質とセキュリティを維持します。

## 5.9 セキュリティ管理

ネットワークの運用において、セキュリティ対策は最優先事項です。各組織でのアクセス制御、証明書管理、暗号化、及び監査ログの取得を徹底することで、システム全体の安全性を確保します。

### 5.9.1 TLS の設定確認

TLS は、ネットワーク内の通信を暗号化し、不正アクセスを防止するための基本機能です。以下のコマンドで TLS 設定や証明書の配置を確認します。

```bash
ls -la organizations/peerOrganizations/org1.example.com/peers/peer0.org1.example.com/tls/
grep -A 10 "tls:" ~/fabric-samples/config/core.yaml
```

### 5.9.2 アクセス制御と MSP の活用

MSP（Membership Service Provider）を用いて、各組織の参加者を厳格に管理します。各ユーザーや管理者に対する権限設定を徹底し、アクセス制御ポリシーの更新を定期的に実施します。

### 5.9.3 セキュリティ監査とコードレビュー

- 定期的なセキュリティ監査とコードレビューを実施し、潜在的な脆弱性や不正アクセスのリスクを低減します。
- 自動テストや静的解析ツールの活用により、開発段階からセキュリティを意識したコーディングを推奨します。

## 5.10 パフォーマンスチューニング

運用中のネットワークパフォーマンスを最適化するためには、リソース割り当て、ブロック設定、キャッシュ設定など、各種パラメータの調整が必要です。

### 5.10.1 Docker コンテナへのリソース割り当て

Docker Compose ファイルを編集し、各コンテナに適切なリソース（CPU、メモリ）を割り当てることで、全体のパフォーマンス向上を図ります。

```yaml
services:
  peer0.org1.example.com:
    deploy:
      resources:
        limits:
          cpus: '0.5'
          memory: 1G
        reservations:
          cpus: '0.25'
          memory: 512M
```

### 5.10.2 ブロックパラメータの最適化

`configtx.yaml` 内のブロック設定（BatchTimeout、BatchSize など）を業務要件に合わせて調整することで、トランザクション処理の効率を向上させます。

```yaml
Orderer: &OrdererDefaults
  BatchTimeout: 1s
  BatchSize:
    MaxMessageCount: 100
    AbsoluteMaxBytes: 10 MB
    PreferredMaxBytes: 2 MB
```

### 5.10.3 キャッシュ設定の最適化

`core.yaml` で、ピアのキャッシュ設定（例: CouchDB のキャッシュサイズなど）を調整することで、データの取得速度やシステム全体の応答性を向上させます。

```yaml
peer:
  couchDBConfig:
    cacheSize: 64
```

これらの調整により、ネットワークのパフォーマンスと安定性を確保し、運用効率を最大化することが可能です。

本章「運用管理」では、Hyperledger Fabric ネットワークの運用に必要な全てのプロセスとベストプラクティスについて、詳細に解説しました。ここで学んだ主要ポイントは以下の通りです。

- **ネットワークコンポーネントの状態確認とログ管理**  
  Docker コマンドや各種ログ解析ツールを用いて、ネットワーク全体の健康状態を常に監視することの重要性。

- **チャネル管理とブロックデータの取得**  
  チャネルの作成、参加状況、及びブロック情報・トランザクション履歴の詳細な取得方法を理解することで、システムの透明性と信頼性を確保する。

- **証明書および秘密鍵の適切な管理**  
  証明書更新、ファイル権限設定、及び HSM の活用により、ネットワークセキュリティを堅牢に保つ手法を習得する。

- **外部モニタリングツールとの連携**  
  Prometheus、Grafana、ELK スタックを用いたリアルタイム監視とログ解析により、ネットワークの障害を早期に検知し、迅速な対応が可能となる。

- **バックアップと障害復旧計画の策定**  
  定期的なバックアップ、復旧手順のドキュメント化、フェイルオーバー手順の整備など、運用環境での万全の対応体制を確立する。

- **ネットワークアップグレードとパフォーマンス最適化**  
  新バージョンの Fabric やチェーンコードのアップグレード、各種リソースパラメータの最適化により、システムの最新状態と高パフォーマンスを維持する方法を習得する。

これらの知識を実践に活かすことで、Hyperledger Fabric を用いたエンタープライズブロックチェーンネットワークの運用管理を高いレベルで実現できるようになります。運用管理は、システムの安定稼働とビジネス継続性に直結するため、定期的なチェックと改善が不可欠です。
