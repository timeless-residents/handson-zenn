# 3. ネットワーク構築：テストネットワークの構築と運用

本章では、Hyperledger Fabric の基本的なネットワーク構築手順から、実運用レベルの詳細な設定やトラブルシューティングまで、幅広い内容を実践的に解説します。Fabric Samples に含まれるテストネットワークを例に、複数組織・チャネル構成の構築、ピアやオーダラー、Certificate Authority（CA）の設定、さらには CouchDB を利用したリッチクエリの実装、ネットワークモニタリングの手法に至るまで、全体像を体系的に学習できます。

---

## 3.1 テストネットワークの概要

Hyperledger Fabric のテストネットワークは、Fabric Samples リポジトリに含まれる `test-network` プロジェクトを利用して構築されます。テストネットワークは、以下の主要コンポーネントで構成されています。

- **2つの組織（Org1 と Org2）**  
  各組織は、最低1つのピア（peer0）を持ち、チェーンコードの実行・検証を担当します。

- **1つのオーダリングサービス（Orderer）**  
  トランザクションの順序付けとブロック生成を行います。

- **Certificate Authority（CA）サーバー（オプション）**  
  ネットワーク内の各組織の証明書発行と管理を担当します。

- **チャネル（Channel）**  
  組織間でプライベートな台帳を共有するための論理的区分です。テストネットワークでは、デフォルトで「mychannel」というチャネルを作成します。

テストネットワークは、開発者が Fabric の基本概念や操作手順を学習するための最適な環境であり、後述する各コマンドの実行例やログ出力などを通じて、実際のネットワーク動作のイメージを掴むことができます。

---

## 3.2 ネットワークの起動

### 3.2.1 テストネットワークの起動手順

まず、ターミナルを開き、Fabric Samples のディレクトリに移動します。

```bash
cd ~/fabric-samples/test-network
```

ネットワークを起動するには、以下のコマンドを実行します。

```bash
./network.sh up
```

このコマンドは、以下の処理を自動的に実施します。

- Docker コンテナの起動  
  オーダラー、各組織のピア、CA サーバー（-ca オプション使用時）のコンテナが立ち上がります。
- ネットワーク作成の初期設定  
  Docker ネットワークの生成、必要なボリュームの作成などが行われます。

実行後、以下のようなメッセージが表示されるはずです。

```
Creating network "fabric_test" with the default driver
Creating orderer.example.com    ... done
Creating peer0.org1.example.com ... done
Creating peer0.org2.example.com ... done
```

これにより、基本的なネットワーク構成が完了します。

### 3.2.2 CA を有効にしてネットワークを起動する

より実践的なネットワーク構築のため、CA サーバーを有効にしてネットワークを起動することができます。以下のコマンドで CA を有効にして起動します。

```bash
./network.sh up -ca
```

CA が有効な場合、各組織の CA コンテナ（例: `ca_org1`、`ca_org2`）が起動し、証明書や秘密鍵の管理が自動化されます。

### 3.2.3 Fabric バージョン指定と CouchDB オプションの利用

特定のバージョンの Fabric を使用する場合、またリッチクエリに対応するため CouchDB を利用する場合は、以下のようなオプションを指定します。

```bash
./network.sh up -ca -s couchdb -i 2.4.1
```

このコマンドは、Fabric 2.4.1 を使用し、CouchDB を有効にしてネットワークを起動します。CouchDB を有効にすることで、リッチクエリがサポートされ、チェーンコードからより複雑なクエリが可能となります。

## 3.3 チャネルの作成と参加確認

### 3.3.1 チャネルの作成

ネットワークが起動したら、次にチャネルの作成を行います。チャネルは、ネットワーク内でプライベートな取引を行うための論理的な区分です。以下のコマンドで「mychannel」というチャネルを作成します。

```bash
./network.sh createChannel -c mychannel
```

コマンドが正常に実行されると、チャネルが作成され、各ピアがそのチャネルに参加します。作成したチャネルは、ネットワーク内の各コンテナに配布され、以降のトランザクションはこのチャネル内で行われます。

### 3.3.2 チャネルへの参加状態の確認

チャネルが作成された後、各組織のピアが正しくチャネルに参加しているかどうかを確認する必要があります。Org1 のピアで参加しているチャネル一覧を確認するには、以下のコマンドを実行します。

```bash
peer channel list
```

出力例は以下のようになります。

```
Channels peers has joined:
  mychannel
```

同様に、Org2 のピアでも同じように確認します。各ピアが「mychannel」に参加していれば、チャネル作成は成功しています。

---

## 3.4 ネットワーク構成の検証

### 3.4.1 Docker コンテナの確認

ネットワークが正しく起動しているかどうかを確認するため、まずは Docker コンテナの状態を確認します。以下のコマンドを実行し、各コンテナが正常に動作しているか確認してください。

```bash
docker ps
```

出力には、`orderer.example.com`、`peer0.org1.example.com`、`peer0.org2.example.com`、（CA を有効にしている場合は `ca_org1`、`ca_org2`）などのコンテナが表示されるはずです。

### 3.4.2 コンテナログの確認

各コンテナのログを確認することで、ネットワーク内の各コンポーネントが正しく動作しているか、またエラーが発生していないかをチェックします。以下のコマンドを使用してください。

```bash
docker logs -f peer0.org1.example.com
docker logs -f orderer.example.com
```

ログにエラーが記録されている場合、そのエラー内容に基づいてトラブルシューティングを実施します。

### 3.4.3 組織ごとの MSP 設定ファイルの確認

各組織の設定ファイル（MSP 設定、証明書、秘密鍵など）が正しく配置されているかも重要です。以下のように、各組織のディレクトリを確認します。

```bash
ls -la organizations/peerOrganizations/org1.example.com/
ls -la organizations/peerOrganizations/org2.example.com/
```

これにより、各組織の MSP ファイルが正しく存在しているか、パーミッションなどが適切に設定されているかを確認できます。

## 3.5 アンカーピアの設定

アンカーピアは、異なる組織間での通信を可能にするための重要な設定項目です。アンカーピアを設定することで、各組織のピアが他の組織と効率的に情報交換を行えるようになります。

### 3.5.1 Org1 のアンカーピアの設定

以下のコマンドを実行して、Org1 のアンカーピアを設定します。

```bash
./network.sh setAnchorPeer -o 1 -c mychannel
```

コマンド実行後、設定が反映される旨のメッセージが表示され、Org1 内の指定されたピアがアンカーピアとして指定されます。

### 3.5.2 Org2 のアンカーピアの設定

同様に、Org2 のアンカーピアを設定するには、以下のコマンドを実行します。

```bash
./network.sh setAnchorPeer -o 2 -c mychannel
```

この設定により、各組織間でのピア通信が円滑に行われ、ネットワーク全体の連携が強化されます。

## 3.6 CouchDB の利用

デフォルトでは、Fabric は LevelDB を台帳データベースとして使用しますが、リッチクエリ機能を利用するためには CouchDB を有効にすることが推奨されます。

### 3.6.1 CouchDB の有効化手順

CouchDB を利用するためには、まずネットワークを停止し、CouchDB オプションを付与して再起動します。

```bash
./network.sh down
./network.sh up -s couchdb
./network.sh createChannel -c mychannel
```

これにより、各ピアは CouchDB を台帳データベースとして使用し、リッチクエリ（JSON クエリ）を実行できるようになります。

### 3.6.2 CouchDB の UI にアクセス

CouchDB の管理用 UI は、ブラウザから以下の URL にアクセスすることで利用できます。

- Org1 の CouchDB: [http://localhost:5984/_utils/](http://localhost:5984/_utils/)
- Org2 の CouchDB: [http://localhost:7984/_utils/](http://localhost:7984/_utils/)

ユーザー名とパスワードは通常「admin/adminpw」と設定されています。ここから、データベースの状態やクエリ結果を確認することが可能です。

## 3.7 ネットワークのモニタリングとログ管理

ネットワーク運用において、各コンポーネントの状態監視やログ管理は非常に重要です。正確なモニタリングを実施することで、トラブル発生時に迅速な対応が可能となります。

### 3.7.1 ログの確認とフィルタリング

各コンテナのログは、以下のコマンドでリアルタイムに確認できます。

```bash
docker logs -f peer0.org1.example.com
docker logs -f orderer.example.com
```

また、特定のキーワード（例: ERROR）でフィルタリングすることで、問題箇所を素早く特定できます。

```bash
docker logs peer0.org1.example.com | grep ERROR
```

### 3.7.2 コンテナへの接続と内部調査

必要に応じて、各コンテナ内にシェルで接続し、内部状態を直接確認することも有効です。

```bash
docker exec -it peer0.org1.example.com bash
```

内部に入ることで、設定ファイルの確認や、環境変数の再確認、その他の診断作業を行えます。

### 3.7.3 外部モニタリングツールとの連携

運用現場では、Prometheus や Grafana、ELK スタックなどの外部モニタリングツールを利用して、ネットワーク全体のパフォーマンスやログの可視化を行うことが推奨されます。これらのツールを利用することで、リアルタイムな監視や過去ログの分析が容易になります。各ツールの設定方法については、別章や付録で詳述しますが、基本的な連携方法としては、各コンテナのメトリクスを収集するエージェントの導入が必要です。

---

## 3.8 ネットワークの停止とクリーンアップ

### 3.8.1 ネットワーク停止の手順

開発やテストが終了したら、ネットワークを適切に停止することが重要です。以下のコマンドで、ネットワーク内のすべてのコンテナを停止・削除できます。

```bash
./network.sh down
```

このコマンドは、起動時に生成されたコンテナ、ボリューム、アーティファクトをすべて削除し、クリーンな状態に戻します。

### 3.8.2 Docker リソースのクリーンアップ

ネットワーク停止後、不要な Docker リソースが残っている場合、以下のコマンドでクリーンアップを実施します。

```bash
docker system prune -a
docker volume prune
```

これにより、ストレージ容量の節約と環境のリセットが行われ、次回のネットワーク起動時にトラブルを未然に防ぐことができます。

## 3.9 複数チャネル・複数組織構成の高度な設定

### 3.9.1 複数チャネルの作成

実運用環境では、異なるビジネス関係や業務プロセスに応じて、複数のチャネルを作成することが一般的です。以下の例は、複数チャネルを作成する手順です。

```bash
./network.sh up
./network.sh createChannel -c channel1
./network.sh createChannel -c channel2
```

各チャネルごとにチェーンコードをデプロイする場合は、`-c` フラグでチャネル名を指定し、適切な設定を行う必要があります。

### 3.9.2 複数組織の追加と統合

大規模なネットワークでは、新たな組織を追加して運用するケースが増えます。Fabric Samples には、既存ネットワークに組織を追加するためのサンプルスクリプトが含まれています。例えば、Org3 を追加する場合、以下の手順を実施します。

```bash
cd ~/fabric-samples/test-network
./network.sh up -ca
./network.sh createChannel -c mychannel

# Org3 を追加するスクリプトを実行
cd addOrg3
./addOrg3.sh up -c mychannel
```

この手順により、既存のネットワークに新たな組織が参加し、チャネルに参加できるようになります。追加後は、各組織のアンカーピア設定や MSP 設定の更新も必要となるため、注意深く作業を行います。

### 3.9.3 カスタム設定ファイルの編集

高度なネットワーク構成を行う場合、`configtx.yaml` や `docker-compose.yaml` といった設定ファイルをカスタマイズすることが求められます。例えば、組織の追加やチャネルの構成を変更する際には、以下の手順で設定ファイルを編集します。

```bash
# カスタムネットワークディレクトリの作成
mkdir -p ~/fabric-custom-network
cp -r ~/fabric-samples/test-network/* ~/fabric-custom-network/
cd ~/fabric-custom-network

# configtx.yaml の編集
nano configtx/configtx.yaml

# docker-compose-test-net.yaml の編集
nano docker/docker-compose-test-net.yaml
```

これにより、自社のビジネス要件に合わせたネットワーク構成が実現でき、柔軟な運用が可能となります。

## 3.10 トラブルシューティングとよくある問題の対策

ネットワーク構築時には、さまざまなトラブルが発生する可能性があります。ここでは、一般的な問題とその対処法をいくつか紹介します。

### 3.10.1 ピアの同期不良

**問題点**: ピアがブロックチェーンの最新ブロックと同期できず、トランザクションの検証に失敗する場合があります。

**対策**:
- ピアのログを確認して、同期エラーやネットワーク通信のエラーが発生していないかをチェックする。
- 必要に応じて、ピアの再起動を行います。
  
  ```bash
  docker stop peer0.org1.example.com
  docker start peer0.org1.example.com
  ```
  
- チャネル参加状態を再確認し、必要ならチャネルから一度離脱し再参加させる手順も検討します。

### 3.10.2 トランザクション失敗

**問題点**: トランザクションが正しくコミットされない場合、エンドースメントポリシーの不一致やチェーンコード内のバグが原因となることがあります。

**対策**:
- オーダラーおよび各ピアのログを確認して、トランザクションエラーの原因を特定する。
  
  ```bash
  docker logs orderer.example.com | grep ERROR
  ```
  
- エンドースメントポリシーが正しく設定されているか確認し、必要に応じて各組織の承認状況を再確認する。
- チェーンコードの実行結果（read–write set）のシミュレーション結果を詳細に検証し、ビジネスロジックの問題がないか確認します。

### 3.10.3 ポート競合

**問題点**: 既に使用されているポート（例: 7050, 7051, 9051）が原因で、コンテナが起動しない場合があります。

**対策**:
- 以下のコマンドで、ポートの使用状況を確認し、競合しているプロセスを特定する。
  
  ```bash
  lsof -i :7050
  lsof -i :7051
  lsof -i :9051
  ```
  
- 該当するプロセスを停止するか、必要に応じてポート番号を変更した上で再起動します。

### 3.10.4 Docker リソース不足

**問題点**: Docker Desktop に割り当てるリソース（CPU、メモリ、ディスク容量）が不足している場合、コンテナのパフォーマンスが低下し、ネットワークが正常に動作しない可能性があります。

**対策**:
- Docker Desktop の設定画面から、リソース割り当てを確認し、必要な場合は設定を見直す。
- 不要なコンテナやボリュームを削除して、システムリソースを解放する。

## 3.11 まとめ

本章では、Hyperledger Fabric のネットワーク構築に関する基本から高度な設定、そしてトラブルシューティングまで、実践的な手順と具体例を通じて詳しく解説しました。以下のポイントを再確認してください。

- **テストネットワークの起動**  
  `./network.sh up` コマンドを用いてネットワークを起動し、各組織のピアやオーダラー、CA サーバーが正しく動作していることを確認する。

- **チャネルの作成と参加確認**  
  `./network.sh createChannel -c mychannel` によりチャネルを作成し、各ピアがチャネルに参加していることを確認する。

- **アンカーピアの設定**  
  異なる組織間の通信を円滑にするため、各組織のアンカーピアを適切に設定する。

- **CouchDB の利用**  
  リッチクエリを利用するため、CouchDB を有効にしてネットワークを起動し、ブラウザから管理 UI でデータを確認する。

- **ネットワークのモニタリング**  
  各コンポーネントのログや Docker コンテナの状態を確認し、トラブルが発生した場合の対策を事前に準備する。

- **高度なネットワーク構成**  
  複数チャネル、複数組織構成、カスタム設定ファイルの編集によって、実際の業務要件に合わせた柔軟なネットワーク設計が可能となる。

- **トラブルシューティング**  
  よく発生するエラーの原因と対策を理解し、実際の運用現場で迅速に問題解決を行うための知識を習得する。

これらの知識を確実に身につけることで、Hyperledger Fabric を用いたネットワーク構築の基本から実運用レベルのシステム構築まで、実践的なスキルが習得できます。次章以降では、ここで構築したネットワークを基盤として、具体的なチェーンコード開発や運用管理の手法に焦点を当て、さらなる実践知識を深めていきます。

## 結語

本章では、Hyperledger Fabric を用いたテストネットワークの構築と運用に関する詳細な手順を解説しました。実践的なコマンド例や設定ファイル、各種トラブルシューティングの方法を通じて、読者は自らネットワークを構築し、各コンポーネントの連携を確認するための知識を体系的に習得できるようになります。これにより、実際のビジネスシナリオに即したブロックチェーンネットワークの設計・運用が可能となり、エンタープライズ向けシステムへの応用がより現実的なものとなります。

次章では、このネットワークを基盤として、さらに具体的なチェーンコード開発の手法や、アプリケーション連携の方法について詳しく解説していきます。ここで学んだネットワーク構築の知識は、後続の章での応用において重要な役割を果たすため、ぜひ本章の内容を十分に理解し、実際に手を動かして確認していただきたいと思います。
