## 第5章 セキュリティの基礎：脆弱性とその対策

スマートコントラクトは一度デプロイされると変更が難しく、もし脆弱性が見つかれば、そこから資産が盗まれたり、コントラクトが正常に機能しなくなる可能性があります。この章では、スマートコントラクト開発において頻繁に発生するセキュリティ上の脆弱性と、それらを防ぐための対策について詳しく解説します。初心者の方にも理解しやすいように、具体的なコード例を交えながら、段階的に説明を進めていきます。

### 5.1 オーバーフローとアンダーフロー

#### 概要と重要性

オーバーフローとアンダーフローは、数値型の変数が扱える範囲を超えた場合に発生する脆弱性です。例えば、`uint256`型の変数が最大値を超えてインクリメントされた場合、ゼロに戻ってしまうのがオーバーフローです。逆に、ゼロからデクリメントされた場合は、最大値になってしまうのがアンダーフローです。これらの現象は、悪意のある攻撃者によってコントラクトのロジックを意図的に狂わせるために利用される可能性があります。

#### オーバーフロー/アンダーフローの仕組み

Solidity 0.8.0以前のバージョンでは、オーバーフローとアンダーフローはデフォルトでチェックされませんでした。そのため、プログラマーが明示的にチェックを行う必要がありました。

```solidity
pragma solidity ^0.7.0;

contract OverflowExample {
    uint256 public balance = 100;

    function withdraw(uint256 amount) public {
        // オーバーフロー/アンダーフローが発生する可能性あり
        balance -= amount;
    }
}
```

上記の例では、`balance`が`amount`より小さい場合、アンダーフローが発生し、`balance`は非常に大きな値になってしまいます。

#### SafeMathライブラリの使用

Solidity 0.8.0以前のバージョンでは、SafeMathライブラリを使用してオーバーフローとアンダーフローを防止するのが一般的でした。SafeMathライブラリは、算術演算を行う前に、オーバーフローやアンダーフローが発生しないかをチェックし、発生する場合は例外をスローします。

```solidity
pragma solidity ^0.7.0;

import "@openzeppelin/contracts/utils/math/SafeMath.sol";

contract SafeMathExample {
    using SafeMath for uint256;

    uint256 public balance = 100;

    function withdraw(uint256 amount) public {
        // SafeMathを使用してアンダーフローを防止
        balance = balance.sub(amount);
    }
}
```

上記の例では、`SafeMath`ライブラリを`uint256`型に対して使用しています。`sub`関数は、アンダーフローが発生した場合に例外をスローします。

#### Solidity 0.8.0以降の対策

Solidity 0.8.0以降のバージョンでは、オーバーフローとアンダーフローのチェックがデフォルトで有効になりました。そのため、SafeMathライブラリを使用する必要はなくなりました。オーバーフローやアンダーフローが発生すると、例外がスローされ、トランザクションがリバートされます。

```solidity
pragma solidity ^0.8.0;

contract OverflowExample {
    uint256 public balance = 100;

    function withdraw(uint256 amount) public {
        // オーバーフロー/アンダーフローが発生すると例外がスローされる
        balance -= amount;
    }
}
```

#### トラブルシューティング

- Solidity 0.8.0以前のバージョンを使用している場合は、SafeMathライブラリを使用することを強く推奨します。
- Solidity 0.8.0以降のバージョンを使用している場合でも、意図的にオーバーフローやアンダーフローを許可したい場合は、`unchecked`ブロックを使用できます。ただし、これは高度なテクニックであり、十分に理解した上で使用する必要があります。

#### まとめと次のステップ

オーバーフローとアンダーフローは、スマートコントラクトのセキュリティにおいて基本的な脆弱性の一つです。SafeMathライブラリの使用、またはSolidity 0.8.0以降のバージョンを使用することで、これらの脆弱性を効果的に防止できます。次のセクションでは、リエントランシー攻撃について解説します。

### 5.2 リエントランシー攻撃

#### 概要と重要性

リエントランシー攻撃は、コントラクトが別のコントラクトを呼び出した後、自身の状態が更新される前に、呼び出し先のコントラクトが再び自身のコントラクトを呼び出すことで発生する脆弱性です。この攻撃を利用することで、攻撃者は本来許可されていない操作を実行したり、資産を不正に引き出したりすることができます。

#### リエントランシー攻撃の仕組みと例

典型的なリエントランシー攻撃の例として、DAO事件が挙げられます。以下のシンプルなコントラクトを考えてみましょう。

```solidity
pragma solidity ^0.7.0;

contract VulnerableContract {
    mapping(address => uint256) public balances;

    function deposit() public payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw(uint256 amount) public {
        require(balances[msg.sender] >= amount, "Insufficient balance");

        (bool success, ) = msg.sender.call{value: amount}(""); // 危険な箇所：状態更新前に外部コントラクトを呼び出し
        require(success, "Transfer failed");

        balances[msg.sender] -= amount;
    }
}
```

このコントラクトにはリエントランシー攻撃の脆弱性があります。攻撃者は、`withdraw`関数が`balances`を更新する前に、`msg.sender.call`を使って再び`withdraw`関数を呼び出すことができます。

攻撃コントラクトの例：

```solidity
pragma solidity ^0.7.0;

interface VulnerableContract {
    function deposit() external payable;
    function withdraw(uint256 amount) external;
}

contract AttackContract {
    VulnerableContract public target;
    address public owner;

    constructor(VulnerableContract _target) public {
        target = _target;
        owner = msg.sender;
    }

    function attack() public payable {
        target.deposit{value: msg.value}();
        target.withdraw(msg.value);
    }

    receive() external payable {
        if (address(target).balance > 0) {
            target.withdraw(address(target).balance); // 再帰的にwithdrawを呼び出す
        } else {
            payable(owner).transfer(address(this).balance);
        }
    }
}
```

攻撃の流れは以下の通りです。
1. 攻撃者はAttackContractをデプロイし、VulnerableContractのインスタンスアドレスを渡します。
2. 攻撃者はAttackContractのattack関数を呼び出し、資金をdepositし、同じ金額をwithdrawしようとします。
3. VulnerableContractのwithdraw関数は、AttackContractにETHを送金します。
4. AttackContractのreceive関数が呼び出されます。この関数は、VulnerableContractからETHを受け取ると、再びwithdraw関数を呼び出します。
5. この時点で、VulnerableContractのbalancesはまだ更新されていないため、AttackContractは再度withdrawできます。
6. この処理を繰り返すことで、AttackContractはVulnerableContractから全てのETHを盗むことができます。

#### Checks-Effects-Interactionsパターン

リエントランシー攻撃を防ぐための最も効果的な方法の一つが、Checks-Effects-Interactionsパターンです。このパターンは、以下の順番で処理を行うことを推奨します。

1. **Checks:** 事前条件のチェック（例：残高が十分かどうかの確認）。
2. **Effects:** 状態変数の更新（例：残高の減算）。
3. **Interactions:** 外部コントラクトとのインタラクション（例：ETHの送金）。

このパターンに従うことで、外部コントラクトとのインタラクションの前に状態変数が更新されるため、リエントランシー攻撃を防ぐことができます。

```solidity
pragma solidity ^0.8.0;

contract SecureContract {
    mapping(address => uint256) public balances;

    function deposit() public payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw(uint256 amount) public {
        require(balances[msg.sender] >= amount, "Insufficient balance");

        // Effects: 状態変数の更新を先に行う
        balances[msg.sender] -= amount;

        // Interactions: 外部コントラクトとのインタラクション
        (bool success, ) = msg.sender.call{value: amount}("");
        require(success, "Transfer failed");
    }
}
```

#### ReentrancyGuardコントラクトの利用

OpenZeppelinのReentrancyGuardコントラクトを使用することも、リエントランシー攻撃を防ぐための有効な手段です。ReentrancyGuardは、コントラクトがリエントラントであるかどうかを追跡し、リエントラントな呼び出しをブロックします。

```solidity
pragma solidity ^0.8.0;

import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract ReentrancyGuardExample is ReentrancyGuard {
    mapping(address => uint256) public balances;

    function deposit() public payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw(uint256 amount) public nonReentrant {
        require(balances[msg.sender] >= amount, "Insufficient balance");

        (bool success, ) = msg.sender.call{value: amount}("");
        require(success, "Transfer failed");

        balances[msg.sender] -= amount;
    }
}
```

上記の例では、`withdraw`関数に`nonReentrant`修飾子を追加しています。これにより、`withdraw`関数が実行中に再び呼び出された場合、例外がスローされます。

#### トラブルシューティング

- 外部コントラクトを呼び出す際は、必ずChecks-Effects-Interactionsパターンに従ってください。
- ReentrancyGuardコントラクトを使用する際は、コントラクトを`ReentrancyGuard`から継承し、リエントランシーから保護したい関数に`nonReentrant`修飾子を追加してください。
- `transfer`関数や`send`関数を使用する代わりに、`call`関数を使用する際は、戻り値を必ず確認してください。

#### まとめと次のステップ

リエントランシー攻撃は、スマートコントラクトのセキュリティにおいて非常に危険な脆弱性の一つです。Checks-Effects-InteractionsパターンやReentrancyGuardコントラクトを使用することで、これらの攻撃を効果的に防止できます。次のセクションでは、アクセス制限の脆弱性について解説します。

### 5.3 アクセス制限の脆弱性

#### 概要と重要性

アクセス制限の脆弱性は、コントラクトの関数が意図しないユーザーによって呼び出される可能性がある場合に発生します。例えば、管理者のみが実行できるべき関数が、誰でも実行できてしまうような場合です。適切なアクセス制限を実装しないと、悪意のあるユーザーによってコントラクトの状態が不正に変更されたり、資産が盗まれたりする可能性があります。

#### 不適切なアクセス制限による脆弱性

以下のコントラクトを考えてみましょう。

```solidity
pragma solidity ^0.7.0;

contract VulnerableContract {
    address public owner;
    uint256 public value;

    constructor() public {
        owner = msg.sender;
    }

    function setValue(uint256 _value) public {
        // アクセス制限がないため、誰でも実行できる
        value = _value;
    }
}
```

このコントラクトでは、`setValue`関数にアクセス制限がないため、誰でも`value`の値を変更することができます。これは、コントラクトの意図された動作を妨げる可能性があります。

#### Ownableコントラクトの利用

OpenZeppelinのOwnableコントラクトを使用することで、コントラクトの所有者を設定し、特定の関数へのアクセスを所有者に制限することができます。

```solidity
pragma solidity ^0.8.0;

import "@openzeppelin/contracts/access/Ownable.sol";

contract SecureContract is Ownable {
    uint256 public value;

    function setValue(uint256 _value) public onlyOwner {
        // 所有者のみが実行できる
        value = _value;
    }
}
```

上記の例では、`Ownable`コントラクトを継承し、`setValue`関数に`onlyOwner`修飾子を追加しています。これにより、`setValue`関数はコントラクトの所有者のみが実行できるようになります。

#### Role-Based Access Control (RBAC)の実装

より複雑なアクセス制御が必要な場合は、Role-Based Access Control (RBAC)を実装することができます。RBACでは、ユーザーに役割を割り当て、役割に基づいて関数へのアクセスを制御します。OpenZeppelinには、RBACを簡単に実装できる`AccessControl`コントラクトが用意されています。

```solidity
pragma solidity ^0.8.0;

import "@openzeppelin/contracts/access/AccessControl.sol";

contract RBACExample is AccessControl {
    bytes32 public constant ADMIN_ROLE = keccak256("ADMIN_ROLE");
    bytes32 public constant MODERATOR_ROLE = keccak256("MODERATOR_ROLE");

    uint256 public value;

    constructor() public {
        _setupRole(ADMIN_ROLE, msg.sender);
        _setRoleAdmin(ADMIN_ROLE, ADMIN_ROLE);
        _setRoleAdmin(MODERATOR_ROLE, ADMIN_ROLE);
    }

    function setValue(uint256 _value) public onlyRole(ADMIN_ROLE) {
        // ADMIN_ROLEを持つユーザーのみが実行できる
        value = _value;
    }

    function moderateValue(uint256 _value) public onlyRole(MODERATOR_ROLE) {
        // MODERATOR_ROLEを持つユーザーのみが実行できる
        value = _value;
    }

    function grantModeratorRole(address _account) public onlyRole(ADMIN_ROLE) {
        grantRole(MODERATOR_ROLE, _account);
    }

    function revokeModeratorRole(address _account) public onlyRole(ADMIN_ROLE) {
        revokeRole(MODERATOR_ROLE, _account);
    }
}
```

上記の例では、`ADMIN_ROLE`と`MODERATOR_ROLE`という2つの役割を定義しています。`setValue`関数は`ADMIN_ROLE`を持つユーザーのみが実行でき、`moderateValue`関数は`MODERATOR_ROLE`を持つユーザーのみが実行できます。`grantModeratorRole`関数と`revokeModeratorRole`関数は、`ADMIN_ROLE`を持つユーザーが`MODERATOR_ROLE`を他のユーザーに付与したり、取り消したりするために使用できます。

#### トラブルシューティング

- コントラクトの関数が意図しないユーザーによって呼び出されないように、適切なアクセス制限を実装してください。
- Ownableコントラクトを使用する場合は、コントラクトの所有者を適切に設定し、所有者のみが実行できるべき関数に`onlyOwner`修飾子を追加してください。
- より複雑なアクセス制御が必要な場合は、RBACを実装し、ユーザーに役割を割り当て、役割に基づいて関数へのアクセスを制御してください。
- 関数にアクセス制限を追加する際は、最小権限の原則に従い、ユーザーに必要な最小限の権限のみを付与してください。

#### まとめと次のステップ

アクセス制限の脆弱性は、スマートコントラクトのセキュリティにおいて非常に一般的な問題です。OwnableコントラクトやRBACを適切に使用することで、これらの脆弱性を効果的に防止できます。次のセクションでは、Denial of Service (DoS)攻撃について解説します。

### 5.4 Denial of Service (DoS)攻撃

#### 概要と重要性

Denial of Service (DoS)攻撃は、コントラクトが正常に機能しなくなるように、リソースを過剰に消費させる攻撃です。DoS攻撃は、コントラクトの可用性を低下させたり、完全に停止させたりする可能性があります。

#### ガスリミットの利用によるDoS攻撃

ガスリミットは、トランザクションが実行できる最大のガス量を指定するものです。攻撃者は、ガスリミットを使い切るような複雑な計算を実行するトランザクションを送信することで、DoS攻撃を仕掛けることができます。

例えば、以下のコントラクトを考えてみましょう。

```solidity
pragma solidity ^0.7.0;

contract VulnerableContract {
    address[] public users;

    function register() public {
        users.push(msg.sender);
    }

    function payout() public {
        for (uint256 i = 0; i < users.length; i++) {
            (bool success, ) = users[i].call{value: 1 wei}("");
            require(success, "Transfer failed");
        }
    }
}
```

このコントラクトでは、`payout`関数が`users`配列のすべてのユーザーに1 weiを送金します。攻撃者は、大量のアカウントを登録することで、`users`配列を非常に大きくすることができます。その結果、`payout`関数を実行する際にガスリミットを超えてしまい、トランザクションがリバートされる可能性があります。

#### 処理の分割と制限

DoS攻撃を防ぐためには、処理を分割し、一度に実行する処理の量を制限することが重要です。

```solidity
pragma solidity ^0.8.0;

contract SecureContract {
    address[] public users;
    uint256 public lastPayoutIndex;

    function register() public {
        users.push(msg.sender);
    }

    function payout(uint256 _usersPerTransaction) public {
        uint256 endIndex = lastPayoutIndex + _usersPerTransaction;
        if (endIndex > users.length) {
            endIndex = users.length;
        }

        for (uint256 i = lastPayoutIndex; i < endIndex; i++) {
            (bool success, ) = users[i].call{value: 1 wei}("");
            require(success, "Transfer failed");
        }

        lastPayoutIndex = endIndex;
    }
}
```

上記の例では、`payout`関数に`_usersPerTransaction`という引数を追加しました。これにより、一度に送金するユーザーの数を制限することができます。また、`lastPayoutIndex`という変数を追加し、最後に送金したユーザーのインデックスを記録しています。これにより、`payout`関数を複数回呼び出すことで、すべてのユーザーに送金することができます。

#### pull over pushパターン

もう一つのDoS攻撃を防ぐためのテクニックとして、pull over pushパターンがあります。pushパターンでは、コントラクトがユーザーに資金を送信しますが、pullパターンでは、ユーザーがコントラクトから資金を引き出す必要があります。

```solidity
pragma solidity ^0.8.0;

contract PullOverPushContract {
    mapping(address => uint256) public balances;

    function deposit() public payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw() public {
        uint256 amount = balances[msg.sender];
        balances[msg.sender] = 0;

        (bool success, ) = msg.sender.call{value: amount}("");
        require(success, "Transfer failed");
    }
}
```

上記の例では、`withdraw`関数がpushパターンを使用しています。攻撃者は、`msg.sender.call`が常に成功するように、悪意のあるコントラクトをデプロイし、そのコントラクトのreceive関数を常に失敗するように設定することができます。その結果、他のユーザーは資金を引き出すことができなくなります。

pullパターンを使用することで、この問題を解決することができます。

```solidity
pragma solidity ^0.8.0;

contract SecurePullOverPushContract {
    mapping(address => uint256) public balances;

    function deposit() public payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw() public {
        uint256 amount = balances[msg.sender];
        balances[msg.sender] = 0;

        payable(msg.sender).transfer(amount);
    }
}
```

上記の例では、`transfer`関数を使用しています。`transfer`関数は、送金に失敗した場合に例外をスローします。そのため、悪意のあるコントラクトが送金を妨げた場合、トランザクションがリバートされ、他のユーザーは資金を引き出すことができます。

#### トラブルシューティング

- ガスリミットを利用したDoS攻撃を防ぐためには、処理を分割し、一度に実行する処理の量を制限してください。
- pushパターンを使用する代わりに、pullパターンを使用することを検討してください。
- 外部コントラクトとのインタラクションを行う際は、常にエラーハンドリングを行ってください。

#### まとめと次のステップ

DoS攻撃は、スマートコントラクトの可用性を低下させる可能性があります。処理の分割と制限、pull over pushパターンなどのテクニックを使用することで、これらの攻撃を効果的に防止できます。次のセクションでは、その他の脆弱性について解説します。

### 5.5 その他の脆弱性

#### フロントランニング攻撃

フロントランニング攻撃は、トランザクションがブロックチェーンに記録される前に、そのトランザクションを観察し、自分自身のトランザクションをより高いガス価格で送信することで、そのトランザクションよりも先に実行されるようにする攻撃です。

例えば、分散型取引所（DEX）で大きな取引が行われることを知った攻撃者は、その取引よりも先に同じトークンを購入することで、価格変動を利用して利益を得ることができます。

フロントランニング攻撃を防ぐための対策としては、以下のものがあります。

- **Commit-Revealスキーム:** ユーザーはまずトランザクションのハッシュをコミットし、後で実際のトランザクションを公開します。これにより、攻撃者はトランザクションの内容を知ることができなくなります。
- **オラクル:** 信頼できるオラクルを使用して、価格情報を取得します。
- **スリッページ許容:** ユーザーは、許容できる最大のスリッページを設定できます。

#### Timestamp依存の問題

ブロックのタイムスタンプは、マイナーによってある程度操作される可能性があります。そのため、ランダムな数を生成したり、重要なロジックを決定するためにタイムスタンプを使用することは避けるべきです。

```solidity
pragma solidity ^0.7.0;

contract VulnerableContract {
    function getRandomNumber() public view returns (uint256) {
        // タイムスタンプに依存しているため、予測可能
        return uint256(block.timestamp);
    }
}
```

上記の例では、`getRandomNumber`関数が`block.timestamp`を使用してランダムな数を生成しています。攻撃者は、`block.timestamp`をある程度操作できるため、この関数が生成する数を予測することができます。

#### Delegatecallの危険性

`delegatecall`は、別のコントラクトのコードを現在のコントラクトのコンテキストで実行するために使用されます。`delegatecall`を使用すると、呼び出されたコントラクトは現在のコントラクトのストレージを使用するため、予期せぬ副作用が発生する可能性があります。

```solidity
pragma solidity ^0.7.0;

contract Delegate {
    uint256 public value;

    function setValue(uint256 _value) public {
        value = _value;
    }
}

contract Caller {
    address public delegateAddress;
    uint256 public value;

    constructor(address _delegateAddress) public {
        delegateAddress = _delegateAddress;
    }

    function callDelegate(uint256 _value) public {
        (bool success, ) = delegateAddress.delegatecall(abi.encodeWithSignature("setValue(uint256)", _value));
        require(success, "Delegatecall failed");
    }
}
```

上記の例では、`Caller`コントラクトが`Delegate`コントラクトの`setValue`関数を`delegatecall`を使用して呼び出しています。`Delegate`コントラクトの`value`変数は、`Caller`コントラクトのストレージに書き込まれます。そのため、`Caller`コントラクトの`value`変数が変更されてしまいます。

#### トラブルシューティング

- フロントランニング攻撃を防ぐためには、Commit-Revealスキームやオラクルを使用することを検討してください。
- タイムスタンプに依存するロジックは避けてください。
- `delegatecall`を使用する際は、十分な注意を払い、予期せぬ副作用が発生しないようにしてください。
