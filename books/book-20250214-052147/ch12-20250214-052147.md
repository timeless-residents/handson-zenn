## 12. スマートコントラクトのセキュリティ監査

スマートコントラクトは、ブロックチェーン技術の核となる存在であり、その安全性は極めて重要です。わずかな脆弱性が、巨額の資金損失やシステムの信頼失墜に繋がる可能性があります。本章では、スマートコントラクトのセキュリティ監査の基礎から応用までを、実践的なアプローチで解説します。セキュリティリスクの種類、静的解析ツール、形式検証という3つの柱を通して、安全なスマートコントラクト開発を支援します。

### 12.1 セキュリティリスクの種類 - Reentrancy, Overflow, Underflow

#### 12.1.1 概要と重要性

スマートコントラクトのセキュリティリスクを理解することは、安全なコントラクト開発の第一歩です。特に、Reentrancy（リエントランシー）、Overflow（オーバーフロー）、Underflow（アンダーフロー）は、頻繁に発生し、重大な損害を引き起こす可能性のある代表的なリスクです。

#### 12.1.2 特徴と利点

*   **Reentrancy (リエントランシー)**: 外部コントラクトへの呼び出しが完了する前に、現在のコントラクトの状態が変更されることによって発生します。攻撃者は、この脆弱性を利用して、本来許可されていないアクションを実行したり、資金を不正に引き出したりすることができます。
*   **Overflow (オーバーフロー)**: 変数がそのデータ型の最大値を超えてしまう現象です。例えば、`uint8`型の変数が255の場合、1を加算すると0に戻ってしまいます。
*   **Underflow (アンダーフロー)**: 変数がそのデータ型の最小値を下回ってしまう現象です。例えば、`uint8`型の変数が0の場合、1を減算すると255になります。

これらのリスクを理解することで、安全なコントラクト設計、コーディング、テストを行うことが可能になります。

#### 12.1.3 事前準備と前提条件

*   Solidityの基本的な文法知識
*   Ethereumの仕組みに関する基本的な理解

#### 12.1.4 基本的な使い方

**Reentrancyの例：**

```solidity
pragma solidity ^0.8.0;

contract VulnerableContract {
    mapping(address => uint256) public balances;
    
    function deposit() public payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw(uint256 amount) public {
        require(balances[msg.sender] >= amount, "Insufficient balance.");
        balances[msg.sender] -= amount;
        (bool success, ) = msg.sender.call{value: amount}("");
        require(success, "Transfer failed."); // 問題点：チェックエフェクトインタラクションパターンに従っていない
    }
}
```

このコントラクトでは、`withdraw`関数がリエントランシー攻撃に対して脆弱です。攻撃者は、`msg.sender.call{value: amount}("")`の呼び出しが完了する前に、自身のコントラクト内で`withdraw`関数を再度呼び出すことができます。

**Overflow/Underflowの例：**

```solidity
pragma solidity ^0.8.0;

contract OverflowUnderflow {
    uint8 public maxUint8 = 255;
    uint8 public minUint8 = 0;

    function overflow() public {
        // Solidity 0.8.0以降では、オーバーフロー/アンダーフローはデフォルトでチェックされるため、下記コードは例外をスローします
        // maxUint8 = maxUint8 + 1;
    }

    function underflow() public {
        // 同様に、例外をスローします
        // minUint8 = minUint8 - 1;
    }
}
```

Solidity 0.8.0以降では、オーバーフロー/アンダーフローに対するチェックがデフォルトで有効になりました。以前のバージョンでは、SafeMathライブラリを使用することで、これらの問題を回避する必要がありました。

#### 12.1.5 実践的なテクニック

*   **Check-Effects-Interactionsパターン:** コントラクトの状態を変更する前に、必要なすべてのチェックを行い、その後に状態を変更し、最後に外部コントラクトとのインタラクションを行うことで、リエントランシー攻撃を防止できます。
*   **Reentrancy Guard:** リエントランシーを防ぐためのModifierを実装します。
*   **SafeMathライブラリ (Solidity 0.8.0より前のバージョン):** オーバーフロー/アンダーフローを防止するために、算術演算にSafeMathライブラリを使用します。Solidity 0.8.0以降では、デフォルトのチェックで保護されますが、SafeMathライブラリの考え方は重要です。
*   **OpenZeppelin Contracts:** セキュリティ対策が施されたコントラクトの標準的な実装を提供します。

**Check-Effects-Interactionsパターンの例：**

```solidity
pragma solidity ^0.8.0;

contract SecureContract {
    mapping(address => uint256) public balances;
    
    function deposit() public payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw(uint256 amount) public {
        require(balances[msg.sender] >= amount, "Insufficient balance.");

        // チェック
        uint256 currentBalance = balances[msg.sender];

        // エフェクト
        balances[msg.sender] = currentBalance - amount;

        // インタラクション
        (bool success, ) = msg.sender.call{value: amount}("");
        require(success, "Transfer failed.");
    }
}
```

**Reentrancy Guardの例：**

```solidity
pragma solidity ^0.8.0;

contract ReentrancyGuard {
    bool private _notEntered;

    constructor() {
        _notEntered = true;
    }

    modifier nonReentrant() {
        require(_notEntered, "ReentrancyGuard: reentrant call");
        _notEntered = false;
        _;
        _notEntered = true;
    }
}

contract MyContract is ReentrancyGuard {
    mapping(address => uint256) public balances;

    function withdraw(uint256 amount) public nonReentrant {
        // ...
    }
}
```

#### 12.1.6 応用例とユースケース

*   DeFi（分散型金融）プロトコル: レンディングプラットフォーム、DEX（分散型取引所）などのセキュリティ監査。
*   NFT（非代替性トークン）: NFTの販売、移転、メタデータ管理などに関するセキュリティ監査。
*   サプライチェーン管理: 製品の追跡、検証プロセスにおけるセキュリティ監査。

#### 12.1.7 トラブルシューティング

*   **Reentrancyのテスト:** コントラクトをデプロイし、リエントランシー攻撃を模倣するテストケースを作成します。
*   **Overflow/Underflowのテスト:** 境界値付近の演算を行い、意図しない挙動が発生しないか確認します。
*   **デバッグ:** Remix IDEやHardhatなどの開発環境で、コントラクトの実行をステップごとに確認します。

#### 12.1.8 まとめと次のステップ

本セクションでは、スマートコントラクトにおける主要なセキュリティリスク、Reentrancy、Overflow、Underflowについて学びました。Check-Effects-InteractionsパターンやReentrancy Guard、SafeMathライブラリ（Solidity 0.8.0以前）などの対策方法も習得しました。次のステップでは、これらの知識を基に、静的解析ツールや形式検証ツールを利用して、より高度なセキュリティ監査を実践していきましょう。

### 12.2 静的解析ツール - Slither, Mythril, Securify

#### 12.2.1 概要と重要性

静的解析ツールは、ソースコードを実行せずに、コードの構造やロジックを解析することで、潜在的な脆弱性やバグを発見するツールです。Slither、Mythril、Securifyは、スマートコントラクトのセキュリティ監査において、広く利用されているツールです。

#### 12.2.2 特徴と利点

*   **Slither:** Python製の静的解析フレームワーク。様々な脆弱性を検出するだけでなく、コードの可読性や保守性を向上させるための情報も提供します。カスタマイズ性が高く、独自の検出ルールを追加することも可能です。
*   **Mythril:** EVMバイトコードを解析し、セキュリティ脆弱性を検出するツール。シンボリック実行やSMTソルバーなどの高度な技術を使用し、Reentrancy、Overflow、Underflow、Timestamp Dependencyなど、様々な脆弱性を検出できます。
*   **Securify:** 形式意味論に基づいた静的解析ツール。コントラクトの意図された動作と実際の動作を比較することで、セキュリティ脆弱性を検出します。

静的解析ツールを利用することで、手動でのコードレビューだけでは見つけにくい脆弱性を効率的に発見し、安全なコントラクト開発を支援できます。

#### 12.2.3 事前準備と前提条件

*   Python (Slither)
*   Docker (Mythril, Securify)
*   ターミナルの基本的な操作

#### 12.2.4 基本的な使い方

**Slitherのインストールと実行：**

```bash
pip install slither-analyzer
slither contract.sol
```

**Mythrilのインストールと実行：**

```bash
docker pull mythril/mythril
docker run -v "$PWD:/tmp" mythril/mythril analyze /tmp/contract.sol
```

**Securifyのインストールと実行：**

Securifyは、現在Webベースのインターフェースで提供されています。公式ウェブサイト ([https://securify.ch/](https://securify.ch/)) にアクセスし、コントラクトのソースコードをアップロードして解析を実行します。

#### 12.2.5 実践的なテクニック

*   **Slither:**
    *   カスタマイズされた検出ルールの作成: 特定のプロジェクトに特有のセキュリティ要件に合わせて、独自の検出ルールを作成します。
    *   CI/CDパイプラインへの統合: コードが変更されるたびに自動的にSlitherを実行し、早期に脆弱性を検出します。
*   **Mythril:**
    *   分析オプションの調整: 分析時間や精度を調整するために、Mythrilのオプションを調整します。
    *   カスタム環境の設定: 特定のコントラクトの動作をエミュレートするために、カスタム環境を設定します。
*   **Securify:**
    *   レポートの分析: Securifyが生成する詳細なレポートを分析し、検出された脆弱性の根本原因を特定します。
    *   結果の検証: Securifyの結果を検証し、誤検知を除外します。

#### 12.2.6 応用例とユースケース

*   スマートコントラクトの開発初期段階での脆弱性検出。
*   既存のスマートコントラクトのセキュリティ監査。
*   オープンソースのスマートコントラクトライブラリのセキュリティレビュー。

#### 12.2.7 トラブルシューティング

*   **Slither:**
    *   依存関係の問題: Pythonの依存関係が競合する場合は、仮想環境を使用します。
    *   解析エラー: コードに構文エラーがある場合は、Solidityコンパイラでコンパイルしてから解析を実行します。
*   **Mythril:**
    *   Dockerの問題: Dockerが正しくインストールされているか確認します。
    *   分析時間の問題: 分析時間が長すぎる場合は、分析オプションを調整します。
*   **Securify:**
    *   アップロードの問題: ファイルサイズ制限を超えていないか確認します。
    *   結果の解釈: Securifyのドキュメントを参照して、結果を正しく解釈します。

### 12.3 形式検証 - TLA+, Alloy

#### 12.3.1 概要と重要性

形式検証は、数理的な手法を用いて、システムの仕様や設計が正しいことを証明する技術です。スマートコントラクトの形式検証では、コントラクトの仕様を形式的に記述し、その仕様が満たされていることを数学的に証明します。TLA+とAlloyは、スマートコントラクトの形式検証に利用できる代表的なツールです。

#### 12.3.2 特徴と利点

*   **TLA+:** Leslie Lamportによって開発された形式仕様記述言語。並行システムや分散システムの検証に広く使用されています。TLA+は、システムの動作を厳密に記述し、その仕様が満たされていることをモデル検査によって検証します。
*   **Alloy:** MITによって開発された形式仕様記述言語。オブジェクト指向のシステムやデータ構造の検証に適しています。Alloyは、システムの構造と制約を記述し、その仕様が満たされていることをスコープ付きのモデル検査によって検証します。

形式検証を利用することで、静的解析ツールでは検出できない、より複雑な論理的な誤りや設計上の欠陥を発見し、安全性の高いコントラクトを開発することができます。

#### 12.3.3 事前準備と前提条件

*   論理学（命題論理、述語論理）の基本的な知識
*   形式仕様記述の基本的な知識
*   各ツールのインストールと設定

#### 12.3.4 基本的な使い方

**TLA+の例：**

TLA+の仕様は、モジュールと呼ばれる単位で記述されます。以下は、簡単なカウンタのTLA+仕様の例です。

```tla
---- MODULE Counter ----
EXTENDS Naturals

VARIABLES counter

Init == counter = 0

Increment ==
    /\ counter' = counter + 1
    /\ UNCHANGED counter

TypeOK == counter \in Nat

Spec == Init /\ [][Increment]_counter

====
```

この仕様は、カウンタの状態変数`counter`を定義し、初期状態`Init`、インクリメント操作`Increment`、型制約`TypeOK`、およびシステムの全体的な仕様`Spec`を記述しています。

**Alloyの例：**

Alloyの仕様は、シグネチャと呼ばれる単位で記述されます。以下は、簡単なリストのAlloy仕様の例です。

```alloy
sig List {
    next: lone List
}

fact {
    no l: List | l in l.^(next)
}

pred NoCycle {
    no l: List | l in l.^(next)
}

run NoCycle for 3 List
```

この仕様は、リストのノード`List`を定義し、`next`フィールドによって次のノードへの参照を保持します。`fact`は、サイクルが存在しないことを制約として記述し、`pred`は、サイクルが存在しないことを述語として定義します。`run`コマンドは、指定されたスコープ内で述語が満たされるかどうかを検証します。

#### 12.3.5 実践的なテクニック

*   **抽象化:** 複雑なコントラクトを検証するために、コントラクトの重要な部分のみを抽出した抽象モデルを作成します。
*   **反復的な検証:** 仕様を段階的に記述し、モデル検査を繰り返し実行することで、初期段階での誤りを検出します。
*   **仕様の改善:** モデル検査の結果に基づいて、仕様を修正し、より正確なモデルを作成します。

#### 12.3.6 応用例とユースケース

*   スマートコントラクトの複雑なビジネスロジックの検証。
*   分散型システムのコンセンサスアルゴリズムの検証。
*   暗号プロトコルのセキュリティ検証。

#### 12.3.7 トラブルシューティング

*   **TLA+:**
    *   モデル検査器の実行時間の問題: モデル検査器が無限ループに陥る場合は、仕様を簡略化するか、モデル検査器のオプションを調整します。
    *   仕様の複雑性の問題: 仕様が複雑すぎる場合は、仕様を分割するか、抽象化を使用します。
*   **Alloy:**
    *   スコープの問題: スコープが小さすぎる場合は、モデルが十分に探索されず、誤りが見逃される可能性があります。スコープが大きすぎる場合は、モデル検査器の実行時間が長くなる可能性があります。
    *   制約の問題: 制約が強すぎる場合は、モデルが存在しない可能性があります。制約が弱すぎる場合は、モデルが意図しない動作を含む可能性があります。
