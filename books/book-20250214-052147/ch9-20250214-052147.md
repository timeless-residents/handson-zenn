## 9. Web3認証とウォレット連携

Web3の世界に飛び込む上で、認証とウォレット連携は避けて通れない重要な概念です。Web3アプリケーション（DApps）がユーザーを識別し、ユーザーのデジタル資産（暗号資産やNFTなど）を安全に管理するためには、これらの技術が不可欠となります。この章では、Web3ウォレットの仕組みから、最新の認証方式、そして未来の認証技術であるAccount Abstractionまで、段階的に解説していきます。Web3開発の初心者から、より深い知識を求める上級者まで、幅広い読者にとって有益な情報を提供することを目指します。

### 9.1 Web3ウォレットの仕組み - MetaMask, WalletConnect

#### 9.1.1 概要と重要性

Web3ウォレットは、従来のウェブアプリケーションにおけるIDとパスワードの役割を担うだけでなく、暗号資産やNFTといったデジタル資産の保管、トランザクションの署名、DAppsとの連携といった機能も備えています。従来の認証方法とは異なり、ユーザーは自分の秘密鍵を自身で管理し、DAppsに対してアクセス権を付与することで、プライバシーを尊重した形でサービスを利用できます。

MetaMaskとWalletConnectは、現在最も広く利用されているWeb3ウォレット連携のためのツールであり、DApps開発者にとっては必須の知識となります。

#### 9.1.2 特徴と利点

**MetaMask:**

*   **特徴:** ブラウザ拡張機能として動作し、手軽に利用できる。イーサリアムとその互換性のあるブロックチェーン（Polygon, Binance Smart Chainなど）をサポート。
*   **利点:** 導入が容易で、初心者にも扱いやすい。多くのDAppsがMetaMaskとの連携をサポートしている。

**WalletConnect:**

*   **特徴:** ウォレットアプリとDAppsをQRコードまたはディープリンク経由で接続するプロトコル。複数のウォレットをサポート。
*   **利点:** モバイルウォレットとの連携に最適。セキュリティが高く、セッション管理が容易。

#### 9.1.3 事前準備と前提条件

*   **MetaMask:** Google Chrome, Brave, FirefoxなどのブラウザにMetaMask拡張機能をインストール。
*   **WalletConnect:** DApps側でWalletConnect SDKを導入。ユーザーはWalletConnect対応のウォレットアプリ（Trust Wallet, Ledger Liveなど）をインストール。
*   **JavaScript/TypeScriptの基本的な知識:** DApps開発で必要となります。

#### 9.1.4 基本的な使い方

**MetaMaskでの接続:**

DAppsは、`window.ethereum`オブジェクトを通してMetaMaskにアクセスします。

```javascript
// MetaMaskがインストールされているか確認
if (typeof window.ethereum !== 'undefined') {
  console.log('MetaMask is installed!');
} else {
  console.log('Please install MetaMask!');
}

// アカウントへのアクセスをリクエスト
async function connectWallet() {
  try {
    const accounts = await window.ethereum.request({ method: 'eth_requestAccounts' });
    const account = accounts[0];
    console.log('Connected account:', account);
    return account;
  } catch (error) {
    console.error(error);
  }
}

// 接続ボタンがクリックされた際に実行
document.getElementById('connectButton').addEventListener('click', connectWallet);
```

**WalletConnectでの接続:**

```javascript
import WalletConnect from "@walletconnect/client";
import QRCodeModal from "@walletconnect/qrcode-modal";

// WalletConnectクライアントを初期化
const connector = new WalletConnect({
  bridge: "https://bridge.walletconnect.org", // Required
  qrcodeModal: QRCodeModal,
});

// セッションが接続されているか確認
if (!connector.connected) {
  // ウォレット接続のリクエスト
  connector.createSession();
}

// 接続イベント
connector.on("connect", (error, payload) => {
  if (error) {
    throw error;
  }

  // Get session variables
  const { accounts, chainId } = payload.params[0];
  console.log("Connected accounts:", accounts);
  console.log("Chain ID:", chainId);
});

// トランザクションの署名リクエスト
connector.on("session_request", (error, payload) => {
  if (error) {
    throw error;
  }

  // リクエストの詳細を表示
  console.log("Session Request Payload:", payload);
});

// 切断イベント
connector.on("disconnect", (error, payload) => {
  if (error) {
    throw error;
  }

  console.log("Disconnected");
});
```

#### 9.1.5 実践的なテクニック

*   **チェーンIDの確認:** ユーザーが正しいネットワークに接続されているか確認する。
*   **エラーハンドリング:** ウォレット接続の失敗やトランザクションの拒否に対する適切なエラーハンドリングを行う。
*   **イベントリスナー:** ウォレットのアカウント変更やネットワーク変更を検知し、UIを更新する。

```javascript
window.ethereum.on('accountsChanged', (accounts) => {
  if (accounts.length > 0) {
    console.log('Account changed:', accounts[0]);
    // UIを更新する
  } else {
    console.log('Account disconnected.');
    // UIを更新する
  }
});

window.ethereum.on('chainChanged', (chainId) => {
  console.log('Chain changed:', chainId);
  // UIを更新する
});
```

#### 9.1.6 応用例とユースケース

*   **NFTマーケットプレイス:** ユーザーがNFTを購入、販売する際にウォレットを接続。
*   **DeFiアプリケーション:** ユーザーがトークンを交換したり、流動性を提供する際にウォレットを接続。
*   **DAO (Decentralized Autonomous Organization):** ユーザーが投票する際にウォレットを接続。

#### 9.1.7 トラブルシューティング

*   **MetaMaskが認識されない:** ブラウザの拡張機能が有効になっているか確認。
*   **トランザクションが失敗する:** ガス代が不足しているか、ネットワークが混雑している可能性がある。
*   **WalletConnect接続ができない:** ウォレットアプリが最新バージョンであるか、DAppsがサポートしているウォレットアプリを使用しているか確認。
*   **コンソールにエラーが出る:** エラーメッセージをよく読み、コードの誤りやライブラリのバージョンを確認。

#### 9.1.8 まとめと次のステップ

Web3ウォレットの仕組み、特にMetaMaskとWalletConnectの基本的な使い方について解説しました。これらのツールを使いこなすことで、DApps開発の幅が大きく広がります。次は、より安全で柔軟な認証方式であるEIP-4361について学びましょう。

### 9.2 認証方式 - EIP-4361 (Sign-In with Ethereum)

#### 9.2.1 概要と重要性

EIP-4361 (Sign-In with Ethereum, SIWE) は、Web3の世界でユーザーを認証するための新しい標準規格です。従来のOAuthのような中央集権的な認証システムとは異なり、ユーザーは自分のウォレットを使ってDAppsに安全にサインインできます。SIWEは、ユーザーのプライバシーを尊重し、検閲耐性を持つWeb3の精神に合致した認証方式です。

#### 9.2.2 特徴と利点

*   **非中央集権:** ユーザーは自分のウォレットでメッセージに署名するだけで認証できるため、中央集権的な認証プロバイダーに依存する必要がない。
*   **プライバシー保護:** ユーザーは自分の個人情報をDAppsに共有する必要がなく、ウォレットアドレスのみで認証できる。
*   **セキュリティ:** ユーザーの秘密鍵はウォレット内に安全に保管されており、DAppsに公開されることはない。
*   **相互運用性:** EIP-4361は標準規格であるため、異なるDApps間で同じウォレットを使って認証できる。
*   **リプレイ攻撃対策:** nonce (一度だけ使用するランダムな値) を利用することで、署名の再利用を防ぎ、セキュリティを向上させています。

#### 9.2.3 事前準備と前提条件

*   **Web3ウォレット:** MetaMask, WalletConnectなどのWeb3ウォレットが必要。
*   **EIP-4361に対応したライブラリ:** JavaScript/TypeScriptで実装する場合、`siwe`ライブラリを使用。
*   **バックエンドサーバー:** 署名を検証するためのバックエンドサーバー（Node.js, Pythonなど）が必要。

#### 9.2.4 基本的な使い方

**フロントエンド (DApp):**

1.  **nonceの生成:** サーバーからnonceを取得する。
2.  **サインインメッセージの作成:** 取得したnonceとDAppの情報を組み合わせて、EIP-4361に準拠したサインインメッセージを作成する。
3.  **メッセージへの署名:** MetaMaskなどのウォレットを使って、作成したメッセージに署名する。
4.  **署名の送信:** 署名、アドレス、メッセージをバックエンドサーバーに送信する。

```javascript
import { SiweMessage } from 'siwe';

async function signInWithEthereum() {
  // 1. nonceの取得 (サーバーから取得)
  const response = await fetch('/api/nonce');
  const { nonce } = await response.json();

  // 2. サインインメッセージの作成
  const domain = window.location.host;
  const address = await getConnectedWalletAddress(); // ユーザーのウォレットアドレスを取得
  const statement = 'Sign in with Ethereum to the app.';
  const uri = window.location.origin;
  const version = '1';
  const chainId = await getConnectedChainId(); // ユーザーが接続しているチェーンIDを取得

  const siweMessage = new SiweMessage({
    domain,
    address,
    statement,
    uri,
    version,
    chainId,
    nonce,
  });

  const message = siweMessage.prepareMessage();

  // 3. メッセージへの署名
  const signer = await getWalletSigner(); // ウォレットの署名オブジェクトを取得
  const signature = await signer.signMessage(message);

  // 4. 署名の送信 (バックエンドへ)
  const verifyResponse = await fetch('/api/verify', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      message,
      signature,
      address,
    }),
  });

  const { success } = await verifyResponse.json();

  if (success) {
    console.log('Sign-in successful!');
    // 認証成功後の処理
  } else {
    console.error('Sign-in failed.');
    // 認証失敗後の処理
  }
}
```

**バックエンド (Node.js):**

1.  **nonceの生成エンドポイント:** ランダムなnonceを生成し、クライアントに返す。
2.  **署名検証エンドポイント:** クライアントから送信された署名、アドレス、メッセージを検証する。
    *   `siwe`ライブラリを使ってメッセージを再構築し、署名が正しいか検証する。
    *   nonceが正しいか検証する (一度しか使われていないか確認)。
    *   署名されたアドレスがメッセージ内のアドレスと一致するか確認する。
3.  **認証情報の保存:** 認証に成功した場合、セッションやJWT (JSON Web Token) を使って認証情報を保存する。

```javascript
// Node.js (Express) の例
const express = require('express');
const { SiweMessage } = require('siwe');
const crypto = require('crypto'); // nonce生成のため
const app = express();
const port = 3000;

app.use(express.json());

// セッション管理 (簡易的な例)
let sessions = {};

// nonce生成API
app.get('/api/nonce', (req, res) => {
  const nonce = crypto.randomBytes(16).toString('hex'); // ランダムなnonceを生成
  res.json({ nonce });
});

// 署名検証API
app.post('/api/verify', async (req, res) => {
  const { message, signature, address } = req.body;

  try {
    // 1. SIWEメッセージの再構築
    const siweMessage = new SiweMessage(message);
    await siweMessage.verify({ signature, nonce: sessions[address] }); // sessionsからnonceを取得して検証

    // 2. 検証
    if (siweMessage.address.toLowerCase() !== address.toLowerCase()) {
      return res.status(400).json({ success: false, message: 'Invalid address.' });
    }
    // nonceの検証はsiweMessage.verify内で行われる

    // 3. 認証成功
    // セッション情報を保存
    sessions[address] = {
      address: siweMessage.address,
      expirationTime: siweMessage.expirationTime,
      // その他の必要な情報を追加
    };

    res.json({ success: true, message: 'Signature verification successful!' });
  } catch (error) {
    console.error(error);
    return res.status(400).json({ success: false, message: error.message });
  }
});

app.listen(port, () => {
  console.log(`Server listening at http://localhost:${port}`);
});
```

#### 9.2.5 実践的なテクニック

*   **nonceの安全な生成:** 推測困難なランダムなnonceを生成する。
*   **署名検証の徹底:** メッセージの改ざんやリプレイ攻撃を防ぐために、署名を厳密に検証する。
*   **セッション管理:** 認証情報を安全に管理するために、セッションやJWTを使用する。
*   **メッセージのカスタマイズ:** DAppの目的に合わせて、サインインメッセージをカスタマイズする。ただし、EIP-4361の要件を満たすように注意する。

#### 9.2.6 応用例とユースケース

*   **DAppsの認証:** ユーザーがDAppsにログインする際にSIWEを使用する。
*   **APIアクセス制御:** 署名されたメッセージをAPIリクエストに含めることで、アクセスを制御する。
*   **DID (Decentralized Identity):** SIWEをDIDの基盤として使用する。

#### 9.2.7 トラブルシューティング

*   **署名検証エラー:** メッセージの形式、署名、アドレスが正しいか確認する。nonceが一致しているか確認する。
*   **nonceの再利用:** nonceが一度しか使われていないか確認する。
*   **ウォレットが署名を拒否する:** ユーザーが署名を拒否した場合、適切なエラーメッセージを表示する。
*   **ライブラリのバージョン不整合:** 最新の`siwe`ライブラリを使用しているか確認する。

#### 9.2.8 まとめと次のステップ

EIP-4361は、Web3認証の未来を担う重要な技術です。SIWEを導入することで、DAppsはより安全でプライバシーを尊重した認証を提供できます。次は、さらに進んだ認証技術であるAccount Abstractionについて学びましょう。

### 9.3 Account Abstraction (EIP-4337)

#### 9.3.1 概要と重要性

Account Abstraction (アカウント抽象化, AA) は、イーサリアムのスマートコントラクトウォレットをより柔軟で使いやすくするための概念です。EIP-4337は、この概念を実現するための具体的な提案であり、ユーザーエクスペリエンスの大幅な向上と、新しいユースケースの創出を可能にします。従来のEOA (Externally Owned Account) とは異なり、スマートコントラクトウォレットは、より高度なセキュリティ機能や柔軟な認証方法を実装できます。

#### 9.3.2 特徴と利点

*   **柔軟な認証:** 生体認証、ソーシャルリカバリー、マルチシグなど、多様な認証方法をサポート。秘密鍵の紛失リスクを軽減し、ユーザーフレンドリーなリカバリーオプションを提供。
*   **ガス代の肩代わり:** ユーザーの代わりにガス代を肩代わりできるため、暗号資産を持たないユーザーでもDAppsを利用可能。
*   **トランザクションのバッチ処理:** 複数のトランザクションをまとめて処理することで、ガス代を削減し、効率を向上。
*   **セキュリティの向上:** スマートコントラクトウォレットは、高度なセキュリティ機能を実装できるため、EOAよりも安全性が高い。トランザクションの事前検証やリスクの高いトランザクションの自動拒否などが可能。
*   **スマートコントラクトロジックの組み込み:** 独自のロジックをウォレットに組み込むことで、自動化されたトランザクションや複雑な条件に基づくトランザクションを実行できる。
*   **ERC-20 ペイマスター:** ERC-20トークンでガス代を支払うことができるため、ETHを保有していなくてもDAppsを利用できる。

#### 9.3.3 事前準備と前提条件

*   **イーサリアムの知識:** スマートコントラクト、ガス代、トランザクションなどの基本的な知識が必要。
*   **Solidityの開発スキル:** スマートコントラクトウォレットを実装するために必要。
*   **EIP-4337に対応したライブラリ:** JavaScript/TypeScriptでDAppsを開発する場合、EIP-4337に対応したライブラリを使用。
*   **テスト環境:** ローカルのイーサリアムテストネット (Ganache, Hardhat) や、Goerliなどのテストネットを使用。

#### 9.3.4 基本的な使い方

**スマートコントラクトウォレットのデプロイ:**

Solidityで記述されたスマートコントラクトウォレットを、イーサリアムネットワークにデプロイします。EIP-4337に準拠したウォレットコントラクトを実装する必要があります。

```solidity
// Solidityのサンプルコード (EIP-4337に準拠した最小限の例)
pragma solidity ^0.8.0;

contract SimpleAccount {
    address public owner;

    constructor(address _owner) {
        owner = _owner;
    }

    function execute(address dest, uint256 value, bytes calldata func) external onlyEOAOrSelf {
        (bool success, ) = dest.call{value: value}(func);
        require(success, "Transaction failed");
    }

    modifier onlyEOAOrSelf() {
        require(msg.sender == tx.origin || msg.sender == address(this), "Only EOA or Self");
        _;
    }

    // 署名検証関数 (簡略化)
    function isValidSignature(bytes32 hash, bytes memory signature) public view returns (bytes4) {
        address signer = ecrecover(hash, signature);
        if (signer == owner) {
            return this.isValidSignature.selector;
        } else {
            return bytes4(0);
        }
    }
}
```

**UserOperationの作成:**

DAppsは、`UserOperation`という構造体を作成し、Bundlerに送信します。`UserOperation`には、トランザクションのペイロード、署名、ガス代などの情報が含まれます。

**Bundlerによる処理:**

Bundlerは、複数の`UserOperation`をまとめて1つのトランザクションとして実行し、Paymasterを使ってガス代を肩代わりします。

**EntryPointコントラクト:**

EntryPointコントラクトは、`UserOperation`の検証と実行を担当します。

```typescript
// Javascriptのサンプルコード
import { ethers } from 'ethers';

// UserOperationを作成する関数
async function createUserOperation(
  accountAddress: string,
  to: string,
  value: ethers.BigNumber,
  data: string,
  signer: ethers.Signer,
  entryPointAddress: string
): Promise<any> {
  const nonce = await getNonce(accountAddress, entryPointAddress);

  const callData = encodeExecute(to, value, data);

  const userOp = {
    sender: accountAddress,
    nonce: nonce,
    initCode: '0x', // アカウントを初めて利用する場合はコントラクトをデプロイするためのコードが必要。ここでは省略
    callData: callData,
    callGasLimit: ethers.BigNumber.from(100000), // 適宜調整
    verificationGasLimit: ethers.BigNumber.from(100000),
    preVerificationGas: ethers.BigNumber.from(21000),
    maxFeePerGas: ethers.BigNumber.from(1000000000), // 適宜調整
    maxPriorityFeePerGas: ethers.BigNumber.from(1000000000), // 適宜調整
    paymasterAndData: '0x', // ガス代を肩代わりする場合はPaymasterのアドレスとデータが必要。ここでは省略
    signature: '0x', // 初期値として0xを設定
  };

  // userOpに署名
  const opHash = await getOpHash(userOp, entryPointAddress, 31337); // networkIdをHardhatのものに設定
  const signature = await signer.signMessage(ethers.utils.arrayify(opHash));

  userOp.signature = signature;

  return userOp;
}

// 実行関数をエンコードする関数
function encodeExecute(to: string, value: ethers.BigNumber, data: string): string {
  const iface = new ethers.utils.Interface(['function execute(address dest, uint256 value, bytes func)']);
  return iface.encodeFunctionData('execute', [to, value, data]);
}

async function getNonce(accountAddress: string, entryPointAddress: string): Promise<ethers.BigNumber> {
    // EntryPointコントラクトからnonceを取得する
    const provider = new ethers.providers.JsonRpcProvider("http://localhost:8545");
    const entryPoint = new ethers.Contract(
        entryPointAddress,
        [ "function getNonce(address sender) external view returns (uint256)" ],
        provider
    );
    const nonce = await entryPoint.getNonce(accountAddress);
    return nonce;
}

// UserOpHashを取得する関数
async function getOpHash(op: any, entryPoint: string, chainId: number): Promise<string> {
    const abiCoder = ethers.utils.defaultAbiCoder;
    const opType = ethers.utils.keccak256(ethers.utils.toUtf8Bytes("UserOperation"));
    const packed = ethers.utils.keccak256(abiCoder.encode(
        [
            "address", "uint256", "bytes32", "bytes32", "uint256", "uint256", "uint256", "uint256", "uint256", "bytes32"
        ],
        [
            op.sender,
            op.nonce,
            ethers.utils.keccak256(op.initCode),
            ethers.utils.keccak256(op.callData),
            op.callGasLimit,
            op.verificationGasLimit,
            op.preVerificationGas,
            op.maxFeePerGas,
            op.maxPriorityFeePerGas,
            ethers.utils.keccak256(op.paymasterAndData),
        ]
    ));

    const domainSeparator = ethers.utils.keccak256(abiCoder.encode(
        [ "bytes32", "address", "uint256" ],
        [ ethers.utils.keccak256(ethers.utils.toUtf8Bytes("EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)")),
            entryPoint,
            chainId
        ]
    ));
    return ethers.utils.keccak256(ethers.utils.concat([
        ethers.utils.toUtf8Bytes("\x19\x01"),
        domainSeparator,
        packed
    ]));
}
```

#### 9.3.5 実践的なテクニック

*   **Paymasterの実装:** ERC-20トークンでガス代を肩代わりするPaymasterを実装する。
*   **ソーシャルリカバリーの実装:** 信頼できる友人や家族を使ってウォレットを復元するソーシャルリカバリー機能を実装する。
*   **トランザクションの事前検証:** トランザクションが実行される前に、そのリスクを評価し、自動的に拒否する機能を実装する。
*   **Gasless Transaction:** ユーザーがガス代を支払うことなくDAppsを利用できるようにする。
*   **カスタムロジックの組み込み:** ウォレットに独自のロジックを組み込むことで、高度な自動化を実現する。

#### 9.3.6 応用例とユースケース

*   **ゲーム:** ユーザーがガス代を気にせずにゲームをプレイできる。
*   **DeFi:** 複雑なDeFiプロトコルをより使いやすくする。
*   **エンタープライズ:** 企業向けの高度なセキュリティと柔軟な認証を提供する。
*   **DAO:** 投票プロセスを簡素化し、ガス代を削減する。

#### 9.3.7 トラブルシューティング

*   **トランザクションが失敗する:** ガス代の設定が適切であるか確認する。スマートコントラクトウォレットのロジックに誤りがないか確認する。
*   **Bundlerが`UserOperation`を受け付けない:** `UserOperation`の形式が正しいか確認する。署名が正しいか確認する。
*   **Paymasterがガス代を肩代わりしない:** Paymasterの残高が十分であるか確認する。Paymasterのロジックに誤りがないか確認する。
*   **コントラクトのデプロイに失敗する:** Solidityコンパイラのバージョンが適切であるか確認する。コントラクトにコンパイルエラーがないか確認する。

#### 9.3.8 まとめと次のステップ

Account Abstractionは、Web3のユーザーエクスペリエンスを革新する可能性を秘めた技術です。EIP-4337を理解し、活用することで、より使いやすく、安全で、柔軟なDAppsを開発できます。Account Abstractionはまだ発展途上の技術であり、今後の動向に注目していくことが重要です。
