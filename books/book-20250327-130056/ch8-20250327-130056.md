## 第 7 章：認証・認可のテスト：なりすましを防ぐための対策

オンラインサービスを利用する上で、認証・認可はセキュリティの根幹をなす重要な要素です。認証は「誰であるか」を証明し、認可は「何ができるか」を決定します。この章では、認証・認可の仕組みを理解し、潜在的な脆弱性を特定し、効果的なテスト戦略を実装することで、なりすましなどの不正アクセスからシステムを保護する方法を解説します。初心者の方にも理解できるよう、基本的な概念から実践的なテクニックまで、段階的に説明していきます。

### 認証・認可の仕組み

#### 概要と重要性

認証と認可は、システムへのアクセスを安全に管理するための二つの柱です。認証はユーザーの身元を確認し、認可は確認されたユーザーがどのリソースにアクセスできるかを制御します。これらの仕組みが脆弱であれば、攻撃者は容易になりすまし、機密情報にアクセスしたり、システムの機能を不正に操作したりすることができます。

#### 認証方式

様々な認証方式が存在し、それぞれに利点と欠点があります。

- **Basic 認証:** 最も単純な認証方式で、ユーザー名とパスワードを Base64 エンコードして HTTP ヘッダに含めます。簡単に実装できますが、暗号化されていないため、HTTPS を使用しない場合はセキュリティリスクが高まります。

  ```
  Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ=
  ```

- **Digest 認証:** Basic 認証のセキュリティを改善したもので、パスワードのハッシュ値を送ることで、パスワード自体がネットワーク上を流れるのを防ぎます。しかし、中間者攻撃には依然として脆弱です。

- **OAuth (Open Authorization):** 第三者アプリケーションに、ユーザーの認証情報を共有せずに、特定の範囲のアクセス権を委譲するための認可フレームワークです。Facebook や Google などのサービスでよく利用されています。

- **OpenID Connect:** OAuth 2.0 を拡張した認証プロトコルで、ユーザー認証に加えて、ユーザーに関する基本的な情報（名前、メールアドレスなど）を提供します。シングルサインオン（SSO）の実現に役立ちます。

#### 認可方式

ユーザーが認証された後、どのリソースにアクセスできるかを決定するための認可方式も重要です。

- **RBAC (Role-Based Access Control):** 役割に基づいてアクセス権を管理する方式です。ユーザーに直接アクセス権を付与するのではなく、役割を割り当て、役割にアクセス権を関連付けます。管理が容易で、大規模なシステムに適しています。例えば、「管理者」「編集者」「閲覧者」といった役割を定義し、それぞれに異なるアクセス権を与えることができます。

- **ABAC (Attribute-Based Access Control):** 属性に基づいてアクセス権を管理する方式です。ユーザー、リソース、環境など、様々な属性を組み合わせてアクセス制御を行います。RBAC よりも柔軟性が高く、より複雑なアクセス制御を実現できます。例えば、「特定の部署の従業員が、特定の期間中に、特定の種類のドキュメントにアクセスできる」といった条件を定義できます。

#### セッション管理

認証されたユーザーのセッションを管理する方法も重要です。

- **Cookie:** ブラウザに保存される小さなテキストファイルで、サーバーがユーザーを識別するために使用します。セッション ID を Cookie に保存することで、ユーザーがページを移動してもログイン状態を維持できます。

- **Session ID:** サーバー側で生成される一意の識別子で、ユーザーのセッション情報を管理するために使用します。セッション ID は Cookie に保存されることが一般的ですが、URL に含めることも可能です（URL リライティング）。

#### 実装例：セッション管理（Node.js + Express）

```javascript
const express = require("express");
const session = require("express-session");
const app = express();

app.use(
  session({
    secret: "your-secret-key", // セッションIDを暗号化するための秘密鍵
    resave: false, // セッションが変更されなくても保存するかどうか
    saveUninitialized: false, // 初期化されていないセッションを保存するかどうか
    cookie: { secure: false }, // HTTPSでのみCookieを送信するかどうか (本番環境ではtrueに設定)
  })
);

app.get("/login", (req, res) => {
  // ログイン処理
  if (認証成功) {
    req.session.user = { id: 123, username: "testuser" }; // セッションにユーザー情報を保存
    res.send("ログイン成功");
  } else {
    res.status(401).send("ログイン失敗");
  }
});

app.get("/profile", (req, res) => {
  if (req.session.user) {
    res.send(`ようこそ、${req.session.user.username}さん`);
  } else {
    res.status(401).send("ログインしてください");
  }
});

app.listen(3000, () => console.log("Server started on port 3000"));
```

**注意点:**

- `secret` は安全なランダムな文字列を使用してください。
- 本番環境では `cookie: { secure: true }` を設定し、HTTPS を使用してください。

### 認証の脆弱性

認証の脆弱性は、攻撃者が不正にユーザーになりすますことを可能にするため、特に危険です。

#### ブルートフォース攻撃、パスワードリスト攻撃

- **ブルートフォース攻撃:** 考えられるすべてのパスワードの組み合わせを試す攻撃です。パスワードが単純な場合や、アカウントロックアウトポリシーがない場合に成功する可能性があります。

- **パスワードリスト攻撃:** 過去に漏洩した可能性のあるパスワードリストを使用してログインを試みる攻撃です。ユーザーが複数のサービスで同じパスワードを使い回している場合に有効です。

**対策:**

- 強力なパスワードポリシーを適用する（長さ、複雑さ、文字種など）。
- アカウントロックアウトポリシーを実装する（一定回数以上ログインに失敗したらアカウントをロックする）。
- 二要素認証（MFA）を導入する。
- レート制限を実装する（一定時間内に試行できるログイン回数を制限する）。

#### パスワードリセットの脆弱性

パスワードリセット機能は、ユーザーがパスワードを忘れた場合に、パスワードを再設定できるようにするためのものですが、実装に不備があると、攻撃者が他のユーザーのパスワードをリセットできてしまう可能性があります。

**脆弱性の例:**

- リセットトークンの予測可能性：リセットトークンが単純な連番やタイムスタンプに基づいて生成されている場合、攻撃者がトークンを予測できる可能性があります。
- リセットリンクの使い回し：リセットリンクが一度しか使えないように実装されていない場合、攻撃者がユーザーのリセットリンクを盗み、パスワードをリセットできてしまう可能性があります。
- ユーザー検証の不備：パスワードリセット時に、ユーザーが本当にそのアカウントの所有者であることを確認するための検証が不十分な場合、攻撃者が別のアカウントのパスワードをリセットできてしまう可能性があります。

**対策:**

- 安全なランダムな文字列をリセットトークンとして使用する。
- リセットトークンは一度しか使えないようにする。
- パスワードリセット時に、ユーザーが本当にそのアカウントの所有者であることを確認するための検証（秘密の質問、メールアドレスの確認など）を行う。
- リセットリンクの有効期限を設定する。

#### 多要素認証 (MFA) の不備

多要素認証（MFA）は、パスワードに加えて、別の認証要素（SMS コード、認証アプリ、生体認証など）を要求することで、セキュリティを強化するものです。しかし、MFA の実装に不備があると、攻撃者が MFA を回避できてしまう可能性があります。

**脆弱性の例:**

- MFA の強制適用がない：MFA がオプションになっている場合、ユーザーが MFA を設定していなければ、攻撃者はパスワードのみでログインできてしまいます。
- SMS ベースの MFA の脆弱性：SMS コードは傍受される可能性があるため、セキュリティが低いと見なされています。
- MFA のバイパス：システムに MFA をバイパスできる脆弱性（バックドアなど）が存在する場合、攻撃者は MFA を回避できてしまいます。

**対策:**

- MFA を強制的に適用する。
- SMS ベースの MFA ではなく、より安全な認証アプリやハードウェアトークンを使用する。
- MFA をバイパスできる脆弱性がないか、定期的にセキュリティテストを実施する。
- MFA のリカバリープロセスを慎重に設計する（MFA デバイスを紛失した場合の復旧方法）。

#### OAuth/OpenID Connect の脆弱性

OAuth/OpenID Connect は、第三者アプリケーションに、ユーザーの認証情報を共有せずに、特定の範囲のアクセス権を委譲するための認可フレームワークですが、実装に不備があると、攻撃者がユーザーになりすますことができてしまう可能性があります。

**脆弱性の例:**

- リダイレクト URI の検証不備：攻撃者が制御できるリダイレクト URI に認証コードが送信される場合、攻撃者がユーザーの認証コードを盗み、ユーザーになりすますことができます。
- クライアントシークレットの漏洩：クライアントシークレットが漏洩した場合、攻撃者がそのアプリケーションになりすますことができます。
- スコープの誤用：アプリケーションが必要以上のスコープを要求している場合、攻撃者がユーザーの機密情報にアクセスできてしまう可能性があります。

**対策:**

- リダイレクト URI を厳密に検証する（許可された URI のリストを使用する）。
- クライアントシークレットを安全に保管する。
- 必要な最小限のスコープのみを要求する。
- OAuth/OpenID Connect ライブラリを最新の状態に保ち、セキュリティアップデートを適用する。
- OAuth/OpenID Connect フローを理解し、ベストプラクティスに従って実装する。

### 認可の脆弱性

認可の脆弱性は、認証されたユーザーが許可されていないリソースにアクセスしたり、操作を実行したりすることを可能にするため、非常に危険です。

#### IDOR (Insecure Direct Object Reference)

IDOR（Insecure Direct Object Reference）は、アプリケーションが内部オブジェクトを参照するために使用する ID を、ユーザーが直接操作できる場合に発生する脆弱性です。攻撃者は、ID を推測または変更することで、許可されていないリソースにアクセスしたり、操作を実行したりできます。

**例:**

- URL にユーザー ID が含まれている場合：`https://example.com/user/123`
  攻撃者は、ID を`123`から別の ID（例えば`456`）に変更することで、他のユーザーのプロフィール情報を閲覧できる可能性があります。
- データベースのプライマリキーを直接使用している場合：
  攻撃者は、API リクエストでデータベースのプライマリキーを直接操作することで、他のユーザーのデータを変更できる可能性があります。

#### 権限昇格、アクセス制御の不備

権限昇格は、攻撃者が通常よりも高い権限を取得し、システムの機能を不正に操作したり、機密情報にアクセスしたりすることを可能にする脆弱性です。

**例:**

- 管理者権限がないユーザーが、管理者権限を必要とする機能を実行できる場合。
- データベースのロールベースのアクセス制御の設定ミスにより、一般ユーザーが管理者権限で SQL を実行できる場合。

#### API エンドポイントの認可不備

API エンドポイントの認可不備は、API エンドポイントへのアクセス制御が適切に設定されていない場合に発生する脆弱性です。攻撃者は、API エンドポイントを不正に呼び出すことで、機密情報にアクセスしたり、システムの機能を不正に操作したりできます。

**例:**

- 認証されていないユーザーが、認証を必要とする API エンドポイントを呼び出すことができる場合。
- API エンドポイントが、リクエストの送信元を検証していない場合（CSRF 攻撃）。

### 実装例：IDOR 脆弱性の発見と対策

#### 異なるユーザーの情報を参照できる脆弱性

**シナリオ:**

ある SNS アプリケーションでは、ユーザーは自分の投稿を編集することができます。投稿の編集画面にアクセスするための URL は次のようになっています。

```
https://example.com/post/edit?id=123
```

ここで、`id`は投稿の ID です。アプリケーションは、ユーザーがログインしているかどうかだけを検証し、投稿の所有者がログインユーザーと一致するかどうかを検証していません。

**脆弱性の検証:**

1.  ユーザー A としてログインし、ID が 123 の投稿を作成します。
2.  ユーザー B としてログインします。
3.  ブラウザのアドレスバーで、URL を`https://example.com/post/edit?id=123`に変更してアクセスします。
4.  ユーザー B が、ユーザー A の投稿を編集できる場合、IDOR 脆弱性が存在します。

**攻撃のステップ:**

1.  攻撃者は、ターゲットユーザー（ユーザー A）の投稿 ID（123）を知る必要があります。これは、公開されている投稿や、他の脆弱性を利用して取得できる場合があります。
2.  攻撃者は、自分のアカウント（ユーザー B）でログインします。
3.  攻撃者は、ブラウザのアドレスバーで URL を`https://example.com/post/edit?id=123`に変更してアクセスします。
4.  攻撃者は、ユーザー A の投稿を編集し、悪意のあるコンテンツを挿入したり、投稿を削除したりできます。

#### 対策：アクセス制御の厳格化、オブジェクト所有権の検証

この脆弱性を修正するためには、アプリケーションは、ユーザーがリソース（この場合は投稿）にアクセスしようとするたびに、そのユーザーがそのリソースの所有者であることを検証する必要があります。

**対策の実装例 (Node.js + Express):**

```javascript
app.get("/post/edit", async (req, res) => {
  const postId = req.query.id;
  const userId = req.session.user.id; // ログインユーザーのID

  try {
    const post = await db.query("SELECT user_id FROM posts WHERE id = ?", [
      postId,
    ]);

    if (post.length === 0) {
      return res.status(404).send("投稿が見つかりません");
    }

    const postUserId = post[0].user_id;

    if (postUserId !== userId) {
      return res.status(403).send("アクセスが拒否されました");
    }

    // 投稿編集画面を表示する処理
    res.send("投稿編集画面");
  } catch (error) {
    console.error(error);
    res.status(500).send("サーバーエラー");
  }
});
```

**解説:**

1.  `req.session.user.id`からログインユーザーの ID を取得します。
2.  データベースから、指定された`postId`を持つ投稿の`user_id`を取得します。
3.  `postUserId`（投稿の所有者の ID）と`userId`（ログインユーザーの ID）を比較します。
4.  もし`postUserId`と`userId`が一致しない場合、403 Forbidden エラーを返します。
5.  もし`postUserId`と`userId`が一致する場合、投稿編集画面を表示します。

**その他の対策:**

- **オブジェクトの所有権を明確にする:** 各リソース（投稿、コメント、プロフィールなど）に、所有者を明確に定義します。
- **アクセス制御リスト (ACL) を使用する:** 各リソースに、誰がアクセスできるかを定義したアクセス制御リストを使用します。
- **ランダムな識別子を使用する:** ID を推測しにくくするために、連番ではなくランダムな文字列を ID として使用します。
- **パラメータ暗号化:** ID などのパラメータを暗号化することで、直接操作されるのを防ぎます。

### トラブルシューティング

- **認証エラーが頻発する場合:**
  - パスワードポリシーを確認し、ユーザーに強力なパスワードを設定するように促してください。
  - アカウントロックアウトポリシーを確認し、誤ったログイン試行によるロックアウトが頻発していないか確認してください。
  - サーバーのタイムゾーンが正しいか確認してください（特に OAuth/OpenID Connect を使用している場合）。
- **認可エラーが頻発する場合:**
  - アクセス制御の設定を見直し、意図しないアクセス許可がないか確認してください。
  - ロールベースのアクセス制御を使用している場合は、ユーザーに正しいロールが割り当てられているか確認してください。
  - API エンドポイントの認可設定を確認し、すべてのエンドポイントが適切に保護されているか確認してください。
- **IDOR 脆弱性が疑われる場合:**
  - すべての API エンドポイントを監査し、ユーザーが直接オブジェクト ID を操作できる箇所がないか確認してください。
  - オブジェクト所有権の検証が適切に行われているか確認してください。
  - ペネトレーションテストを実施し、IDOR 脆弱性を特定してください。

### まとめと次のステップ

この章では、認証・認可の仕組み、脆弱性、および対策について学びました。認証・認可はセキュリティの根幹をなす重要な要素であり、これらの仕組みを理解し、潜在的な脆弱性を特定し、効果的なテスト戦略を実装することで、なりすましなどの不正アクセスからシステムを保護することができます。

**次のステップ:**

- OWASP Testing Guide などのセキュリティテストに関するドキュメントを読み、より詳細なテスト手法を学びましょう。
- ペネトレーションテストを実施し、実際の攻撃をシミュレートして、システムのセキュリティを評価しましょう。
- 開発プロセスにセキュリティを組み込み、開発の初期段階からセキュリティを考慮するようにしましょう（Shift Left）。
- セキュリティに関する最新の情報を常に収集し、新たな脆弱性や攻撃手法に対応できるようにしましょう。
