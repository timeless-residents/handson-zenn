## 第 8 章：セッション管理のテスト：セッションハイジャックを防ぐ

セッション管理は Web アプリケーションセキュリティの中核を担う部分です。ユーザー認証後、ユーザーがアプリケーションを利用している間、その状態を維持するために不可欠な役割を果たします。しかし、セッション管理に脆弱性があると、セッションハイジャックなどの攻撃を受け、ユーザーアカウントが乗っ取られる危険性があります。この章では、セッション管理の仕組みを深く理解し、セッションハイジャックを防ぐためのテスト手法、具体的な対策について解説します。

### セッション管理の仕組み

#### Cookie の仕組みと属性

**概要と重要性**

Web アプリケーションはステートレスな HTTP プロトコル上で動作するため、ユーザーが複数のページを跨いで操作する際に、その状態を維持する仕組みが必要です。そこで利用されるのがセッション管理であり、その実現に重要な役割を果たすのが Cookie です。Cookie は、サーバーからクライアント（ブラウザ）に送信される小さなテキストデータであり、クライアント側に保存されます。クライアントは以降のリクエスト時に、この Cookie をサーバーに自動的に送信します。

**特徴と利点**

- **シンプルさ:** HTTP プロトコルに組み込まれており、実装が比較的簡単です。
- **永続性:** Cookie には有効期限を設定できるため、ユーザーがブラウザを閉じても、一定期間セッションを維持できます。

**基本的な使い方**

サーバーから Cookie を送信するには、HTTP レスポンスヘッダーの`Set-Cookie`を使用します。

```http
HTTP/1.1 200 OK
Content-Type: text/html
Set-Cookie: session_id=abcdef123456; Expires=Wed, 21 Oct 2024 07:28:00 GMT; Path=/; HttpOnly; Secure; SameSite=Strict
```

クライアントは、以降のリクエストで`Cookie`ヘッダーにこの Cookie を自動的に含めます。

```http
GET /profile HTTP/1.1
Host: example.com
Cookie: session_id=abcdef123456
```

**Cookie の属性**

`Set-Cookie`ヘッダーには、Cookie の動作を制御する様々な属性を指定できます。セキュリティに関わる重要な属性は以下の通りです。

- **Expires:** Cookie の有効期限を設定します。指定しない場合は、ブラウザが閉じられるまで有効なセッション Cookie となります。
- **Path:** Cookie が有効なパスを指定します。`/` を指定すると、ドメイン全体で有効になります。
- **Domain:** Cookie が有効なドメインを指定します。
- **HttpOnly:** JavaScript からの Cookie へのアクセスを禁止します。XSS 攻撃対策として非常に重要です。
- **Secure:** HTTPS 接続でのみ Cookie を送信するように指定します。中間者攻撃による Cookie の傍受を防ぎます。
- **SameSite:** Cookie の送信を同一サイトからのリクエストに限定します。CSRF 攻撃対策として有効です。`Strict`、`Lax`、`None`のいずれかを指定します。`None`を指定する場合は、`Secure`属性も必須となります。

**トラブルシューティング**

- Cookie が設定されない場合、ドメインやパスの設定が誤っている可能性があります。
- `HttpOnly`属性が設定されていない場合、XSS 攻撃の危険性があります。
- `Secure`属性が設定されていない場合、HTTP 接続で Cookie が送信され、傍受される可能性があります。
- `SameSite=None`を設定する場合は、`Secure`属性も必ず設定してください。

#### Session ID の生成と管理

**概要と重要性**

Session ID は、サーバー側で生成される一意な識別子であり、個々のユーザーセッションを区別するために使用されます。クライアントに保存された Cookie（通常は`session_id`という名前）に含まれ、サーバーはこれを使ってユーザーのセッション情報を特定します。Session ID の生成と管理は、セッションハイジャックを防ぐ上で非常に重要です。

**特徴と利点**

- **サーバー側管理:** セッション情報はサーバー側で管理されるため、クライアントに機密情報を公開する必要がありません。
- **スケーラビリティ:** ユーザー数が増えても、セッション情報を効率的に管理できます。

**基本的な使い方**

多くの Web フレームワークや言語では、セッション ID の生成と管理を自動的に行う機能が提供されています。

**PHP の例:**

```php
<?php
session_start(); // セッションを開始

if (!isset($_SESSION['user_id'])) {
    // ユーザーがログインしていない場合
    $_SESSION['user_id'] = 123; // 仮のユーザーIDを設定
}

echo "Session ID: " . session_id(); // セッションIDを表示
?>
```

**Python (Flask) の例:**

```python
from flask import Flask, session

app = Flask(__name__)
app.secret_key = 'your_secret_key' # セッションを保護するための秘密鍵

@app.route('/')
def index():
    if 'user_id' not in session:
        session['user_id'] = 123  # 仮のユーザーIDを設定
    return f"Session ID: {session.sid}"

if __name__ == '__main__':
    app.run(debug=True)
```

**実践的なテクニック**

- **Session ID のランダム性:** Session ID は十分にランダムで予測困難な値である必要があります。弱い乱数ジェネレーターを使用すると、Session ID が予測可能になり、セッションハイジャックのリスクが高まります。`/dev/urandom`などの暗号学的に安全な乱数ジェネレーターを使用することを推奨します。
- **Session ID のローテーション:** 一定時間経過後、またはユーザーの権限が変更された場合（例：ログイン後、パスワード変更後）、Session ID を再生成することを推奨します。これにより、Session ID が漏洩した場合のリスクを軽減できます。
- **セッションデータの暗号化:** セッションデータに機密情報が含まれる場合は、暗号化して保存することを推奨します。
- **セッションストレージの保護:** セッション情報を保存する場所（データベース、ファイルシステムなど）へのアクセスを制限し、不正アクセスを防ぐ必要があります。

**応用例とユースケース**

- EC サイトでのカート情報の保持
- オンラインバンキングでの取引情報の保持
- SNS でのログイン状態の維持

**トラブルシューティング**

- Session ID が毎回変わる場合、Cookie の設定が誤っているか、ブラウザが Cookie を拒否している可能性があります。
- Session ID が予測可能な場合、乱数ジェネレーターが脆弱である可能性があります。
- セッション情報が消失する場合、セッションストレージに問題がある可能性があります。

#### セッションタイムアウト、セッション固定攻撃

**概要と重要性**

セッションタイムアウトは、セッションが有効な期間を制限する仕組みです。ユーザーが一定時間操作を行わない場合、セッションを自動的に終了させることで、セッションハイジャックのリスクを軽減できます。

セッション固定攻撃は、攻撃者が用意した Session ID をユーザーに強制的に使用させる攻撃です。攻撃者はユーザーがログインした後、その Session ID を使ってアカウントを乗っ取ることができます。

**特徴と利点**

- **セッションタイムアウト:** 不正アクセスを防ぎ、リソースの浪費を抑制します。
- **セッション固定攻撃対策:** ユーザーアカウントの安全性を高めます。

**基本的な使い方**

多くの Web フレームワークや言語では、セッションタイムアウトを設定する機能が提供されています。

**PHP の例:**

```php
<?php
session_start();
// セッションの有効期限を30分に設定
ini_set('session.gc_maxlifetime', 1800);
?>
```

**Python (Flask) の例:**

```python
from flask import Flask, session, timedelta

app = Flask(__name__)
app.secret_key = 'your_secret_key'
app.permanent_session_lifetime = timedelta(minutes=30) # セッションの有効期限を30分に設定

@app.route('/')
def index():
    session.permanent = True # セッションを永続化
    if 'user_id' not in session:
        session['user_id'] = 123
    return f"Session ID: {session.sid}"

if __name__ == '__main__':
    app.run(debug=True)
```

**セッション固定攻撃の対策**

- **セッション ID の再生成:** ユーザーがログインした後、必ず Session ID を再生成します。これにより、攻撃者が用意した Session ID が無効になります。
- **セッション ID のランダム性強化:** Session ID は十分にランダムで予測困難な値である必要があります。
- **ログインページでの HTTPS の使用:** ログインページでは必ず HTTPS を使用し、中間者攻撃による Session ID の傍受を防ぎます。
- **Cookie のセキュリティ属性の設定:** `Secure`、`HttpOnly`、`SameSite`属性を適切に設定します。

**応用例とユースケース**

- オンラインバンキングでの一定時間操作がない場合の自動ログアウト
- 社内システムでのセッションタイムアウトによるセキュリティ強化

**トラブルシューティング**

- セッションが予期せずタイムアウトする場合、セッションタイムアウトの設定が短すぎる可能性があります。
- セッション固定攻撃を受ける可能性がある場合、Session ID の再生成処理が適切に行われていない可能性があります。

### セッション管理の脆弱性

#### セッションハイジャック、セッション固定攻撃

**概要と重要性**

セッションハイジャックは、攻撃者がユーザーの Session ID を不正に入手し、その Session ID を使ってユーザーになりすます攻撃です。セッション固定攻撃は、攻撃者が用意した Session ID をユーザーに強制的に使用させ、その後その Session ID を使ってユーザーになりすます攻撃です。これらの攻撃は、ユーザーアカウントの乗っ取りに繋がり、甚大な被害をもたらす可能性があります。

**セッションハイジャックの例:**

1.  攻撃者が XSS 攻撃を利用して、ユーザーの Session ID を盗み出す。
2.  攻撃者がネットワークを傍受して、ユーザーの Session ID を盗み出す。
3.  攻撃者がブルートフォースアタックで Session ID を推測する。

**セッション固定攻撃の例:**

1.  攻撃者が`http://example.com/?session_id=attackers_session_id`のような URL をユーザーに送信する。
2.  ユーザーがその URL をクリックし、攻撃者の用意した Session ID で Web サイトにアクセスする。
3.  ユーザーがログインすると、攻撃者はその Session ID を使ってユーザーになりすます。

**対策**

- **セッションハイジャック:**
  - Session ID のランダム性強化
  - Session ID のローテーション
  - HTTPS の使用
  - Cookie のセキュリティ属性の設定
  - XSS 対策
- **セッション固定攻撃:**
  - ユーザーがログインした後、必ず Session ID を再生成する。

#### Cookie のセキュリティ属性 (Secure, HttpOnly, SameSite) の設定不備

**概要と重要性**

Cookie のセキュリティ属性の設定不備は、セッションハイジャックのリスクを高めます。それぞれの属性の役割と適切な設定について理解することが重要です。

- **Secure:** HTTPS 接続でのみ Cookie を送信するように指定します。HTTP 接続で Cookie が送信されると、中間者攻撃によって傍受される可能性があります。
- **HttpOnly:** JavaScript からの Cookie へのアクセスを禁止します。XSS 攻撃によって Cookie が盗まれるのを防ぎます。
- **SameSite:** Cookie の送信を同一サイトからのリクエストに限定します。CSRF 攻撃を軽減します。

**設定不備によるリスク**

- **Secure 属性がない場合:** HTTP 接続で Cookie が送信され、中間者攻撃によって傍受される可能性があります。
- **HttpOnly 属性がない場合:** XSS 攻撃によって Cookie が盗まれ、セッションハイジャックされる可能性があります。
- **SameSite 属性がない場合、または`None`属性で`Secure`属性がない場合:** CSRF 攻撃を受ける可能性があります。

**適切な設定例**

```http
Set-Cookie: session_id=abcdef123456; Expires=Wed, 21 Oct 2024 07:28:00 GMT; Path=/; HttpOnly; Secure; SameSite=Strict
```

**テスト方法**

ブラウザの開発者ツールを使って、Cookie の設定を確認します。また、Burp Suite などのプロキシツールを使って、HTTP リクエストとレスポンスを傍受し、Cookie の設定を確認することもできます。

#### セッション ID の予測可能性、セッション ID の漏洩

**概要と重要性**

セッション ID が予測可能である場合、攻撃者はブルートフォースアタックによって Session ID を推測し、セッションハイジャックを試みることができます。また、Session ID がログファイルや URL に含まれるなどして漏洩した場合、攻撃者はその Session ID を使ってユーザーになりすますことができます。

**対策**

- **Session ID のランダム性強化:** 暗号学的に安全な乱数ジェネレーターを使用し、十分にランダムで予測困難な Session ID を生成します。
- **Session ID のローテーション:** 一定時間経過後、またはユーザーの権限が変更された場合、Session ID を再生成します。
- **ログファイルの保護:** ログファイルに Session ID が含まれないようにするか、含まれる場合はアクセス制限を厳格に設定します。
- **URL への Session ID の埋め込み回避:** Session ID を URL に埋め込むことは、セキュリティ上非常に危険です。どうしても必要な場合は、HTTPS を使用し、Session ID を暗号化するなど、適切な対策を講じる必要があります。

### 実装例：セッション固定攻撃の検証と対策

#### 攻撃者が用意した Session ID をユーザーに強制的に使用させる

**概要**

このセクションでは、セッション固定攻撃の具体的な検証方法と、その対策について解説します。実際に攻撃を再現することで、その危険性を理解し、対策の重要性を認識することができます。

**事前準備**

- 検証用の Web アプリケーション（PHP、Python (Flask)など）を用意します。
- Burp Suite などのプロキシツールをインストールします。

**検証手順**

1.  攻撃者が用意した Session ID（例：`attackers_session_id`）を Web アプリケーションに設定します。例えば、URL パラメータを使って設定できます。`http://example.com/?session_id=attackers_session_id`
2.  ユーザーがその URL にアクセスし、ログインします。
3.  ログイン後、Burp Suite を使って HTTP リクエストを傍受し、Session ID が攻撃者の用意した Session ID（`attackers_session_id`）になっていることを確認します。
4.  攻撃者が、その Session ID を使って Web アプリケーションにアクセスし、ユーザーになりすますことができることを確認します。

**コード例 (PHP): 脆弱な例**

```php
<?php
session_start();

if (isset($_GET['session_id'])) {
    session_id($_GET['session_id']); // 攻撃者が用意したSession IDを設定
}

if (!isset($_SESSION['user_id'])) {
    // ログイン処理
    if (isset($_POST['username']) && isset($_POST['password'])) {
        // 認証処理（ここでは省略）
        $_SESSION['user_id'] = 123;
        echo "ログイン成功";
    } else {
        ?>
        <form method="POST">
            Username: <input type="text" name="username"><br>
            Password: <input type="password" name="password"><br>
            <input type="submit" value="Login">
        </form>
        <?php
    }
} else {
    echo "ログイン済み (User ID: " . $_SESSION['user_id'] . ")";
}
?>
```

#### 対策：セッション ID の再生成、セッション ID のランダム性強化

**セッション ID の再生成**

ユーザーがログインした後、必ず Session ID を再生成します。これにより、攻撃者が用意した Session ID が無効になります。

**コード例 (PHP): 対策済みの例**

```php
<?php
session_start();

if (isset($_GET['session_id'])) {
    // セッションIDを直接設定するのは危険なので、無視する
    // session_id($_GET['session_id']);
}

if (!isset($_SESSION['user_id'])) {
    // ログイン処理
    if (isset($_POST['username']) && isset($_POST['password'])) {
        // 認証処理（ここでは省略）
        $_SESSION['user_id'] = 123;

        // ログイン後、Session IDを再生成
        session_regenerate_id(true);

        echo "ログイン成功";
    } else {
        ?>
        <form method="POST">
            Username: <input type="text" name="username"><br>
            Password: <input type="password" name="password"><br>
            <input type="submit" value="Login">
        </form>
        <?php
    }
} else {
    echo "ログイン済み (User ID: " . $_SESSION['user_id'] . ")";
}
?>
```

**セッション ID のランダム性強化**

Session ID は十分にランダムで予測困難な値である必要があります。PHP では、`session_regenerate_id()`関数を使用する際に、`true`を指定することで、古いセッションデータを削除し、新しい Session ID を生成することができます。また、`session.entropy_file`と`session.entropy_length`を設定することで、乱数のソースを強化することができます。

**トラブルシューティング**

- Session ID が再生成されない場合、`session_regenerate_id()`関数が正しく呼び出されているか確認してください。
- Session ID のランダム性が低い場合、`session.entropy_file`と`session.entropy_length`の設定を確認してください。

**まとめと次のステップ**

この章では、セッション管理の仕組みと脆弱性、そしてセッションハイジャックを防ぐための具体的な対策について解説しました。セッション管理は Web アプリケーションセキュリティの重要な部分であり、常に最新の脅威に対応できるよう、知識をアップデートし続ける必要があります。

次のステップとしては、OWASP のセッション管理に関するガイドラインなどを参考に、より深くセッション管理について学習することをおすすめします。また、ペネトレーションテストなどを実施し、実際の Web アプリケーションのセッション管理の脆弱性を評価することも有効です。

**実践的なテクニック (応用)**

- **セッション固定攻撃対策の自動テスト:** Web アプリケーションのテストフレームワーク (Selenium, Cypress など) を使用して、セッション固定攻撃に対する対策が正しく実装されていることを自動的に検証するテストを構築することができます。
- **WAF (Web Application Firewall) の導入:** WAF を導入することで、セッションハイジャックやセッション固定攻撃などの攻撃を検知し、防御することができます。

この章で学んだ知識を活かし、安全な Web アプリケーションを開発・運用していきましょう。
