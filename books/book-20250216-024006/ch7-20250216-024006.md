## 第7章：APIのモニタリングとロギング

APIのモニタリングとロギングは、APIの安定稼働、パフォーマンス改善、セキュリティ確保のために不可欠な要素です。 適切なモニタリングとロギングを実装することで、問題発生時の迅速な特定と解決、将来的な問題の予防、そしてAPIの利用状況の把握が可能になります。 この章では、可用性、パフォーマンス、エラー率のモニタリング、アクセスログ、エラーログ、監査ログのロギング、そして分散トレーシングについて、実践的なアプローチで解説します。

### 7.1 APIモニタリング：可用性、パフォーマンス、エラー率

#### 概要と重要性

APIモニタリングは、APIが正常に動作しているか、パフォーマンスは十分か、エラーは発生していないかを継続的に監視することです。 これは、APIの品質を維持し、ユーザーに安定したサービスを提供するために極めて重要です。 問題を早期に検知し、対応することで、より大きな障害やユーザーへの影響を未然に防ぐことができます。

#### 特徴と利点

* **可用性の監視:** APIが正常に動作しているかを監視し、ダウンタイムを最小限に抑えます。
* **パフォーマンスの監視:** APIの応答時間やスループットを監視し、パフォーマンスボトルネックを特定します。
* **エラー率の監視:** APIで発生するエラーの数を監視し、問題の原因を特定します。
* **リアルタイムな情報:** ダッシュボードやアラートを通じて、APIの状態をリアルタイムに把握できます。
* **データに基づいた意思決定:** モニタリングデータに基づいて、APIの改善策を検討できます。

#### 事前準備と前提条件

* 監視対象のAPIが構築済みであること。
* モニタリングツールをインストールおよび設定するための権限があること。
* モニタリングツールがAPIにアクセスできるネットワーク環境であること。

#### モニタリングツールの選定：Prometheus, Grafana, Datadog, New Relic

APIモニタリングツールは数多く存在しますが、ここでは代表的な4つのツール、Prometheus、Grafana、Datadog、New Relicについて解説します。

* **Prometheus:** オープンソースのモニタリングシステムで、時系列データを収集し、柔軟なクエリ言語 (PromQL) を使用して分析できます。アラート機能も充実しています。
    * **利点:** 無料で利用可能、柔軟性が高い、Kubernetesとの連携が容易。
    * **欠点:** 設定がやや複雑、データの長期保存には別途ストレージが必要。

* **Grafana:** 様々なデータソース（Prometheus, Datadog, Elasticsearchなど）からデータを取得し、美しいダッシュボードを作成できるツールです。
    * **利点:** 直感的なインターフェース、豊富なグラフの種類、多くのデータソースに対応。
    * **欠点:** データ収集機能は持たないため、Prometheusなどのデータソースと組み合わせて使用する必要がある。

* **Datadog:** SaaS型のモニタリングプラットフォームで、インフラ、アプリケーション、ログなど、様々なデータを一元的に監視できます。
    * **利点:** 設定が簡単、豊富な機能、SaaS型のため運用負荷が低い。
    * **欠点:** 有料、Prometheusに比べて柔軟性が低い場合がある。

* **New Relic:** SaaS型のAPM (Application Performance Monitoring) ツールで、アプリケーションのパフォーマンスを詳細に分析できます。
    * **利点:** アプリケーションのパフォーマンス分析に特化、詳細なトランザクショントレース、SaaS型のため運用負荷が低い。
    * **欠点:** 有料、インフラ監視には別途ツールが必要となる場合がある。

**ツールの選び方:**

* **予算:** 無料のツール (Prometheus, Grafana) を使うか、有料のSaaS型ツール (Datadog, New Relic) を使うか。
* **必要な機能:** インフラ監視、アプリケーション監視、ログ分析など、必要な機能を洗い出す。
* **技術スキル:** 設定や運用に必要な技術スキルを考慮する。
* **インフラ環境:** Kubernetes環境で利用するかどうか。

#### 基本的な使い方 (PrometheusとGrafanaの例)

1. **Prometheusの設定:**

   ```yaml
   # prometheus.yml
   global:
     scrape_interval:     15s
     evaluation_interval: 15s

   scrape_configs:
     - job_name: 'api'
       metrics_path: '/metrics'  # APIのエンドポイントに合わせて変更
       static_configs:
         - targets: ['api.example.com:8080'] # 監視対象のAPIサーバーのアドレスとポート
   ```

   APIサーバーは、Prometheusが監視できる `/metrics` エンドポイントを公開する必要があります。 このエンドポイントは、APIのメトリクス（例：リクエスト数、エラー数、応答時間）をPrometheusが解釈できる形式で提供します。

2. **APIサーバーの実装 (Python Flaskの例):**

   ```python
   from flask import Flask, request, jsonify
   from prometheus_client import make_wsgi_app, Counter, Histogram
   from werkzeug.serving import run_simple
   import time

   app = Flask(__name__)

   # メトリクスの定義
   REQUEST_COUNT = Counter('api_requests_total', 'Total number of API requests')
   REQUEST_LATENCY = Histogram('api_request_latency_seconds', 'API request latency in seconds')

   @app.route('/api/data')
   def get_data():
       start = time.time()
       REQUEST_COUNT.inc() # リクエスト数をカウント
       # 何らかの処理 (ここではsleepで遅延をシミュレート)
       time.sleep(0.1)
       end = time.time()
       REQUEST_LATENCY.observe(end - start) # レイテンシを記録
       return jsonify({'message': 'Hello, world!'})

   @app.route('/metrics')
   def metrics():
       from prometheus_client import generate_latest
       return generate_latest()

   if __name__ == '__main__':
       # Prometheusのエンドポイントを公開
       from werkzeug.wsgi import DispatcherMiddleware
       app_metrics = DispatcherMiddleware(app, {'/metrics': make_wsgi_app()})
       run_simple('localhost', 8000, app_metrics)
   ```

   このコードでは、`prometheus_client` ライブラリを使用して、リクエスト数とレイテンシをPrometheus形式で公開しています。 `/metrics` エンドポイントにアクセスすると、これらのメトリクスがテキスト形式で表示されます。

3. **Grafanaの設定:**

   * Grafanaを起動し、Prometheusをデータソースとして追加します。
   * ダッシュボードを作成し、Prometheusから取得したメトリクスを表示します。
   * 例：リクエスト数をグラフで表示、平均応答時間をグラフで表示、エラー率をグラフで表示。

#### アラート設定：異常検知時の通知 (Prometheus Alertmanagerの例)

Prometheus Alertmanagerは、Prometheusから送信されるアラートを処理し、メール、Slack、PagerDutyなどのチャネルを通じて通知を行うツールです。

1. **Alertmanagerの設定:**

   ```yaml
   # alertmanager.yml
   global:
     smtp_smarthost: 'localhost:25'
     smtp_from: 'alertmanager@example.com'
     smtp_require_tls: false

   route:
     group_wait:      30s
     group_interval:  5m
     repeat_interval: 1h
     receiver: 'email-notifications'

   receivers:
   - name: 'email-notifications'
     email_configs:
     - to: 'your_email@example.com'
   ```

   この設定では、メールで通知するように設定しています。 `smtp_smarthost` や `smtp_from` は、環境に合わせて変更する必要があります。

2. **Prometheusのアラートルール:**

   ```yaml
   # alert.rules.yml
   groups:
   - name: ExampleAlerts
     rules:
     - alert: APIHighLatency
       expr: api_request_latency_seconds_sum / api_request_latency_seconds_count > 0.5 # 平均レイテンシが0.5秒を超えた場合
       for: 1m  # 1分間継続した場合
       labels:
         severity: warning
       annotations:
         summary: "API latency is high"
         description: "API latency is above 0.5 seconds for more than 1 minute."
   ```

   このルールでは、APIの平均レイテンシが0.5秒を超えた場合にアラートを発行します。 `expr` はPromQLの式で、アラートの条件を定義します。 `for` は、アラートを発行するまでの継続時間を定義します。 `labels` はアラートの重要度などを定義します。 `annotations` はアラートの説明などを定義します。

3. **Prometheusの設定変更:**

   ```yaml
   # prometheus.yml
   rule_files:
     - "alert.rules.yml"

   alerting:
     alertmanagers:
       - static_configs:
           - targets:
             - localhost:9093 # Alertmanagerのアドレスとポート
   ```

   Prometheusにアラートルールを読み込ませ、Alertmanagerにアラートを送信するように設定します。

#### 実践的なテクニック

* **SLI/SLOに基づいたモニタリング:** サービスレベル指標 (SLI) とサービスレベル目標 (SLO) を定義し、それらに基づいてモニタリングを設定します。
    * **例:**
        * **SLI:** APIのリクエスト成功率
        * **SLO:** リクエスト成功率99.9%以上
* **ベースラインの確立:** 通常時のパフォーマンスデータを収集し、ベースラインを確立します。 これにより、異常値を検出しやすくなります。
* **合成監視:** 実際のユーザーの行動をシミュレートするテストを実行し、APIの可用性とパフォーマンスを監視します。
* **相関分析:** 複数のメトリクスを組み合わせて分析することで、問題の原因を特定しやすくします。

#### 応用例とユースケース

* **eコマースサイト:** 注文APIの可用性とパフォーマンスを監視し、注文処理の遅延やエラーを早期に検知します。
* **金融サービス:** 取引APIのセキュリティログを監視し、不正アクセスを検知します。
* **ソーシャルメディア:** 投稿APIのパフォーマンスを監視し、高負荷時のパフォーマンス劣化を防ぎます。

#### トラブルシューティング

* **メトリクスが表示されない:**
    * APIサーバーがメトリクスエンドポイントを公開しているか確認します。
    * Prometheusの設定が正しいか確認します。
    * PrometheusがAPIサーバーにアクセスできるか確認します。
* **アラートが通知されない:**
    * Alertmanagerの設定が正しいか確認します。
    * Prometheusのアラートルールが正しいか確認します。
    * Alertmanagerがメールサーバーに接続できるか確認します。

#### まとめと次のステップ

APIモニタリングは、APIの品質を維持し、ユーザーに安定したサービスを提供するために不可欠です。 Prometheus、Grafana、Datadog、New Relicなどのツールを活用し、可用性、パフォーマンス、エラー率を継続的に監視しましょう。 次のステップとして、SLI/SLOに基づいたモニタリング、ベースラインの確立、合成監視、相関分析など、より高度なモニタリング手法を検討することをおすすめします。

### 7.2 ロギング：アクセスログ、エラーログ、監査ログ

#### 概要と重要性

ロギングは、APIの動作に関する情報を記録することです。 アクセスログ、エラーログ、監査ログなど、様々な種類のログを記録することで、APIの利用状況の把握、問題の原因特定、セキュリティインシデントの追跡が可能になります。

#### 特徴と利点

* **問題の特定:** エラーログを分析することで、APIで発生している問題の原因を特定できます。
* **利用状況の把握:** アクセスログを分析することで、APIの利用状況を把握できます。
* **セキュリティ監査:** 監査ログを分析することで、APIに対する不正アクセスを検知できます。
* **コンプライアンス対応:** 法規制や業界標準に準拠するために、必要なログを記録できます。
* **デバッグの効率化:** ログを分析することで、デバッグ作業を効率化できます。

#### 事前準備と前提条件

* ロギング対象のAPIが構築済みであること。
* ログ収集ツールをインストールおよび設定するための権限があること。
* ログ収集ツールがAPIサーバーにアクセスできるネットワーク環境であること。
* ログを保存するためのストレージを用意すること。

#### ロギングの種類

* **アクセスログ:** APIへのリクエストに関する情報を記録します。
    * **例:** リクエスト日時、クライアントIPアドレス、リクエストURI、HTTPメソッド、ステータスコード、レスポンス時間。
* **エラーログ:** APIで発生したエラーに関する情報を記録します。
    * **例:** エラー日時、エラーメッセージ、スタックトレース。
* **監査ログ:** APIに対するセキュリティ関連の操作に関する情報を記録します。
    * **例:** ユーザー認証、認可、データ変更。

#### ログ収集ツールの選定：Fluentd, Logstash

ログ収集ツールは、APIサーバーからログを収集し、集約、変換、転送する役割を果たします。ここでは代表的な2つのツール、FluentdとLogstashについて解説します。

* **Fluentd:** オープンソースのデータコレクターで、様々なデータソースからログを収集し、柔軟なプラグインアーキテクチャを通じて変換および転送できます。
    * **利点:** 軽量、柔軟性が高い、豊富なプラグイン。
    * **欠点:** 設定がやや複雑、Logstashに比べてコミュニティが小さい。

* **Logstash:** オープンソースのデータ処理パイプラインで、様々なデータソースからログを収集し、フィルタリング、変換、エンリッチメントを行い、様々な出力先に転送できます。
    * **利点:** 設定が比較的簡単、豊富なフィルタリング機能、大規模なコミュニティ。
    * **欠点:** Fluentdに比べてリソース消費量が多い。

**ツールの選び方:**

* **パフォーマンス:** 大量のログを処理する必要がある場合は、Fluentdが適しています。
* **機能:** 複雑なフィルタリングや変換が必要な場合は、Logstashが適しています。
* **使いやすさ:** 設定の容易さを重視する場合は、Logstashが適しています。
* **プラグイン:** 必要なプラグインが利用可能かどうかを確認します。

#### 基本的な使い方 (Fluentdの例)

1. **Fluentdのインストール:**

   ```bash
   # 例：Ubuntu
   curl -fsSL https://toolbelt.treasuredata.com/sh/install-ubuntu-trusty.sh | sh
   ```

2. **Fluentdの設定:**

   ```conf
   # fluentd.conf
   <source>
     @type tail
     path /var/log/api.log  # 監視対象のAPIログファイル
     pos_file /var/log/api.log.pos # 読み込み位置を記録するファイル
     tag api.access # タグ
     <parse>
       @type json  # ログ形式がJSONの場合
     </parse>
   </source>

   <match api.access>
     @type elasticsearch
     host localhost  # Elasticsearchのアドレス
     port 9200 # Elasticsearchのポート
     index_name api_access_log # インデックス名
     type_name access_log
     include_tag_key true # タグをログに含める
     tag_key @log_name
   </match>
   ```

   この設定では、`/var/log/api.log` ファイルを監視し、JSON形式のログを読み込み、`api.access` タグを付与し、Elasticsearchに転送します。

3. **APIサーバーの設定:**

   APIサーバーで、ログをJSON形式でファイルに書き出すように設定します。 例：Python Flaskの場合

   ```python
   import logging
   import json
   from flask import Flask, request

   app = Flask(__name__)

   # ロガーの設定
   logger = logging.getLogger('api')
   logger.setLevel(logging.INFO)
   handler = logging.FileHandler('/var/log/api.log') # ログファイル
   formatter = logging.Formatter('%(asctime)s - %(levelname)s - %(message)s')
   handler.setFormatter(formatter)
   logger.addHandler(handler)

   @app.route('/api/data')
   def get_data():
       data = {'message': 'Hello, world!'}
       log_data = {
           'path': request.path,
           'method': request.method,
           'data': data
       }
       logger.info(json.dumps(log_data)) # JSON形式でログ出力
       return data

   if __name__ == '__main__':
       app.run(debug=True)
   ```

#### ログ分析：Elasticsearch, Kibana

ログ分析ツールは、収集したログを検索、分析、可視化する役割を果たします。ここでは代表的なツール、ElasticsearchとKibanaについて解説します。

* **Elasticsearch:** オープンソースの分散型検索エンジンで、大量のデータを高速に検索および分析できます。
    * **利点:** 高速な検索、柔軟なスキーマ、スケーラビリティ。
    * **欠点:** 設定がやや複雑、リソース消費量が多い。

* **Kibana:** Elasticsearchのデータを可視化するためのツールで、ダッシュボードを作成したり、ログを検索したりできます。
    * **利点:** 直感的なインターフェース、豊富なグラフの種類、Elasticsearchとの連携が容易。
    * **欠点:** Elasticsearchと組み合わせて使用する必要がある。

**基本的な使い方 (ElasticsearchとKibanaの例)**

1. **ElasticsearchとKibanaのインストール:**
    * 各自の環境に合わせてインストールします。 (Dockerを利用するのが簡単です。)

2. **Kibanaの設定:**
    * Kibanaを起動し、Elasticsearchをデータソースとして追加します。
    * インデックスパターンを作成し、Elasticsearchのインデックスを指定します。
    * ダッシュボードを作成し、ログを可視化します。
    * 例：アクセス数推移、エラー数推移、リクエストURI別のアクセス数。

#### 実践的なテクニック

* **構造化ロギング:** ログを構造化された形式 (JSONなど) で記録することで、ログの分析が容易になります。
* **ログレベルの適切な設定:** DEBUG、INFO、WARNING、ERROR、CRITICALなどのログレベルを適切に設定することで、必要な情報だけを記録できます。
* **ログローテーション:** ログファイルが肥大化するのを防ぐために、ログローテーションを設定します。
* **ログの暗号化:** 機密情報を含むログは、暗号化して保存します。

#### 応用例とユースケース

* **セキュリティインシデントの調査:** 監査ログを分析することで、不正アクセスやデータ漏洩などのセキュリティインシデントを調査できます。
* **APIの利用状況分析:** アクセスログを分析することで、APIの利用状況を把握し、利用状況に基づいた改善策を検討できます。
* **問題の早期発見:** エラーログを分析することで、APIで発生している問題を早期に発見し、対応できます。

#### トラブルシューティング

* **ログが収集されない:**
    * ログ収集ツールの設定が正しいか確認します。
    * APIサーバーがログを出力しているか確認します。
    * ログ収集ツールがAPIサーバーにアクセスできるか確認します。
* **ログが分析できない:**
    * Elasticsearchの設定が正しいか確認します。
    * Kibanaの設定が正しいか確認します。
    * ログの形式が分析ツールでサポートされているか確認します。

#### まとめと次のステップ

ロギングは、APIの利用状況の把握、問題の原因特定、セキュリティインシデントの追跡に不可欠です。 Fluentd、Logstash、Elasticsearch、Kibanaなどのツールを活用し、アクセスログ、エラーログ、監査ログを適切に記録し、分析しましょう。 次のステップとして、構造化ロギング、ログレベルの適切な設定、ログローテーション、ログの暗号化など、より高度なロギング手法を検討することをおすすめします。

### 7.3 分散トレーシング：リクエスト追跡、ボトルネック特定

#### 概要と重要性

分散トレーシングは、マイクロサービスアーキテクチャのような分散システムにおいて、リクエストが複数のサービスを通過する際の処理の流れを追跡する技術です。 これにより、リクエストの遅延やエラーの原因となっているサービスを特定し、パフォーマンスボトルネックを解消できます。

#### 特徴と利点

* **リクエストの追跡:** リクエストが複数のサービスを通過する際の処理の流れを可視化できます。
* **ボトルネックの特定:** リクエストの遅延やエラーの原因となっているサービスを特定できます。
* **パフォーマンスの最適化:** パフォーマンスボトルネックを解消することで、API全体のパフォーマンスを向上させることができます。
* **デバッグの効率化:** 分散システムにおける問題のデバッグを効率化できます。
* **依存関係の把握:** サービス間の依存関係を把握できます。

#### 事前準備と前提条件

* 分散トレーシング対象のマイクロサービスが構築済みであること。
* 分散トレーシングツールをインストールおよび設定するための権限があること。
* 分散トレーシングツールがマイクロサービスにアクセスできるネットワーク環境であること。
* 各マイクロサービスにトレーシングライブラリを組み込むための知識があること。

#### 分散トレーシングツールの選定：Jaeger, Zipkin

分散トレーシングツールは、トレースデータを収集、保存、可視化する役割を果たします。ここでは代表的な2つのツール、JaegerとZipkinについて解説します。

* **Jaeger:** Uberによって開発されたオープンソースの分散トレーシングシステムで、OpenTracing APIをサポートしています。
    * **利点:** オープンソース、クラウドネイティブ環境に適している、OpenTracing APIをサポート。
    * **欠点:** 設定がやや複雑、Zipkinに比べてコミュニティが小さい。

* **Zipkin:** Twitterによって開発されたオープンソースの分散トレーシングシステムで、様々なプログラミング言語とフレームワークをサポートしています。
    * **利点:** オープンソース、様々なプログラミング言語とフレームワークをサポート、設定が比較的簡単。
    * **欠点:** Jaegerに比べてクラウドネイティブ環境への対応が弱い。

**ツールの選び方:**

* **技術スキル:** 設定や運用に必要な技術スキルを考慮する。
* **インフラ環境:** クラウドネイティブ環境で利用するかどうか。
* **サポート:** 利用しているプログラミング言語やフレームワークがサポートされているか確認する。
* **OpenTracing/OpenTelemetry:** OpenTracingまたはOpenTelemetryとの互換性を確認する。

#### トレーシングの実装：OpenTelemetry

OpenTelemetryは、分散トレーシング、メトリクス、ログを収集するためのオープンソースのオブザーバビリティフレームワークです。 これにより、ベンダーに依存しない形でトレーシングを実装できます。

1. **OpenTelemetry SDKのインストール:**

   各マイクロサービスに、OpenTelemetry SDKをインストールします。 例：Pythonの場合

   ```bash
   pip install opentelemetry-api opentelemetry-sdk opentelemetry-exporter-jaeger # Jaegerにエクスポートする場合
   ```

2. **トレーシングの実装:**

   各マイクロサービスで、トレーシングを実装します。 例：Python Flaskの場合

   ```python
   from flask import Flask, request
   from opentelemetry import trace
   from opentelemetry.sdk.trace import TracerProvider
   from opentelemetry.sdk.trace.export import BatchSpanProcessor
   from opentelemetry.exporter.jaeger.thrift import JaegerExporter
   from opentelemetry.sdk.resources import SERVICE_NAME, Resource

   app = Flask(__name__)

   # サービス名を設定
   resource = Resource(attributes={
       SERVICE_NAME: "api-service" # サービス名
   })

   # Jaegerエクスポーターの設定
   jaeger_exporter = JaegerExporter(
       collector_endpoint="http://localhost:14268/api/traces", # Jaegerコレクターのエンドポイント
       service_name="api-service",
   )

   # TracerProviderの設定
   tracer_provider = TracerProvider(resource=resource)
   processor = BatchSpanProcessor(jaeger_exporter)
   tracer_provider.add_span_processor(processor)
   trace.set_tracer_provider(tracer_provider)

   # Tracerの取得
   tracer = trace.get_tracer(__name__)

   @app.route('/api/data')
   def get_data():
       with tracer.start_as_current_span("get_data_handler"): # Span開始
           data = {'message': 'Hello, world!'}
           return data

   if __name__ == '__main__':
       app.run(debug=True)
   ```

   このコードでは、OpenTelemetry SDKを使用して、`get_data_handler` というSpanを作成し、リクエストの処理を追跡します。

3. **Jaegerの設定:**

   Jaegerを起動し、トレースデータを受信するように設定します。 (Dockerを利用するのが簡単です。)

4. **リクエストの実行:**

   APIにリクエストを実行すると、JaegerのUIでトレースデータを確認できます。

#### 実践的なテクニック

* **Spanの適切な設定:** 各サービス、各関数、各処理ブロックに対して、Spanを適切に設定することで、詳細なトレースデータを得られます。
* **Context Propagation:** サービス間でリクエストIDなどのコンテキスト情報を伝播させることで、リクエスト全体を追跡できます。 OpenTelemetryは自動的にContext Propagationを行います。
* **タグの利用:** Spanにタグを追加することで、Spanに関する追加情報を記録できます。
* **ログとの連携:** トレーシングとロギングを連携させることで、問題の特定を容易にします。

#### 応用例とユースケース

* **マイクロサービスアーキテクチャ:** 複数のマイクロサービスが連携するシステムにおいて、リクエストの遅延やエラーの原因となっているサービスを特定します。
* **クラウドネイティブアプリケーション:** クラウド環境で動作するアプリケーションにおいて、パフォーマンスボトルネックを解消します。
* **分散データベース:** 分散データベースにおいて、クエリの実行時間を分析し、パフォーマンスを最適化します。

#### トラブルシューティング

* **トレースデータが表示されない:**
    * OpenTelemetry SDKの設定が正しいか確認します。
    * Jaegerの設定が正しいか確認します。
    * 各マイクロサービスがSpanを生成しているか確認します。
    * 各マイクロサービスがJaegerにアクセスできるか確認します。
* **Context Propagationがうまくいかない:**
    * OpenTelemetryの設定が正しいか確認します。
    * 各マイクロサービスがContext情報を伝播させているか確認します。

#### まとめと次のステップ

分散トレーシングは、マイクロサービスアーキテクチャのような分散システムにおいて、リクエストの遅延やエラーの原因となっているサービスを特定し、パフォーマンスボトルネックを解消するために不可欠です。 Jaeger、Zipkin、OpenTelemetryなどのツールを活用し、分散トレーシングを実装しましょう。 次のステップとして、Spanの適切な設定、Context Propagation、タグの利用、ログとの連携など、より高度な分散トレーシング手法を検討することをおすすめします。 そして、得られたトレースデータを元に、パフォーマンス改善を実施し、モニタリングを継続することで、APIの品質を継続的に向上させることができます。
