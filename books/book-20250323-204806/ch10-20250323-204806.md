## 第 10 章：モニタリングとロギング - 運用状況を可視化する

システム運用において、モニタリングとロギングは不可欠な要素です。これらは、システムの健全性を維持し、問題発生時の迅速な対応を可能にするための羅針盤となります。もし、モニタリングやロギングを怠ると、システムがブラックボックス化し、小さな問題が深刻な障害に発展するまで気づかない、なんて事態にもなりかねません。

本章では、ログ収集基盤の構築、モニタリングツールの活用、そして APM の導入という 3 つの柱を中心に、システム運用におけるモニタリングとロギングの実践的な手法を解説します。初心者の方でも理解できるように、段階的な説明と具体的なコード例を交えながら、より深く、そして実践的な知識を習得できるように構成しました。

### ログ収集基盤の構築

#### 概要と重要性

ログは、システムやアプリケーションの活動記録です。エラー、警告、情報など、様々な種類のメッセージが記録されており、これらを分析することで、システムの挙動を理解し、問題を特定し、パフォーマンスを改善することができます。ログ収集基盤は、これらのログを一元的に収集、処理、保存するための仕組みです。

ログ収集基盤がない場合、各サーバーやアプリケーションから個別にログを確認する必要があり、非常に手間がかかります。また、ログが分散していると、問題の根本原因を特定するのが困難になります。ログ収集基盤を構築することで、これらの課題を解決し、効率的なシステム運用を実現することができます。

#### 特徴と利点

- **一元管理:** 全てのログを一箇所に集約することで、検索や分析が容易になります。
- **リアルタイム分析:** ログをリアルタイムで分析することで、問題発生時に迅速に対応できます。
- **長期保存:** ログを長期的に保存することで、過去の障害分析や監査に役立てることができます。
- **可視化:** ログデータを可視化することで、システムの状況を直感的に把握できます。
- **セキュリティ:** ログをセキュリティ対策に活用することで、不正アクセスや情報漏洩を検知できます。

#### 事前準備と前提条件

- **サーバーまたは仮想マシン:** ログ収集基盤を構築するためのサーバーが必要です。
- **ストレージ:** ログを保存するためのストレージが必要です。容量は、ログの量と保存期間によって異なります。
- **ログ収集ツール:** Fluentd、Logstash、Filebeat など、ログを収集するためのツールが必要です。
- **ログ処理ツール:** Elasticsearch、Splunk など、ログを処理するためのツールが必要です。
- **可視化ツール:** Kibana、Grafana など、ログデータを可視化するためのツールが必要です。

ここでは、広く利用されている Fluentd を例に、設定例を記述していきます。

#### 基本的な使い方

Fluentd は、ログ収集、変換、転送を行うためのオープンソースのデータコレクタです。様々な入力プラグインと出力プラグインが用意されており、様々なデータソースからログを収集し、様々なデータストアにログを転送することができます。

**インストール**

```bash
# Debian/Ubuntu
curl -fsSL https://packages.treasuredata.com/GPG-KEY-td-agent | gpg --dearmor | sudo tee /etc/apt/trusted.gpg.d/treasuredata.gpg > /dev/null
echo "deb https://packages.treasuredata.com/4/debian/$(lsb_release -cs) $(lsb_release -cs) main" | sudo tee /etc/apt/sources.list.d/treasuredata.list
sudo apt-get update
sudo apt-get install td-agent

# CentOS/RHEL
curl -fsSL https://packages.treasuredata.com/GPG-KEY-td-agent | gpg --dearmor | sudo tee /etc/pki/rpm-gpg/RPM-GPG-KEY-td-agent
sudo yum install -y https://packages.treasuredata.com/4/redhat/$(rpm -E %{rhel})/x86_64/td-agent-4.4.0-1.el$(rpm -E %{rhel}).x86_64.rpm
```

**設定ファイルの作成 (`/etc/td-agent/td-agent.conf`)**

```conf
<source>
  @type tail
  path /var/log/syslog
  pos_file /var/log/td-agent/syslog.pos
  tag system.syslog
  <parse>
    @type syslog
  </parse>
</source>

<match system.**>
  @type file
  path /var/log/td-agent/system
  <format>
    @type json
  </format>
</match>
```

この設定例では、`/var/log/syslog` からログを収集し、JSON 形式で `/var/log/td-agent/system` に保存しています。

**Fluentd の起動と停止**

```bash
sudo systemctl start td-agent
sudo systemctl stop td-agent
sudo systemctl restart td-agent
```

#### 実践的なテクニック

- **フィルタリング:** 不要なログを除外することで、ログの量を削減し、分析効率を向上させることができます。

  ```conf
  <filter system.**>
    @type grep
    exclude message "unnecessary log"
  </filter>
  ```

- **変換:** ログデータを整形することで、分析しやすい形式に変換することができます。

  ```conf
  <filter system.**>
    @type record_transformer
    <record>
      hostname ${hostname}
    </record>
  </filter>
  ```

- **集計:** ログデータを集計することで、システムの全体像を把握しやすくなります。

  ```conf
  <match system.**>
    @type aggregate
    period 60
    output_tag aggregated.system
    <aggregation>
      worker_count 2
      calculate count
    </aggregation>
  </match>
  ```

#### 応用例とユースケース

- **セキュリティ監視:** ログを分析することで、不正アクセスや異常なアクティビティを検知することができます。例えば、特定の IP アドレスからのログイン試行回数が多い場合、ブルートフォースアタックの可能性を疑うことができます。
- **パフォーマンス分析:** ログを分析することで、システムのボトルネックを特定し、パフォーマンスを改善することができます。例えば、特定の API エンドポイントの応答時間が長い場合、その API の処理ロジックを改善する必要があります。
- **障害分析:** ログを分析することで、障害の原因を特定し、再発防止策を講じることができます。例えば、エラーログを分析することで、特定のコードパスでエラーが発生していることを特定できます。

#### トラブルシューティング

- **Fluentd が起動しない:** 設定ファイルに構文エラーがある可能性があります。`td-agent -c /etc/td-agent/td-agent.conf -t` コマンドで設定ファイルを検証することができます。
- **ログが収集されない:** 入力プラグインの設定が間違っている可能性があります。`path` パラメータが正しいか、パーミッションは適切かなどを確認してください。
- **ログが処理されない:** フィルタや出力プラグインの設定が間違っている可能性があります。設定ファイルを見直してください。

#### まとめと次のステップ

ログ収集基盤の構築は、システム運用において非常に重要な要素です。Fluentd をはじめとするツールを活用することで、ログを一元的に収集、処理、保存し、システムの状況を可視化することができます。次のステップとして、収集したログを分析し、システムの改善に役立てる方法を学ぶことをお勧めします。

### モニタリングツールの活用

#### 概要と重要性

モニタリングツールは、システムやアプリケーションのパフォーマンス、リソース使用率、エラー率などのメトリクスを収集し、可視化するためのツールです。これらのメトリクスを監視することで、システムの異常を早期に検知し、問題発生時の迅速な対応を可能にします。

モニタリングツールがない場合、システムの状態を把握するのが難しく、問題が発生しても気づくのが遅れる可能性があります。また、問題の原因を特定するのも困難になり、復旧に時間がかかることがあります。モニタリングツールを活用することで、これらの課題を解決し、システムの安定稼働を支援します。

#### 特徴と利点

- **リアルタイム監視:** システムの状態をリアルタイムで監視できます。
- **異常検知:** 設定した閾値を超えた場合にアラートを発行し、異常を早期に検知できます。
- **可視化:** グラフやダッシュボードでメトリクスを可視化し、システムの状況を直感的に把握できます。
- **自動化:** アラートに基づいて自動的に対応する仕組みを構築できます。
- **分析:** 過去のデータを分析することで、トレンドを把握し、将来の予測に役立てることができます。

#### 事前準備と前提条件

- **サーバーまたは仮想マシン:** モニタリングツールをインストールするためのサーバーが必要です。
- **モニタリング対象のシステム:** 監視対象となるシステムが必要です。
- **エージェント:** モニタリング対象のシステムにエージェントをインストールする必要がある場合があります。
- **モニタリングツール:** Prometheus、Grafana、Zabbix など、モニタリングツールが必要です。

ここでは、Prometheus と Grafana を組み合わせて利用する例を紹介します。Prometheus はメトリクス収集に、Grafana は可視化に特化したツールです。

#### 基本的な使い方

**Prometheus のインストール**

```bash
# Linux (例: Ubuntu)
wget https://github.com/prometheus/prometheus/releases/download/v2.45.0/prometheus-2.45.0.linux-amd64.tar.gz
tar xvfz prometheus-2.45.0.linux-amd64.tar.gz
cd prometheus-2.45.0.linux-amd64
sudo mv prometheus /usr/local/bin/
sudo mv promtool /usr/local/bin/
sudo mv prometheus.yml /etc/prometheus/
```

**Prometheus の設定ファイル (`/etc/prometheus/prometheus.yml`)**

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: "prometheus"
    static_configs:
      - targets: ["localhost:9090"]
```

この設定例では、Prometheus 自身を監視するように設定しています。

**Prometheus の起動**

```bash
sudo ./prometheus --config.file=/etc/prometheus/prometheus.yml
```

**Grafana のインストール**

```bash
# Debian/Ubuntu
sudo apt-get install -y apt-transport-https software-properties-common wget
wget -q -O - https://apt.grafana.com/gpg.key | sudo apt-key add -
echo "deb https://apt.grafana.com stable main" | sudo tee /etc/apt/sources.list.d/grafana.list
sudo apt-get update
sudo apt-get install grafana

# CentOS/RHEL
sudo yum install -y wget
wget -q -O - https://packages.grafana.com/gpg.key | sudo apt-key add -
echo '[grafana]
name=grafana
baseurl=https://packages.grafana.com/oss/rpm
repo_gpgcheck=1
enabled=1
gpgcheck=1
gpgkey=https://packages.grafana.com/gpg.key
sslverify=1
sslcacert=/etc/pki/tls/certs/ca-bundle.crt' | sudo tee /etc/yum.repos.d/grafana.repo
sudo yum install grafana
```

**Grafana の起動**

```bash
sudo systemctl start grafana-server
sudo systemctl enable grafana-server
```

**Grafana で Prometheus をデータソースとして設定**

1.  Grafana にブラウザでアクセスします (デフォルト: `http://localhost:3000`)。
2.  データソースを追加します。
3.  データソースの種類として Prometheus を選択します。
4.  Prometheus の URL を入力します (例: `http://localhost:9090`)。

#### 実践的なテクニック

- **アラート設定:** 重要なメトリクスに対してアラートを設定することで、異常発生時に迅速に対応できます。例えば、CPU 使用率が 80%を超えた場合、アラートを発行するように設定することができます。
- **ダッシュボード作成:** ダッシュボードを作成することで、システムの状況を可視化し、異常を早期に検知できます。例えば、CPU 使用率、メモリ使用率、ディスク I/O などのメトリクスを一つのダッシュボードに表示することができます。
- **カスタムメトリクス:** 標準的なメトリクスに加えて、アプリケーション固有のカスタムメトリクスを収集することで、より詳細な分析が可能になります。Prometheus の場合、Exporter を利用してカスタムメトリクスを公開することができます。

#### 応用例とユースケース

- **Web アプリケーションの監視:** Web アプリケーションのレスポンスタイム、エラー率、リクエスト数などのメトリクスを監視することで、パフォーマンスの問題や障害を検知することができます。
- **データベースの監視:** データベースの CPU 使用率、メモリ使用率、ディスク I/O、クエリ実行時間などのメトリクスを監視することで、パフォーマンスの問題や障害を検知することができます。
- **インフラストラクチャの監視:** サーバーの CPU 使用率、メモリ使用率、ディスク I/O、ネットワークトラフィックなどのメトリクスを監視することで、リソース不足や障害を検知することができます。

#### トラブルシューティング

- **Prometheus がメトリクスを収集しない:** 設定ファイルに誤りがある可能性があります。`prometheus --config.file=/etc/prometheus/prometheus.yml --web.listen-address=:9090` コマンドで Prometheus を実行し、ログを確認してください。
- **Grafana が Prometheus に接続できない:** Prometheus の URL が間違っている可能性があります。Grafana の設定を見直してください。
- **アラートが発行されない:** アラートの閾値が適切でない可能性があります。アラートの設定を見直してください。

#### まとめと次のステップ

モニタリングツールの活用は、システムの安定稼働に不可欠です。Prometheus と Grafana をはじめとするツールを活用することで、システムの状態をリアルタイムで監視し、異常を早期に検知することができます。次のステップとして、APM (Application Performance Monitoring) を導入し、アプリケーション内部のパフォーマンスを詳細に分析する方法を学ぶことをお勧めします。

### APM (Application Performance Monitoring) の導入

#### 概要と重要性

APM (Application Performance Monitoring) は、アプリケーションのパフォーマンスを監視し、ボトルネックを特定するためのツールです。トランザクションの追跡、コードレベルでのパフォーマンス分析、エラーの追跡など、詳細な情報を提供します。

従来のモニタリングツールは、サーバーやインフラストラクチャのメトリクスを監視することに重点を置いていましたが、APM はアプリケーション内部のパフォーマンスに焦点を当てています。APM を導入することで、アプリケーションのパフォーマンス問題を迅速に特定し、解決することができます。

#### 特徴と利点

- **トランザクション追跡:** リクエストがアプリケーション内でどのように処理されるかを追跡できます。
- **コードレベルの分析:** パフォーマンスボトルネックとなっているコードを特定できます。
- **エラー追跡:** エラーが発生した場所と原因を特定できます。
- **サービス依存関係の可視化:** アプリケーションが依存するサービスとの関係を可視化できます。
- **エンドユーザエクスペリエンスの監視:** エンドユーザの体感速度を監視できます。

#### 事前準備と前提条件

- **APM ツール:** New Relic、Datadog APM、Dynatrace、Elastic APM など、APM ツールが必要です。
- **アプリケーション:** 監視対象となるアプリケーションが必要です。
- **APM エージェント:** アプリケーションに APM エージェントをインストールする必要があります。
- **プログラミング言語のサポート:** APM ツールが使用しているプログラミング言語をサポートしている必要があります。

ここでは、Elastic APM を例に説明します。Elastic APM は、Elasticsearch、Kibana と連携して利用できる APM ツールです。

#### 基本的な使い方

**Elasticsearch と Kibana のインストール**

Elastic APM は、Elasticsearch にデータを保存し、Kibana で可視化します。まずは Elasticsearch と Kibana をインストールする必要があります。Elasticsearch と Kibana のインストール手順は、Elastic の公式サイトを参照してください。

**Elastic APM エージェントのインストール**

Elastic APM エージェントは、監視対象のアプリケーションにインストールする必要があります。各プログラミング言語に対応したエージェントが提供されています。

例えば、Node.js アプリケーションの場合、次の手順で Elastic APM エージェントをインストールします。

```bash
npm install elastic-apm-node --save
```

**アプリケーションのコードに APM エージェントを組み込む**

```javascript
// アプリケーションの最初に以下のコードを追加
const apm = require("elastic-apm-node").start({
  serviceName: "my-node-app",
  secretToken: "YOUR_SECRET_TOKEN",
  serverUrl: "http://localhost:8200", // APM Server の URL
  environment: "production",
});

// Express アプリケーションの例
const express = require("express");
const app = express();

app.get("/", (req, res) => {
  res.send("Hello World!");
});

app.listen(3000, () => {
  console.log("Example app listening on port 3000!");
});
```

`serviceName`、`secretToken`、`serverUrl` は、ご自身の環境に合わせて変更してください。

**Elastic APM Server のインストールと起動**

Elastic APM Server は、APM エージェントから送られてくるデータを受け取り、Elasticsearch に保存します。Elastic APM Server のインストール手順は、Elastic の公式サイトを参照してください。

**Kibana で APM データを可視化**

Kibana で APM データを可視化するには、APM アプリケーションをインストールする必要があります。Kibana のメニューから APM アプリケーションを選択し、インストールしてください。

#### 実践的なテクニック

- **カスタムトランザクション:** 標準的なトランザクションに加えて、アプリケーション固有のカスタムトランザクションを定義することで、より詳細な分析が可能になります。
- **カスタムエラー:** エラーが発生した場合に、エラーメッセージだけでなく、カスタムのコンテキスト情報を追加することで、エラーの原因を特定しやすくなります。
- **分散トレーシング:** 複数のサービスにまたがるリクエストを追跡することで、マイクロサービスアーキテクチャにおけるパフォーマンスボトルネックを特定できます。

#### 応用例とユースケース

- **Web アプリケーションのパフォーマンス改善:** Web アプリケーションのレスポンスタイムが遅い場合、APM を利用してボトルネックとなっているコードを特定し、パフォーマンスを改善することができます。
- **マイクロサービスアーキテクチャの監視:** マイクロサービスアーキテクチャでは、複数のサービスが連携して動作するため、APM を利用してサービス間の依存関係を可視化し、パフォーマンス問題を特定することができます。
- **本番環境での障害対応:** 本番環境で障害が発生した場合、APM を利用してエラーの原因を特定し、迅速に復旧することができます。

#### トラブルシューティング

- **APM エージェントがデータを送信しない:** 設定ファイルに誤りがある可能性があります。`serviceName`、`secretToken`、`serverUrl` が正しいか確認してください。
- **Kibana で APM データが表示されない:** Elasticsearch にデータが保存されていない可能性があります。APM Server のログを確認してください。
- **パフォーマンスオーバーヘッド:** APM エージェントがアプリケーションのパフォーマンスに影響を与える可能性があります。APM エージェントの設定を調整し、パフォーマンスオーバーヘッドを最小限に抑えるようにしてください。

#### まとめと次のステップ

APM の導入は、アプリケーションのパフォーマンスを改善するために非常に有効です。Elastic APM をはじめとするツールを活用することで、アプリケーション内部のパフォーマンスを詳細に分析し、ボトルネックを特定することができます。次のステップとして、IaC(Infrastructure as Code)の導入を検討し、インフラの構築からアプリケーションのデプロイまでの一連の流れを自動化することをお勧めします。
