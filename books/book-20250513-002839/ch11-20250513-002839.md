## 第 11 章：アップグレード対策：スムーズな移行計画とテスト

ServiceNow は進化を続け、定期的に新しい機能や改善がリリースされます。アップグレードは、最新の機能を利用できるだけでなく、パフォーマンス向上やセキュリティ強化にも繋がります。しかし、計画なしにアップグレードを行うと、既存の機能が壊れたり、カスタマイズが正常に動作しなくなる可能性があります。

この章では、ServiceNow のアップグレードを成功させるための実践的な方法を解説します。アップグレード前の準備、テスト戦略、アップグレード後の対応について、具体的な手順とベストプラクティスを学び、スムーズな移行を実現しましょう。

### 11.1 アップグレード前の準備：互換性チェック、カスタマイズの評価

**1. 概要と重要性**

アップグレード前の準備は、成功の鍵を握ります。互換性チェックとカスタマイズの評価を徹底することで、アップグレード後の問題を未然に防ぎ、ダウンタイムを最小限に抑えることができます。この段階を怠ると、アップグレード後に想定外のトラブルが発生し、ビジネスに大きな影響を与える可能性があります。

**2. 特徴と利点**

- **互換性チェック:** アップグレード後のシステムが既存の機能と互換性があることを確認します。
- **カスタマイズの評価:** カスタマイズがアップグレードによって影響を受けるかどうかを特定し、必要な修正を計画します。
- **リスク軽減:** アップグレードに伴う潜在的なリスクを特定し、対策を講じることができます。
- **計画的なアップグレード:** アップグレードのスケジュール、リソース、および必要な手順を事前に計画できます。

**3. 事前準備と前提条件**

- **ServiceNow インスタンスへのアクセス:** アップグレードを計画するインスタンスへの管理者権限が必要です。
- **ServiceNow の知識:** ServiceNow の基本的な操作、カスタマイズ、およびリリースノートに関する知識が必要です。
- **テスト環境:** アップグレードをテストするための独立したテスト環境が必要です。
- **アップグレード計画ドキュメント:** アップグレードの目的、範囲、スケジュール、および責任者を記述したドキュメントを用意します。

**4. 基本的な使い方**

#### 4.1 ServiceNow リリースノートの確認

**4.1.1 リリースノートの重要性**

ServiceNow のリリースノートは、新機能、改善点、変更点、および既知の問題に関する重要な情報源です。アップグレード前にリリースノートを注意深く確認することで、アップグレード後の影響を理解し、適切な対策を講じることができます。

**4.1.2 リリースノートの確認方法**

ServiceNow のドキュメントサイト (例えば、[無効な URL を削除しました]) にアクセスし、アップグレード先のバージョンに対応するリリースノートを確認します。リリースノートには、以下の情報が含まれています。

- **新機能:** 追加された新機能とその使用方法。
- **機能の変更:** 既存の機能の変更点とその影響。
- **非推奨機能:** 今後サポートされなくなる機能とその代替手段。
- **既知の問題:** アップグレード後に発生する可能性のある問題とその回避策。
- **互換性情報:** アップグレードに関する互換性の問題に関する情報。

**4.1.3 リリースノートの活用例**

例えば、リリースノートに特定のスクリプト API の動作変更が記載されている場合、その API を使用しているスクリプトを特定し、必要に応じて修正する必要があります。

#### 4.2 Upgrade Center の利用

**4.2.1 Upgrade Center の概要**

Upgrade Center は、ServiceNow が提供するアップグレード支援ツールです。Upgrade Center を利用することで、アップグレードの準備状況を評価し、必要なタスクを特定し、アップグレードプロセスを管理することができます。

**4.2.2 Upgrade Center へのアクセス**

ServiceNow インスタンスにログインし、ナビゲーターで "Upgrade Center" を検索してアクセスします。

**4.2.3 Upgrade Center の機能**

- **アップグレード準備の評価:** システムのアップグレード準備状況を評価し、必要な改善点を特定します。
- **アップグレードタスクの管理:** アップグレードに必要なタスクをリストアップし、進捗状況を追跡します。
- **互換性チェック:** インスタンス内のカスタマイズとアプリケーションが、アップグレード後のバージョンと互換性があるかどうかをチェックします。
- **リスク評価:** アップグレードに伴う潜在的なリスクを評価し、対策を提案します。
- **アップグレードスケジュールの管理:** アップグレードのスケジュールを設定し、関係者に通知します。

**4.2.4 Upgrade Center の利用例**

Upgrade Center を実行し、推奨されるタスク（例えば、特定のスクリプトの修正、アプリケーションの更新など）を完了させることで、アップグレードのリスクを軽減できます。

```javascript
// サンプルスクリプト：非推奨APIの使用例
// Upgrade Centerで検出される可能性のある例
var ga = new GlideAggregate("incident");
ga.addAggregate("COUNT");
ga.query();
if (ga.next()) {
  var count = ga.getAggregate("COUNT");
  gs.info("Incident Count: " + count);
}
```

このスクリプトを、より新しい API（例えば、GlideRecord の`getRowCount()`）を使用するように書き換える必要があります。

#### 4.3 カスタマイズの影響範囲の特定

**4.3.1 カスタマイズの重要性**

ServiceNow インスタンスは、ビジネスニーズに合わせてカスタマイズされることが一般的です。しかし、アップグレード時にこれらのカスタマイズが問題を引き起こす可能性があります。カスタマイズの影響範囲を特定し、アップグレード後の動作を検証することは非常に重要です。

**4.3.2 カスタマイズの特定方法**

- **カスタムスクリプトの検索:** スクリプトインクルード、クライアントスクリプト、ビジネスルール、UI アクションなどのカスタムスクリプトを検索します。
  - ナビゲーターで "Scripts - Background" を検索し、以下のクエリを実行して、特定のテキストを含むスクリプトを検索できます。
  ```javascript
  var gr = new GlideRecord("sys_script");
  gr.addQuery("script", "CONTAINS", "deprecatedFunction()"); // 非推奨関数を含むスクリプトを検索
  gr.query();
  while (gr.next()) {
    gs.info("Script Name: " + gr.name + ", Script: " + gr.script);
  }
  ```
- **カスタムテーブルとフィールドの特定:** カスタムテーブルとフィールドのリストを作成し、それらがどのように使用されているかを調べます。
- **カスタムアプリケーションの特定:** ServiceNow ストアで提供されていないカスタムアプリケーションを特定します。
- **インスタンスのドキュメント化:** カスタマイズに関するドキュメントを作成し、アップグレード後の検証に使用します。

**4.3.3 カスタマイズの影響範囲の評価**

カスタマイズがアップグレードによって影響を受けるかどうかを評価します。以下の点を考慮してください。

- **非推奨の API の使用:** カスタムスクリプトが非推奨の API を使用している場合、修正が必要です。
- **変更された機能への依存:** カスタマイズが変更された機能に依存している場合、修正が必要です。
- **パフォーマンスへの影響:** カスタマイズがパフォーマンスに悪影響を与える可能性がある場合、最適化が必要です。

**5. 実践的なテクニック**

- **ServiceNow のベストプラクティスに従う:** カスタマイズは、ServiceNow のベストプラクティスに従って行うようにします。
- **バージョン管理システムの使用:** カスタマイズをバージョン管理システム (Git など) で管理し、変更履歴を追跡します。
- **コードレビューの実施:** カスタムスクリプトをコードレビューし、品質を確保します。
- **定期的なテスト:** カスタマイズを定期的にテストし、問題がないことを確認します。

**6. 応用例とユースケース**

- **顧客ポータルのカスタマイズ:** 顧客ポータルのルックアンドフィールをカスタマイズしている場合、アップグレード後にデザインが崩れていないか確認する必要があります。
- **インテグレーション:** 外部システムとのインテグレーションがある場合、アップグレード後にインテグレーションが正常に動作することを確認する必要があります。
- **承認ワークフロー:** カスタムの承認ワークフローがある場合、アップグレード後にワークフローが正常に動作することを確認する必要があります。

**7. トラブルシューティング**

- **アップグレード後にカスタマイズが動作しない:** カスタムスクリプトのエラーログを確認し、問題を特定します。
- **アップグレード後にパフォーマンスが低下する:** パフォーマンス監視ツールを使用して、ボトルネックを特定します。
- **アップグレード後に予期しないエラーが発生する:** ServiceNow のログファイルを確認し、エラーの原因を特定します。

**8. まとめと次のステップ**

アップグレード前の準備は、成功への第一歩です。リリースノートの確認、Upgrade Center の利用、カスタマイズの影響範囲の特定を徹底し、アップグレード計画を立てましょう。次のステップでは、テスト環境の構築とテストケースの作成について解説します。

### 11.2 アップグレードテスト：テスト環境の構築とテストケースの作成

**1. 概要と重要性**

アップグレードテストは、本番環境へのアップグレード前に、新しいバージョンが既存の機能と互換性があることを確認するために不可欠です。テスト環境を構築し、網羅的なテストケースを作成することで、潜在的な問題を早期に発見し、本番環境への影響を最小限に抑えることができます。

**2. 特徴と利点**

- **リスク軽減:** 本番環境での障害を未然に防ぎます。
- **互換性の確認:** アップグレード後のシステムが既存の機能と互換性があることを確認します。
- **カスタマイズの検証:** カスタマイズがアップグレードによって影響を受けないことを確認します。
- **ユーザーエクスペリエンスの向上:** アップグレード後のシステムの使いやすさを確認します。
- **ダウンタイムの削減:** 問題を事前に解決することで、本番環境のダウンタイムを最小限に抑えます。

**3. 事前準備と前提条件**

- **テスト環境:** 本番環境と同一の構成を持つテスト環境が必要です。
- **テストデータ:** 本番環境のデータを匿名化または削減したテストデータが必要です。
- **テスト計画:** テストの目的、範囲、およびスケジュールを記述した計画が必要です。
- **テストケース:** テストする機能と期待される結果を記述したテストケースが必要です。
- **テスト担当者:** テストを実行し、結果を記録する担当者が必要です。

**4. 基本的な使い方**

#### 4.1 テスト環境の構築とデータ移行

**4.1.1 テスト環境の構築**

本番環境と同一の構成を持つテスト環境を構築します。以下の点を考慮してください。

- **ハードウェア:** 本番環境と同じハードウェア構成を使用します。
- **ソフトウェア:** 本番環境と同じソフトウェアバージョンを使用します。
- **ネットワーク:** 本番環境と同じネットワーク構成を使用します。
- **データベース:** 本番環境と同じデータベース構成を使用します。

テスト環境は、本番環境から完全に隔離されている必要があります。

**4.1.2 データ移行**

本番環境のデータをテスト環境に移行します。以下の点を考慮してください。

- **データの匿名化:** 個人情報や機密情報を含むデータを匿名化または削減します。

  - 例えば、`sys_user` テーブルの `email` フィールドをランダムなメールアドレスに置き換えるスクリプトを作成します。

  ```javascript
  var gr = new GlideRecord("sys_user");
  gr.query();
  while (gr.next()) {
    gr.email = "test" + Math.floor(Math.random() * 1000) + "@example.com";
    gr.update();
  }
  ```

- **データの削減:** テストに必要なデータのみを移行し、データベースのサイズを削減します。
- **データの整合性:** 移行後のデータが整合性があり、使用可能な状態であることを確認します。
- **バックアップ:** データ移行前に、テスト環境のデータベースをバックアップします。

**4.2 テストケースの作成と実行**

**4.2.1 テストケースの作成**

テストケースは、テストする機能、入力データ、期待される結果、およびテスト手順を記述したドキュメントです。網羅的なテストケースを作成することで、潜在的な問題を早期に発見できます。

- **機能テスト:** 各機能が正常に動作することを確認します。
- **統合テスト:** 複数の機能が連携して動作することを確認します。
- **回帰テスト:** 既存の機能がアップグレードによって壊れていないことを確認します。
- **パフォーマンステスト:** システムのパフォーマンスが許容範囲内であることを確認します。
- **ユーザビリティテスト:** システムの使いやすさを確認します。

テストケースの例：

| テストケース ID | 機能             | 説明                                             | 入力データ                                                         | 期待される結果                                           | 手順                                                                                                           | 合否        |
| --------------- | ---------------- | ------------------------------------------------ | ------------------------------------------------------------------ | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ----------- |
| TC-001          | インシデント作成 | ユーザーがインシデントを作成できることを確認する | ユーザー：John Doe、カテゴリ：ハードウェア、説明：プリンターが故障 | インシデントが正常に作成され、ステータスが「新規」になる | 1. ユーザーとしてログインする。2. インシデント作成フォームを開く。3. 必要なフィールドを入力する。4. 送信する。 | 合格/不合格 |

**4.2.2 テストケースの実行**

作成したテストケースを実行し、結果を記録します。テスト担当者は、テスト手順に従ってシステムを操作し、期待される結果が得られるかどうかを確認します。

- **テスト環境へのログイン:** テスト担当者は、テスト環境にログインします。
- **テストケースの実行:** テスト担当者は、テストケースの手順に従ってシステムを操作します。
- **結果の記録:** テスト担当者は、テスト結果を記録します。期待される結果が得られた場合は「合格」、得られなかった場合は「不合格」と記録します。
- **問題の報告:** テスト担当者は、不合格となったテストケースに関する問題を報告します。

**4.3 回帰テストの自動化**

**4.3.1 回帰テストの自動化の重要性**

回帰テストは、アップグレード後に既存の機能が壊れていないことを確認するために不可欠です。しかし、手動で回帰テストを行うのは時間と労力がかかります。回帰テストを自動化することで、効率的にテストを実施し、品質を向上させることができます。

**4.3.2 Automated Test Framework (ATF) の利用**

ServiceNow には、回帰テストを自動化するための Automated Test Framework (ATF) が用意されています。ATF を利用することで、GUI ベースのテストを作成し、実行することができます。

**4.3.3 ATF の基本的な使い方**

1.  **テストスイートの作成:** テストスイートは、関連するテストケースをまとめたものです。
2.  **テストケースの作成:** テストケースは、テストする機能と期待される結果を定義します。
3.  **テストステップの追加:** テストステップは、テストケースを実行するための具体的な手順を定義します。
4.  **テストの実行:** テストスイートまたはテストケースを実行し、結果を確認します。

**4.3.4 ATF の活用例**

- **ログインテスト:** ユーザーが正常にログインできることを確認するテストを自動化します。
- **インシデント作成テスト:** ユーザーがインシデントを正常に作成できることを確認するテストを自動化します。
- **承認ワークフローテスト:** 承認ワークフローが正常に動作することを確認するテストを自動化します。

```javascript
// ATFのサンプル：インシデント作成のテストステップ
// 1. UIアクション "New" をクリック
// 2. フィールド "Caller" に値を入力
// 3. フィールド "Short description" に値を入力
// 4. UIアクション "Submit" をクリック
// 5. 作成されたインシデントのレコードが正しいことを検証
```

**5. 実践的なテクニック**

- **リスクベーステスト:** リスクの高い機能に焦点を当ててテストします。
- **探索的テスト:** 計画されたテストケース以外にも、自由にシステムを操作して潜在的な問題を発見します。
- **ユーザー受け入れテスト (UAT):** エンドユーザーにシステムをテストしてもらい、フィードバックを収集します。

**6. 応用例とユースケース**

- **大規模な ServiceNow インスタンスのアップグレード:** 大規模な ServiceNow インスタンスをアップグレードする場合、テスト環境を構築し、網羅的なテストケースを作成することが特に重要です。
- **複雑なカスタマイズを含む ServiceNow インスタンスのアップグレード:** 複雑なカスタマイズを含む ServiceNow インスタンスをアップグレードする場合、カスタマイズがアップグレードによって影響を受けないことを確認するために、特に注意が必要です。
- **規制要件を満たす必要がある ServiceNow インスタンスのアップグレード:** 規制要件を満たす必要がある ServiceNow インスタンスをアップグレードする場合、コンプライアンスを維持するために、厳格なテストを実施する必要があります。

**7. トラブルシューティング**

- **テスト環境の構築に失敗する:** ハードウェア、ソフトウェア、またはネットワーク構成を確認します。
- **データ移行に失敗する:** データ変換ルールを確認します。
- **テストケースの実行に失敗する:** テスト手順を確認します。
- **ATF のテストが失敗する:** テストステップの設定を確認します。

**8. まとめと次のステップ**

アップグレードテストは、本番環境へのアップグレードを成功させるために不可欠です。テスト環境を構築し、網羅的なテストケースを作成し、回帰テストを自動化することで、潜在的な問題を早期に発見し、本番環境への影響を最小限に抑えることができます。次のステップでは、アップグレード後の対応について解説します。

### 11.3 アップグレード後の対応：問題点の修正とパフォーマンスチェック

**1. 概要と重要性**

アップグレード後の対応は、アップグレードプロセスを完了させ、システムが安定して動作することを保証するために重要です。アップグレード後の動作確認、問題点の特定と修正、およびパフォーマンスの監視と最適化を行うことで、システムの信頼性とパフォーマンスを維持することができます。

**2. 特徴と利点**

- **安定性の確保:** アップグレード後のシステムが安定して動作することを確認します。
- **問題の早期解決:** 問題点を早期に特定し、修正することで、ダウンタイムを最小限に抑えます。
- **パフォーマンスの最適化:** システムのパフォーマンスを監視し、最適化することで、ユーザーエクスペリエンスを向上させます。
- **ビジネス継続性の確保:** アップグレード後のシステムがビジネス継続性をサポートすることを確認します。
- **ユーザー満足度の向上:** アップグレード後のシステムがユーザーのニーズを満たすことを確認します。

**3. 事前準備と前提条件**

- **アップグレード後のシステムへのアクセス:** アップグレード後のシステムへの管理者権限が必要です。
- **監視ツール:** システムのパフォーマンスを監視するためのツールが必要です。
- **問題管理プロセス:** 問題を特定、報告、および解決するためのプロセスが必要です。
- **コミュニケーション計画:** アップグレード後の状況を関係者に伝えるための計画が必要です。

**4. 基本的な使い方**

#### 4.1 アップグレード後の動作確認

**4.1.1 動作確認の重要性**

アップグレード後の動作確認は、システムが正常に動作することを確認するために不可欠です。以下の点に注意して確認作業を進めます。

- **主要機能の確認:** 主要な機能が正常に動作することを確認します。例えば、インシデントの作成、変更、解決、承認ワークフロー、サービスカタログ、レポートなど。
- **カスタマイズの確認:** カスタマイズがアップグレードによって影響を受けていないことを確認します。例えば、カスタムスクリプト、UI アクション、ビジネスルール、UI ポリシーなど。
- **インテグレーションの確認:** 外部システムとのインテグレーションが正常に動作することを確認します。例えば、REST API、SOAP API、JDBC など。
- **セキュリティの確認:** セキュリティ設定が正しく構成されていることを確認します。例えば、アクセス制御リスト (ACL)、認証、認可など。
- **ユーザーインターフェースの確認:** ユーザーインターフェースが正しく表示されることを確認します。例えば、フォーム、リスト、ダッシュボードなど。

**4.1.2 動作確認の手順**

1.  **チェックリストの作成:** 確認する項目をリストアップしたチェックリストを作成します。
2.  **テストの実施:** チェックリストに従って、システムを操作し、期待される結果が得られるかどうかを確認します。
3.  **結果の記録:** テスト結果をチェックリストに記録します。
4.  **問題の報告:** 問題が見つかった場合は、詳細な情報を記録し、問題管理プロセスに従って報告します。

**4.2 問題点の特定と修正**

**4.2.1 問題点の特定**

動作確認中に問題が見つかった場合は、詳細な情報を収集し、問題の原因を特定します。以下の情報を収集します。

- **問題の説明:** 問題の具体的な内容を説明します。
- **発生条件:** 問題が発生する条件を説明します。
- **エラーメッセージ:** エラーメッセージが表示された場合は、その内容を記録します。
- **ログ:** 関連するログファイルを確認し、エラーの原因を特定します。
- **ユーザー:** 問題を報告したユーザーの情報を記録します。

**4.2.2 問題点の修正**

問題の原因を特定したら、修正作業を行います。以下の点に注意してください。

- **バックアップ:** 修正作業を行う前に、システムのバックアップを作成します。
- **テスト環境での修正:** 本番環境で直接修正するのではなく、テスト環境で修正作業を行い、問題が解決されることを確認します。
- **変更履歴の記録:** 修正内容を記録し、変更履歴を管理します。
- **影響範囲の確認:** 修正が他の機能に影響を与えないことを確認します。
- **本番環境への反映:** テスト環境で修正が完了したら、本番環境に修正を反映します。

**4.3 パフォーマンスの監視と最適化**

**4.3.1 パフォーマンス監視の重要性**

アップグレード後にシステムのパフォーマンスが低下する可能性があります。パフォーマンスを監視し、ボトルネックを特定し、最適化することで、ユーザーエクスペリエンスを向上させることができます。

**4.3.2 パフォーマンス監視の手法**

- **ServiceNow Performance Analytics:** ServiceNow Performance Analytics を使用すると、システムのパフォーマンスをリアルタイムで監視し、傾向を分析することができます。
- **ServiceNow System Logs:** ServiceNow System Logs を確認し、エラーや警告メッセージを分析します。
- **Transaction Timing:** Transaction Timing を使用すると、特定のトランザクションの実行時間を計測することができます。
- **外部監視ツール:** 外部の監視ツール (例えば、New Relic、Dynatrace) を使用すると、システム全体のパフォーマンスを監視することができます。

**4.3.3 パフォーマンス最適化の手法**

- **スクリプトの最適化:** スクリプトのパフォーマンスを最適化します。例えば、不要な処理を削除したり、効率的なアルゴリズムを使用したりします。
- **データベースクエリの最適化:** データベースクエリのパフォーマンスを最適化します。例えば、インデックスを使用したり、不要な結合を避けたりします。
- **キャッシュの利用:** キャッシュを利用して、頻繁にアクセスされるデータを高速に取得します。
- **ハードウェアの増強:** 必要に応じて、ハードウェア (例えば、CPU、メモリ、ディスク) を増強します。

**5. 実践的なテクニック**

- **段階的なロールアウト:** アップグレードを段階的にロールアウトし、影響範囲を限定します。
- **A/B テスト:** 新しい機能と既存の機能を A/B テストし、ユーザーエクスペリエンスを比較します。
- **ユーザーからのフィードバック:** ユーザーからのフィードバックを収集し、改善点を見つけます。

**6. 応用例とユースケース**

- **大規模な ServiceNow インスタンスのアップグレード:** 大規模な ServiceNow インスタンスをアップグレードする場合、アップグレード後の動作確認とパフォーマンス監視が特に重要です。
- **ミッションクリティカルな ServiceNow インスタンスのアップグレード:** ミッションクリティカルな ServiceNow インスタンスをアップグレードする場合、ダウンタイムを最小限に抑えるために、慎重な計画とテストが必要です。
- **規制要件を満たす必要がある ServiceNow インスタンスのアップグレード:** 規制要件を満たす必要がある ServiceNow インスタンスをアップグレードする場合、コンプライアンスを維持するために、厳格な手順に従う必要があります。

**7. トラブルシューティング**

- **アップグレード後にシステムが正常に動作しない:** ログファイルを確認し、エラーの原因を特定します。
- **アップグレード後にパフォーマンスが低下する:** パフォーマンス監視ツールを使用して、ボトルネックを特定します。
- **アップグレード後に予期しないエラーが発生する:** ServiceNow のサポートに連絡し、支援を求めます。

**8. まとめと次のステップ**

アップグレード後の対応は、アップグレードプロセスを完了させ、システムが安定して動作することを保証するために重要です。アップグレード後の動作確認、問題点の特定と修正、およびパフォーマンスの監視と最適化を行うことで、システムの信頼性とパフォーマンスを維持することができます。この章で解説した手順とテクニックを参考に、スムーズなアップグレードを実現してください。

ServiceNow のアップグレードは、継続的なプロセスです。常に最新の情報を収集し、計画的にアップグレードを進めることで、システムの価値を最大限に引き出すことができます。
