## 第 9 章：トラブルシューティング：エラー解決の鉄則

エラーは、開発者にとって避けて通れない試練です。しかし、エラーを恐れるのではなく、それを成長の機会と捉え、体系的なアプローチで解決していくことが重要です。本章では、ServiceNow プラットフォームにおけるエラー解決のための鉄則を、ログ分析、デバッグ、エラーメッセージの解釈という 3 つの柱を中心に解説します。これらの技術を習得することで、エラーに迅速かつ効果的に対応し、開発効率を飛躍的に向上させることができるでしょう。

### 9.1 ログ分析：エラーの原因特定と解決

#### 概要と重要性

ログ分析は、システム内で発生したイベントの記録を解析し、問題の原因を特定するための基本的なテクニックです。ServiceNow プラットフォームでは、システムログ、スクリプトログ、トランザクションログなど、様々なログが利用可能です。これらのログを適切に分析することで、エラーの根本原因を突き止め、迅速な解決に繋げることができます。特に、本番環境で発生した問題の切り分けや、パフォーマンスボトルネックの特定に役立ちます。

#### 特徴と利点

- **包括的な情報**: システム全体の動作状況を把握できる
- **原因特定の迅速化**: エラー発生時の状況を詳細に追跡できる
- **問題の未然防止**: 傾向分析により潜在的な問題を予測できる
- **パフォーマンス改善**: ボトルネックを特定し、システム最適化に繋げられる
- **セキュリティ監査**: 不正アクセスやセキュリティインシデントの調査に役立つ

#### 事前準備と前提条件

- ServiceNow インスタンスへの管理者権限、または適切なログアクセス権限
- ServiceNow プラットフォームの基本的な操作知識（ナビゲーターの使用など）
- 問題が発生した日時、状況、関連するスクリプトや設定に関する情報

#### 基本的な使い方

1.  **システムログの確認**: ServiceNow インスタンスにログインし、ナビゲーターで「System Logs」を検索し、関連するログを選択します。
2.  **フィルタリング**: ログの種類（エラー、警告、情報など）、ソース（スクリプト名、ビジネスルール名など）、日時などでフィルタリングし、関連性の高いログを絞り込みます。
3.  **ログ詳細の確認**: ログメッセージを注意深く読み、エラーの原因、発生箇所、関連する情報を把握します。
4.  **スクリプトログの活用**: `gs.log()`、`gs.error()`、`gs.warn()`などの関数を使用して、スクリプト内にログを出力します。
5.  **トランザクションログの確認**: パフォーマンスの問題を調査するために、トランザクションログ（syslog_transaction テーブル）を確認します。実行時間、クエリ数などを分析し、ボトルネックを特定します。

#### 実践的なテクニック

- **キーワード検索**: ログメッセージに特定のキーワード（テーブル名、フィールド名、ユーザー名など）が含まれている場合に絞り込むことで、関連するログを効率的に見つけられます。
- **タイムスタンプの利用**: エラーが発生した時間帯に焦点を当て、その前後のログを詳細に分析することで、原因を特定しやすくなります。
- **ログレベルの活用**: 開発環境ではログレベルを DEBUG に設定し、詳細なログを出力することで、問題の早期発見に繋げます。本番環境ではログレベルを WARN または ERROR に設定し、ログの量を最小限に抑えます。
- **ログローテーションの設定**: システムログのサイズが肥大化するのを防ぐために、ログローテーションを設定します。古いログを自動的にアーカイブまたは削除することで、パフォーマンスを維持し、ストレージ容量を節約できます。

```javascript
// スクリプトログの例
try {
  // 何らかの処理
  gs.info("処理が正常に完了しました。レコードID: " + current.sys_id);
} catch (e) {
  gs.error("エラーが発生しました: " + e.message + " (スクリプト名: my_script)");
}
```

#### 応用例とユースケース

- **インシデント管理**: インシデントがエスカレーションされた原因をログ分析で特定し、根本原因を解決することで、同様のインシデントの再発を防ぎます。
- **変更管理**: 変更セットの適用後にエラーが発生した場合、ログ分析で変更による影響範囲を特定し、ロールバックが必要かどうかを判断します。
- **サービスカタログ**: サービスカタログのリクエストが失敗した場合、ログ分析でエラーの原因を特定し、カタログアイテムの設定やスクリプトを修正します。
- **パフォーマンス監視**: トランザクションログを定期的に分析し、実行時間の長いクエリやスクリプトを特定し、パフォーマンス改善のための対策を講じます。

#### トラブルシューティング

- **ログが見つからない**: 適切なログレベルが設定されているか、フィルタリング条件が厳しすぎないかを確認します。
- **ログメッセージが理解できない**: ログメッセージのキーワードを検索エンジンで調べたり、ServiceNow コミュニティで質問したりすることで、情報を収集します。
- **ログが多すぎる**: フィルタリング条件を絞り込むか、ログレベルを下げることで、ログの量を減らすことができます。

#### まとめと次のステップ

ログ分析は、エラー解決の第一歩です。ログを読み解き、問題の原因を特定する能力は、開発者にとって不可欠なスキルです。次のステップとして、スクリプトデバッガの使い方を学び、さらに詳細な分析を行えるようにしましょう。

### 9.2 デバッグ：スクリプトのステップ実行と変数監視

#### 概要と重要性

デバッグは、スクリプトの実行中に発生するエラーを特定し、修正するための重要なプロセスです。ServiceNow プラットフォームには、スクリプトデバッガという強力なツールが搭載されており、スクリプトのステップ実行、変数の監視、ブレークポイントの設定など、様々な機能を利用できます。デバッグスキルを習得することで、複雑なスクリプトのエラーを効率的に解決し、開発時間を短縮できます。

#### 特徴と利点

- **ステップ実行**: スクリプトを一行ずつ実行し、処理の流れを詳細に追跡できる
- **変数監視**: スクリプトの実行中に変数の値を監視し、期待どおりの値になっているか確認できる
- **ブレークポイント**: 特定の行でスクリプトの実行を一時停止し、その時点での変数の状態を調べられる
- **コールスタック**: 関数の呼び出し履歴を確認し、エラーが発生した箇所を特定できる
- **リモートデバッグ**: サーバーサイドのスクリプトをリアルタイムでデバッグできる

#### 事前準備と前提条件

- ServiceNow インスタンスへの管理者権限、またはスクリプトデバッグ権限
- ServiceNow プラットフォームのスクリプトに関する基本的な知識（ビジネスルール、クライアントスクリプトなど）
- デバッグ対象のスクリプトとその動作に関する情報

#### 基本的な使い方

1.  **スクリプトデバッガの有効化**: ServiceNow インスタンスにログインし、「System Diagnostics」>「Script Debugger」>「Enable Debugging」を選択します。デバッグ対象に応じて、「Server Script Debugger (Background)」、「Client Script Debugger」などを選択します。
2.  **ブレークポイントの設定**: デバッグ対象のスクリプトを開き、ブレークポイントを設定したい行の左側の余白をクリックします。
3.  **スクリプトの実行**: デバッグ対象のスクリプトを実行します。
4.  **デバッグウィンドウの操作**: スクリプトがブレークポイントで一時停止したら、デバッグウィンドウで以下の操作を行います。
    - **ステップオーバー**: 次の行を実行します。
    - **ステップイン**: 関数呼び出しの中に入ります。
    - **ステップアウト**: 現在の関数から抜け出します。
    - **変数の監視**: 変数ウィンドウで、変数の値を確認します。必要に応じて、変数の値を変更することもできます。
    - **コールスタックの確認**: コールスタックウィンドウで、関数の呼び出し履歴を確認します。
5.  **デバッグの終了**: デバッグが完了したら、「Resume」をクリックしてスクリプトの実行を再開するか、「Terminate」をクリックしてスクリプトの実行を終了します。
6.  **スクリプトデバッガの無効化**: デバッグが終了したら、「System Diagnostics」>「Script Debugger」>「Disable Debugging」を選択して、スクリプトデバッガを無効化します。

#### 実践的なテクニック

- **条件付きブレークポイント**: 特定の条件が満たされた場合にのみブレークポイントで一時停止するように設定できます。これにより、特定の状況下でのみ発生するエラーを効率的にデバッグできます。
- **ウォッチ式の利用**: 変数の値を監視するだけでなく、式の結果を監視することもできます。例えば、`current.getValue('priority') == '1'`というウォッチ式を設定すると、優先度が 1 の場合にのみブレークポイントで一時停止します。
- **ログポイントの活用**: ブレークポイントを設定せずに、特定の変数の値をログに出力できます。これにより、スクリプトの実行を一時停止せずに、変数の状態を監視できます。
- **リモートデバッグの活用**: 本番環境で発生したエラーをデバッグするために、リモートデバッグを利用できます。ただし、本番環境でのデバッグは慎重に行う必要があります。

```javascript
// 条件付きブレークポイントの例
if (current.priority == "1") {
  // この行にブレークポイントを設定
  gs.info("優先度が1のインシデントが処理されました。");
}
```

#### 応用例とユースケース

- **ビジネスルールのデバッグ**: ビジネスルールの実行時にエラーが発生した場合、スクリプトデバッガを使用して、ビジネスルールのロジックを検証し、エラーの原因を特定します。
- **クライアントスクリプトのデバッグ**: クライアントスクリプトが期待どおりに動作しない場合、ブラウザの開発者ツールと ServiceNow のクライアントスクリプトデバッガを組み合わせて、スクリプトのロジックを検証し、エラーの原因を特定します。
- **フローデザイナーのデバッグ**: フローデザイナーで作成したフローが正しく動作しない場合、フローデザイナーのデバッグ機能を使用して、フローの実行状況を追跡し、エラーの原因を特定します。
- **REST API のデバッグ**: REST API の呼び出しが失敗した場合、スクリプトデバッガを使用して、API リクエストのパラメータやレスポンスを検証し、エラーの原因を特定します。

#### トラブルシューティング

- **スクリプトデバッガが有効にならない**: 必要な権限がないか、スクリプトデバッガの設定が正しくない可能性があります。管理者権限でログインしているか、スクリプトデバッガの設定を確認してください。
- **ブレークポイントで停止しない**: ブレークポイントの設定位置が正しいか、スクリプトがブレークポイントを通るかどうかを確認してください。
- **変数の値が正しく表示されない**: 変数のスコープを確認してください。スコープ外の変数は、デバッグウィンドウに表示されない場合があります。

#### まとめと次のステップ

スクリプトデバッガは、エラー解決のための強力な武器です。様々な機能を使いこなすことで、複雑なスクリプトのエラーを効率的に解決し、開発効率を向上させることができます。次のステップとして、エラーメッセージの解釈を学び、エラーの原因をより深く理解できるようにしましょう。

### 9.3 エラーメッセージの解釈：よくあるエラーと対処法

#### 概要と重要性

エラーメッセージは、エラーが発生した原因や場所に関する貴重な情報を提供してくれます。しかし、エラーメッセージは必ずしも分かりやすいとは限りません。エラーメッセージを正しく解釈し、必要な情報を抽出する能力は、エラー解決において非常に重要です。ServiceNow プラットフォームでよく発生するエラーの種類と、その対処法を学ぶことで、エラー解決の速度と精度を向上させることができます。

#### 特徴と利点

- **エラーの原因特定**: エラーメッセージから、エラーが発生した原因を特定できる
- **解決策のヒント**: エラーメッセージに、解決策のヒントが含まれている場合がある
- **問題箇所の特定**: エラーメッセージから、エラーが発生したスクリプトや設定を特定できる
- **迅速な対応**: エラーメッセージを解釈することで、迅速な対応が可能になる
- **知識の蓄積**: エラーメッセージの解釈を通して、ServiceNow プラットフォームの知識を深められる

#### 事前準備と前提条件

- ServiceNow プラットフォームのエラーに関する基本的な知識
- 発生したエラーのエラーメッセージ
- エラーが発生した状況に関する情報

#### 基本的な使い方

1.  **エラーメッセージの確認**: エラーが発生した際に表示されるエラーメッセージを注意深く読みます。
2.  **エラーメッセージの検索**: エラーメッセージに含まれるキーワードを検索エンジンで検索し、関連情報を収集します。
3.  **ServiceNow ドキュメントの参照**: ServiceNow のドキュメントで、エラーメッセージに関する情報を探します。
4.  **コミュニティフォーラムの活用**: ServiceNow コミュニティフォーラムで、同様のエラーに関する質問や回答を検索します。
5.  **エラーメッセージの分解**: エラーメッセージを分解し、重要な情報（テーブル名、フィールド名、スクリプト名、行番号など）を抽出します。
6.  **エラーの再現**: 可能であれば、エラーを再現させ、より詳細な情報を収集します。

#### 実践的なテクニック

- **GlideRecord エラー**: GlideRecord オブジェクトを使用したスクリプトで発生するエラーです。例えば、「`Invalid GlideRecord: Table does not exist`」というエラーは、指定したテーブルが存在しないことを意味します。テーブル名が正しいか、スペルミスがないかを確認してください。
- **スクリプトエラー**: JavaScript の構文エラーや実行時エラーです。例えば、「`TypeError: Cannot read property 'value' of null`」というエラーは、null または undefined のオブジェクトのプロパティにアクセスしようとしたことを意味します。変数が初期化されているか、null チェックを行っているかを確認してください。
- **API エラー**: REST API や SOAP API の呼び出し時に発生するエラーです。例えば、「`400 Bad Request`」というエラーは、リクエストの形式が正しくないことを意味します。リクエストパラメータやヘッダーが正しいかを確認してください。
- **ACL エラー**: アクセス制御リスト（ACL）の設定に問題がある場合に発生するエラーです。例えば、「`Access denied`」というエラーは、ユーザーがリソースにアクセスする権限がないことを意味します。ACL の設定を確認し、適切な権限を付与してください。

```javascript
// GlideRecordエラーの例
var gr = new GlideRecord("non_existent_table"); // 存在しないテーブル
if (gr.next()) {
  // エラーが発生
  gs.info(gr.getValue("name"));
}
```

#### 応用例とユースケース

- **インシデント管理**: インシデントの自動割り当てルールが正しく動作しない場合、ログに記録されたエラーメッセージを解析し、割り当てルールの設定やスクリプトを修正します。
- **サービスカタログ**: サービスカタログのリクエストが失敗した場合、エラーメッセージから、カタログアイテムの設定やワークフローに問題がないかを確認します。
- **統合**: 外部システムとの統合でエラーが発生した場合、API のエラーメッセージを解析し、リクエストパラメータや認証情報が正しいかを確認します。
- **パフォーマンス監視**: パフォーマンスの問題が発生した場合、トランザクションログのエラーメッセージを解析し、実行時間の長いスクリプトやクエリを特定します。

#### トラブルシューティング

- **エラーメッセージが不親切**: エラーメッセージが十分に説明的でない場合、関連するコードや設定を詳細に調べ、エラーの原因を特定します。
- **エラーメッセージの意味が分からない**: エラーメッセージに含まれるキーワードを検索エンジンで調べたり、ServiceNow コミュニティで質問したりすることで、情報を収集します。
- **エラーが再現しない**: エラーが発生した状況を再現するために、環境やデータを調整します。再現しない場合は、エラーが一時的なものであった可能性もあります。

#### まとめと次のステップ

エラーメッセージの解釈は、エラー解決の鍵となります。エラーメッセージを正しく理解し、必要な情報を抽出することで、エラーの原因を特定し、迅速な解決に繋げることができます。本章で学んだ知識を活かし、エラーに臆することなく、積極的に解決に取り組んでください。今後は、ServiceNow のアップデート情報やコミュニティフォーラムを定期的にチェックし、最新のエラー情報や対処法を習得するように心がけましょう。
