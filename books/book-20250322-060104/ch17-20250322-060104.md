## 第 17 章: セキュリティ・バイ・デザイン - 最初から安全なシステムを

ソフトウェア開発において、セキュリティは後回しにされがちな課題です。しかし、開発の最終段階でセキュリティ対策を施すだけでは、根本的な脆弱性を解消することは難しく、結果としてコストと手間が増大するだけでなく、システムの信頼性を損なう可能性もあります。本章では、セキュリティ・バイ・デザインの原則に基づき、システムの設計段階からセキュリティを組み込むことで、より安全で堅牢なシステムを構築する方法を解説します。

### 17.1 セキュリティの原則：最小権限の原則、防御的プログラミング

#### 17.1.1 概要と重要性

セキュリティ・バイ・デザインとは、システム開発の初期段階からセキュリティを考慮し、設計、実装、運用を通じて継続的にセキュリティ対策を組み込むアプローチです。このアプローチを採用することで、初期段階での脆弱性の発見と修正が可能になり、開発コストの削減、セキュリティリスクの軽減、そして最終的な製品の信頼性向上に貢献します。

本セクションでは、セキュリティ・バイ・デザインを実現するための基盤となる二つの重要な原則、「最小権限の原則」と「防御的プログラミング」について詳しく解説します。

#### 17.1.2 最小権限の原則

**特徴と利点:**

最小権限の原則とは、ユーザー、プロセス、システムに対して、そのタスクを実行するために必要最小限の権限のみを与えるという原則です。この原則を適用することで、仮に攻撃者がシステムに侵入した場合でも、その影響範囲を最小限に抑えることができます。

**事前準備と前提条件:**

- システムの各コンポーネントの機能を理解する。
- 各機能に必要な権限を明確に定義する。
- ユーザーグループとロールを設計し、権限を適切に割り当てる。

**基本的な使い方:**

- **ユーザーアカウント:** 各ユーザーには、個別のタスクに必要な最小限の権限のみを与えます。管理者権限は、本当に必要なユーザーにのみ付与し、日常的な作業には使用させないようにします。
- **プロセス:** プロセスがアクセスできるファイルやリソースを制限します。
- **システムサービス:** システムサービスは、必要最低限の権限で実行するように設定します。

**実践的なテクニック:**

- **Linux の例:** `sudo` コマンドを利用して、特定のコマンドのみを一時的に管理者権限で実行させます。
  ```bash
  # 特定のユーザーに、特定のコマンドのみsudo権限を付与
  sudo visudo
  # 以下を追記 (例: user1 が /opt/script.sh をsudoで実行可能)
  user1 ALL=(ALL) NOPASSWD: /opt/script.sh
  ```
- **データベース:** データベースのユーザーアカウントには、必要なテーブルへのアクセス権のみを付与します。`GRANT` 句と `REVOKE` 句を使用して、権限を細かく制御します。

  ```sql
  -- ユーザー 'webapp' に 'products' テーブルへの SELECT 権限のみを付与
  GRANT SELECT ON products TO 'webapp'@'localhost';

  -- ユーザー 'webapp' から 'products' テーブルへの UPDATE 権限を剥奪
  REVOKE UPDATE ON products FROM 'webapp'@'localhost';
  ```

**応用例とユースケース:**

- **クラウド環境:** クラウドプロバイダーの IAM（Identity and Access Management）サービスを利用して、仮想マシンやストレージへのアクセス権を細かく制御します。
- **API:** API エンドポイントへのアクセスを認証と認可によって制限し、不正なアクセスを防止します。

**トラブルシューティング:**

- 権限不足によるエラーが発生した場合、ログを確認し、必要な権限を最小限の範囲で付与します。
- 過剰な権限が付与されているアカウントがないか定期的に監査します。

#### 17.1.3 防御的プログラミング

**特徴と利点:**

防御的プログラミングとは、予期せぬ入力や状況が発生しても、システムが安全に動作し続けるように設計・実装する手法です。この原則を適用することで、バグや脆弱性が悪用されるリスクを軽減することができます。

**事前準備と前提条件:**

- 開発チーム全体で、入力検証、エラー処理、例外処理の重要性を共有する。
- セキュアなコーディング規約を策定し、チーム全体で共有する。
- テストケースを作成する際に、異常系ケース（無効な入力、境界値など）を網羅的に考慮する。

**基本的な使い方:**

- **入力検証:** ユーザーからの入力や API からのレスポンスなど、外部からの入力は必ず検証します。
- **エラー処理:** エラーが発生した場合に、適切なエラーメッセージを表示し、システムが停止しないように処理します。
- **例外処理:** 予期せぬ例外が発生した場合に、ログを記録し、システムを安全な状態に戻します。

**実践的なテクニック:**

- **入力検証:**
  - **サニタイズ:** 入力に含まれる可能性のある有害なコード（例：SQL インジェクション、クロスサイトスクリプティング）を無効化します。
  - **バリデーション:** 入力が期待される形式（例：メールアドレス、電話番号）に合致するかどうかを検証します。
  - **エスケープ:** HTML、URL、SQL 文など、特定のコンテキストで使用される特殊文字をエスケープします。
- **エラー処理:**
  - エラーメッセージは、攻撃者にシステムの情報を提供しないように、簡潔かつ一般的にします。
  - エラーログは、詳細な情報を記録し、デバッグに役立てます。
- **例外処理:**
  - `try-except` ブロック（Python の場合）や `try-catch` ブロック（Java, C#の場合）を使用して、例外を捕捉し、適切に処理します。
  - 例外発生時に、システムの状態をロールバックし、データの整合性を維持します。

**コード例（Python）：**

```python
def process_input(user_input):
    try:
        # 入力検証
        if not isinstance(user_input, str):
            raise ValueError("入力は文字列である必要があります")
        user_input = user_input.strip()  # 前後の空白を削除
        if len(user_input) > 100:
            raise ValueError("入力は100文字以下である必要があります")

        # サニタイズ (例: HTMLエスケープ)
        user_input = html.escape(user_input)

        # 処理
        result = do_something_with_input(user_input)
        return result

    except ValueError as e:
        # エラー処理
        print(f"エラー: {e}")
        return None # または適切なデフォルト値を返す

    except Exception as e:
        # 予期せぬ例外処理
        logging.exception("予期せぬエラーが発生しました")
        return None  # または例外を再送出する

def do_something_with_input(input_string):
    # ここで入力文字列を使った処理を行う
    # 潜在的な脆弱性 (例: SQLインジェクション) を考慮
    # 安全な関数またはライブラリを使用
    return f"処理結果: {input_string}"

```

**応用例とユースケース:**

- **Web アプリケーション:** ユーザーからの入力データを検証し、SQL インジェクションやクロスサイトスクリプティングなどの攻撃を防止します。
- **API:** API エンドポイントで入力パラメータを検証し、不正なリクエストを拒否します。
- **IoT デバイス:** デバイスのファームウェアを定期的にアップデートし、既知の脆弱性を修正します。

**トラブルシューティング:**

- 入力検証のエラーメッセージが不明確な場合、ユーザーに分かりやすいメッセージに変更します。
- エラーログが十分に記録されていない場合、ログレベルを上げて詳細な情報を記録するように設定します。
- 例外処理が適切に行われていない場合、例外ハンドラを追加し、システムを安全な状態に戻すように修正します。

#### 17.1.4 セキュアなコーディング規約

**概要と重要性:**

セキュアなコーディング規約とは、脆弱性を作り込まないためのプログラミングルールやガイドラインの集まりです。規約を定めることで、開発者間でのセキュリティ意識の統一を図り、コードの品質向上、レビューの効率化、脆弱性の早期発見に貢献します。

**特徴と利点:**

- 脆弱性の発生を未然に防ぐ
- コードレビューの効率化
- 開発者間のセキュリティ意識の統一
- 長期的な保守性の向上

**事前準備と前提条件:**

- OWASP（Open Web Application Security Project）などの業界標準のガイドラインを参考にする。
- チームの技術レベルや開発環境に合わせてカスタマイズする。
- 規約の内容を定期的に見直し、最新の脅威に対応する。

**基本的な使い方:**

- **入力検証:** 前述の通り、外部からの入力は必ず検証する。
- **出力エンコード:** HTML、URL、SQL 文などのコンテキストに合わせて、適切に出力をエンコードする。
- **認証と認可:** ユーザーの認証と認可を確実に行う。
- **暗号化:** 機密性の高い情報は暗号化して保存する。
- **セッション管理:** セッション ID を安全に管理し、セッションハイジャックを防止する。
- **エラー処理:** エラーメッセージは、攻撃者にシステムの情報を提供しないように、簡潔かつ一般的にする。
- **ログ:** 監査ログを記録し、不正アクセスやシステム障害を検知する。

**実践的なテクニック:**

- **サードパーティライブラリの利用:** 脆弱性が報告されていない信頼できるライブラリのみを使用する。
- **アップデート:** 使用しているライブラリやフレームワークを最新バージョンに保ち、既知の脆弱性を修正する。
- **静的解析ツール:** 静的解析ツールを使用して、コード内の潜在的な脆弱性を検出する。
- **ペネトレーションテスト:** ペネトレーションテストを実施して、システムのセキュリティを検証する。

**例：Java のセキュアなコーディング規約**

- **SQL インジェクション対策:** PreparedStatement を使用する。

  ```java
  String sql = "SELECT * FROM users WHERE username = ? AND password = ?";
  PreparedStatement pstmt = connection.prepareStatement(sql);
  pstmt.setString(1, username);
  pstmt.setString(2, password);
  ResultSet rs = pstmt.executeQuery();
  ```

- **クロスサイトスクリプティング (XSS) 対策:** 出力時にエスケープ処理を行う。

  ```java
  String escapedInput = StringEscapeUtils.escapeHtml4(userInput);
  ```

- **セッション固定化対策:** ログイン時にセッション ID を再生成する。
  ```java
  HttpSession session = request.getSession(false);
  if (session != null) {
      session.invalidate();
  }
  session = request.getSession(true);
  ```

**応用例とユースケース:**

- **Web アプリケーション開発:** Web アプリケーションフレームワーク（例：Spring Security, Django）のセキュリティ機能を活用する。
- **モバイルアプリケーション開発:** モバイルアプリケーションのセキュリティに関するガイドライン（例：OWASP Mobile Security Project）に従う。
- **IoT デバイス開発:** IoT デバイスのセキュリティに関するガイドライン（例：NISTIR 8228）に従う。

**トラブルシューティング:**

- 規約が守られていないコードが見つかった場合、コードレビューで指摘し、修正を促す。
- 規約の内容が古くなっている場合、最新の脅威に対応するように改訂する。
- 開発チーム全体で規約の内容を共有し、理解を深めるためのトレーニングを実施する。

#### 17.1.5 まとめと次のステップ

本セクションでは、セキュリティ・バイ・デザインの基盤となる「最小権限の原則」と「防御的プログラミング」、そして「セキュアなコーディング規約」について解説しました。これらの原則を理解し、実践することで、より安全で堅牢なシステムを構築することができます。

次のステップでは、システムに対する潜在的な脅威を特定し、対策を講じるための「脅威モデリング」について詳しく解説します。

### 17.2 脅威モデリング：攻撃者の視点から考える

#### 17.2.1 概要と重要性

脅威モデリングとは、システムに対する潜在的な脅威を特定し、リスクを評価し、対策を講じるための体系的なプロセスです。攻撃者の視点からシステムを分析することで、設計段階では見過ごされがちな脆弱性を発見し、事前にセキュリティ対策を施すことができます。

脅威モデリングは、開発サイクルの早い段階で実施することで、後から脆弱性を修正するよりもコスト効率が高く、セキュリティ対策の効果を最大化することができます。

#### 17.2.2 特徴と利点

- 潜在的な脆弱性の早期発見
- リスクベースのセキュリティ対策の優先順位付け
- 開発チーム全体のセキュリティ意識の向上
- コンプライアンス要件の遵守

#### 17.2.3 事前準備と前提条件

- システムのアーキテクチャ図、データフロー図などのドキュメントを用意する。
- システムの機能、役割、および関連するアセットを明確に定義する。
- 脅威モデリングの専門知識を持つメンバーをチームに加える（またはトレーニングを提供する）。

#### 17.2.4 基本的な使い方

脅威モデリングの一般的なステップは以下の通りです。

1.  **システムの理解:** システムのアーキテクチャ、データフロー、および関連するアセットを理解します。
2.  **脅威の特定:** 攻撃者がシステムをどのように攻撃するかを予測し、潜在的な脅威を特定します。
3.  **リスクの評価:** 各脅威の発生可能性と影響度を評価します。
4.  **対策の策定:** 脅威を軽減するためのセキュリティ対策を策定します。
5.  **検証と改善:** セキュリティ対策の効果を検証し、必要に応じて改善します。

**脅威モデリングの手法:**

- **STRIDE:** Microsoft が開発した脅威分類モデル。なりすまし(Spoofing)、改ざん(Tampering)、否認(Repudiation)、情報漏洩(Information Disclosure)、サービス拒否(Denial of Service)、特権昇格(Elevation of Privilege)の頭文字を取ったもの。
- **DREAD:** リスク評価モデル。損害(Damage potential)、再現性(Reproducibility)、悪用可能性(Exploitability)、影響を受けるユーザー(Affected Users)、発見可能性(Discoverability)の頭文字を取ったもの。

#### 17.2.5 実践的なテクニック

**STRIDE を使った脅威モデリングの例:**

- **システム:** Web アプリケーション
- **コンポーネント:** ログインフォーム

| 脅威            | 説明                                                                           | 対策                                                                             |
| --------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| なりすまし(S)   | 攻撃者が他のユーザーの資格情報を盗み、そのユーザーとしてログインする。         | 強力なパスワードポリシーの適用、多要素認証の実装、ブルートフォースアタック対策。 |
| 改ざん(T)       | 攻撃者がログインフォームのデータを改ざんして、システムを不正に操作する。       | 入力検証、出力エンコード、改ざん検知システムの導入。                             |
| 否認(R)         | ユーザーが自分の行動を否認する。                                               | 監査ログの記録、デジタル署名の利用。                                             |
| 情報漏洩(I)     | 攻撃者がユーザーの資格情報や個人情報を盗み出す。                               | SSL/TLS による通信の暗号化、機密情報の暗号化保存、脆弱性対策。                   |
| サービス拒否(D) | 攻撃者がログインフォームに大量のリクエストを送りつけ、システムをダウンさせる。 | レート制限、キャプチャの導入、DDoS 攻撃対策。                                    |
| 特権昇格(E)     | 攻撃者が通常のユーザー権限を管理者権限に昇格させる。                           | 最小権限の原則の適用、脆弱性対策、アクセス制御リストの設定。                     |

**DREAD を使ったリスク評価の例:**

上記の STRIDE で特定した脅威に対して、DREAD を使ってリスクを評価します。各要素を 1 ～ 5 のスケールで評価し、合計スコアに基づいてリスクレベルを決定します。

| 脅威          | 損害 | 再現性 | 悪用可能性 | 影響を受けるユーザー | 発見可能性 | 合計スコア | リスクレベル |
| ------------- | ---- | ------ | ---------- | -------------------- | ---------- | ---------- | ------------ |
| なりすまし(S) | 4    | 5      | 5          | 5                    | 4          | 23         | 高           |
| 改ざん(T)     | 3    | 4      | 4          | 4                    | 3          | 18         | 中           |
| ...           | ...  | ...    | ...        | ...                  | ...        | ...        | ...          |

#### 17.2.6 応用例とユースケース

- **クラウド環境:** クラウドプロバイダーが提供する脅威モデリングツールやサービスを利用して、クラウド環境のセキュリティリスクを評価します。
- **IoT デバイス:** IoT デバイスのファームウェアや通信プロトコルに対する脅威をモデル化し、セキュアな設計を支援します。
- **金融システム:** 金融システムのトランザクション処理やデータ管理における脅威をモデル化し、不正行為の防止策を講じます。

#### 17.2.7 トラブルシューティング

- 脅威モデリングの結果が現実的でない場合、システムの理解を深め、攻撃者の視点に立って分析し直します。
- 脅威モデリングのプロセスが複雑すぎる場合、よりシンプルな手法（例：アタックツリー）を試します。
- 脅威モデリングの結果に基づいてセキュリティ対策を実施しても、脆弱性が残っている場合、ペネトレーションテストを実施して、セキュリティ対策の効果を検証します。

#### 17.2.8 まとめと次のステップ

本セクションでは、脅威モデリングの重要性、基本的な使い方、実践的なテクニックについて解説しました。脅威モデリングは、システムに対する潜在的な脅威を特定し、リスクを評価し、対策を講じるための重要なプロセスです。

セキュリティ・バイ・デザインは、一度きりの取り組みではありません。脅威は常に進化するため、脅威モデリングを定期的に実施し、セキュリティ対策を継続的に改善していく必要があります。

次のステップでは、本章で学んだセキュリティの原則と脅威モデリングの手法を組み合わせて、より安全で堅牢なシステムを構築するための具体的な方法について解説します。
