## 第7章: パフォーマンスチューニング - フレームレートの最適化

ゲームやインタラクティブな3Dアプリケーションにおいて、滑らかなアニメーションと操作感はユーザーエクスペリエンスを大きく左右します。そのため、高いフレームレートを維持することは非常に重要です。この章では、WebGLアプリケーションにおけるフレームレートを最適化するための実践的なテクニックについて解説します。オブジェクトの描画負荷軽減からシェーダーの最適化、メモリ管理、そしてプロファイリングまで、段階的にパフォーマンス改善のアプローチを学び、快適なWebGL体験を実現しましょう。

### 8.1 レンダリング負荷の軽減 - オブジェクト数の削減、カリング

#### 概要と重要性

WebGLのレンダリングパイプラインにおいて、描画するオブジェクトの数はフレームレートに直接影響します。オブジェクト数が増えるほど、GPUの処理負荷が増大し、フレームレートが低下する可能性があります。特に複雑なシーンでは、オブジェクト数の削減がパフォーマンス改善の鍵となります。また、全てのオブジェクトが常に画面に表示されているわけではありません。画面外のオブジェクトや他のオブジェクトに隠蔽されているオブジェクトを描画しないようにすることで、無駄な処理を省き、パフォーマンスを向上させることができます。

#### 特徴と利点

オブジェクト数の削減は、描画に必要な頂点データの転送量を減らし、GPUの処理時間を短縮します。カリング技術は、描画する必要のないオブジェクトを事前に排除することで、GPUの負荷を軽減し、フレームレートを向上させます。これらの技術を組み合わせることで、より複雑なシーンでも滑らかな描画を実現できます。

#### 事前準備と前提条件

*   WebGLの基本的な知識 (頂点バッファ、インデックスバッファ、描画呼び出し)
*   3Dモデルの作成およびインポートの知識
*   開発環境 (エディタ、WebGL対応ブラウザ)

#### 基本的な使い方

**8.1.1 オブジェクト数の削減 (Instancing, LOD)**

*   **Instancing:** 類似した形状のオブジェクトを大量に描画する場合、Instancingを用いることで、描画呼び出しの回数を大幅に削減できます。

    ```javascript
    // Instanced Arrays extension を有効化
    const ext = gl.getExtension('ANGLE_instanced_arrays');
    if (!ext) {
      console.error("ANGLE_instanced_arrays extension is not supported");
      return;
    }

    // 頂点バッファ、インデックスバッファの準備 (通常通り)

    // インスタンスごとの変換行列を格納するバッファの作成
    const matrixBuffer = gl.createBuffer();
    gl.bindBuffer(gl.ARRAY_BUFFER, matrixBuffer);
    // 仮に10個のインスタンスを生成
    const numInstances = 10;
    const matrixData = new Float32Array(numInstances * 16); // 4x4行列 * インスタンス数

    // 各インスタンスの変換行列を計算して matrixData に格納 (省略)
    for (let i = 0; i < numInstances; ++i) {
        // 例：i番目のインスタンスを x 方向に i だけ移動
        const mat = mat4.create();
        mat4.translate(mat, mat, [i, 0, 0]); // mat4 は gl-matrix などのライブラリを使用
        for (let j = 0; j < 16; ++j) {
            matrixData[i * 16 + j] = mat[j];
        }
    }

    gl.bufferData(gl.ARRAY_BUFFER, matrixData, gl.STATIC_DRAW);

    // シェーダーでインスタンスごとの行列を受け取る attribute 変数のロケーションを取得
    const matrixLocation0 = gl.getAttribLocation(program, 'matrix0'); //mat4は4つのvec4として渡す
    const matrixLocation1 = gl.getAttribLocation(program, 'matrix1');
    const matrixLocation2 = gl.getAttribLocation(program, 'matrix2');
    const matrixLocation3 = gl.getAttribLocation(program, 'matrix3');

    // 各 attribute 変数に対して、バッファを割り当てる (vec4 を4つ割り当てる)
    const bytesPerMatrix = 16 * 4; // 4x4 matrix, 4 bytes per float
    gl.enableVertexAttribArray(matrixLocation0);
    gl.enableVertexAttribArray(matrixLocation1);
    gl.enableVertexAttribArray(matrixLocation2);
    gl.enableVertexAttribArray(matrixLocation3);

    gl.bindBuffer(gl.ARRAY_BUFFER, matrixBuffer);

    gl.vertexAttribPointer(matrixLocation0, 4, gl.FLOAT, false, bytesPerMatrix, 0);
    gl.vertexAttribPointer(matrixLocation1, 4, gl.FLOAT, false, bytesPerMatrix, 16);
    gl.vertexAttribPointer(matrixLocation2, 4, gl.FLOAT, false, bytesPerMatrix, 32);
    gl.vertexAttribPointer(matrixLocation3, 4, gl.FLOAT, false, bytesPerMatrix, 48);

    // インスタンスごとの更新頻度を設定 (1回描画するごとに更新)
    ext.vertexAttribDivisorANGLE(matrixLocation0, 1);
    ext.vertexAttribDivisorANGLE(matrixLocation1, 1);
    ext.vertexAttribDivisorANGLE(matrixLocation2, 1);
    ext.vertexAttribDivisorANGLE(matrixLocation3, 1);


    // 描画呼び出し
    // 通常の gl.drawElements() の代わりに、インスタンス描画関数を使用
    ext.drawElementsInstancedANGLE(gl.TRIANGLES, indexCount, gl.UNSIGNED_SHORT, 0, numInstances);

    ```

    **シェーダーコード (GLSL):**

    ```glsl
    #version 300 es
    in vec3 a_position;
    in vec4 matrix0;
    in vec4 matrix1;
    in vec4 matrix2;
    in vec4 matrix3;

    uniform mat4 u_viewProjection;
    out vec3 v_normal; //法線をフラグメントシェーダーに渡す

    void main() {
        mat4 instanceMatrix = mat4(matrix0, matrix1, matrix2, matrix3);
        gl_Position = u_viewProjection * instanceMatrix * vec4(a_position, 1.0);
    }
    ```

*   **LOD (Level of Detail):** カメラからの距離に応じて、モデルのディテールレベルを調整します。遠くのオブジェクトには、よりシンプルなモデルを使用することで、ポリゴン数を削減します。

    LODは、複数の異なるディテールレベルのモデルを用意し、カメラからの距離に応じて描画するモデルを切り替えることで実現します。

    ```javascript
    // 距離に応じてモデルを切り替える例
    function render(cameraPosition) {
        const distance = vec3.distance(cameraPosition, objectPosition);

        if (distance < 10) {
            // 高ディテールモデルを描画
            drawModel(highDetailModel);
        } else if (distance < 50) {
            // 中ディテールモデルを描画
            drawModel(mediumDetailModel);
        } else {
            // 低ディテールモデルを描画
            drawModel(lowDetailModel);
        }
    }
    ```

**8.1.2 Frustum Cullingによる描画範囲の制限**

*   **Frustum Culling:** カメラの視錐台（Frustum）の外にあるオブジェクトは描画しません。オブジェクトのバウンディングボリューム (球、AABBなど) が視錐台と交差するかどうかを判定し、交差しない場合は描画をスキップします。

    視錐台カリングの実装はやや複雑ですが、多くの3Dライブラリやエンジンが組み込みの機能として提供しています。ここでは、基本的な考え方を示します。

    ```javascript
    // 視錐台カリングの基本的な考え方
    function isObjectInFrustum(objectBoundingVolume, frustumPlanes) {
        // frustumPlanes は、視錐台を構成する平面の配列 (平面は法線ベクトルと距離で定義)

        for (let i = 0; i < frustumPlanes.length; ++i) {
            const plane = frustumPlanes[i];
            const distance = plane.normal.x * objectBoundingVolume.center.x +
                             plane.normal.y * objectBoundingVolume.center.y +
                             plane.normal.z * objectBoundingVolume.center.z +
                             plane.distance;

            // バウンディングボリュームが平面の外側にある場合、視錐台の外側にあると判定
            if (distance < -objectBoundingVolume.radius) {
                return false; // カリング対象
            }
        }

        return true; // 視錐台の中にある
    }

    //レンダリングループ
    function render() {
        //視錐台の平面を計算 (projectionMatrix, viewMatrix から計算)
        const frustumPlanes = calculateFrustumPlanes(projectionMatrix, viewMatrix);

        //オブジェクトごとに視錐台カリングを実行
        for (const object of objects) {
            if (isObjectInFrustum(object.boundingVolume, frustumPlanes)) {
                //描画
                drawObject(object);
            }
        }
    }

    ```

**8.1.3 Occlusion Cullingによる隠蔽面の描画抑制**

*   **Occlusion Culling:** 他のオブジェクトによって隠蔽されているオブジェクトは描画しません。深度バッファ (Zバッファ) を利用して、オブジェクトが隠蔽されているかどうかを判定します。

    Occlusion Culling は Frustum Culling よりも複雑で、事前計算が必要となる場合もあります。

    1.  **可視オブジェクトの決定:** まず、カメラに近いオブジェクトや、シーンの中で重要なオブジェクトなど、可視オブジェクトの候補を決定します。
    2.  **深度バッファのレンダリング:** 決定した可視オブジェクトのみを深度バッファにレンダリングします。この際、カラーバッファへの描画は行いません。
    3.  **カリング判定:** 各オブジェクトに対して、そのオブジェクトのバウンディングボリューム (球、AABBなど) の頂点を深度バッファと比較します。もし、バウンディングボリュームの全ての頂点が深度バッファよりも奥にある場合、そのオブジェクトは完全に隠蔽されていると判断し、描画をスキップします。

    WebGLでOcclusion Cullingを実装する際の考慮事項：

    *   **パフォーマンス:** Occlusion Cullingの判定処理自体がオーバーヘッドになる可能性があります。シーンの複雑さやオブジェクトの数に応じて、適切な実装方法を選択する必要があります。
    *   **精度:** 深度バッファの精度によっては、誤ったカリング判定が行われる可能性があります。

#### 実践的なテクニック

*   大規模なシーンでは、空間分割構造 (Octree, BSP Tree) を用いて、カリングの効率を向上させます。
*   Static Batching：静的なオブジェクト（移動しないオブジェクト）を結合して、1つの大きなジオメトリとして描画することで、描画呼び出しの回数を減らすことができます。
*   Dynamic Batching：動的なオブジェクト（移動するオブジェクト）でも、同じマテリアルを使用している場合は、まとめて描画することで描画呼び出しの回数を減らすことができます。ただし、オブジェクト間の距離が遠すぎると、パフォーマンスが低下する可能性があるため注意が必要です。

#### 応用例とユースケース

*   オープンワールドゲーム: 遠景のLOD調整とFrustum Cullingによる描画負荷軽減。
*   都市シミュレーション: Instancingによる建物や車の大量描画。Occlusion Cullingによる隠蔽オブジェクトの描画抑制。

#### トラブルシューティング

*   カリングが正しく機能しない場合: バウンディングボリュームの計算ミス、視錐台の平面計算ミス、深度バッファの精度不足などが考えられます。
*   Instancingで描画が崩れる場合: 変換行列の計算ミス、頂点属性の設定ミスなどが考えられます。

#### まとめと次のステップ

オブジェクト数の削減とカリング技術は、WebGLアプリケーションのパフォーマンスを向上させるための基本的なテクニックです。これらの技術を組み合わせることで、より複雑なシーンでも快適なフレームレートを維持することができます。次は、シェーダーの最適化について学びましょう。

### 8.2 シェーダーの最適化 - 複雑さの軽減、精度調整

#### 概要と重要性

シェーダーはGPU上で実行されるプログラムであり、頂点の位置計算やピクセルの色計算を行います。シェーダーの処理負荷が高いほど、GPUの処理時間が増加し、フレームレートが低下する可能性があります。シェーダーの最適化は、パフォーマンス改善において非常に重要な要素です。

#### 特徴と利点

シェーダーコードの簡素化は、GPUの処理時間を短縮し、コンパイル時間を短縮します。変数の精度調整は、メモリ使用量を削減し、GPUの演算精度を調整することで、パフォーマンスを向上させます。テクスチャサンプリングの最適化は、テクスチャへのアクセス回数を減らし、キャッシュ効率を向上させることで、パフォーマンスを改善します。

#### 事前準備と前提条件

*   GLSLの基本的な知識 (変数、関数、演算子)
*   シェーダープログラムの作成およびコンパイルの知識
*   WebGLのテクスチャの知識

#### 基本的な使い方

**8.2.1 シェーダーコードの簡素化**

*   不要な計算を削除する
*   複雑な計算をより効率的な方法に置き換える
*   外部ライブラリの利用を検討する（例：gl-matrix）
*   フラグメントシェーダーでの計算をできる限り頂点シェーダーに移動する（頂点数はピクセル数より少ない場合が多い）

    **例:**

    ```glsl
    // 最適化前
    vec3 color = vec3(1.0, 0.5, 0.2);
    float intensity = dot(normal, lightDirection);
    gl_FragColor = vec4(color * intensity, 1.0);

    // 最適化後 (clamp を使用して、0以下の値を切り捨てる)
    vec3 color = vec3(1.0, 0.5, 0.2);
    float intensity = clamp(dot(normal, lightDirection), 0.0, 1.0);
    gl_FragColor = vec4(color * intensity, 1.0);
    ```

**8.2.2 変数の精度調整 (highp, mediump, lowp)**

*   `highp`: 高精度。最も負荷が高い。
*   `mediump`: 中精度。
*   `lowp`: 低精度。最も負荷が低い。

    ```glsl
    // 例: フラグメントシェーダーでの精度指定
    #ifdef GL_FRAGMENT_PRECISION_HIGH
    precision highp float;
    #else
    precision mediump float;
    #endif

    varying mediump vec3 v_normal; // 法線ベクトルは中精度で十分な場合が多い
    ```
    精度を下げる際には、意図しないアーティファクトが発生しないか確認することが重要です。

**8.2.3 テクスチャサンプリングの最適化**

*   **ミップマップ:** テクスチャの縮小表示にミップマップを使用することで、エイリアシングを軽減し、パフォーマンスを向上させます。
*   **テクスチャアトラス:** 複数のテクスチャを1つの大きなテクスチャにまとめることで、テクスチャ切り替えの回数を減らし、パフォーマンスを向上させます。
*   **テクスチャ圧縮:** テクスチャを圧縮することで、メモリ使用量を削減し、テクスチャのロード時間を短縮します。
*   **不要なテクスチャサンプリングの削減:** 不要なテクスチャサンプリングを避ける。例えば、シェーダー内で常に同じ値になるテクスチャサンプリングの結果は、uniform変数としてシェーダーに渡すことを検討する。

    **ミップマップの生成:**

    ```javascript
    // テクスチャの生成と設定
    const texture = gl.createTexture();
    gl.bindTexture(gl.TEXTURE_2D, texture);

    // テクスチャ画像をロード (例: Imageオブジェクトを使用)
    const image = new Image();
    image.onload = function() {
        gl.bindTexture(gl.TEXTURE_2D, texture);
        gl.texImage2D(gl.TEXTURE_2D, 0, gl.RGBA, gl.RGBA, gl.UNSIGNED_BYTE, image);

        // ミップマップを生成
        gl.generateMipmap(gl.TEXTURE_2D);

        // テクスチャのフィルタリング設定 (ミップマップを使用)
        gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MIN_FILTER, gl.LINEAR_MIPMAP_LINEAR);
        gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MAG_FILTER, gl.LINEAR); //拡大時はLINEAR
    };
    image.src = "your_texture.png";

    ```

#### 実践的なテクニック

*   計算結果を再利用する: シェーダー内で何度も同じ計算を行う場合は、一度計算した結果を変数に格納し、再利用することで処理負荷を軽減できます。
*   Unroll Loop：短いループであれば、ループを展開することで、分岐処理のオーバーヘッドを削減できます。
*   WebGL Inspectorなどのツールを使用して、シェーダーのパフォーマンスを分析し、ボトルネックを特定する。

#### 応用例とユースケース

*   モバイルゲーム: 低スペックデバイスでのパフォーマンスを考慮したシェーダーの最適化。
*   VRアプリケーション: 高いフレームレートを維持するためのシェーダー最適化。

#### トラブルシューティング

*   精度を下げると描画結果が大きく変わる: 精度を上げるか、アルゴリズムを見直す。
*   シェーダーのコンパイルエラー: GLSLのバージョン、構文エラー、サポートされていない機能などを確認する。

#### まとめと次のステップ

シェーダーの最適化は、WebGLアプリケーションのパフォーマンスを大きく左右する重要な要素です。シェーダーコードの簡素化、変数の精度調整、テクスチャサンプリングの最適化など、様々なテクニックを駆使して、より効率的なシェーダープログラムを作成しましょう。次は、メモリ管理について学びましょう。

### 8.3 メモリ管理 - テクスチャ、ジオメトリの解放

#### 概要と重要性

WebGLアプリケーションでは、テクスチャやジオメトリなどのリソースを大量にメモリ上に展開します。メモリリークが発生すると、アプリケーションの動作が不安定になったり、クラッシュしたりする可能性があります。適切なメモリ管理は、安定したWebGLアプリケーションの開発に不可欠です。

#### 特徴と利点

不要なリソースの解放は、メモリ使用量を削減し、パフォーマンスを向上させます。メモリリークの防止は、アプリケーションの安定性を向上させ、クラッシュを防ぎます。

#### 事前準備と前提条件

*   JavaScriptのメモリ管理の基本的な知識 (ガベージコレクション)
*   WebGLのテクスチャ、バッファオブジェクトの知識

#### 基本的な使い方

**8.3.1 不要なテクスチャの解放**

*   `gl.deleteTexture(texture)`: テクスチャオブジェクトを削除し、メモリを解放します。

    ```javascript
    // テクスチャの解放
    gl.deleteTexture(texture);
    texture = null; // JavaScriptの参照も削除
    ```

**8.3.2 不要なジオメトリの解放**

*   `gl.deleteBuffer(buffer)`: バッファオブジェクトを削除し、メモリを解放します。
*   `gl.deleteVertexArray(vao)`: Vertex Array Object (VAO) を削除し、関連するバッファの参照を解放します。

    ```javascript
    // バッファの解放
    gl.deleteBuffer(vertexBuffer);
    vertexBuffer = null; // JavaScriptの参照も削除

    gl.deleteBuffer(indexBuffer);
    indexBuffer = null; // JavaScriptの参照も削除

    //VAOの解放 (もし使用している場合)
    gl.deleteVertexArray(vao);
    vao = null;
    ```

**8.3.3 メモリリークの防止**

*   リソースを使用し終わったら、すぐに解放する
*   循環参照を避ける
*   デバッグツールを使用して、メモリリークを検出する (Chrome DevTools, Spector.js)

#### 実践的なテクニック

*   リソースプール: オブジェクトの生成と破棄を繰り返す場合に、リソースプールを用いることで、メモリ割り当てのオーバーヘッドを削減できます。
*   WeakRef：大規模なアプリケーションで、特定のオブジェクトがガベージコレクションされるタイミングを制御する必要がある場合に、WeakRefを使用することで、メモリリークを防止できます。

#### 応用例とユースケース

*   動的なシーン: オブジェクトの生成と破棄が頻繁に行われるシーンでのメモリ管理。
*   長時間実行アプリケーション: メモリリークによるクラッシュを防ぐためのメモリ管理。

#### トラブルシューティング

*   WebGLコンテキストのエラー: 解放済みのリソースにアクセスしようとした場合に発生します。
*   メモリ使用量の増加: メモリリークが発生している可能性があります。デバッグツールを使用して、原因を特定してください。

#### まとめと次のステップ

メモリ管理は、WebGLアプリケーションの安定性を維持するために不可欠な要素です。不要なリソースの解放、メモリリークの防止など、適切なメモリ管理を行い、安定したWebGLアプリケーションを開発しましょう。次は、プロファイリングについて学びましょう。

### 8.4 プロファイリング - Chrome DevTools, Spector.js

#### 概要と重要性

パフォーマンスのボトルネックを特定し、改善するためには、プロファイリングが不可欠です。プロファイリングツールを使用することで、WebGLアプリケーションのパフォーマンスを詳細に分析し、ボトルネックとなっている箇所を特定することができます。

#### 特徴と利点

Chrome DevToolsは、JavaScriptの実行時間、メモリ使用量、ネットワークリクエストなど、様々な情報を分析できます。Spector.jsは、WebGL APIコールの詳細な情報を分析できます。これらのツールを組み合わせることで、WebGLアプリケーションのパフォーマンスを包括的に分析できます。

#### 事前準備と前提条件

*   Chromeブラウザ
*   Spector.js (ブラウザ拡張機能、またはJavaScriptライブラリ)

#### 基本的な使い方

**8.4.1 Chrome DevToolsによるパフォーマンス分析**

1.  Chrome DevToolsを開く (F12キー、または右クリック > 「検証」)
2.  「Performance」タブを選択
3.  「Record」ボタンをクリックして、プロファイリングを開始
4.  WebGLアプリケーションを操作して、パフォーマンスを測定
5.  「Stop」ボタンをクリックして、プロファイリングを停止
6.  タイムラインビューで、JavaScriptの実行時間、GPUの処理時間、メモリ使用量などを分析

    **注目すべき点:**

    *   **JavaScript:** 関数の実行時間、ガベージコレクションの頻度
    *   **Rendering:** フレームのレンダリング時間、レイアウトの再計算時間
    *   **Memory:** メモリ使用量の推移、メモリリークの有無

**8.4.2 Spector.jsによるWebGL APIコールの分析**

1.  Spector.jsをインストール (ブラウザ拡張機能、またはJavaScriptライブラリ)
2.  Spector.jsを起動
3.  WebGLアプリケーションを操作して、WebGL APIコールをキャプチャ
4.  Spector.jsのインターフェースで、各APIコールの実行時間、パラメータなどを分析

    **注目すべき点:**

    *   `drawElements`, `drawArrays` などの描画呼び出しの回数と時間
    *   `bindTexture`, `bindBuffer` などのステート変更の頻度
    *   シェーダーのコンパイル時間

**8.4.3 ボトルネックの特定と改善**

1.  Chrome DevToolsとSpector.jsを使用して、パフォーマンスのボトルネックとなっている箇所を特定
2.  特定したボトルネックに対して、適切な最適化手法を適用 (オブジェクト数の削減、シェーダーの最適化、メモリ管理など)
3.  再度プロファイリングを行い、改善効果を確認
4.  ボトルネックが解消されるまで、手順1〜3を繰り返す

#### 実践的なテクニック

*   フレームレートの目標値を設定し、目標値を下回る場合にプロファイリングを行う
*   特定の操作やシーンに絞ってプロファイリングを行う
*   プロファイリング結果を保存し、改善前後の比較を行う

#### 応用例とユースケース

*   ゲーム開発: フレームレートの安定化、ロード時間の短縮
*   インタラクティブな3Dアプリケーション: スムーズな操作感の実現

#### トラブルシューティング

*   プロファイリングツールが正常に動作しない: ブラウザのバージョン、拡張機能の競合などを確認する。
*   プロファイリング結果の解釈が難しい: ドキュメントやチュートリアルを参照する。

#### まとめと次のステップ

プロファイリングは、WebGLアプリケーションのパフォーマンスを改善するための強力なツールです。Chrome DevToolsとSpector.jsを使いこなして、パフォーマンスのボトルネックを特定し、効果的な最適化を行いましょう。この章で学んだテクニックを実践することで、より快適なWebGL体験を提供できるようになるでしょう。

**次のステップ:**

*   より高度なプロファイリングツール (RenderDocなど) の利用
*   WebGLのパフォーマンスに関する最新情報の収集
*   WebGLコミュニティへの参加

この章を通して、WebGLアプリケーションのパフォーマンスチューニングに関する基本的な知識と実践的なテクニックを習得できたはずです。これらの知識を活かして、より高品質なWebGLアプリケーションを開発してください。
