## 第6章：冗長化構成の設計 - 高可用性を実現する

システム運用において、可用性は重要な要素です。どんなに優れた機能を持つシステムでも、ダウンタイムが発生すればビジネスに大きな損害を与えてしまいます。本章では、システムの可用性を高めるための冗長化構成について解説します。ロードバランサー、フェイルオーバー、データベースクラスタリング、ストレージレプリケーションといった技術を用いて、障害発生時にもサービスを継続できるシステムを構築する方法を学びましょう。

### ロードバランサー入門：HAProxy, Nginx Plusの活用

**概要と重要性**

ロードバランサーは、複数のサーバーにトラフィックを分散し、システム全体の負荷を軽減すると同時に、可用性を向上させる重要な役割を担います。サーバーが1台ダウンしても、残りのサーバーが処理を引き継ぐため、サービス停止を防ぐことができます。

**特徴と利点**

*   **負荷分散:** トラフィックを均等に分散し、サーバーの負荷を軽減します。
*   **高可用性:** サーバーの障害時に自動的にトラフィックを切り替え、サービス継続を保証します。
*   **柔軟性:** サーバーの追加・削除を容易に行え、スケーラビリティに優れています。
*   **セキュリティ:** SSL/TLS終端やWAF (Web Application Firewall) 機能を提供し、セキュリティを強化します。

**事前準備と前提条件**

*   HAProxyまたはNginx Plusがインストールされたサーバー
*   バックエンドサーバー (Webサーバーなど) が複数台稼働していること
*   DNS設定 (ロードバランサーのIPアドレスにドメイン名を紐付ける)

**基本的な使い方**

**HAProxyの設定例:**

```
frontend http_frontend
    bind *:80
    mode http
    default_backend http_backend

backend http_backend
    balance roundrobin
    server web1 192.168.1.101:80 check
    server web2 192.168.1.102:80 check
```

*   `frontend`: クライアントからの接続を受け付ける設定。
*   `backend`: トラフィックを転送するバックエンドサーバーの設定。
*   `balance`: 負荷分散アルゴリズム (roundrobinは順番に分散)。
*   `server`: バックエンドサーバーのIPアドレスとポートを指定。`check`オプションでヘルスチェックを行う。

**Nginx Plusの設定例:**

```nginx
http {
    upstream backend {
        server 192.168.1.101:80;
        server 192.168.1.102:80;
    }

    server {
        listen 80;
        server_name example.com;

        location / {
            proxy_pass http://backend;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
        }
    }
}
```

*   `upstream`: バックエンドサーバーのグループを定義。
*   `proxy_pass`: リクエストをバックエンドサーバーに転送。
*   `proxy_set_header`: ヘッダー情報をバックエンドサーバーに転送 (オリジナルのクライアント情報など)。

**実践的なテクニック**

*   **ヘルスチェック:** バックエンドサーバーが正常に動作しているかを定期的にチェックし、異常があればトラフィックを転送しないように設定します。
*   **セッションパーシステンス:** 特定のユーザーからのリクエストを常に同じサーバーに転送することで、セッション情報を維持します (Cookieベース、IPアドレスベースなど)。
*   **SSL/TLS終端:** ロードバランサーでSSL/TLS暗号化を終端することで、バックエンドサーバーの負荷を軽減し、セキュリティを強化します。

**応用例とユースケース**

*   **ECサイト:** 複数のWebサーバーにトラフィックを分散し、高負荷時でも安定したサービスを提供します。
*   **APIサーバー:** APIサーバーの障害時に自動的にトラフィックを切り替え、サービス継続を保証します。
*   **コンテンツ配信:** 静的コンテンツをキャッシュサーバーに分散し、配信速度を向上させます。

**トラブルシューティング**

*   **バックエンドサーバーがヘルスチェックに失敗する:** サーバーがダウンしているか、応答が遅い可能性があります。サーバーの状態を確認し、必要に応じて再起動または設定変更を行います。
*   **トラフィックが均等に分散されない:** 負荷分散アルゴリズムの設定が適切でない可能性があります。アルゴリズムを変更するか、サーバーのスペックを調整します。
*   **セッションパーシステンスが機能しない:** Cookieの設定やIPアドレスの変更など、セッション情報が失われる原因がないか確認します。

**まとめと次のステップ**

ロードバランサーは、可用性を高めるための重要な要素です。HAProxyやNginx Plusのようなツールを活用することで、容易に冗長化構成を構築できます。次は、フェイルオーバー構成について学びましょう。

### フェイルオーバー構成：Keepalivedによる仮想IPアドレス制御

**概要と重要性**

フェイルオーバー構成は、主系サーバーに障害が発生した場合に、待機系サーバーが自動的に処理を引き継ぎ、サービスを継続する仕組みです。Keepalivedは、VRRP (Virtual Router Redundancy Protocol) を実装し、仮想IPアドレスを制御することで、このフェイルオーバーを実現します。

**特徴と利点**

*   **自動フェイルオーバー:** 主系サーバーの障害時に自動的に待機系サーバーに切り替わります。
*   **高速フェイルオーバー:** 短時間で切り替えが完了するため、サービス停止時間を最小限に抑えられます。
*   **シンプル:** 設定が比較的簡単で、導入しやすいです。
*   **柔軟性:** 複数の待機系サーバーを構成でき、より高度な冗長化を実現できます。

**事前準備と前提条件**

*   Keepalivedがインストールされたサーバー (主系、待機系)
*   仮想IPアドレス (未使用のIPアドレス)
*   フェイルオーバーさせるサービス (Webサーバー、データベースサーバーなど) が稼働していること

**基本的な使い方**

**Keepalivedの設定例 (主系サーバー):**

```
vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 100
    advert_int 1

    authentication {
        auth_type PASS
        auth_pass mypassword
    }

    virtual_ipaddress {
        192.168.1.100/24 dev eth0
    }

    track_script {
        chk_httpd
    }
}

vrrp_script chk_httpd {
    script "/etc/keepalived/check_httpd.sh"
    interval 2
    weight 2
}
```

**Keepalivedの設定例 (待機系サーバー):**

```
vrrp_instance VI_1 {
    state BACKUP
    interface eth0
    virtual_router_id 51
    priority 90
    advert_int 1

    authentication {
        auth_type PASS
        auth_pass mypassword
    }

    virtual_ipaddress {
        192.168.1.100/24 dev eth0
    }

    track_script {
        chk_httpd
    }
}

vrrp_script chk_httpd {
    script "/etc/keepalived/check_httpd.sh"
    interval 2
    weight 2
}
```

*   `state`: サーバーの状態 (MASTERまたはBACKUP)。
*   `interface`: 使用するネットワークインターフェース。
*   `virtual_router_id`: VRRPグループのID (主系、待機系で同じ値を設定)。
*   `priority`: 優先度 (数値が大きいほど優先度が高い)。
*   `virtual_ipaddress`: 仮想IPアドレス。
*   `track_script`: 監視スクリプト (サービスの状態を監視し、異常があれば優先度を下げる)。

**監視スクリプト (check_httpd.sh) の例:**

```bash
#!/bin/bash
if pidof httpd > /dev/null; then
    exit 0
else
    exit 1
fi
```

**実践的なテクニック**

*   **複数の監視スクリプト:** HTTPDだけでなく、データベースやその他のサービスの監視スクリプトを追加し、より確実に障害を検知します。
*   **preempt_delay:** フェイルオーバー後に主系サーバーが復旧した場合、すぐに主系に戻るのではなく、一定時間待機することで、不要な切り替えを防止します。
*   **notify_master/backup/fault:** イベント発生時に実行するスクリプトを指定することで、ログ出力やアラート送信などの処理を自動化します。

**応用例とユースケース**

*   **Webサーバー:** Webサーバーの障害時に自動的に待機系サーバーに切り替え、サービス継続を保証します。
*   **データベースサーバー:** データベースサーバーの障害時に自動的に待機系サーバーに切り替え、データ損失を最小限に抑えます。
*   **ルーター:** ルーターの障害時に自動的に待機系ルーターに切り替え、ネットワークの可用性を向上させます。

**トラブルシューティング**

*   **フェイルオーバーが発生しない:** Keepalivedの設定に誤りがあるか、監視スクリプトが正常に動作していない可能性があります。設定ファイルとスクリプトを確認し、ログを調べて原因を特定します。
*   **スプリットブレイン:** 2台のサーバーが両方ともMASTER状態になってしまう現象。設定ファイルの `virtual_router_id` が一致しているか、ネットワークの疎通性を確認します。認証設定 (`authentication`) が正しく設定されていることも重要です。
*   **フェイルオーバー後にサービスが正常に動作しない:** 待機系サーバーの設定が不十分な可能性があります。必要な設定 (Webサーバーの設定、データベースの設定など) がすべて完了しているか確認します。

**まとめと次のステップ**

Keepalivedは、フェイルオーバー構成を容易に構築できる強力なツールです。仮想IPアドレスを制御することで、サービス停止時間を最小限に抑えられます。次は、データベースクラスタリングについて学びましょう。

### データベースクラスタリング：MySQL/PostgreSQLのレプリケーション

**概要と重要性**

データベースは、システムの重要なデータを格納する場所です。データベースに障害が発生すると、システム全体が停止してしまう可能性があります。データベースクラスタリングは、複数のデータベースサーバーを連携させ、冗長化することで、可用性を高める仕組みです。

**特徴と利点**

*   **高可用性:** データベースサーバーに障害が発生しても、別のサーバーが処理を引き継ぎ、サービス継続を保証します。
*   **データ保護:** データを複数のサーバーに複製することで、データ損失のリスクを軽減します。
*   **負荷分散:** リードレプリカを設けることで、読み込み処理を分散し、パフォーマンスを向上させます。
*   **スケーラビリティ:** 必要に応じてサーバーを追加することで、データベースの処理能力を向上させます。

**事前準備と前提条件**

*   MySQLまたはPostgreSQLがインストールされたサーバーが複数台
*   レプリケーションの設定 (マスターサーバー、スレーブサーバー)
*   ネットワークの設定 (サーバー間の通信が可能であること)

**基本的な使い方**

**MySQLのレプリケーション設定例:**

**マスターサーバー (my.cnf):**

```
[mysqld]
server-id=1
log_bin=mysql-bin
binlog_format=ROW
```

**スレーブサーバー (my.cnf):**

```
[mysqld]
server-id=2
relay_log=relay-bin
log_slave_updates=1
```

**スレーブサーバーで実行するSQL:**

```sql
CHANGE MASTER TO
    MASTER_HOST='master_ip_address',
    MASTER_USER='replication_user',
    MASTER_PASSWORD='replication_password',
    MASTER_LOG_FILE='mysql-bin.000001',
    MASTER_LOG_POS=4;

START SLAVE;
```

**PostgreSQLのレプリケーション設定例:**

**マスターサーバー (postgresql.conf):**

```
wal_level = replica
archive_mode = on
archive_command = 'cp %p /path/to/archive/%f'
max_wal_senders = 3
```

**スレーブサーバー (postgresql.conf):**

```
hot_standby = on
```

**スレーブサーバーで実行するSQL:**

```sql
SELECT pg_start_backup('initial_backup');
```

(マスターサーバーでファイルシステムレベルのバックアップを実行)

```sql
SELECT pg_stop_backup();
```

(スレーブサーバーでバックアップファイルをリストア)

**スレーブサーバー (recovery.conf):**

```
standby_mode = on
primary_conninfo = 'host=master_ip_address port=5432 user=replication_user password=replication_password'
trigger_file = '/tmp/trigger_file'
```

**実践的なテクニック**

*   **GTID (Global Transaction Identifier) レプリケーション (MySQL):** トランザクションを一意に識別し、より安定したレプリケーションを実現します。
*   **Logical Replication (PostgreSQL):** 特定のテーブルやスキーマのみをレプリケーションし、柔軟性を向上させます。
*   **Semi-Synchronous Replication (MySQL):** マスターサーバーがトランザクションをコミットする前に、少なくとも1台のスレーブサーバーに書き込みを確認することで、データ損失のリスクを軽減します。

**応用例とユースケース**

*   **ECサイト:** 顧客情報や注文履歴などの重要なデータを保護し、高可用性を実現します。
*   **金融システム:** 取引履歴などのデータを保護し、データ損失のリスクを最小限に抑えます。
*   **分析システム:** リードレプリカを設けることで、分析クエリの負荷を分散し、パフォーマンスを向上させます。

**トラブルシューティング**

*   **レプリケーションが停止する:** ネットワークの問題、データの不整合、設定ミスなどが原因として考えられます。ログを調べて原因を特定し、修正します。
*   **データが同期されない:** レプリケーションラグ (マスターサーバーとスレーブサーバーのデータ差) が大きくなる場合、ネットワークの問題やサーバーの負荷が高い可能性があります。ネットワークの帯域幅を増やしたり、サーバーのスペックを向上させたりします。
*   **フェイルオーバー後にデータが損失する:** Semi-Synchronous Replicationを使用していない場合、フェイルオーバー時に最新のデータが損失する可能性があります。Semi-Synchronous Replicationを有効にするか、定期的にバックアップを取得します。

**まとめと次のステップ**

データベースクラスタリングは、可用性とデータ保護を両立させるための重要な要素です。MySQLやPostgreSQLのレプリケーション機能を活用することで、容易に冗長化構成を構築できます。次は、ストレージレプリケーションについて学びましょう。

### ストレージレプリケーション：DRBD, GlusterFSの構築

**概要と重要性**

ストレージは、データベースと同様に重要なデータを格納する場所です。ストレージに障害が発生すると、システム全体が停止してしまう可能性があります。ストレージレプリケーションは、データを複数のストレージデバイスに複製し、冗長化することで、可用性を高める仕組みです。

**特徴と利点**

*   **高可用性:** ストレージデバイスに障害が発生しても、別のデバイスが処理を引き継ぎ、サービス継続を保証します。
*   **データ保護:** データを複数のデバイスに複製することで、データ損失のリスクを軽減します。
*   **データアクセス速度の向上:** 複数のデバイスからデータを並行して読み込むことで、アクセス速度を向上させます。
*   **柔軟性:** 必要に応じてストレージデバイスを追加することで、容量を拡張できます。

**事前準備と前提条件**

*   DRBDまたはGlusterFSがインストールされたサーバーが複数台
*   ストレージデバイス (HDD, SSD) が複数台
*   ネットワークの設定 (サーバー間の通信が可能であること)

**基本的な使い方**

**DRBDの設定例:**

**設定ファイル (/etc/drbd.conf):**

```
resource data {
    on node1 {
        device     /dev/drbd0;
        disk       /dev/sdb1;
        address    192.168.1.101:7788;
        meta-disk  /dev/sdb2[0];
    }
    on node2 {
        device     /dev/drbd0;
        disk       /dev/sdb1;
        address    192.168.1.102:7788;
        meta-disk  /dev/sdb2[0];
    }
    net {
        protocol C;
    }
}
```

**DRBDの初期化:**

```
drbdadm create-md data
drbdadm up data
```

**DRBDの昇格 (プライマリノードに設定):**

```
drbdadm primary data
mkfs.ext4 /dev/drbd0
mount /dev/drbd0 /mnt/data
```

**GlusterFSの設定例:**

**Brickの作成 (各ノード):**

```
mkdir -p /glusterfs/brick1
```

**GlusterFSサーバーの起動:**

```
glusterd
```

**信頼プールの設定:**

```
gluster peer probe node2
gluster peer status
```

**ボリュームの作成:**

```
gluster volume create data replica 2 transport tcp node1:/glusterfs/brick1 node2:/glusterfs/brick1 force
gluster volume start data
```

**クライアントからのマウント:**

```
mount.glusterfs node1:/data /mnt/data
```

**実践的なテクニック**

*   **DRBDのSplit Brain対策:** スプリットブレインが発生した場合、`drbdadm disconnect data` コマンドで接続を切り、どちらか一方のノードをプライマリに昇格させます。データが失われた場合は、最新のデータをコピーします。
*   **GlusterFSの分散ボリューム:** データを複数のBrickに分散することで、データアクセス速度を向上させます。
*   **GlusterFSのレプリカボリューム:** データを複数のBrickに複製することで、データ損失のリスクを軽減します。

**応用例とユースケース**

*   **ファイルサーバー:** 複数のサーバーでファイルを共有し、高可用性を実現します。
*   **データベースストレージ:** データベースのデータを保護し、データ損失のリスクを最小限に抑えます。
*   **仮想環境:** 仮想マシンのイメージファイルを格納し、仮想マシンの可用性を向上させます。

**トラブルシューティング**

*   **DRBDが同期しない:** ネットワークの問題、ストレージデバイスの故障、設定ミスなどが原因として考えられます。ログを調べて原因を特定し、修正します。
*   **GlusterFSのボリュームが起動しない:** Brickが正常に作成されていない、ネットワークの問題、設定ミスなどが原因として考えられます。ログを調べて原因を特定し、修正します。
*   **パフォーマンスが低い:** ネットワークの帯域幅が低い、ストレージデバイスの性能が低い、設定ミスなどが原因として考えられます。ネットワークの帯域幅を増やしたり、ストレージデバイスの性能を向上させたり、設定を最適化します。

**まとめと次のステップ**

ストレージレプリケーションは、データの可用性と保護を両立させるための重要な要素です。DRBDやGlusterFSのようなツールを活用することで、容易に冗長化構成を構築できます。

### コンテナオーケストレーション：Kubernetes入門（別章で詳述）

Kubernetesについては、別章で詳述するため、ここでは概要のみ説明します。コンテナオーケストレーションは、コンテナ化されたアプリケーションのデプロイ、スケーリング、管理を自動化する仕組みです。Kubernetesは、代表的なコンテナオーケストレーションツールであり、可用性の高いシステムを構築するために不可欠です。

### トラブルシューティング：スプリットブレイン、フェイルオーバー時の問題

冗長化構成を構築しても、予期せぬ問題が発生することがあります。ここでは、よくあるトラブルシューティングについて解説します。

*   **スプリットブレイン:** 複数のノードが同時にプライマリノードになってしまう現象。Keepalived、DRBDなどで発生する可能性があります。設定ファイルの確認、ネットワークの疎通性の確認、認証設定の確認などを行います。
*   **フェイルオーバー後にサービスが正常に動作しない:** 待機系サーバーの設定が不十分な可能性があります。必要な設定 (Webサーバーの設定、データベースの設定など) がすべて完了しているか確認します。
*   **パフォーマンスが低下する:** フェイルオーバー後、リソースが不足している可能性があります。サーバーのスペックを向上させたり、不要なプロセスを停止したりします。

冗長化構成は、可用性を高めるための強力な手段ですが、適切な設計と運用が必要です。障害発生時の対応手順を事前に決めておくことで、迅速な復旧が可能になります。

本章では、冗長化構成の設計について解説しました。ロードバランサー、フェイルオーバー、データベースクラスタリング、ストレージレプリケーションといった技術を組み合わせることで、障害発生時にもサービスを継続できるシステムを構築できます。次章では、システムの監視について学びましょう。
